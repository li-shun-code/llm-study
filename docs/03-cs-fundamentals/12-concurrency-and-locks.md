在并发导论中我们看到了并发编程的根本问题：我们希望**原子地**执行一系列指令，但由于单处理器上中断的存在（或多处理器上多线程的并发执行），做不到。本章正面强攻这个问题，引入称为**锁**（lock）的东西。程序员在源代码中用锁标注、把临界区包起来，从而确保任何这样的临界区都像单条原子指令一样执行。

## 锁：基本思想

假设临界区是对共享变量的经典更新：

```c
balance = balance + 1;
```

当然临界区也可以是别的：往链表加元素、对共享结构做更复杂的更新等。使用锁的方式是在临界区前后加一些代码：

```c
1  lock_t mutex;    // 某个全局分配的锁 "mutex"
2  ...
3  lock(&mutex);
4  balance = balance + 1;
5  unlock(&mutex);
```

锁就是一个变量。要使用锁，必须声明某种锁变量（如上面的 `mutex`）。这个锁变量（简称"锁"）保存锁在任一瞬间的状态：要么**可用**（available / unlocked / free），没有线程持有；要么**已获取**（acquired / locked / held），恰好有一个线程持有并（大概率）正处于临界区。也可以在数据类型里存别的信息——哪个线程持有锁、用于排序锁获取的队列——但这些对锁的使用者隐藏。

`lock()` 与 `unlock()` 的语义很简单。调用 `lock()` 尝试获取锁：如果没有其他线程持有（即锁空闲），线程获得锁、进入临界区；该线程有时被称为锁的**持有者**（owner）。如果随后另一个线程对同一个锁变量调用 `lock()`，**它不会返回**——只要锁被别的线程持有；这样就在第一个线程处于临界区期间把其他线程挡在外面。持有者调用 `unlock()` 后，锁重新可用（空闲）：没有其他线程在等，就把状态改回 free；有线程在等（卡在 `lock()` 里），其中之一（最终）会注意到（或被通知到）状态变化，获取锁、进入临界区。

锁为程序员提供了**对调度的少量控制权**。一般而言，线程由程序员创建、却由 OS 以其选定的任意方式调度；锁把一部分控制权还给程序员——在一段代码外加上锁，程序员就能保证**至多一个线程**能在该代码中活跃。锁就这样把传统 OS 调度的混乱变成更可控的活动。

## Pthread 锁

POSIX 库把锁称为 **mutex**（互斥量），因为它用于提供线程间的互斥：一个线程在临界区内，其他线程就被排除在外、直到它完成。下面这段 POSIX 线程代码做的正是上面的事（我们仍用带错误检查的包装函数）：

```c
1  pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
2
3  Pthread_mutex_lock(&lock);   // 包装；失败即退出
4  balance = balance + 1;
5  Pthread_mutex_unlock(&lock);
```

注意 POSIX 版本向 lock/unlock 传入变量——我们可能用**不同的锁保护不同的变量**。这能提升并发度：与其用一把大锁、任何临界区都要抢它（**粗粒度**锁策略），不如用不同的锁保护不同的数据与数据结构，让更多线程同时处于各自被锁保护的代码中（**细粒度**方法）。

> **问题的核心：如何构建一把锁？**
> 如何构建高效的锁？高效的锁以低成本提供互斥，还可能具备下面讨论的其他性质。需要什么硬件支持？需要什么 OS 支持？
> 构建能用的锁，需要老朋友硬件与好伙伴 OS 的帮助。多年来各种体系结构的指令集加入了多种硬件原语；我们不研究这些指令如何实现（那是计算机体系结构课的主题），而是研究如何用它们构建锁这样的互斥原语，以及 OS 如何参与其中、让我们能构建成熟的锁库。

## 如何评价锁

构建锁之前先明确目标，即如何评价某个锁实现的好坏。三条基本标准：

1. **互斥**：锁的基本任务完成了吗？能否阻止多个线程进入临界区？
2. **公平**（fairness）：每个竞争线程在锁空闲时都能得到公平的机会吗？看极端情形：有没有线程在竞争中**饿死**（starve）、永远拿不到锁？
3. **性能**：使用锁增加的时间开销。几种情形值得分别考虑：无竞争（单线程抓锁放锁，开销几何？）；多线程在**单 CPU** 上竞争锁；多线程分布在**多个 CPU** 上竞争锁。

## 控制中断

最早的互斥方案之一：在临界区内**禁用中断**；这是为单处理器系统发明的：

```c
1  void lock() {
2      DisableInterrupts();
3  }
4  void unlock() {
5      EnableInterrupts();
6  }
```

进入临界区前关中断（用某种特殊硬件指令），确保临界区代码不被打断、如同原子执行；完成后重新开中断。

优点是**简单**——不用费脑子就能看懂为什么可行：没有中断，线程执行的代码必将执行完、没有其他线程能干扰。

缺点则不幸有很多：

1. **要求信任任意调用线程执行特权操作**（开关中断）。任何需要信任任意程序的时候，我们多半有麻烦：贪婪的程序可以在开头调用 lock() 独占处理器；更糟的是，失误或恶意程序调用 lock() 后进入死循环——OS 再也无法夺回系统控制权，唯一的出路是重启。把关中断当通用同步方案，对应用的信任要求太高。
2. **多处理器上无效**。多个线程跑在不同 CPU 上、都试图进入同一临界区时，关不关中断无所谓——其他处理器上的线程照样能进临界区。多处理器早已是常态，通用方案必须更靠谱。
3. **长期关中断会导致中断丢失**，引发严重系统问题。想象 CPU 错过了磁盘设备完成读请求的通知：OS 怎么知道该唤醒等待该读的进程？

因此，关中断只在受限场合用作互斥原语。例如 OS 自身有时会用中断屏蔽保证访问自己数据结构时的原子性——这在 OS 内部说得通：信任问题消失了（OS 总是信任自己执行特权操作）。

## 一次失败的尝试：只用加载/存储

超越中断技术就要依靠 CPU 硬件及其提供的指令。先用单个**标志变量**（flag）试建简单锁：

```c
1  typedef struct __lock_t { int flag; } lock_t;
2
3  void init(lock_t *mutex) {
4      // 0 -> 锁可用, 1 -> 已持有
5      mutex->flag = 0;
6  }
7
8  void lock(lock_t *mutex) {
9      while (mutex->flag == 1)  // TEST 标志
10         ;                      // 自旋等待（什么都不做）
11     mutex->flag = 1;           // 现在 SET 它！
12 }
13
14 void unlock(lock_t *mutex) {
15     mutex->flag = 0;
16 }
```

思路直观：flag 指示锁是否被持有。第一个进入临界区的线程调用 lock()，测试 flag 是否为 1（不是），然后把 flag 置 1 表明自己持有锁；出临界区时 unlock() 清零。另一个线程在临界区期间调用 lock()，就在 while 循环里**自旋等待**（spin-wait），等持有者清零后再置 1 进入。

可惜这段代码有两个问题。**正确性问题**：设想下面的交错执行（初始 flag=0）——

```
线程1                        线程2
call lock()
while (flag == 1)
                             ← 中断：切换到线程2
                             call lock()
                             while (flag == 1)
                             flag = 1;
                             ← 中断：切换到线程1
flag = 1;   // 也把 flag 置 1！
```

在"恰到好处"（其实是不合时宜）的中断下，两个线程都把 flag 置 1、都进入了临界区——用行话说这叫"糟糕"：最基本的互斥要求都没达成。

**性能问题**：线程等待已被持有的锁的方式是无休止地检查 flag——即自旋等待，浪费大量时间。单处理器上浪费尤其惨烈：等待者等的目标线程根本没机会运行（至少要等一次上下文切换）！

> **技巧：把并发想象成恶意调度器**
> 理解并发执行的方法论：假装自己是一个**恶意调度器**——总在最不合适的时点打断线程、挫败它们构建同步原语的微弱尝试。多么卑鄙的调度器！虽然这一确切的中断序列不太可能发生，但它**可能**发生，而这就足以证明某种方法不可行。偶尔恶意地思考是很有用的！

## 用 Test-And-Set 构建可用的自旋锁

关中断在多处理器上不行，纯加载/存储的朴素方案也不行，系统设计者开始为锁发明**硬件支持**。1960 年代早期的多处理器系统（如 Burroughs B5000）就有这种支持；如今所有系统都提供，连单 CPU 系统也不例外。

最容易理解的硬件支持是 **test-and-set**（或称**原子交换**）指令。用 C 伪代码定义它做什么：

```c
1  int TestAndSet(int *old_ptr, int new) {
2      int old = *old_ptr;  // 取 old_ptr 处的旧值
3      *old_ptr = new;      // 把 new 存入 old_ptr
4      return old;          // 返回旧值
5  }
```

test-and-set 返回 old_ptr 指向的**旧值**，同时把该值更新为 new；关键在于这一串操作**原子地**完成。它叫"测试并设置"，因为让你"测试"旧值（返回值）的同时"设置"内存位置为新值。这条稍强一点的指令就足以构建一个简单的**自旋锁**（spin lock）：

```c
1  typedef struct __lock_t {
2      int flag;
3  } lock_t;
4
5  void init(lock_t *lock) {
6      // 0: 锁可用, 1: 锁被持有
7      lock->flag = 0;
8  }
9
10 void lock(lock_t *lock) {
11     while (TestAndSet(&lock->flag, 1) == 1)
12         ; // 自旋等待（什么都不做）
13 }
14
15 void unlock(lock_t *lock) {
16     lock->flag = 0;
17 }
```

为什么这把锁能工作？情形一：线程调用 lock() 时无人持有锁（flag=0）。`TestAndSet(flag, 1)` 返回旧值 0——线程不会困在 while 循环里，成功获取锁；同时原子地把值置 1。用完临界区后 unlock() 把 flag 归零。

情形二：锁已被别的线程持有（flag=1）。本线程调用 `TestAndSet(flag, 1)`，返回旧值 1（锁被持有）、同时再次置 1。只要锁被持有，TestAndSet 就反复返回 1，线程就一直自旋；等某个线程把 flag 清零，本线程再调 TestAndSet 时返回 0、原子置 1——获取锁、进入临界区。

把"测试旧锁值"与"设置新值"合并为**单个原子操作**，就保证了只有一个线程能拿到锁——这就是构建可用的互斥原语的方法！

你现在也明白这类锁为什么叫**自旋锁**了：它是最简单的锁，就是单纯地自旋、烧 CPU 周期，直到锁可用。要在单处理器上正确工作，它需要**抢占式调度器**（时钟中断时不时打断线程去运行别的线程）；没有抢占，自旋锁在单 CPU 上毫无意义——自旋的线程永远不会让出 CPU。

> **附：Dekker 与 Peterson 算法**
> 1960 年代 Dijkstra 把并发问题抛给朋友们，数学家 Theodorus Jozef Dekker 给出了一个解法：只用加载与存储（假定它们彼此原子——在早期硬件上为真），不用特殊硬件指令与 OS 支持。Peterson 随后改进了 Dekker 的方案，用 flag[2] 与 turn 两个变量保证两线程永不同时进入临界区。不知为何，"不靠特殊硬件造锁"风靡一时，给理论家们出了不少题；而当人们意识到假设一点点硬件支持要容易得多（何况该支持自多处理之始就存在），这条研究路线就相当没用了。此外这些算法在现代硬件上并不正确（由于放松的内存一致性模型）。更多研究被扫进历史的灰尘堆……

## 评价自旋锁

按三条标准评估这把基本自旋锁：

- **互斥**：是的——自旋锁一次只允许一个线程进入临界区。这是一把**正确**的锁。
- **公平**：坏消息——自旋锁不提供任何公平性保证。竞争之下，一个自旋的线程可能**永远自旋**。简单自旋锁不公平、可能导致饥饿。
- **性能**：单 CPU 上可能很痛。想象持有锁的线程在临界区内被抢占：调度器接着运行其他 N−1 个线程，每个都试图拿锁、各自自旋整整一个时间片才让出 CPU——纯属浪费。但在**多 CPU** 上自旋锁表现相当好（线程数约等于 CPU 数时）：线程 A 在 CPU 1 拿到锁、线程 B 在 CPU 2 尝试后开始自旋；临界区大概率很短，锁很快可用、B 拿到。在另一个处理器上自旋等锁，这里没浪费多少周期，因此有效。

## Compare-And-Swap

一些系统提供的另一个硬件原语是 **compare-and-swap**（SPARC 上的叫法）或 **compare-and-exchange**（x86 上的叫法）。这条指令的 C 伪代码：

```c
1  int CompareAndSwap(int *ptr, int expected, int new) {
2      int original = *ptr;
3      if (original == expected)
4          *ptr = new;
5      return original;
6  }
```

基本思想：测试 ptr 所指地址的值是否等于 expected；相等则把 ptr 指向的内存位置更新为 new，否则什么都不做。两种情况下都返回该内存位置的**原值**，让调用方知道成功与否。

用 compare-and-swap 构建锁与 test-and-set 非常相似——替换 lock() 例程即可：

```c
1  void lock(lock_t *lock) {
2      while (CompareAndSwap(&lock->flag, 0, 1) == 1)
3          ; // 自旋
4  }
```

工作方式类似：检查 flag 是否为 0，是则原子换入 1、拿到锁；竞争失败的线程卡在自旋直到锁释放。compare-and-swap 其实比 test-and-set **更强大**——将来讨论无锁同步（lock-free synchronization）时会用到这份力量；但若只用它构建简单自旋锁，行为与上面分析的自旋锁一模一样。

## Load-Linked 与 Store-Conditional

一些平台提供一对协同工作的指令来构建临界区。例如 MIPS 架构的 **load-linked** 与 **store-conditional**（Alpha、PowerPC、ARM 提供类似指令）：

```c
1  int LoadLinked(int *ptr) {
2      return *ptr;
3  }
4
5  int StoreConditional(int *ptr, int value) {
6      if (no update to *ptr since LL to this addr) {
7          *ptr = value;
8          return 1;   // 成功！
9      } else {
10         return 0;   // 更新失败
11     }
12 }
```

load-linked 与典型加载指令差不多：取内存值放进寄存器。关键差别在 store-conditional：**只有**自上次 load-linked 以来该地址没有发生过其他写入，它才成功（并更新该地址的值）；成功返回 1 并更新 *ptr，失败返回 0 且不更新。用这对指令构建锁：

```c
1  void lock(lock_t *lock) {
2      while (1) {
3          while (LoadLinked(&lock->flag) == 1)
4              ;        // 自旋直到它为 0
5          if (StoreConditional(&lock->flag, 1) == 1)
6              return;  // 置 1 成功：搞定
7                       // 否则：再试
8      }
9  }
```

lock() 是唯一有趣的部分：线程先自旋等待 flag 变 0；然后尝试用 store-conditional 拿锁；成功即原子地把 flag 变 1、进入临界区。

store-conditional 何时失败？线程 A 调 lock()、执行 load-linked 返回 0（锁未持有）；在它尝试 store-conditional 之前被中断，另一个线程 B 进入锁代码、也执行 load-linked 得到 0 并继续。此时两个线程都执行过 load-linked、都准备 store-conditional。这对指令的关键特性：**只有一个线程**能成功把 flag 更新为 1 并拿到锁；后尝试 store-conditional 的线程失败（因为另一个线程在它的 LL 与 SC 之间更新了 flag 的值），只好重新尝试。

> **技巧：代码越少越好（Lauer 定律）**
> 程序员爱吹嘘自己写了多少代码——这从根本上就是错的。该吹嘘的是用**多少的代码**完成了任务。短小精悍的代码总是更可取：更易懂、bug 更少。正如 Hugh Lauer 谈 Pilot 操作系统的构建时所说："如果同样的人有双倍的时间，他们能用一半的代码造出同样好的系统。"下次吹嘘代码量之前，三思——或者更好，回去重写，让代码尽可能清晰简洁。

## Fetch-And-Add 与票据锁

最后一个硬件原语是 **fetch-and-add**：原子地递增某地址的值、同时返回旧值：

```c
1  int FetchAndAdd(int *ptr) {
2      int old = *ptr;
3      *ptr = old + 1;
4      return old;
5  }
```

用它可构建更有趣的**票据锁**（ticket lock）——不是单一值，而是组合使用 ticket 与 turn 两个变量：

```c
1  typedef struct __lock_t {
2      int ticket;
3      int turn;
4  } lock_t;
5
6  void lock_init(lock_t *lock) {
7      lock->ticket = 0;
8      lock->turn = 0;
9  }
10
11 void lock(lock_t *lock) {
12     int myturn = FetchAndAdd(&lock->ticket);
13     while (lock->turn != myturn)
14         ; // 自旋
15 }
16
17 void unlock(lock_t *lock) {
18     lock->turn = lock->turn + 1;
19 }
```

操作很直白：线程想拿锁时，先对 ticket 做一次原子的 fetch-and-add；返回值就是该线程的"我的号"（myturn）。全局共享的 `lock->turn` 决定轮到谁：当某线程的 myturn == turn，就轮到它进临界区。unlock 把 turn 加一，下一个等待线程（若有）得以进入。

注意与此前方案的一个重要区别：**它保证所有线程都能前进**（progress）。一旦线程领到号，它终将被调度（前面的线程依次过完临界区、释放锁）。之前的方案没有这种保证——比如在 test-and-set 上自旋的线程可能永远自旋，哪怕别的线程反复获取、释放锁。

## 自旋太多：怎么办？

基于硬件的锁简单（几行代码）且正确——系统与代码的两大优秀品质。但某些情形下这些方案可能相当低效。想象单处理器上跑两个线程：线程 0 在临界区、持有锁，不幸被中断；线程 1 尝试拿锁、发现锁被持有，开始自旋。自旋。再自旋。直到时钟中断终于到来、线程 0 重新运行并释放锁，线程 1（下次运行时）才能拿到。**只要线程陷入这种自旋，它就浪费了整个时间片，只是反复检查一个不会变化的值！** N 个线程竞争一把锁时更糟：N−1 个时间片可能以同样方式被浪费。于是下一个问题：

> **问题的核心：如何避免自旋？**
> 如何开发一种不在 CPU 上无谓浪费时间的锁？
> 光靠硬件支持解决不了——还需要 OS 支持！

## 简单方案：让出 CPU（Yield）

硬件支持让我们走得很远：能用的锁，甚至（票据锁那样的）公平性。但问题仍在：临界区内发生上下文切换、线程们开始无休止自旋等待那个被打断的持锁线程重新运行时，怎么办？

第一次尝试是个简单友好的方案：要自旋的时候，**把 CPU 让给别的线程**（yield）：

```c
1  void init() {
2      flag = 0;
3  }
4
5  void lock() {
6      while (TestAndSet(&flag, 1) == 1)
7          yield();   // 让出 CPU
8  }
9
10 void unlock() {
11     flag = 0;
12 }
```

假设 OS 提供原语 `yield()`：线程想放弃 CPU、让别的线程运行时调用它。线程可处于三种状态（运行、就绪、阻塞）；yield 只是把调用者从运行态挪到就绪态的系统调用，从而让别的线程上位运行——让出者实际上是把自己去调度了。

两个线程一个 CPU 的情形下，yield 方案工作得很好：发现锁被持有就让出 CPU，另一线程跑完临界区。但设想很多线程（比如 100 个）反复竞争一把锁：一个线程拿到锁、还没释放就被抢占，其余 99 个各自调 lock()、发现锁被持有、让出 CPU。假设轮转调度器，这 99 个线程都得跑完"运行并让出"的循环，持锁线程才能再次运行。比自旋方案（浪费 99 个时间片）好些，代价仍高：**上下文切换本身成本可观**，浪费依旧。

更糟的是，yield 方案不解决**饥饿**：一个线程可能困在无尽的 yield 循环里，而其他线程反复进出临界区。我们需要正面解决饥饿的方案。

## 用队列：睡眠而非自旋

此前某些方案（票据锁除外）的真正问题在于**把太多事情交给运气**：调度器决定下一个运行谁；调度器选错，运行中的线程要么自旋等锁（方案一），要么立刻让出 CPU（方案二）——都可能浪费、都无法防止饥饿。

因此我们必须**显式控制**当前持有者释放锁后，下一个获取锁的是谁。为此需要更多 OS 支持，以及一个**队列**记录等待拿锁的线程。为简单起见，用 Solaris 提供的两个调用：`park()` 把调用线程置为睡眠；`unpark(threadID)` 唤醒 threadID 指定的特定线程。两者配合，可以构建"试图获取已持有的锁就睡眠、锁空闲时被唤醒"的锁：

```c
1  typedef struct __lock_t {
2      int flag;
3      int guard;
4      queue_t *q;
5  } lock_t;
6
7  void lock_init(lock_t *m) {
8      m->flag = 0;
9      m->guard = 0;
10     queue_init(m->q);
11 }
12
13 void lock(lock_t *m) {
14     while (TestAndSet(&m->guard, 1) == 1)
15         ;  // 自旋获取 guard 锁
16     if (m->flag == 0) {
17         m->flag = 1;      // 拿到锁
18         m->guard = 0;
19     } else {
20         queue_add(m->q, gettid());  // 排队
21         m->guard = 0;
22         park();           // 睡眠
23     }
24 }
25
26 void unlock(lock_t *m) {
27     while (TestAndSet(&m->guard, 1) == 1)
28         ;  // 自旋获取 guard 锁
29     if (queue_empty(m->q))
30         m->flag = 0;      // 没人要锁，释放
31     else
32         unpark(queue_remove(m->q)); // 直接把锁交给下一个
33     m->guard = 0;
34 }
```

这段代码做了几件有趣的事。第一，把老的 test-and-set 思想与**显式的锁等待队列**结合，造出更高效的锁。第二，用队列控制下一个拿到锁的是谁、从而**避免饥饿**。

你可能注意到 **guard** 的用法：它基本上是套在 flag 与队列操作外面的一个小自旋锁——所以这个方案并没有完全消除自旋等待：线程仍可能在获取/释放锁的过程中被中断，导致其他线程为它自旋。但自旋时间非常有限（只是 lock/unlock 代码里的几条指令，而不是用户自定义的临界区），因此可以接受。

你可能还观察到：lock() 中线程拿不到锁时，我们小心地先把自己加入队列（gettid() 取当前线程 ID）、把 guard 清零、**然后**才 park()。思考题：如果 guard 的释放放在 park() **之后**而不是之前，会发生什么？提示：不好的事情。

再注意：别的线程被唤醒时，flag **并没有**被置回 0。为什么？这不是错误，而是必须如此！被唤醒的线程如同从 park() 返回；但它此刻不持有 guard、甚至没法尝试把 flag 置 1。因此我们让锁**直接从释放者手中传给下一个获取者**——中间不把 flag 置 0。

最后你可能察觉到 park() 调用之前有一个"看似的竞态"：时机最糟的情况下，线程正准备 park（以为自己该睡到锁释放为止），此刻切到另一个线程（比如正持有锁的线程），后者释放了锁——第一个线程随后的 park 可能**睡到永远**。这有时称为**唤醒/等待竞态**（wakeup/waiting race）。Solaris 通过增加第三个系统调用 `setpark()` 解决：线程先声明自己即将 park；若随后被中断、且别的线程在 park 真正调用前调用了 unpark，那么接下来的 park **立即返回**而不睡眠。lock() 内的改动很小：

```c
1  queue_add(m->q, gettid());
2  setpark();   // 新增
3  m->guard = 0;
```

另一种方案是把 guard 传入内核：由内核小心地原子地释放锁并把运行线程出队。

> **附：避免自旋的更多理由：优先级反转**
> 避免自旋锁的一个理由是性能（如正文所述）；但某些系统上还有另一个有趣的理由：**正确性**。要警惕的问题叫**优先级反转**（priority inversion）——不幸的是它是一种"星系级瘟疫"，在地球与火星上都发生过（火星探路者号的真实事故）！
> 设线程 T2 优先级高、T1 优先级低；调度器在两者都可运行时总选 T2，T1 只在 T2 不能运行（如阻塞在 I/O）时运行。现在：T2 因故阻塞，T1 运行、抓到一把自旋锁、进入临界区；T2 随即解除阻塞（I/O 完成了），调度器立即调度 T2（把 T1 打下去）。T2 尝试拿锁、拿不到（T1 持有），只能自旋。因为这是**自旋锁**，T2 永远自旋——系统挂死。
> 只避免自旋锁还不足以避免反转。设想三个线程 T1、T2、T3，T3 优先级最高、T1 最低：T1 拿了锁；T3 启动、因优先级高立即抢占 T1；T3 想拿 T1 持有的锁、卡住等待；此时 T2 若运行，优先级高于 T1，于是运行——而高优先级的 T3 卡在等 T1，T1 却因 T2 在跑而可能永远运行不上。强壮的 T3 跑不了，卑微的 T2 掌控 CPU——高优先级早已不复当年之勇。
> 解决办法：避免使用自旋锁（如上）；更一般地，让等待低优先级线程的高优先级线程**暂时提升**低者的优先级使其得以运行——即**优先级继承**（priority inheritance）；最简单的方案：确保所有线程同一优先级。

## 不同的 OS，不同的支持

我们看到了一种 OS 为构建更高效锁提供的支持；其他 OS 提供类似支持，细节各异。例如 Linux 提供 **futex**（fast user-space mutex）：与 Solaris 接口类似但内核功能更多——每个 futex 关联一个特定物理内存位置，以及一个内核内的每 futex 队列；调用者用 futex 调用按需睡眠与唤醒。具体有两个调用：`futex_wait(address, expected)` 在 address 处的值等于 expected 时让调用线程睡眠，不等则立即返回；`futex_wake(address)` 唤醒队列上一个等待线程。Linux mutex 的用法（glibc 的 nptl 库中 lowlevellock.h 的节选）：

```c
1  void mutex_lock (int *mutex) {
2      int v;
3      // 第 31 位原本为 0：拿到了 mutex（快速路径）
4      if (atomic_bit_test_set (mutex, 31) == 0)
5          return;
6      atomic_increment (mutex);
7      while (1) {
8          if (atomic_bit_test_set (mutex, 31) == 0) {
9              atomic_decrement (mutex);
10             return;
11         }
12         // 先等：确保我们监视的 futex 值为负（已锁）
13         v = *mutex;
14         if (v >= 0)
15             continue;
16         futex_wait (mutex, v);
17     }
18 }
19
20 void mutex_unlock (int *mutex) {
21     // 计数加上 0x80000000 后为 0 当且仅当没有其他等待者
22     if (atomic_add_zero (mutex, 0x80000000))
23         return;
24
25     // 有其他线程在等这把 mutex，唤醒其一。
26     futex_wake (mutex);
27 }
```

这段真实世界的锁代码有两点值得注意。第一，它用**单个整数**同时跟踪锁是否被持有（最高位）与等待者的数量（其余各位）：整数为负即被持有（最高位决定符号）。第二，它展示了如何为**无竞争的常见情形**优化：只有一个线程获取与释放锁时，只做极少的工作（加锁一个原子位测试与设置、解锁一个原子加法）。去把这段"真实世界"的锁的其余部分琢磨透吧——成为 Linux 锁大师！

## 两阶段锁

最后一笔：Linux 方案的风味属于一种时断时续用了多年的老办法——至少可以追溯到 1960 年代早期的 Dahm Locks——如今称为**两阶段锁**（two-phase lock）。两阶段锁意识到自旋可能有用，尤其当锁**即将**被释放时：第一阶段，先自旋一小会儿，希望拿到锁；若第一阶段没能拿到，进入第二阶段——调用者睡眠，直到锁变为空闲才被唤醒。上面的 Linux 锁就是这种锁的一种形态，只是它只自旋一次；推广版可以在用 futex 睡眠前循环自旋固定时长。

两阶段锁又是**混合方法**的一个实例：两个好主意的结合确实可能产生更好的一个。当然是否真的更好，很大程度上取决于硬件环境、线程数量与其他工作负载细节。一如既往，造出一把对所有用例都好的通用锁，相当有挑战。

## 小结

以上就是如今真实世界的锁的构建方式：一些硬件支持（以更强大指令的形式）加一些操作系统支持（如 Solaris 的 park()/unpark 原语或 Linux 的 futex）。细节各异，具体加锁代码通常经过高度调优；想看更多细节可以去读 Solaris 或 Linux 的代码库——非常引人入胜。对现代多处理器上各种锁策略的出色比较，见 David 等人的工作。

对本模块的学习路线而言，这条脉络已经清晰：线程共享数据 → 临界区与竞态 → 硬件原子指令（test-and-set/CAS/LL-SC/fetch-and-add）→ 自旋锁 → 混合睡眠策略（park/unpark、futex）。剩下的拼图是**条件变量**与**信号量**——它们解决"一个线程等待另一个"的同步问题，完整推导见《条件变量与信号量》（OSTEP 第 30、31 章）；等待链条一旦互相纠缠，就是《死锁与同步》。

- **你每天都在用 futex**：Python 的 `threading.Lock`、`queue.Queue`，Go 的 `sync.Mutex`，底层最终都落到本文"不同的 OS，不同的支持"一节讲的 futex/park-unpark 类原语——快速路径在用户态几条原子指令完成，争用时才陷入内核睡眠。这正是 `Queue.put()` 便宜而 `busy-wait` 可耻的原理差别。
- **CAS 撑起了无锁计数与连接池**：推理服务里的"当前批大小、活跃请求数、令牌桶限流器"这类简单共享计数，标准实现就是 `atomic.CompareAndSwap`/`fetch-and-add` 风格的无锁操作（Python 层对应的 `queue.Queue`、`itertools.count` 底层同样如此）；争用激烈时再升级为锁。
- **锁粒度即吞吐量**：本文"粗粒度 vs 细粒度"一段就是推理服务的排队设计问题——一把大锁保护整个批处理队列，还是 per-session 锁 + 无锁队列？vLLM、Triton Inference Server 的调度器文档里都能找到这条取舍的影子。
- **承接后两篇**：锁解决"谁进临界区"，但还有两个问题没答完——"怎么等某个条件成立"见《条件变量与信号量》，"多把锁互相等待怎么办"（四条件、预防、避免、检测）见《死锁与同步》；进程之间的那一套则从《信号与进程通信》讲起。
