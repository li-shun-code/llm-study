当有人用挖掘机挖断了一根光缆，数据包就可能丢失。（曾有整国断网，只因船锚拖过海底网络光缆！）软件错误、计算机崩溃、路由器故障都能惹出麻烦。

但我们不想操心这些。我们希望有个角色替我们处理这一切，然后在数据**完整、无损、按序**到位时告诉我们。

TCP 就是那个角色。它替我们操心丢包；等到确认所有正确的数据都到手了，**才**把数据交给我们。

我们将了解：

- TCP 的总体目标
- 它在网络协议栈中的位置
- TCP 端口回顾
- TCP 如何建立、使用与关闭连接
- 数据完整性机制：维持包的顺序、检测错误
- 流量控制——接收方如何避免被压垮
- 拥塞控制——发送方如何避免压垮互联网

TCP 是个非常复杂的话题，这里只掠过要点。想深入的话，必读之书是已故大师 W. Richard Stevens 的《TCP/IP Illustrated Volume 1》。

## 14.1 TCP 的目标

- 提供可靠的通信
- 在分组交换网络上模拟电路式的连接
- 提供流量控制（flow control）
- 提供拥塞控制（congestion control）
- 支持带外数据（out-of-band data）

## 14.2 在网络协议栈中的位置

回忆网络分层（前述的互联网分层模型）：

| 层 | 职责 | 示例协议 |
|---|---|---|
| 应用 | 结构化的应用数据 | HTTP, FTP, TFTP, Telnet, SSH, SMTP, POP, IMAP |
| 传输 | 数据完整性、分包与重组 | TCP, UDP |
| 互联网 | 路由 | IP, IPv6, ICMP |
| 链路 | 物理层、线缆上的信号 | Ethernet, PPP, token ring |

TCP 位于**传输层**。它下面的 IP 负责路由，它上面的应用层尽情享用 TCP 提供的一切特性。

这就是为什么我们写 HTTP 客户端与服务器时完全不必操心数据完整性——用了 TCP，它替我们搞定了！

## 14.3 TCP 端口

回忆一下：用 TCP 时必须指定要连接的端口号；即便客户端，OS 也会自动分配本地端口（如果我们没有自己 `bind()` 的话）。

IP 用 IP 地址标识**主机**。

但数据到了主机之后，是**端口号**让 OS 把数据交付给正确的**进程**。

打个比方：IP 地址像街道地址，端口号像这个街道地址里的门牌/房间号。

## 14.4 TCP 概览

一条 TCP 连接的生命期主要做三件事：

1. 建立连接
2. 传输数据
3. 关闭连接

每一步都涉及在客户端与服务器之间来回发送**特殊的非用户数据包**。我们将认识几种特殊包类型：SYN、SYN-ACK、ACK、FIN。

### 14.4.1 建立连接

这就是著名的"**三次握手**"（three-way handshake）。由于传输途中任何包都可能丢失，TCP 特别小心地确保连接双方都准备好了才开始传数据。

1. 客户端向服务器发送 **SYN**（synchronize，同步）包。
2. 服务器向客户端回复 **SYN-ACK**（synchronize acknowledge，同步确认）包。
3. 客户端向服务器回复 **ACK**（acknowledge，确认）包。

任何一步在合理时间内没有回复，包就会被重发。

### 14.4.2 传输数据

TCP 拿到一串数据流，把它切成块；每块附上一个 TCP 头部，然后交给 IP 层投递。头部加数据块合称一个 TCP **段**（segment）。

（我们把"TCP 包"与"TCP 段"混用，但 segment 更准确。）

TCP 发出一个段后，期望接收方回复一个确认（ACK）。如果没等到 ACK，TCP 就假定出了岔子、需要重发该段。

段是**编号**的，因此即使乱序到达，TCP 也能按正确顺序把它们拼回去。

### 14.4.3 关闭连接

一侧想关闭连接时，发送 **FIN**（finis，终结）包。远端通常回复一个 ACK 加上它自己的 FIN；本地一侧再回一个 ACK，挂断完成。

在某些 OS 上，若一台主机关闭连接时还有未读数据，它会回一个 **RST**（reset，重置）表明这种状态。此时套接字程序可能打印 "Connection reset by peer"（连接被对端重置）。

## 14.5 数据完整性

可能出岔子的地方太多了：数据可能乱序到达、可能损坏、可能重复、也可能根本没到。

TCP 有应对这一切意外的机制。

### 14.5.1 包排序

发送方给每个段打上**递增的序列号**。"这是 3490 号段。这是 3491 号段。"

接收方回复发送方一个含该序列号的 ACK 包。"我收到了 3490 号。我收到了 3491 号。"

两个段乱序到达？TCP 按序列号排序就能恢复顺序。

> 类比时间！假如你把一沓纸抛向空中，怎么知道它们原来的顺序？只要每页都正确编了号，排个序就行。这正是序列号在 TCP 中的角色。

重复段到达？TCP 看到已经见过这个序列号，放心丢弃。

某段丢了？TCP 可以请求重传——反复 ACK 前一个段，发送方就会重发下一段。

或者，发送方一段时间内没等到某个段的 ACK，也可能自行重发该段（猜它可能丢了）。这种重传随每次超时变得越来越悲观；每次超时后服务器把超时时长**翻倍**。

最后一点：在建立连接的三次握手期间，序列号被初始化为**随机值**。

### 14.5.2 错误检测

发送方发出段之前，为该段计算一个**校验和**（checksum）。

接收方收到段后，自己也算一遍该校验和。

两个校验和一致，则认为数据无错；不一致，数据被丢弃，由发送方超时重传。

校验和是一个 16 位数：把全部 TCP 头部与载荷数据、以及相关的 IP 地址一起灌入一个摘要函数得到。

## 14.6 流量控制

**流量控制**（flow control）是两台通信设备互相提醒"数据得发慢点"的机制。你不可能往一台只能处理 100 Mbs 的设备上浇 1000 Mbs（兆比特每秒）。设备需要办法提醒发送方减速。

> 类比时间：打电话时你告诉对方"你说得太快我跟不上！慢点儿！"——就是这个机制。

最简单的做法（TCP 并不这么做）：发送方发一段数据，等接收方回一个带该序列号的 ACK，再发下一包。这样接收方想让发送方减速时，拖一拖 ACK 就行。

但这样一问一答太慢；网络通常足够可靠，发送方完全可以不等回复就连发多个段。

然而这么做，发送方就有可能发得比接收方能处理的**更快**！

TCP 用所谓**滑动窗口**（sliding window）解决：它放在接收方 ACK 包 TCP 头部的"窗口"（window）字段里。

在该字段中，数据接收方声明自己**还愿意再接收多少数据（以字节计）**。发送方在此额度内可以不发 ACK 连续发送；一旦发满就必须等 ACK，而拿到的 ACK 又会携带新的窗口信息。

用这个机制，接收方能对发送方说："你发了 X 字节之后，必须等一个 ACK 告诉你还能发多少。"

注意这是**字节**数而非段数。只要总字节数不超过接收方通告的窗口大小，发送方完全可以连发多个段而收不到任何 ACK。

## 14.7 拥塞控制

流量控制运作于两台计算机之间，但还有"整个互联网"这个更大的问题。如果一台路由器被压垮，它会开始丢包，导致发送方开始重传——于事无补反而雪上加霜。而且这压根不在流量控制的雷达上：因为包根本到不了接收方。

1986 年就发生过这种事：[NSFNET](https://en.wikipedia.org/wiki/National_Science_Foundation_Network)（商业前时代的互联网前身，愿它安息）被一群不知道见好就收、执着重传的发送方压垮，吞吐量跌到正常水平的 0.1%。相当不妙。

为修复此问题，TCP 实现了若干估算并消除网络拥塞的机制。注意：这些是在接收方通告的**流量控制窗口**之外的额外限制。发送方必须同时服从流量控制上限**与**估算的网络拥塞上限，取其低者。网络上未确认的段不能超过这个限额；超了就得停止发送、等一些 ACK 回来。

换个角度想：发送方发出新的 TCP 段，是在**加剧**网络拥塞；收到 ACK 则表明该段已离开网络，拥塞**减轻**。

为缓解 NSFNET 遭遇的问题，加入了两大算法：**慢启动**（Slow Start）与**拥塞避免**（Congestion Avoidance）。

**注意：**下面是这两个算法的简化视图。完整细节及其复杂互动（以及更多拥塞控制内容）见《TCP Congestion Control》（RFC 5681）。

### 14.7.1 慢启动（Slow Start）

连接刚建立时，发送方无从知晓网络有多拥塞。第一阶段的目标是形成一个粗略估计。

于是它从保守开始，假定拥塞程度很高。（若网络确实已经很堵，大方地往里灌数据毫无助益。）

它先给自己一个初始的**拥塞窗口**（congestion window）：允许同时在途的未 ACK 字节数（也是段数——但我们暂且只想字节）。

ACK 到来时，拥塞窗口按已确认的字节数增长。粗略地说：一个段被 ACK 后可以发两个；这两个都被成功 ACK 后，可以发四个。

所以它起步时允许的在途未确认段非常少，但**增长极快**（指数式）。

最终某个 ACK 丢了——这时慢启动决定大幅减速：把拥塞窗口**减半**，然后 TCP 切换到拥塞避免算法。

### 14.7.2 拥塞避免（Congestion Avoidance）

这个算法与慢启动相似，但步子迈得克制得多。再没有那种指数增长的花活。

每成功传输一个拥塞窗口量的数据，它就往窗口里**再加一个段**大小的字节，谨慎加码——允许网络上再多一个未 ACK 的段。没问题的话，再放宽一个。依此类推。

它在"不拥塞网络的前提下能成功发送的极限"边缘反复试探，但推得很慢。这叫**加性增**（additive-increase），增长大致是线性的（对比慢启动的大致指数）。

不过最终总会推过头、不得不重传某个包。此时拥塞窗口被设为很小，算法退回慢启动。
