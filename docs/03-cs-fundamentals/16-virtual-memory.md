以**分页**（paging）作为支撑虚拟内存的核心机制，会带来高昂的性能开销：把地址空间切成小而固定大小的单元（页），意味着需要**大量**映射信息；而映射信息一般存在物理内存里，因此分页在逻辑上要求程序的**每个**虚拟地址生成时都多一次内存查找。每次取指令、每次显式加载/存储之前都要先访问内存取翻译信息——慢得令人发指。于是有了问题：

> **问题的核心：如何加速地址翻译？**
> 如何加速地址翻译、并普遍避免分页似乎必需的额外内存引用？需要什么硬件支持？需要 OS 做什么？

想让东西变快，OS 通常需要帮手，而帮手常来自 OS 的老朋友：硬件。为加速地址翻译，我们要加入一个（出于历史原因）叫**旁路翻译缓冲**（translation-lookaside buffer，TLB）的部件：它是芯片**内存管理单元**（MMU）的一部分，本质上就是热门"虚拟地址→物理地址"翻译的**硬件缓存**——所以更贴切的名字其实是"地址翻译缓存"。每次虚拟内存引用时，硬件先查 TLB 看有没有想要的翻译；有就直接（快速地）完成翻译，无需去翻记录全部翻译的页表。TLB 对性能影响巨大，某种意义上是它让虚拟内存成为可能。

## TLB 的基本算法

假设简单的线性页表（页表是个数组）与硬件管理的 TLB，硬件处理虚拟地址翻译的大致流程如下：

```
1  VPN = (VirtualAddress & VPN_MASK) >> SHIFT
2  (Success, TlbEntry) = TLB_Lookup(VPN)
3  if (Success == True)                    // TLB 命中
4      if (CanAccess(TlbEntry.ProtectBits) == True)
5          Offset = VirtualAddress & OFFSET_MASK
6          PhysAddr = (TlbEntry.PFN << SHIFT) | Offset
7          Register = AccessMemory(PhysAddr)
8      else
9          RaiseException(PROTECTION_FAULT)
10 else                                    // TLB 缺失
11     PTEAddr = PTBR + (VPN * sizeof(PTE))
12     PTE = AccessMemory(PTEAddr)
13     if (PTE.Valid == False)
14         RaiseException(SEGMENTATION_FAULT)
15     else if (CanAccess(PTE.ProtectBits) == False)
16         RaiseException(PROTECTION_FAULT)
17     else
18         TLB_Insert(VPN, PTE.PFN, PTE.ProtectBits)
19     RetryInstruction()
```

硬件的算法是：先从虚拟地址中取出**虚拟页号**（VPN，第 1 行），查 TLB 中是否有该 VPN 的翻译（第 2 行）。有——**TLB 命中**（TLB hit）：从相应 TLB 项取出**物理帧号**（PFN），拼上原虚拟地址的页内偏移，形成目标物理地址（PA），访问内存（第 5–7 行），前提是保护检查通过（第 4 行）。

如果 CPU 在 TLB 里找不到翻译（**TLB 缺失**，TLB miss），就要多干些活：硬件访问页表找到翻译（第 11–12 行），假设该虚拟内存引用有效且可访问（第 13、15 行），则用该翻译更新 TLB（第 18 行）。这些动作代价高昂，主要因为访问页表需要额外的内存引用（第 12 行）。TLB 更新完毕后硬件**重试**该指令；这次翻译在 TLB 里了，内存引用被快速处理。

和所有缓存一样，TLB 建立在"常见情形下翻译都能在缓存中找到（即命中）"的前提上。命中时几乎无额外开销——TLB 就在处理核心旁边，设计得相当快。发生缺失时，分页的高昂代价浮现：必须访问页表找翻译，产生一次（页表更复杂时是多次）额外内存引用。若缺失频发，程序会明显变慢——相对大多数 CPU 指令，内存访问代价高昂，而 TLB 缺失带来更多内存访问。所以要尽一切可能避免 TLB 缺失。

> **技巧：能缓存就缓存**
> 缓存是计算机系统最基本的性能技术之一，被反复用来"让常见情形变快"。硬件缓存的思想是利用指令与数据引用的**局部性**（locality）。局部性有两类：**时间局部性**（temporal locality）——最近被访问过的指令或数据很可能很快被再次访问（想想循环变量、循环体里的指令）；**空间局部性**（spatial locality）——程序访问了地址 x，很可能很快访问 x 附近的内存（想想顺序流过数组、一个元素接一个元素）。当然这些性质取决于程序的具体行为，是经验法则而非铁律。
> 你可能想问：既然缓存（如 TLB）这么棒，为什么不把缓存做大、把所有数据都塞进去？遗憾的是我们撞上了物理学这类更根本的法则：想要快的缓存就必须小——光速等物理约束开始发威。大缓存按定义就是慢的，反而失去意义。所以我们只能用小而快的缓存，剩下的问题是如何最好地利用它们提升性能。

## 示例：访问一个数组

用一个简单的虚拟地址访问序列看 TLB 如何提升性能。假设内存中有一个 10 个 4 字节整数组成的数组，起始于虚拟地址 100；再假设 8 位小虚拟地址空间、16 字节页——虚拟地址可分为 4 位 VPN（16 个虚拟页）与 4 位偏移（每页 16 字节）。

数组铺在 16 个 16 字节的页上：`a[0]` 从 (VPN=06, offset=04) 开始，该页只装得下 3 个整数；数组延续到下一页（VPN=07），放着 a[3]…a[6]；最后三个元素 a[7]…a[9] 在再下一页（VPN=08）。

考虑简单循环访问每个数组元素：

```c
int i, sum = 0;
for (i = 0; i < 10; i++) {
    sum += a[i];
}
```

为简单起见假装循环只产生对数组的访问（忽略 i、sum 和指令本身）。访问 `a[0]` 时，CPU 看到对虚拟地址 100 的加载；硬件取出 VPN=06 查 TLB。假设这是程序第一次访问该数组，结果是 **TLB 缺失**。

下一个访问是 `a[1]`，好消息：**TLB 命中**！因为数组第二个元素紧挨第一个、位于同一页，访问第一个元素时该页的翻译已载入 TLB。访问 `a[2]` 同样命中（与 a[0]、a[1] 同页）。

不妙的是访问 `a[3]` 时再次缺失。但接下来 a[4]…a[6] 都命中——它们同页。最后 `a[7]` 造成一次缺失，硬件查页表、更新 TLB；最后两次访问（a[8]、a[9]）坐享其成，再获两次命中。

十次访问的 TLB 活动汇总：**缺失，命中，命中，缺失，命中，命中，命中，缺失，命中，命中**。命中率（命中数 ÷ 总访问数）为 **70%**。虽不算高（我们想要逼近 100%），却是非零的——这已令人惊喜：尽管是程序第一次访问该数组，TLB 仍因**空间局部性**改善了性能。数组元素紧密打包在页内（空间上彼此邻近），因此每页只有首次访问产生缺失。

页大小在此扮演了角色：若页大小翻倍（32 字节而非 16），缺失更少。典型页大小是 4KB，这类密集的数组式访问能取得极佳的 TLB 性能——每页访问只有一次缺失。最后一个观察：若循环结束后程序很快再次访问该数组，且 TLB 足以缓存所需翻译，结果更漂亮：**十次全命中**。这次是**时间局部性**（内存项在时间上的快速重引用）立功。与任何缓存一样，TLB 的成功依赖空间与时间两种局部性——而这都是**程序的属性**。只要程序展现出这类局部性（许多程序都如此），TLB 命中率就会很高。

## 谁来处理 TLB 缺失？

两种可能：硬件，或软件（OS）。早年间硬件走**复杂指令集**（CISC）路线，硬件厂商不太信任那些鬼鬼祟祟的 OS 开发者，于是由硬件全权处理 TLB 缺失。为此，硬件必须确切知道页表在内存的位置（通过**页表基址寄存器**）及其确切格式；缺失时硬件"遍历"（walk）页表、找到正确的页表项、取出翻译、更新 TLB、重试指令。采用硬件管理 TLB 的"较老"架构是 Intel x86，它使用固定的多级页表，当前页表由 CR3 寄存器指向。

更现代的架构（如 MIPS R10k、Sun 的 SPARC v9，两者都是 RISC——精简指令集计算机）采用**软件管理 TLB**。TLB 缺失时，硬件只抛出一个异常，暂停当前指令流、提升特权级到内核模式、跳转到**陷阱处理程序**（trap handler）——你猜得到，这是 OS 中专为处理 TLB 缺失编写的代码。它运行时在页表中查找翻译、用特殊"特权"指令更新 TLB、从陷阱返回；此时硬件重试指令（这次 TLB 命中）。

软件管理方案的主要优势是**灵活性**：OS 可以用任意数据结构实现页表，无需改硬件。另一个优势是**简单性**：硬件在缺失时几乎啥也不干——抛个异常，剩下的交给 OS 的 TLB 缺失处理程序。

两个重要细节：

1. **从陷阱返回的方式不同**。服务系统调用时，return-from-trap 应在进入 OS 的那条指令**之后**恢复执行（正如过程调用的返回点在调用之后）；而处理 TLB 缺失的陷阱返回时，硬件必须在**导致陷阱的那条指令**恢复执行——重试才能命中。因此按陷阱/异常的成因不同，硬件陷入 OS 时必须保存不同的 PC。
2. **避免无限 TLB 缺失链**。运行 TLB 缺失处理代码时，OS 必须格外小心别让自己又引发一连串 TLB 缺失。办法很多：比如把 TLB 缺失处理程序放在**物理内存**（不映射、不受地址翻译管辖）；或在 TLB 中保留一些永久有效的表项给处理程序代码——这些"接线"（wired）翻译永远命中。

> **附：TLB 的有效位 ≠ 页表的有效位**
> 常见错误是把 TLB 里的 valid 位与页表里的 valid 位混为一谈。页表中某页表项（PTE）标记为无效，意味着该页未被进程分配、正常程序不应访问；访问无效页的通常反应是陷入 OS，由 OS 杀死进程。而 TLB 的 valid 位只是说明该 TLB 项里**有没有一条有效翻译**：系统刚启动时每个 TLB 项常被置为无效（还没缓存任何翻译）；虚拟内存启用、程序开始访问各自地址空间后，TLB 逐渐填充、有效项越来越多。上下文切换时 TLB 有效位也很有用：把所有 TLB 项置无效，可确保即将运行的进程不会误用上一进程的翻译。

## TLB 的内容

典型 TLB 可能有 32、64 或 128 项，且是**全相联**（fully associative）的——意思是任一翻译可以放在 TLB 的任何位置，硬件并行搜索整个 TLB 找到目标。TLB 项大致形如：

```
VPN | PFN | 其他位
```

注意 VPN 与 PFN 都要在场——因为翻译可能落在任何位置（硬件术语：全相联缓存），硬件并行比对各项找匹配。

更有趣的是"其他位"：常见的有**有效位**（valid bit，该项是否含有效翻译）；**保护位**（protection bits，决定页如何被访问，与页表中一致——比如代码页标"读+执行"，堆页标"读+写"）；还可能有**地址空间标识符**（ASID）、**脏位**（dirty bit）等字段。

## TLB 问题一：上下文切换

进程（从而地址空间）之间切换时，TLB 带来新问题：TLB 中包含**只对当前运行进程有效**的虚拟→物理翻译，对其他进程毫无意义。因此从一个进程切到另一个时，硬件或 OS（或两者）必须确保即将运行的进程不会误用之前进程的翻译。

看例子：进程 P1 运行时，TLB 缓存着来自 P1 页表的翻译，设 P1 的第 10 个虚拟页映射到物理帧 100。另一进程 P2 的第 10 个虚拟页映射到物理帧 170。若两个进程的表项都在 TLB：

```
VPN  PFN  valid  prot
10   100  1      rwx     ← P1
—    —    0      —
10   170  1      rwx     ← P2
—    —    0      —
```

问题一目了然：VPN 10 到底翻译成 PFN 100（P1）还是 PFN 170（P2）？硬件无法区分。要正确且高效地支持跨进程虚拟化，还得做点事：

> **问题的核心：上下文切换时如何管理 TLB 内容？**
> 切换进程时，TLB 中上一个进程的翻译对即将运行的进程没有意义。硬件或 OS 该怎么办？

方案一：**切换时清空 TLB**（flush），运行下一个进程前把它腾空。软件管理系统上用一条显式的（特权）硬件指令完成；硬件管理的 TLB 则可在页表基址寄存器改变时触发清空（反正 OS 切换时必须改 PTBR）。清空只是把所有有效位置 0。这方案能工作——进程绝不会撞上错误翻译；但有代价：进程每次运行、触碰其数据与代码页时都要经历 TLB 缺失。若 OS 频繁切换进程，代价可能很高。

为降低开销，一些系统增加了**跨切换共享 TLB** 的硬件支持：在 TLB 中加入**地址空间标识符**（ASID）字段。可以把 ASID 想成进程标识符（PID），只是位数更少（如 ASID 8 位 vs PID 32 位）。加上 ASID 后，两个进程可以大方地共享 TLB——只需 ASID 字段即可区分原本相同的翻译：

```
VPN  PFN  valid  prot  ASID
10   100  1      rwx   1
—    —    0      —     —
10   170  1      rwx   2
—    —    0      —     —
```

有了 ASID，TLB 可同时容纳不同进程的翻译而不致混淆。当然，硬件翻译时也需知道当前运行的是哪个进程，因此 OS 在上下文切换时要把当前进程的 ASID 设入某个特权寄存器。

顺带一提另一种"表项很像"的情形：两个不同进程的两个不同 VPN 指向**同一物理页**——例如两个进程共享一个（代码）页：P1 把物理页 101 映射进自己地址空间的第 10 页，P2 映射到第 50 页。共享代码页（二进制或共享库）很有用：减少占用中的物理页数，降低内存开销。

## TLB 问题二：替换策略

与任何缓存一样，TLB 还有**缓存替换**问题：装入新表项时必须替换旧的，那么替换谁？目标当然是把缺失率降到最低（命中率提上去）。

常见做法之一是驱逐**最近最少使用**（LRU，least-recently-used）的表项——LRU 利用内存引用流的局部性，认定"最近没用过的项"是好淘汰对象。另一种典型做法是**随机**策略——随机驱逐一条 TLB 映射。随机策略的价值在于简单、且能规避极端行为：比如当程序循环访问 n+1 个页而 TLB 容量为 n 时，"合理"的 LRU 会变得相当不合理——**每次访问都缺失**；随机策略反而好得多。

> **技巧：RAM 并不总是 RAM（Culler 定律）**
> 随机访问存储器（RAM）一词暗示访问任何一块 RAM 都一样快。虽然这样想通常没问题，但由于 TLB 这类硬件/OS 特性的存在，访问某个特定内存页可能代价高昂——尤其当该页未被 TLB 映射时。所以记住这条实践箴言：**RAM 并不总是 RAM**。随机访问你的地址空间——特别是访问页数超过 TLB 覆盖范围时——可能招致严重的性能惩罚。因为我们的导师 David Culler 总把 TLB 指为诸多性能问题的源头，我们以他的名字命名这条定律。

## 一个真实的 TLB 表项

最后简要看一个真实 TLB：MIPS R4000（软件管理 TLB 的现代系统）。其 TLB 表项（简化）为：

```
VPN | G | ASID | PFN | C | D | V
```

MIPS R4000 支持 32 位地址空间、4KB 页，因而虚拟地址典型地是 20 位 VPN + 12 位偏移。但 TLB 中 VPN 只有 19 位——原来用户地址只来自地址空间的一半（另一半留给内核），所以只需 19 位 VPN。VPN 可翻译为最多 24 位的物理帧号（PFN），从而支持多达 64GB 的物理主存（2^24 个 4KB 页）。

其他有趣的位：**全局位**（G）用于在进程间全局共享的页——置位时 ASID 被忽略；**8 位 ASID** 供 OS 区分地址空间（思考题：同时运行的进程超过 256（2^8）个时 OS 该怎么办？）；**3 个一致性位**（C，Coherence）决定硬件如何缓存该页；**脏位**（D）在该页被写入后标记；**有效位**（V）告诉硬件该表项是否有有效翻译。还有未展示的**页掩码**（page mask）字段支持多种页大小。部分 64 位未被使用。

MIPS TLB 通常有 32 或 64 个表项，多数供运行中的用户进程使用，少数保留给 OS。OS 可设置一个**wired 寄存器**告诉硬件为 OS 保留几个 TLB 槽位；OS 用这些保留映射存放关键时刻（如 TLB 缺失处理程序内）要访问、而 TLB 缺失会很麻烦的代码与数据。

因为 MIPS TLB 是软件管理的，需要有更新 TLB 的指令。MIPS 提供四条：**TLBP**（探测某翻译是否在 TLB 中）、**TLBR**（把 TLB 表项内容读入寄存器）、**TLBWI**（替换指定 TLB 表项）、**TLBWR**（替换随机表项）。OS 用它们管理 TLB 内容。这些指令当然必须是特权的——想象一下用户进程若能修改 TLB 内容能干什么（提示：几乎为所欲为，包括接管机器、运行自己的恶意"OS"，甚至让太阳消失）。

## 小结

我们看到了硬件如何帮我们加速地址翻译：提供一个小的、专用片上 TLB 作为地址翻译缓存，多数内存引用有望不必访问主存中的页表。常见情形下，程序性能几乎与"内存未被虚拟化"时无异——这是操作系统了不起的成就，也是分页得以在现代系统中立足的关键。

不过 TLB 并非对一切程序都慷慨：若程序在短时间内访问的页数超出 TLB 容量，就会产生大量 TLB 缺失、明显变慢——这叫**超出 TLB 覆盖范围**（exceeding the TLB coverage），对某些程序是相当大的问题。一个解法（下章详述）是支持**更大的页**：把关键数据结构映射到由大页覆盖的地址空间区域，扩大 TLB 的有效覆盖。数据库管理系统（DBMS）这类程序常利用大页支持——它们有些数据结构既庞大又被随机访问。

最后一个值得一提的问题：TLB 访问很容易成为 CPU 流水线的瓶颈，尤其是在所谓**物理索引缓存**（physically-indexed cache）中——必须先完成地址翻译才能访问缓存，拖慢速度。为此人们研究了各种用虚拟地址直接访问缓存的巧妙办法（虚拟索引缓存），在缓存命中时避开昂贵的翻译步骤；这类设计解决了一些性能问题，也带来了新的硬件设计难题。

> 译注（衔接"空闲空间管理"）：TLB 解决的是"翻译快不快"；虚拟内存的另一块拼图是**空闲空间管理**（free-space management）——当用空闲链表等结构管理变长的空闲内存时，会遇到外部碎片、分割、合并与"最佳/最差/首次适配"等策略问题，详见 OSTEP 第 17 章（Free-Space Management）。两者合起来构成"页表之外"的内存管理全貌。

## 编者补充

> 本节为站点编者补充，串联前后篇目与 LLM 应用场景，非 OSTEP 原文翻译。

- **vLLM 的 PagedAttention 就是"分页思想"的移植**：它把 OS 管理物理内存的办法搬到 GPU 的 KV cache 上——把每条请求的 KV cache 切成固定大小的"块"（block，对应页），用"块表"（对应页表）做逻辑连续到物理离散的映射，从而消除为每条请求预留连续显存造成的碎片。读懂本文与上一篇的地址空间，PagedAttention 的论文就只剩 tensor 并行的细节了。
- **大页与大模型**：正文提到 DBMS 用大页对抗 TLB 覆盖不足；推理服务同理——Linux 上用 `hugetlbfs`/transparent huge pages 映射权重与 KV cache，可显著降低 TLB 缺失（几十 GB 的权重远超 TLB 覆盖，"RAM 并不总是 RAM"在这里真实发生）。
- **局部性决定 KV cache 访问效率**：自回归解码对每条请求的 KV cache 是顺序追加、重复读取（时间+空间局部性都好），这正是硬件缓存友好的访问模式；而注意力计算中的跨请求随机访问则是 TLB/缓存杀手——批处理调度时要有所权衡。
