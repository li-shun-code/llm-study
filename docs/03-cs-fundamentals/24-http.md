**HTTP** 是一种用于获取 HTML 文档等**资源**（resource）的协议。它是 Web 上任何数据交换的基础：它是一种**客户端-服务器**（client-server）协议，意味着请求由接收方发起——通常是 Web 浏览器。一份完整的文档通常由文本内容、布局说明、图片、视频、脚本等多种资源拼装而成。

客户端与服务器通过交换**一条条独立的消息**进行通信（而不是数据流）。客户端发出的消息称为**请求**（request）；服务器作为回答发出的消息称为**响应**（response）。

HTTP 设计于 1990 年代早期，是一种**可扩展**协议，随时间不断演化。它是一个应用层协议，经由 **TCP**（或经 TLS 加密的 TCP 连接）发送——理论上任何可靠的传输协议都可以。凭借可扩展性，它不只用来获取超文本文档，还用来获取图片与视频、向服务器提交内容（如 HTML 表单的结果）。HTTP 还可用于按需获取文档的一部分来更新 Web 页面。

## 基于 HTTP 的系统的组成

HTTP 是客户端-服务器协议：请求由一个实体——**用户代理**（user-agent，或代表它的代理）——发出。多数时候用户代理是 Web 浏览器，但也可以是任何东西，比如为搜索引擎抓取、建立并维护索引的爬虫机器人。

每个请求被发送到一台**服务器**，服务器处理后给出一个称为**响应**的答复。客户端与服务器之间有大量实体，统称**代理**（proxy），它们执行不同的操作、充当网关或缓存等。

实际上，浏览器与处理请求的服务器之间还有更多计算机：路由器、调制解调器等等。多亏 Web 的分层设计，这些都被隐藏在网络层与传输层；HTTP 位于最上面的应用层。这些底层虽然对诊断网络问题很重要，但与 HTTP 的描述基本无关。

### 客户端：用户代理

**用户代理**是代表用户行事的任何工具。这一角色主要由浏览器扮演，但也可以是工程师与 Web 开发者用来调试应用的程序。

浏览器**永远**是发起请求的一方，服务器从来不是（虽然多年来增加了一些模拟"服务器发起消息"的机制）。

要显示一个 Web 页面，浏览器先发送原始请求获取代表该页面的 HTML 文档；然后解析这个文件，发出额外的请求：对应要执行的脚本、要显示的布局信息（CSS）、以及页面包含的子资源（通常是图片与视频）。浏览器随后把这些资源拼合成完整文档——Web 页面。浏览器执行的脚本还能在后续阶段获取更多资源，浏览器相应地更新页面。

Web 页面是**超文本**文档：显示内容的一部分是**链接**（link），可被激活（通常点击鼠标）以获取新的 Web 页面，让用户引导自己的用户代理在 Web 中穿行。浏览器把这些"指令"翻译成 HTTP 请求，并进一步解读 HTTP 响应、向用户呈现清晰的结果。

### Web 服务器

通信信道的另一端是服务器，按客户端的请求**伺服**（serve）文档。一台服务器在表象上只是一台机器，实际上可能是分担负载的一组服务器（负载均衡）、或其他软件（如缓存、数据库服务器、电商服务器），全部或按需部分地生成文档。

服务器未必是一台机器——同一台机器上可以宿主多个服务器软件实例；有了 HTTP/1.1 与 `Host` 头部，它们甚至可以共享同一个 IP 地址。

### 代理

在浏览器与服务器之间，大量计算机与机器中继 HTTP 消息。由于 Web 协议栈的分层结构，其中大多数工作在传输层、网络层或物理层，对 HTTP 层是透明的，但对性能可能有显著影响。工作在**应用层**的那些通常称为**代理**。代理可以是**透明的**——原样转发收到的请求、不做任何改动；也可以是**非透明的**——把请求传给服务器之前以某种方式改变它。代理能执行的功能很多：

- 缓存（缓存可以是公共的或私有的，比如浏览器缓存）
- 过滤（如防病毒扫描或家长控制）
- 负载均衡（让多台服务器服务不同的请求）
- 认证（控制对不同资源的访问）
- 日志（允许保存历史信息）

## HTTP 的基本性质

### HTTP 是简单的

HTTP 总体上设计为**人类可读**——即使 HTTP/2 通过把 HTTP 消息封装进帧（frame）引入了额外复杂性。HTTP 消息能被人读懂与理解：开发者更容易测试，新人更容易上手。

### HTTP 是可扩展的

自 HTTP/1.0 引入的 **HTTP 头部**（headers）让协议易于扩展与试验。只要客户端与服务器就某个新头部的语义达成一致，甚至可以引入新功能。

### HTTP 是无状态的，但不是无会话的

HTTP 是**无状态**的（stateless）：同一连接上先后执行的两个请求之间没有任何关联。这对想连贯地与某些页面交互的用户立刻构成问题——比如电商购物车。不过，虽然 HTTP 本体的核心是无状态的，**HTTP Cookies** 让有状态的会话成为可能：利用头部的可扩展性，Cookie 被加入工作流，让每个 HTTP 请求共享同一上下文、同一状态，从而创建会话。

### HTTP 与连接

**连接**由传输层控制，因此从根本上不在 HTTP 的管辖范围内。HTTP 不要求底层传输协议基于连接，只要求它**可靠**（不丢消息，至少在这种情况下报错）。互联网上两个最常见的传输协议中，TCP 可靠而 UDP 不可靠，因此 HTTP 依赖基于连接的 TCP 标准。

客户端与服务器在交换 HTTP 请求/响应对之前，必须先建立一条 TCP 连接——这一过程需要多个往返。HTTP/1.0 的默认行为是为每个 HTTP 请求/响应对打开**单独的** TCP 连接；当多个请求接踵而至时，这比共享一条 TCP 连接低效。

为缓解这一缺陷，HTTP/1.1 引入了**流水线**（pipelining，后被证明难以实现）与**持久连接**：底层 TCP 连接可以部分地通过 `Connection` 头部控制。HTTP/2 更进一步，在单条连接上**多路复用**（multiplex）消息，让连接保持"温热"、更加高效。

设计更适合 HTTP 的更好传输协议的实验仍在进行：例如 Google 试验的 **QUIC**，构建在 UDP 之上以提供更可靠、更高效的传输协议。

## HTTP 能控制什么

HTTP 的可扩展天性让 Web 的控制力与功能性与时俱进。缓存与认证方法在 HTTP 早期就已具备；相比之下，**放宽同源约束**的能力直到 2010 年代才加入。

以下是 HTTP 可控制的常见功能：

- **缓存（Caching）**：文档如何缓存可由 HTTP 控制。服务器可以指示代理与客户端缓存什么、缓存多久；客户端可以指示中间缓存代理忽略已存文档。
- **放宽同源约束**：为防窥探与其他隐私侵犯，浏览器在网站之间强制严格隔离——只有**同源**（same origin）页面才能访问某 Web 页面的全部信息。这种约束对服务器是负担；HTTP 头部可以在服务器一侧放宽这种严格隔离，让一份文档可以拼缀来自不同域的信息（甚至可能有安全方面的理由这么做）。
- **认证（Authentication）**：某些页面可以保护起来，只允许特定用户访问。HTTP 可提供基本认证，使用 `WWW-Authenticate` 及类似头部，或通过 HTTP cookies 建立特定会话。
- **代理与隧道**：服务器或客户端常位于内网、对其他计算机隐藏真实 IP；HTTP 请求经代理跨越这道网络屏障。并非所有代理都是 HTTP 代理——例如 SOCKS 协议工作在更低的层次；FTP 等其他协议也能由这些代理处理。
- **会话（Sessions）**：用 HTTP cookies 把请求与服务器的状态关联起来，就创建了会话——尽管基本 HTTP 是无状态协议。这不仅对电商购物车有用，对任何允许用户自定义输出的站点都有用。

## HTTP 流程

客户端要与服务器（最终服务器或中间代理）通信时，执行以下步骤：

1. **打开一条 TCP 连接**：TCP 连接用于发送一个或多个请求并接收回答。客户端可以开新连接、复用既有连接，或开多条到服务器的 TCP 连接。
2. **发送 HTTP 消息**：HTTP/2 之前，HTTP 消息是人类可读的。HTTP/2 中消息被封装进帧、无法直接阅读，但原理不变。例如：

   ```http
   GET / HTTP/1.1
   Host: developer.mozilla.org
   Accept-Language: fr
   ```

3. **读取服务器发来的响应**，比如：

   ```http
   HTTP/1.1 200 OK
   Date: Sat, 09 Oct 2010 14:28:02 GMT
   Server: Apache
   Last-Modified: Tue, 01 Dec 2009 20:18:22 GMT
   ETag: "51142bc1-7449-479b075b2891b"
   Accept-Ranges: bytes
   Content-Length: 29769
   Content-Type: text/html

   <!doctype html>…（这里是所请求网页的 29769 字节）
   ```

4. **关闭连接，或为后续请求复用连接**。

若开启了 HTTP 流水线（pipelining），多个请求可以不等第一个响应完整收到就发出。但 HTTP 流水线已被证明在旧软件与现代软件共存的实际网络中难以实现，在 HTTP/2 中被帧内更稳健的请求多路复用取代。

## HTTP 消息

HTTP/1.1 及更早版本定义的 HTTP 消息是人类可读的。HTTP/2 中，消息被嵌入一种二进制结构——**帧**（frame）——以支持头部压缩、多路复用等优化。即使在这个版本里只有原始 HTTP 消息的一部分被发送，每条消息的**语义**不变，客户端（在概念上）重建出原始的 HTTP/1.1 请求。因此用 HTTP/1.1 格式理解 HTTP/2 消息依然有用。

HTTP 消息有两种类型：请求与响应，各有自己的格式。

### 请求

HTTP 请求的示例：

```http
GET / HTTP/1.1
Host: developer.mozilla.org
Accept-Language: fr
```

请求由以下元素组成：

- 一个 **HTTP 方法**（method）：通常是动词，如 `GET`、`POST`；或名词，如 `OPTIONS`、`HEAD`。它定义客户端要执行的操作——典型地，获取资源（用 `GET`）或提交 HTML 表单的值（用 `POST`），其他场景可能需要更多操作。
- 要获取的**资源路径**：资源的 URL 去掉那些从上下文即可明显得知的元素——如协议（`http://`）、域名（这里 `developer.mozilla.org`）、TCP 端口（这里 `80`）。
- HTTP 协议的**版本**。
- 可选的**头部**，向服务器传递附加信息。
- 一个**主体**（body）：某些方法（如 `POST`）才有，与响应中的主体类似，包含被发送的资源。

### 响应

响应的示例：

```http
HTTP/1.1 200 OK
Date: Sat, 09 Oct 2010 14:28:02 GMT
Server: Apache
Last-Modified: Tue, 01 Dec 2009 20:18:22 GMT
ETag: "51142bc1-7449-479b075b2891b"
Accept-Ranges: bytes
Content-Length: 29769
Content-Type: text/html

<!doctype html>…
```

响应由以下元素组成：

- 所遵循的 HTTP 协议**版本**。
- 一个**状态码**（status code）：表明请求成功与否，以及原因。
- 一个**状态消息**：状态码的非权威简短描述。
- HTTP **头部**：与请求的类似。
- 可选的**主体**：包含被获取的资源。

## 基于 HTTP 的 API

最常用的基于 HTTP 的 API 是 **Fetch API**：在 JavaScript 中发起 HTTP 请求，取代了 `XMLHttpRequest` API。

另一个 API，**服务器推送事件**（server-sent events，SSE），是一种单向服务：让服务器以 HTTP 为传输机制向客户端发送事件。客户端使用 `EventSource` 接口打开连接并建立事件处理器；浏览器自动把 HTTP 流上到达的消息转换成相应的 `Event` 对象，交给为该事件 `type` 注册的处理器（若无特定类型的处理器，则交给 `onmessage` 处理器）——这正是本模块《SSE 与 WebSocket》一篇的主角。

## 结语

HTTP 是易用且可扩展的协议。客户端-服务器结构加上添加头部的能力，让 HTTP 得以伴随 Web 能力的扩展一路前行。虽然 HTTP/2 为提升性能把消息嵌入帧、增加了一些复杂性，但消息的基本结构自 HTTP/1.0 以来保持不变；会话流程依旧基础，使它可以被 HTTP 网络监视器直接观察与调试。

> 译注：对本站读者，HTTP 的一个"新面孔"用途值得点名——**LLM 应用的流式输出**：OpenAI/Anthropic 等兼容 API 的 `stream: true` 就是在一条 HTTP 响应上用 `Content-Type: text/event-stream`（SSE）逐段推送生成内容；底层正是本文讲的"持久 HTTP 连接 + TCP 可靠传输"。相关细节见本模块《SSE 与 WebSocket》与《TCP》。
