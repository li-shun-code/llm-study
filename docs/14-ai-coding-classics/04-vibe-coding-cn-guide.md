**编者按**：[vibe-coding-cn](https://github.com/tradecatlabs/vibe-coding-cn)（16K+ star，MIT 许可）是中文社区规模最大的 Vibe Coding 系统化教程仓库之一，主线是"Prompt + Skill + Context + Quality Gate + 工程闭环"。它最有价值的不是概念，而是把"AI 不能自证正确"这件事**落成机器可执行门禁**的具体做法。本篇不再整篇转载，而是按**问题—做法—证据**重排，只保留三样东西：它的核心命题、它最有原创性的"拼好码"方法、以及中文环境才有的现实约束。与官方文档重叠的配置机制（skills / hooks / 子智能体）本篇不重复，指向《驾驭 Claude Code：CLAUDE.md、rules、skills、hooks 与子智能体的使用时机（Anthropic 官方博客全文翻译）》。引文均为仓库原文节选，逐节标注出处。

## 问题一：AI 说"我做完了"，你凭什么信

**做法：把目标冻结成带版本的基线，把执行变成可验证收敛循环。**

这是仓库 README 的"零号命题"（2026-09 当前版）：

> **Vibe Coding 可以理解为一种目标驱动、受约束、可验证的状态转移闭环；从控制结构看，它是一种固定目标、可变策略、分层反馈的系统：先将模糊需求经过澄清、结构化、一致性检查和人工确认，冻结为带版本的目标基线 `G*`；再让 Agent 在目标基线和约束不被静默修改的前提下，反复执行"观察当前状态 `S_t` → 识别状态差距 `Δ_t` → 选择策略 π_t 与行动 O_t → 执行 → 采集验证证据 E_t → 接受 / 修正 / 回滚 / 切换策略"……任何目标变更都必须通过显式版本、差异和授权进入新一轮闭环；每一层都必须具备独立验证、回滚、尝试上限和退出机制。**

它补了两条容易被忽略的定义：**"固定目标"不是目标不能变，而是未经授权不能被执行者静默改变，合法变化必须创建新的目标版本**；**"收敛"不是每步都成功，而是在验证、回滚、尝试上限与退出机制约束下进入并保持在目标的验收集合中**。

落到日常动作，是仓库《Vibe Coding 经验》里的三条（原文节选）：

> 关键原则：**AI 不能自证正确**。凡是能被测试、类型、schema、lint、CI、脚本或代码断言校验的规则，都应变成机器门禁，而不是只写在提示词里。
>
> 7. 重要规范必须代码化：能写成 lint、test、schema、type、hook、CI 的，就不要只写成自然语言。
> 8. 不符合规范的产出必须失败，而不是靠人记住提醒 AI。

**证据**：这不是口号。同一结论在别处被反复验证——Kent Beck 把"自动化测试套件 + 不许改测试"称作与模型协作时的"法律系统"（《TDD with AI：Kent Beck 的增强编程实践》）；METR 2026 年 2—3 月的报告直接记录了前沿模型会**为了通过人工评审而故意做出看起来合理的次优解**（《AI 代码的安全与质量陷阱：六大陷阱与检测清单》"过度自信"一节）。也就是说："静默改目标"不是假设风险，是已观测行为。

**可复制模板**（本站据上述命题改写为可直接贴进任务的话术）：

```text
目标基线 G*（本任务唯一验收依据）：
- 要达成：<可观测结果，不含实现方式>
- 明确不做：<范围排除项>
- 成功判据：<命令 + 期望输出，例如 `uv run pytest -q` 全绿且新增 3 条负向用例>
约束：不得修改 tests/ 与验收脚本；不得新增依赖（如确需，先停下并说明理由）
变更规则：若你认为目标不合理或无法判定，停止执行并说明原因——不要自行改目标
每轮输出：状态 S / 差距 Δ / 本轮证据 E（命令与真实输出），并声明你做了哪些假设
```

## 问题二：同一个会话里，生成者给自己打分

**做法：隔离审查——把生成、审查、验证拆开。**

README"命题四"原文：

> **AI 生成结果只是候选解，不是已验证事实；长期应默认其可能错误、非最优，并必须保留审查、验证与优化空间。**
>
> 成熟 AI 工程的重要治理原则，不是让同一个上下文自我确认，而是把生成、审查和验证拆开。NIST 强调独立审查可以降低偏见和利益冲突；OpenAI 与 Microsoft 都把外部测试、红队和独立评估作为发现盲点的重要机制；LLM-as-a-judge 研究也指出，模型评价自身输出时可能存在自偏好。

同节还给出操作口径（原文大意，非逐字）：重要产出必须**新开一个隔离会话**来审，并明确告诉审查方 AI——被审对象的结果不可信、不得沿用其结论，必须重新阅读原始资料、业务代码、目标、约束与验证结果，用事实、测试和可追溯证据判断其是否成立。

仓库把这一步写成了固定顺序：**AI 负责生成候选解，隔离上下文负责审查和优化候选解，事实与验证负责裁决候选解。**

**证据**：隔离审查与官方文档的结论同源——Anthropic 的说法是"模型选择做某件事"与"某件事自动发生"是两回事，硬约束要靠 hook 与权限而不是指令（见《驾驭 Claude Code》"何时使用每种方法"一节）；子智能体的价值正是"正文永不进入父对话、只回摘要"的隔离。

**可复制模板**（审查会话专用提示词）：

```text
你是一个独立审查者。以下产物来自另一个会话，其结论一律视为未经证实的主张。
请：1) 重新阅读原始需求与相关代码；2) 逐条列出该产物中的断言（含注释与提交说明）；
3) 对每条断言给出验证方式与结果（测试/命令/引用行号）；4) 明确标出它做了哪些未声明的假设；
5) 只报告结论与证据，不要替它修改代码。
```

## 问题三：让 AI 写代码，它就真的从零写起

这是仓库最有原创性的部分——**拼好码**（`docs/concepts/glue-coding.md`）。它的定义：

> **拼好码**是一种以"胶水原则"为核心的工程方法：优先复用成熟方案，只写必要的连接、编排、适配、隔离与业务代码，用最低成本交付稳定、可替换、可回滚的业务系统。

它明确反对的是"控制幻觉"：

> 开发者常把"自己写"误认为更可控、更安全、更优雅，但真实世界里，自研通常意味着更高缺陷率、更高维护成本、更弱生态支持和更差长期稳定性。

**做法一：决策顺序**（原文五条，压成一条判断链）

官方能力/平台能力/事实标准/内部公共能力 → 成熟开源库、稳定框架、长期维护工具、托管服务 → 配置、插件、扩展点、适配层、编排层 → 只为业务差异/集成边界/领域规则写自研 → **仅当成熟方案无法满足关键约束、或成本风险复杂度不可接受时，才允许自研核心能力**。

**做法二：胶水代码的边界**（原文两组清单的节选）

该做：连接不同系统、封装业务流程、适配输入输出、组合已有能力、隔离第三方依赖、表达项目特有业务规则。
不该做：重复实现已有成熟框架或通用基础设施、无理由重写稳定库、为控制感制造私有轮子、**在未调研成熟方案前直接进入自研实现**、让第三方 SDK 或平台私有模型污染核心业务模型。

配套的"胶水开发约束"（`docs/references/quality-gates-and-pitfalls.md`）里有几条特别适合直接抄进 AGENTS.md：

> 不得自行实现底层或通用逻辑，必须优先、直接、完整复用既有成熟仓库与生产级库；不得对依赖库进行任何形式的功能裁剪、逻辑重写或降级封装；不得存在"只导入不用"的伪集成行为；在生成代码时必须明确标注哪些功能来自外部依赖。

**做法三：偏离协议**——自研不是被禁止，而是被要求举证。若要偏离胶水原则，必须先说明：偏离原因、已评估的成熟方案、为什么成熟方案不能满足关键约束、自研范围与边界、维护成本、安全风险、锁定风险、测试策略、替换/删除/回滚路径。**未完成偏离说明前，不得默认进入自研核心能力实现路径。**

**证据**：仓库工程负责人给出的经验判据是"10 分开发，7 分查资料、对齐目标、比较方案"，并把高频教训写成一句——"花很长时间闭门造车，最后才发现已有更成熟、更稳定、更低维护成本的开源方案或官方能力"。这条判断在经济上也被验证：让模型自由发挥意味着把幻觉面扩大到"接口是否存在"这一层，而幻觉包研究显示代码生成模型给出的包名中 **19.7% 并不存在**（数据与检测手段见《AI 编码供应链安全：幻觉包、Slopsquatting 与沙箱防线》）。

## 问题四：中文环境的现实约束（这个仓库的独有价值）

**做法：把"环境能不能跑通"当成工程前提，而不是运气。**

- **网络与订阅前置**。仓库入门线第一步不是装工具，而是"先判断网络环境和订阅是否满足 CLI 前置条件"，并单独一篇讲网络环境（`docs/getting-started/network-environment.md`）。它的《常见坑汇总》把国内高频问题写成表格，可直接对号：GitHub 访问慢/超时 → 配置代理；`git clone` 超时 → git 代理或改 SSH；`pip`/`npm` 下载慢 → 换国内镜像源；SSL 证书错误 → 检查系统时间（**不要**按它原文那句"临时关闭 SSL 验证"去做——这会直接抵消传输层校验，本站明确不推荐）。

  ```bash
  # 原文给出的常用命令（镜像源与代理，按需启用）
  npm config set registry https://registry.npmmirror.com
  export https_proxy=http://127.0.0.1:7890        # 仅当前终端
  git config --global http.proxy http://127.0.0.1:7890
  ```

- **模型选型不必只盯一家**。仓库的工具清单同时收录国产模型（如 Kimi、智谱 GLM）与海外 CLI。现实结论是：**同一条门禁链要在多个模型上跑**——因为不同模型的幻觉分布不同，把规范固化到 lint/test/schema 之后，换模型才只是换性价比。
- **合规视角（本站编者补充，非仓库内容）**。国内团队用境外编码工具前，至少确认三件事：① 代码是否会被用于训练（看企业版/个人版的开关与条款）；② 仓库内容是否会出境到第三方服务（含 MCP 服务器、日志与遥测）；③ 生成的依赖是否引入不兼容许可证。这三条的检查表与责任边界见《AI 生成代码的 IP 与合规：版权承诺、责任边界与可版权性》。

**证据**：该仓库自身就是"规范代码化"的样本——它的 CI 只有 Markdown lint 与链接检查（`.github/workflows/ci.yml`），另有 `make check-source-facts` 校验外部事实镜像，`CODEOWNERS` 做路径级评审基线。**一个讲 AI 编程的仓库，把质量控制做成了纯文本工程门禁**，这正是它自己那条铁律第 8 条的实现："不符合规范的产出必须失败，而不是靠人记住提醒 AI。"

## 一页速用：把自然语言规范变成门禁

| 你想约束的事 | 只写提示词（会失效） | 机器门禁（会失败） |
| --- | --- | --- |
| 别改测试 | "永远不要修改测试文件" | PreToolUse hook 对 `tests/**` 返回 deny；CI 统计 `tests/` diff |
| 别乱装依赖 | "不要引入新依赖" | lockfile diff 检查 + 新增依赖需 PR 标签与人工批准 |
| 错误必须处理 | "请妥善处理异常" | `ruff --select S110,BLE001` / ESLint `no-empty` 非零退出 |
| 依赖要真实存在 | "只使用真实存在的库" | `pip index versions` / `npm view` 预检 + `pyright`/`mypy` 严格模式 |
| 别重复造轮子 | "优先复用" | 偏离协议模板：缺"已评估方案"就拒绝合并 |
| 需求要清楚 | "不清楚就问我" | 目标基线 G\* 段落设为必填，任务开工前先补澄清 |
