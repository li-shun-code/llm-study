我们与数十个跨行业的团队合作构建过 LLM 智能体（Agent）。一个始终成立的结论是：最成功的实现用的都是简单、可组合的模式，而非复杂框架。

> **注**：自 2024 年 12 月本文发布以来，文中描述的许多工具生态已经变化。想了解我们当前的做法，参见《[How we built Claude Managed Agents](https://www.anthropic.com/engineering/managed-agents)》及 Managed Agents 文档。

过去一年里，我们与数十个跨行业的团队合作构建 LLM 智能体。这些最成功的实现有一个共同点：它们没有使用复杂框架或专门的库，而是用简单、可组合的模式来构建。

本文分享我们服务客户和自己动手构建智能体的经验，为开发者提供构建高效智能体的实用建议。

## 什么是智能体？

"Agent"有多种定义方式。一些客户把 Agent 定义为能在长时间内独立运行、使用各种工具完成复杂任务的完全自主系统；另一些客户则用这个词描述遵循预定义工作流的更"脚本化"的实现。在 Anthropic，我们把所有这些变体统称为**智能体系统（Agentic Systems）**，但在架构上对**工作流（Workflow）**与**智能体（Agent）**做出重要区分：

- **工作流（Workflows）**：LLM 和工具通过*预定义的代码路径*来编排的系统。
- **智能体（Agents）**：LLM *动态地指挥自己的处理过程和工具使用*、对如何完成任务保持掌控的系统。

下文将详细探讨这两类系统。附录 1（"实践中的智能体"）描述了两个客户从中获得显著价值的领域。

## 何时（以及何时不）使用智能体

用 LLM 构建应用时，我们建议寻找尽可能简单的方案，只在需要时才增加复杂度。这可能意味着根本不构建智能体系统。智能体系统通常用延迟和成本换取更好的任务表现，你需要判断这种权衡何时划算。

当确实需要更多复杂度时：对于定义清晰的任务，工作流提供可预测性和一致性；当需要大规模的灵活性和模型驱动的决策时，智能体是更好的选择。而对许多应用来说，用检索和上下文内示例优化单次 LLM 调用通常就足够了。

## 何时以及如何使用框架

有许多框架能让智能体系统更容易实现，包括：

- [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)；
- AWS 的 [Strands Agents SDK](https://strandsagents.com/latest/)；
- [Rivet](https://rivet.ironcladapp.com/)：拖拽式 GUI LLM 工作流构建器；
- [Vellum](https://www.vellum.ai/)：另一个用于构建和测试复杂工作流的 GUI 工具。

这些框架通过简化调用 LLM、定义和解析工具、串联调用等标准底层任务，让入门变得容易。但它们往往引入额外的抽象层，遮蔽了底层的提示词与响应，使调试更困难；也可能诱使你在更简单的配置就够用的情况下增加复杂度。

我们建议开发者从直接调用 LLM API 开始：许多模式用几行代码就能实现。如果确实要用框架，请确保理解框架底层的代码。对"引擎盖下发生了什么"的错误假设是客户出错的常见来源。

示例实现参见我们的 [cookbook](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)。

## 构件、工作流与智能体

本节探讨我们在生产环境中见到的常见智能体系统模式。我们从基础构件——增强型 LLM——出发，逐步增加复杂度，从简单的组合式工作流一直到自主智能体。

### 构件：增强型 LLM（The Augmented LLM）

智能体系统的基本构件，是被检索、工具、记忆等能力增强过的 LLM。我们当前的模型能够主动使用这些能力——自己生成搜索查询、选择合适的工具、决定要保留哪些信息。

![增强型 LLM](https://www-cdn.anthropic.com/images/4zrzovbb/website/d3083d3f40bb2b6f477901cc9a240738d3dd1371-2401x1000.png)

*图：增强型 LLM。*

我们建议关注实现中的两个关键点：针对你的具体用例定制这些能力；确保它们为 LLM 提供简单、文档完善的接口。实现这些增强的方式很多，其中一种是利用我们发布的模型上下文协议（Model Context Protocol，MCP）——它让开发者通过简单的客户端实现，接入不断增长的第三方工具生态。

本文余下部分假设每次 LLM 调用都能使用这些增强能力。

### 工作流：提示链（Prompt Chaining）

提示链把任务分解为一系列步骤，每次 LLM 调用处理上一步的输出。你可以在任意中间步骤上添加程序化检查（见下图中的"门控/gate"），确保流程仍在正轨上。

![提示链工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/7418719e3dab222dccb379b8879e1dc08ad34c78-2401x1000.png)

*图：提示链工作流。*

**何时使用**：任务可以轻松、干净地分解为固定子任务时，提示链是理想选择。主要目标是用延迟换取更高的准确率——让每次 LLM 调用都变成更简单的任务。

**示例**：

- 生成营销文案，然后把它翻译成另一种语言。
- 先写文档大纲，检查大纲是否满足某些标准，再基于大纲写全文。

### 工作流：路由（Routing）

路由对输入分类，并将其导向专门化的后续任务。这种工作流实现了关注点分离，让你能构建更专门化的提示。没有它，针对一类输入的优化可能会损害其他输入的表现。

![路由工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/5c0c0e9fe4def0b584c04d37849941da55e5e71c-2401x1000.png)

*图：路由工作流。*

**何时使用**：复杂任务存在明显可分开处理的类别、且分类可以被准确完成（由 LLM 或更传统的分类模型/算法）时，路由效果很好。

**示例**：

- 把不同类型的客服问题（一般咨询、退款请求、技术支持）导入不同的下游流程、提示与工具。
- 把简单/常见的问题路由给更小、更便宜的模型（如 Claude Haiku 4.5），把困难/罕见的问题路由给更强的模型（如 Claude Sonnet 4.5），以优化性能与成本的平衡。

### 工作流：并行化（Parallelization）

LLM 有时可以同时处理一个任务，其输出由程序聚合。并行化工作流有两种关键变体：

- **分段（Sectioning）**：把任务拆成可并行运行的独立子任务。
- **投票（Voting）**：把同一任务运行多次以获得多样化输出。

![并行化工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/406bb032ca007fd1624f261af717d70e6ca86286-2401x1000.png)

*图：并行化工作流。*

**何时使用**：当拆出的子任务可以并行执行以提速，或者需要多个视角/多次尝试来获得更高置信度的结果时，并行化行之有效。对有多种考量维度的复杂任务，让每次 LLM 调用专注处理一个维度，通常比一次调用处理所有维度表现更好。

**示例**：

- **分段**：
  - 实现护栏（Guardrails）：一个模型实例处理用户查询，另一个实例同时筛查不当内容或请求。让同一次 LLM 调用既做护栏又做核心回答，通常表现更差。
  - 自动化 LLM 性能评估（Evals）：每次 LLM 调用评估模型表现在某个给定提示上的不同方面。
- **投票**：
  - 审查一段代码是否存在漏洞：用几个不同的提示分别审查，发现问题即标记。
  - 判断某内容是否不当：多个提示评估不同方面，或要求不同的投票阈值，以平衡误报与漏报。

### 工作流：编排者-工作者（Orchestrator-Workers）

在编排者-工作者工作流中，一个中心 LLM 动态地分解任务，把子任务委派给工作者 LLM，并综合它们的结果。

![编排者-工作者工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/8985fc683fae4780fb34eab1365ab78c7e51bc8e-2401x1000.png)

*图：编排者-工作者工作流。*

**何时使用**：适用于无法预测需要哪些子任务的复杂任务（例如编码任务中，需要改多少个文件、每个文件改什么，往往取决于具体任务）。它在拓扑上与并行化相似，但关键区别在于灵活性——子任务不是预先定义的，而是由编排者根据具体输入动态决定。

**示例**：

- 每次需要对多个文件做复杂修改的编码产品。
- 需要从多个来源收集并分析信息、寻找可能相关信息的搜索任务。

### 工作流：评估者-优化者（Evaluator-Optimizer）

在评估者-优化者工作流中，一次 LLM 调用生成回答，另一次调用在循环中提供评估与反馈。

![评估者-优化者工作流](https://www-cdn.anthropic.com/images/4zrzovbb/website/14f51e6406ccb29e695da48b17017e899a6119c7-2401x1000.png)

*图：评估者-优化者工作流。*

**何时使用**：当我们有明确的评估标准、且迭代完善能带来可度量的价值时，这种工作流特别有效。两个"适配良好"的信号：第一，当人类清楚表达反馈时，LLM 的回答可以被证实地改进；第二，LLM 自己也能给出这样的反馈。这类似于人类作家打磨文稿时的迭代写作过程。

**示例**：

- 文学翻译：翻译 LLM 初译可能漏掉细微差别，而评估 LLM 能提出有用的批评。
- 需要多轮搜索与分析才能收集全面信息的复杂搜索任务：由评估者判断是否值得继续搜索。

### 智能体（Agents）

随着 LLM 在关键能力上日趋成熟——理解复杂输入、推理与规划、可靠地使用工具、从错误中恢复——智能体正在生产环境中崭露头角。智能体的工作始于人类用户的一条指令或一次交互式讨论。任务明确后，智能体独立地规划与操作，并可能在需要进一步信息或判断时回到人类身边。执行过程中，智能体必须在每一步从环境中获取"事实依据"（Ground Truth，如工具调用结果或代码执行输出）来评估自身进度；它可以在检查点或遇到阻塞时暂停以获取人类反馈。任务通常在完成时终止，但也常设置停止条件（如最大迭代次数）以保持控制。

![自主智能体](https://www-cdn.anthropic.com/images/4zrzovbb/website/58d9f10c985c4eb5d53798dea315f7bb5ab6249e-2401x1000.png)

*图：自主智能体。*

**何时使用智能体**：智能体适用于开放性问题——难以或不可能预测所需步骤数、无法硬编码固定路径的问题。LLM 可能会运行许多轮，你必须对其决策有一定程度的信任。智能体的自主性使它们成为在可信环境中规模化执行任务的理想选择。

智能体的自主性意味着更高的成本与误差累积（Compounding Errors）的可能。我们建议在沙箱环境中进行充分测试，并配备适当的护栏。

**示例**（来自我们自己的实现）：

- 解决 [SWE-bench 任务](https://www.anthropic.com/research/swe-bench-sonnet)的编码 Agent——根据任务描述对多个文件进行修改；
- 我们的["计算机使用"参考实现](https://github.com/anthropics/anthropic-quickstarts/tree/main/computer-use-demo)——Claude 操作一台计算机来完成任务。

![编码智能体的高层流程](https://www-cdn.anthropic.com/images/4zrzovbb/website/4b9a1f4eb63d5962a6e1746ac26bbc857cf3474f-2400x1666.png)

*图：编码智能体的高层流程。*

## 组合与定制这些模式

这些构件并非死规矩，而是开发者可以塑造、组合以适配不同用例的常见模式。与所有 LLM 特性一样，成功的关键是度量表现并迭代实现。再强调一次：只有当增加复杂度*确实能*改善结果时，才去增加它。

## 总结

在 LLM 领域取得成功，不在于构建最复杂的系统，而在于构建*适合你需求*的系统。从简单的提示词开始，用全面的评估去优化它们，只有当更简单的方案力不从心时，才引入多步智能体系统。

实现智能体时，我们遵循三条核心原则：

1. 在智能体设计中保持**简单性（Simplicity）**。
2. 通过显式展示智能体的规划步骤来优先保证**透明性（Transparency）**。
3. 通过完善的工具**文档与测试**，精心打磨你的智能体-计算机接口（Agent-Computer Interface，ACI）。

框架能帮你快速起步，但走向生产时，不要犹豫去减少抽象层、用基础组件构建。遵循这些原则，你可以创造出不仅强大，而且可靠、可维护、被用户信任的智能体。

## 附录 1：实践中的智能体

与客户的合作揭示了两个特别有前景的 AI 智能体应用，印证了上述模式的实际价值。两个应用都说明：当任务同时需要对话与行动、有明确的成功标准、能形成反馈闭环、并支持有意义的人类监督时，智能体的价值最大。

### A. 客户支持

客户支持把熟悉的聊天机器人界面与工具集成带来的增强能力结合起来。它天然适合较为开放式的智能体，原因如下：

- 支持对话天然遵循会话流程，同时又需要访问外部信息与执行操作；
- 可以集成工具来拉取客户数据、订单历史和知识库文章；
- 退款、更新工单等动作可以程序化处理；
- 成功与否可以通过用户定义的"问题是否解决"清晰度量。

一些公司通过"只为成功解决的案例计费"的用量计费模式，证明了这条路线的可行性——这也体现了他们对自家智能体有效性的信心。

### B. 编码智能体

软件开发领域已展现出 LLM 特性的巨大潜力，能力从代码补全一路演进到自主解决问题。智能体在这里特别有效，因为：

- 代码方案可以通过自动化测试验证；
- 智能体可以拿测试结果当反馈来迭代方案；
- 问题空间定义清晰、结构良好；
- 输出质量可以被客观度量。

在我们自己的实现中，智能体已经能仅凭 pull request 描述就解决 [SWE-bench Verified](https://www.anthropic.com/research/swe-bench-sonnet) 基准中的真实 GitHub issue。不过，自动化测试帮助验证功能正确性，人工审查对于确保方案符合更广泛的系统需求仍然至关重要。

## 附录 2：给你的工具做提示工程

无论构建哪种智能体系统，工具都可能是智能体的重要组成部分。工具让 Claude 通过在 API 中指定精确的结构和定义来与外部服务和 API 交互；当 Claude 计划调用某个工具时，它会在 API 响应中包含一个工具使用块。工具的定义与规范，值得获得与你整体提示词同等的提示工程投入。本附录简述如何给你的工具做提示工程。

同一个动作往往有多种规定方式。例如编辑文件可以写一个 diff，也可以重写整个文件；结构化输出可以把代码放在 markdown 里，也可以放在 JSON 里。在软件工程中，这类差异是"表面的"，可以无损互转。但对 LLM 来说，有些格式写起来比其他格式难得多：写 diff 需要在写出新代码之前就知道块头部（chunk header）里改动的行数；把代码写进 JSON（相比 markdown）需要对换行和引号做额外转义。

我们对工具格式的建议：

- 给模型足够的 token 去"思考"，别让它把自己逼进死角。
- 让格式尽量接近模型在互联网文本中自然见过的样子。
- 确保没有格式上的"额外负担"，比如要求精确统计数千行代码的行数，或对它写的代码做字符串转义。

一条经验法则：想想人机接口（HCI）要投入多少心思，然后为打造良好的*智能体*-计算机接口（ACI）投入同样多的心思。具体来说：

- 设身处地站在模型的角度想：仅凭描述和参数，这个工具怎么用是否显而易见？如果你都要仔细琢磨，模型多半也是。好的工具定义通常包含使用示例、边界情况、输入格式要求，以及与其他工具的清晰边界。
- 能否通过改参数名或描述让事情更直白？把这当作给团队里的初级开发者写一份出色的 docstring。当存在许多相似工具时尤其重要。
- 测试模型如何使用你的工具：在工作台里跑大量示例输入，观察模型犯什么错，然后迭代。
- 给你的工具做[防错设计（Poka-yoke）](https://en.wikipedia.org/wiki/Poka-yoke)：调整参数设计，让犯错变得更难。

在为 [SWE-bench](https://www.anthropic.com/research/swe-bench-sonnet) 构建智能体时，我们花在优化工具上的时间实际上超过了优化整体提示词。例如，我们发现当智能体离开根目录后，模型在使用相对文件路径的工具时会出错。为修复这一点，我们把工具改成强制要求绝对文件路径——之后模型对这种用法运用得毫无瑕疵。
