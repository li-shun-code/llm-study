用大语言模型构建生成式 AI 应用会带来新的挑战。一个关键问题是：如何保证模型针对给定用户请求所生成内容的质量（准确性与相关性）。在前面的课程中，我们讨论过提示工程（Prompt Engineering）与检索增强生成（Retrieval-Augmented Generation，RAG）这两种技术，它们都通过**修改输入给现有模型的提示词**来解决问题。本课讨论第三种技术——**微调（Fine-Tuning）**，它尝试通过**用额外数据重新训练模型本身**来应对这一挑战。

## 什么是面向语言模型的微调

按照定义，大语言模型是在来自互联网等多元来源的海量文本上**预训练（Pre-training）**出来的。正如前面课程所学，我们需要提示工程、RAG 这类技术来提升模型回答用户问题（"提示词"）的质量。

一种流行的提示工程技巧是为模型提供更多关于期望输出的指引：要么提供**指令**（显式引导），要么**给它几个示例**（隐式引导）。这被称为少样本学习（Few-shot Learning），但它有两个局限：

- 模型的 token 上限会限制你能给出的示例数量，进而限制效果。
- 模型的 token 成本会让"每个提示词都附示例"变得昂贵，限制灵活性。

微调是机器学习系统中的常见做法：取一个预训练模型，用新数据重新训练，以提升其在特定任务上的表现。对语言模型而言，我们可以**用为某个任务或领域精心整理的一批示例**来微调预训练模型，得到一个在该任务/领域上更准确、更相关的**定制模型**。微调还有一个附带好处：它可以减少少样本学习所需的示例数量，从而降低 token 用量与相关成本。

## 什么时候、为什么应该微调

在本课的语境下，微调指的是**有监督（Supervised）微调**：用**不属于原始训练集的新数据**进行再训练。这与无监督微调不同——后者是用原始数据但换一组超参数重新训练。

要记住的关键一点是：微调是一项进阶技术，需要一定的专业积累才能得到理想结果。如果做得不好，不仅可能没有预期提升，甚至可能让模型在你目标领域上的表现变差。

所以在学习"如何"微调之前，先要弄清"为什么"要走这条路、"什么时候"该启动微调。先问自己这几个问题：

- **使用场景（Use Case）**：你想用微调解决什么？希望改进现有预训练模型的哪个方面？
- **替代方案（Alternatives）**：是否已经尝试过其他技术？先用它们建立对比基线。
  - 提示工程：先试少样本提示（附上相关问答示例），评估回答质量。
  - 检索增强生成（RAG）：把检索到的数据结果拼进提示词，评估回答质量。
- **成本（Costs）**：是否核算过微调的成本？
  - 可调性——目标预训练模型是否开放微调？
  - 人力——准备训练数据、评估与迭代模型的投入。
  - 算力——运行微调任务、部署微调模型的费用。
  - 数据——是否有足够多的高质量样本支撑微调。
- **收益（Benefits）**：是否确认了微调的收益？
  - 质量——微调后的模型是否胜过基线？
  - 成本——提示词简化后是否降低了 token 开销？
  - 扩展性——基座模型能否复用到新领域？

回答完这些问题，你就能判断微调是否是当前场景的正确选择。理想情况下，只有当收益大于成本时才值得微调。决定继续之后，就可以开始考虑"如何"微调预训练模型了。

::: tip 编者注：一条实用的选型经验
原课程的决策顺序值得反复强调：**先提示工程、再 RAG、最后才微调**。提示工程几分钟就能迭代一轮；RAG 解决"模型不知道你的私有/最新知识"的问题，且知识可以随时增删；而微调改变的是模型"会什么、像什么"，适合风格、格式、领域行为对齐，不能可靠地注入随时变化的事实知识。三者常常组合使用：微调定风格与行为，RAG 供知识，提示工程做最后一层控制。
:::

## 微调一个预训练模型需要什么

微调预训练模型需要准备：

- 一个待微调的预训练模型
- 一份用于微调的数据集
- 一个运行微调任务的训练环境
- 一个部署微调后模型的托管环境

## 三种微调技术怎么选

当今主流平台（如 Microsoft Foundry，它把原来的 Azure OpenAI Studio 与 Azure AI Studio 整合在了一起）普遍支持三种微调技术。原课程建议：**从 SFT 开始**——它覆盖的场景最广。底层实现上，Foundry 使用 **LoRA（低秩适应，Low-Rank Adaptation）**进行高效微调，比重新训练所有权重更快、更省。

| 技术 | 做什么 | 什么时候用 |
| --- | --- | --- |
| **有监督微调（SFT）** | 用输入/输出示例对训练，让模型学会产出你想要的回答。 | 大多数任务的默认选择：领域专业化、任务性能、风格语气、指令遵循、语言适配。 |
| **直接偏好优化（DPO）** | 从"偏好 vs 非偏好"回答对中学习，使输出与人类偏好对齐。 | 当你拥有比较型反馈数据时，用于提升回答质量、安全性与对齐度。 |
| **强化微调（RFT）** | 用评分器（grader）给出的奖励信号，以强化学习优化复杂行为。 | 有明确对错、以推理为主的客观领域（数学、化学、物理）。需要更多机器学习专业能力。 |

## 微调最佳实践

原课程整理的平台推荐做法，同样适用于自建训练流程：

- **先做基线。** 微调之前，先用提示工程和 RAG 度量基座模型表现，这样你才能证明微调带来的增益。
- **小步启动，再扩大。** 先用 50–100 条高质量样本验证方向有效，再增长到 500+ 条进入生产。质量胜过数量——果断剔除低质量样本。
- **正确组织数据格式。** 训练与验证文件应为 JSONL、UTF-8（带 BOM）、单文件 512 MB 以内，使用 chat-completions 消息格式。务必准备验证集，以便观察过拟合（Overfitting）。
- **训练时的系统提示词在推理时保留。** 调用模型时使用与训练时相同的 system 消息。
- **评估多个检查点，不要盲信最后一个。** 平台通常保留最后几个 epoch 的可部署检查点；观察 `train_loss` / `valid_loss` 与 token 准确率，选择泛化最好的那个。
- **对比质量的同时度量 token 成本。**
- **用持续微调迭代。** 可以在已微调模型上用新数据继续微调。
- **留意托管成本。** 定制模型按小时计费，长期闲置的部署会被回收——及时清理不用的部署。

## 小结

- 提示工程、RAG、微调是三条互补的路径：前者改输入，中者供知识，后者改模型。
- 微调是有监督的再训练：收益真实存在，但需要数据、算力与专业能力的持续投入。
- 动手微调前，先用提示工程与 RAG 建立可度量的基线，并确认收益大于成本。
- 选定微调后，SFT 是默认起点；有偏好数据用 DPO；有客观奖励信号的推理任务考虑 RFT。
