在构建 LLM 应用时，**分块（Chunking）**指把大段文本切分成更小的片段（chunk）。它是决定向量数据库中内容相关性的关键预处理步骤：块要足够大以承载有意义的信息，又要足够小以保证检索增强生成（RAG）与智能体工作流的性能和低延迟。本文先讲清分块方法与权衡，再用 Anthropic 的上下文检索（Contextual Retrieval）回应分块最棘手的问题——"丢上下文"。

## 为什么必须分块？

任何涉及向量数据库或 LLM 的应用都需要分块，原因有二：保证嵌入模型（Embedding Model）能把数据装进上下文窗口，以及保证块本身含有"可被检索"的信息。

所有嵌入模型都有上下文窗口，决定了能处理进单个定长向量的 token 数量。超出窗口的多余 token 可能被截断丢弃，导致重要上下文从文本表示中消失，检索时永远浮不上来。此外，仅仅把数据切到合适大小还不够——块内必须包含与搜索相关的信息。如果一块内的句子离开上下文就毫无意义，查询时它们可能根本不会被召回。

### 分块在语义搜索中的角色

在语义搜索（Semantic Search）中，我们为文档语料建立索引，相似度是**以块为单位**与查询向量比较的，返回的也是相似的块。分块策略有效，搜索结果才能准确捕捉用户查询的要点。块太大或太小都会导致结果不精确或漏掉相关内容。经验法则：**如果一段文字在没有上下文的情况下人能看懂，语言模型也能看懂**。

### 分块在 RAG 与智能体应用中的角色

智能体需要最新信息来调用工具、做决策、回答问题。检索返回的块会占用会话上下文，并为智能体的回答提供事实依据。如果智能体被误导，或拿到的信息缺乏足够上下文，它可能浪费 token 去生成幻觉或调用错误的工具。

### 长上下文 LLM 时代还要分块吗？

某些情况下（如使用 200k 上下文窗口的模型），不分块的文档也能塞进上下文。但用大块仍会增加下游响应的延迟与成本。更重要的是，长上下文嵌入模型与 LLM 都受"迷失在中间（Lost in the Middle）"问题困扰：埋在长文档中间的相关信息容易被忽略。解决办法恰恰是把最优数量的信息传给下游 LLM——这必然降低延迟、保证质量。

## 选择分块策略要想清楚的四个问题

1. **切的是什么数据？** 是文章、书籍这类长文档，还是推文、商品描述、聊天消息这类短内容？短文档可能根本不用切；长文档往往自带结构（小标题、章节），可以借力。
2. **用哪个嵌入模型？** 不同模型的信息容量不同（尤其在代码、金融、医疗、法律等领域），训练数据也影响实战表现。选定模型后，分块策略要与其训练时预期的文档类型对齐。
3. **用户查询的长度与复杂度如何？** 短而具体，还是长而复杂？查询形态应与块粒度相关联，让查询嵌入与块嵌入更"对味"。
4. **检索结果如何被使用？** 语义搜索、问答、RAG 还是智能体工作流？人工审阅所需的信息量与 LLM 生成回答所需的信息量可能差异巨大。

## 短内容与长内容的嵌入行为差异

嵌入**句子**时，向量聚焦句子的具体含义，适合句子级分类、推荐系统、或"先搜摘要再进长文档"的应用。若每句话本身就是一个独立文档，那根本无需分块。

嵌入**整段或整个文档**时，嵌入过程会考虑整体上下文以及句间关系，得到更全面的向量表示，但也可能引入噪声、稀释单个句子的显著性，使精确匹配更难。这类块适合问答等"答案可能要好几段"的场景。现代 AI 应用大多面对长文档，几乎都必须分块。

## 分块方法

### 固定大小分块（Fixed-size Chunking）

最常见、最直接：定好每块的 token 数，按此切块。该数字通常取嵌入模型的最大上下文窗口（如 1024 或 8192）。注意不同模型分词（tokenize）方式不同，token 数要准确估算。**大多数场景固定分块就是最优起点**——先从这里开始，确认不够用再迭代。

### 内容感知分块（Content-aware Chunking）

固定分块容易忽略文档中的关键结构。内容感知分块遵循结构来帮助定义块的语义边界。

#### 简单句子/段落切分

有些嵌入模型对句子级内容做了优化。要从未预处理的大文本中挖句子时，可用：

- **朴素切分**：按句号、换行或空白切；
- **NLTK**：Python 自然语言工具包，提供训练好的句子分词器；
- **spaCy**：提供成熟的句子切分能力，块内上下文保留更好。

#### 递归字符分块（Recursive Character Chunking）

LangChain 实现了 [RecursiveCharacterTextSplitter](https://python.langchain.com/docs/how_to/recursive_text_splitter/)：按给定顺序尝试分隔符，默认 `["\n\n", "\n", " ", ""]`，先切段落、再切句子、再切词，直到满足块大小。这是"固定按字符切"与"语义切分"之间很好的折中，同时尽量保证块大小可控。

#### 基于文档结构的分块

对 PDF、DOCX、HTML、代码、Markdown、LaTeX 等结构化大文档，专用分块方法能保留原有结构：

- PDF 含大量标题、正文、表格，需要预处理后分块；
- 网页 HTML 含 `<p>`（段落）、`<title>`（标题）等标签，可据此切分识别；
- **Markdown**：识别标题、列表、代码块等语法，按结构与层级智能切分，块语义更连贯；
- **LaTeX**：解析命令与环境，按章节、小节、公式的逻辑组织切分。

### 语义分块（Semantic Chunking）

构建 LLM 应用时你多半已经有嵌入能力——而嵌入可以抽取数据中的语义。语义分块把文档切成句子，把每个句子与其邻近句子分组并生成嵌入，比较相邻组之间的语义距离，距离突变处即为主题切换点，也就是块的边界。

### LLM 上下文分块（Contextual Chunking）

有些复杂文档在不丢上下文的前提下无法直接分块：数百页、频繁切换主题、或必须结合多处内容才能理解。Anthropic 在 2024 年提出的上下文检索（Contextual Retrieval）正是解决这个问题——下一章全文展开。

## 深入：Anthropic 上下文检索（Contextual Retrieval）

> 以下翻译自 Anthropic 工程博客《Introducing Contextual Retrieval》（2024-09-19）。

传统 RAG 在编码信息时会丢掉上下文，导致系统无法从知识库中取回相关内容。上下文检索用两个子技术——**上下文嵌入（Contextual Embeddings）**与**上下文 BM25（Contextual BM25）**——把检索失败率降低 49%，配合重排序（Reranking）可降低 67%。

### 先说"直接用长提示词"

有时最简单的方案就是最好的。如果知识库小于 200,000 token（约 500 页），直接把整个知识库放进提示词即可，无需 RAG。配合提示词缓存（Prompt Caching），延迟可降低 2 倍以上、成本最多降 90%。但知识库继续增长时，就需要更可扩展的方案——上下文检索。

### RAG 入门：扩展到更大的知识库

对装不进上下文窗口的知识库，RAG 的标准预处理是：

1. 把知识库（文档语料）切成较小的文本块，通常不超过几百 token；
2. 用嵌入模型把块转成编码语义的向量嵌入；
3. 把嵌入存入支持语义相似度搜索的向量数据库。

运行时，用向量数据库找到与查询语义最相关的块，加入提示词发给生成模型。

嵌入模型擅长语义关系，但可能漏掉关键的精确匹配。这时老技术 BM25（Best Matching 25）就能补位：它基于词法匹配做精确的词/短语匹配，对包含唯一标识符或专业术语的查询特别有效。BM25 建立在 TF-IDF 之上，并考虑文档长度、对词频应用饱和函数，防止常见词主导结果。

举例：用户在技术支持库中查询 "Error code TS-999"。嵌入模型可能找到泛泛讲错误码的内容，却错过精确的 "TS-999"；BM25 则会精确命中该字符串。两者结合的流程：

1. 切块；
2. 为块创建 TF-IDF 编码与语义嵌入；
3. 用 BM25 按精确匹配取 top 块；
4. 用嵌入按语义相似度取 top 块；
5. 用排名融合（Rank Fusion）合并去重两路结果；
6. 把 top-K 块加入提示词生成回答。

这套方案能经济地扩展到远超单个提示词容量的知识库，但有显著局限：**它常常破坏上下文**。

### 传统 RAG 的上下文难题

传统 RAG 把文档切成小块检索，单个块可能缺乏足够上下文。设想知识库中嵌入了一批美国 SEC 财报，收到问题："ACME Corp 2023 年 Q2 的营收增长是多少？"相关块可能只是："该公司营收环比增长 3%。"这一块既没说哪家公司、也没说哪个季度，既难检索到，也难被正确使用。

### 上下文检索的做法

在嵌入（Contextual Embeddings）与建 BM25 索引（Contextual BM25）之前，给每个块**前置**一段针对该块的说明性上下文。还是 SEC 例子：

```text
original_chunk = "The company's revenue grew by 3% over the previous quarter."
contextualized_chunk = "This chunk is from an SEC filing on ACME corp's performance in Q2 2023; the previous quarter's revenue was $314 million. The company's revenue grew by 3% over the previous quarter."
```

值得说明：此前也有利用上下文改进检索的方案——[给块加通用文档摘要](https://aclanthology.org/W02-0405.pdf)（Anthropic 实验证实收益非常有限）、[假设性文档嵌入](https://arxiv.org/abs/2212.10496)（HyDE）、[基于摘要的索引](https://www.llamaindex.ai/blog/a-new-document-summary-index-for-llm-powered-qa-systems-9a32ece2f9ec)（评估表现不佳）——都与本文方法不同。

当然，人工给成千上万甚至上百万个块写注释不现实，于是用 Claude 来写。对每个块，用如下提示词生成上下文：

```text
<document> 
{{WHOLE_DOCUMENT}} 
</document> 
Here is the chunk we want to situate within the whole document 
<chunk> 
{{CHUNK_CONTENT}} 
</chunk> 
Please give a short succinct context to situate this chunk within the overall document for the purposes of improving search retrieval of the chunk. Answer only with the succinct context and nothing else. 
```

生成的上下文文本通常 50-100 token，前置到块上再做嵌入与 BM25 索引。借助提示词缓存，整份文档只需载入缓存一次，各块依次引用即可。按 800 token 的块、8k token 的文档、50 token 的指令、每块 100 token 上下文计算，**生成上下文化的块的一次性成本约为每百万文档 token $1.02**。

### 实验结果

Anthropic 在多个知识领域（代码库、小说、ArXiv 论文、科学论文）、多种嵌入模型与检索策略上实验，评估指标为 1 − recall@20（top-20 块中未取回相关文档的比例）。使用表现最好的嵌入配置与 top-20 检索时：

- **上下文嵌入**把 top-20 检索失败率降低 35%（5.7% → 3.7%）；
- **上下文嵌入 + 上下文 BM25**把失败率降低 49%（5.7% → 2.9%）。

**表：上下文检索对检索失败率（1 − recall@20）的改善**

| 方法 | 失败率 | 相对改善 |
| --- | --- | --- |
| 基线（嵌入 + BM25） | 5.7% | — |
| + 上下文嵌入 | 3.7% | −35% |
| + 上下文嵌入 + 上下文 BM25 | 2.9% | −49% |
| + 再加重排序 | 1.9% | −67% |

### 实施要点

1. **块边界**：块大小、边界与重叠的选择都会影响检索性能；
2. **嵌入模型**：上下文检索对所有受测嵌入模型都有提升，Gemini 与 Voyage 的嵌入表现尤佳；
3. **自定义上下文提示词**：针对你的领域定制（例如附上仅在其他文档中定义的术语表）可能效果更好；
4. **块的数量**：送入上下文窗口的块越多，包含相关信息的机会越大，但也更"分心"。试过 5、10、20 个块，20 个表现最好，但值得在你的场景实测。

**务必跑评估（Evals）**：把上下文化的块传给生成模型时，区分"哪些是上下文、哪些是块本体"，可能进一步改善生成。

### 叠加重排序（Reranking）

传统 RAG 初检常返回成百上千个相关性参差的块。重排序是常用的过滤手段：只把最相关的块传给模型，既改善回答，又省钱省延迟。步骤：

1. 初检拿 top-N 潜在相关块（Anthropic 用 150）；
2. 把 top-N 块连同查询送入重排模型；
3. 按相关性打分后取 top-K（用 20）；
4. 把 top-K 块作为上下文传给模型生成最终结果。

重排模型市场上有多种选择，Anthropic 测试用的是 Cohere Rerank（Voyage 亦提供重排器，但未及测试）。注意：重排在运行时多了一步，即使并行打分也会增加少量延迟；"重排更多块换更好效果"与"重排更少块换低延迟低成本"之间存在天然权衡，建议按用例实测。

### 结论

Anthropic 的大量对比实验总结如下：

1. 嵌入 + BM25 优于纯嵌入；
2. 受测模型中 Voyage 与 Gemini 的嵌入最好；
3. 传 top-20 块优于 top-10 或 top-5；
4. 给块加上下文能大幅提升检索准确率；
5. 重排序优于不重排；
6. **这些收益可以叠加**：上下文嵌入 + 上下文 BM25 + 重排 + top-20 块，组合出最大性能提升。
