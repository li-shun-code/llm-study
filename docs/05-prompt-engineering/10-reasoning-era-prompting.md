从"提示词工程"这门手艺诞生起，就有一个反问一直没停过：模型都会自己推理了，还需要我教它怎么想吗？在 2026 年这一代模型上，答案比"需要/不需要"更具体——**你不再负责教它思考，你负责定义问题、口径和交回来的形状**。这篇把这些原则摊开，并给出可跑的代价测量。

## 发生了什么变化：CoT 从提示技巧变成模型能力

思维链最初是一项**提示技术**：Wei et al. (2022) 在 PaLM 540B 上，把 GSM8K 从标准提示的 17.9% 拉到 CoT 的 56.9%；Kojima et al. (2022) 更省，一句 "Let's think step by step" 就能触发。这一切的前提是：**模型默认不会自己展开中间步骤**，所以要靠提示词把它拽出来。

推理模型把这个前提拆掉了。它们在后训练阶段（可验证奖励的强化学习一类方法）学会了内生地产生思考 token，再给出答案。用本站模型口径表的说法：`reasoning_effort`、`thinking`、extended thinking 这类参数把"推理时计算量"变成了可调旋钮，而不是提示词里的一句话。

于是提示词的分工变了：

| 提示词该做的 | 提示词不该再做的 |
|---|---|
| 定义目标与成功判据 | 规定"先想 A 再想 B"的思考顺序 |
| 给出领域口径、判定规则 | 补一句 "think step by step" 来"激活"推理 |
| 约束输出的形状与长度 | 手写 CoT 演示来"教会"模型推理 |
| 划定工具与权限边界 | 用"给小费/威胁"之类话术激励模型 |

## 五条原则

**1. 写少，但要写得准。** 官方指南的推荐路线与 Anthropic 在上下文工程里说的是同一件事：**先用能拿到的最强模型测一条最小提示**，看它在你任务上怎么失败，再针对失败模式补指令。"最小"不等于"短"——它指**不写任何模型已经会做的事**。

**2. 推理量用参数控制，不用文字控制。** `reasoning_effort` 档位（minimal/low/medium/high）决定模型想多久、愿不愿意多调工具；`verbosity` 决定最终答案写多长，**与思考长度是两回事**。指南原话是：默认 `medium`，任务复杂就上调，"很多工作流在 medium 甚至 low 上就能稳定产出结果"。反过来说：在提示词里写"请详细分析、逐一比较三种方案"是在改**输出长度**，不是在买**思考深度**——花的是同一份 token 预算，却换不到更好的判断。

**3. 别手写 CoT 咒语。** 对推理模型，"Step 1 复述问题、Step 2 列五个概念、Step 3 画决策树"这类模板不会提升推理质量，只会把输出绑架成模板形状，并显著推高 token 账单（下一节有实测）。Kojima 那句咒语现在只对**非推理档**（各家 mini/nano/flash）还有意义，那里它仍然是便宜的第一招。

**4. 矛盾指令的代价被放大了。** 这一代模型被训练得**字面**遵循指令。官方对 GPT-5 的描述很直白：它"像外科手术一样精确地遵循提示指令"，因此**含混或互相矛盾的提示比对旧模型更有害**——它会消耗推理 token 去试图把两条冲突的规则同时满足，而不是随便挑一条。Cursor 团队在调自己的提示库时发现：删掉重复与矛盾条目，性能明显变好。这正是《提示词的迭代与评估方法》那篇里"软约束分叉"的机理版解释。

**5. 规划、持久性与收尾，仍然要写。** 模型会自己推理，但不会自己决定"什么时候停"。指南建议的两类提醒至今有效：**上下文收集口径**（"先广撒获取上下文，命中收敛就停止搜索并动手"，用来压住过度探索）与**持久性**（"在彻底解决用户问题之前不要交还控制权"，用来防止过早收尾）。这两条一个管**别做太多**，一个管**别做太少**，是提示词在 Agent 时代最稳定的价值。

## 可运行示例：咒语买到了什么

比较同一道题的两种写法，记录时间与 token。运行前置 `pip install openai python-dotenv`，密钥读自 `.env`：

```python
"""手写 CoT 步骤模板 vs 短提示：同一道题，量一下代价。"""
import os
import time

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI()
MODEL = os.getenv("OPENAI_MODEL", "gpt-5.4-mini")

QUESTION = "我们的支付回调接口偶发重复通知，重试会造成重复扣款。该从哪里入手？"

# 上一代习惯：把"怎么想"逐步写死
SPELL = f"""请按以下步骤逐步回答，每一步单独成段：
Step 1: 复述我的问题
Step 2: 列出 5 个相关概念并逐个解释，每个不少于三句
Step 3: 画出决策树（用文字表示）
Step 4: 逐一比较三种方案的优劣
Step 5: 以"综上"开头给出总结
问题：{QUESTION}"""

# 这一代写法：只给目标、口径、输出约束
TERSE = f"你是资深后端工程师。针对下面的问题给出可落地的处理顺序，不超过 200 字，先给结论再给理由。\n问题：{QUESTION}"


def run(label: str, prompt: str, budget: int) -> None:
    t = time.time()
    resp = client.responses.create(model=MODEL, input=prompt, max_output_tokens=budget)
    u = resp.usage
    text = resp.output_text.strip()
    print(
        f"{label}: {time.time() - t:.1f}s  输入 {u.input_tokens or u.prompt_tokens}  "
        f"输出 {u.output_tokens or u.completion_tokens}  正文 {len(text)} 字"
    )
    print("   ", (text[:120] or "（无正文：思考 token 用尽了预算）").replace("\n", " | "), "\n")


if __name__ == "__main__":
    run("短提示（推荐）", TERSE, 2000)
    run("咒语版·预算 2000", SPELL, 2000)
    run("咒语版·预算 4000", SPELL, 4000)
```

本机实测（同一模型、同一台机器，脚本原样跑一遍）：

```
短提示（推荐）: 6.4s  输入 96  输出 711  正文 250 字
    **结论**：优先从幂等性设计入手，其次优化响应逻辑，再结合数据库约束和监控兜底。**理由**：
    1. **幂等性设计**：通过记录已处理订单状态（如唯一索引、Redis 标记），确保重复通知只执行一次…

咒语版·预算 2000: 16.4s  输入 145  输出 1222  正文 1686 字
    Step 1: 复述我的问题 | 您的问题是支付回调接口存在偶发重复通知现象……
    Step 2: 列出 5 个相关概念并逐个解释 **幂等性设计**：幂等性指同一操作……

咒语版·预算 4000: 23.8s  输入 145  输出 2105  正文 3855 字
    # 支付回调重复通知问题分析与解决方案 ## Step 1: 复述问题 …… ## Step 2: 列出5个相关概念……
```

对比很清楚：**输出 token 1.7~3 倍、正文长度 6.7~15 倍、延迟 2.5~3.7 倍，换来的不是更好的判断，而是模板填空**——第一行结论在短提示版里 6.4 秒就给了，咒语版要到 Step 5 才肯收尾。

再补一条同一段代码在其他轮次里出现过的失败模式：把 `max_output_tokens` 压到 2000 时，咒语版有一次花了 31.4 秒、烧掉 1998 个输出 token，**正文一个字没吐**（推理模型的思考 token 也算在这个额度里，见《提示词的基本要素与格式》"常见坑"）。同一份提示换一次运行就正常了——这种**预算边界的抖动**本身就是"手写步骤模板"的典型代价：它把输出长度推高，于是把失败概率也一起推高。

## 哪些情况下仍然要把步骤写出来

"别写 CoT 咒语"不等于"永远别写过程"。四类场景例外：

1. **非推理档模型**。各家 mini/nano/flash 这一档不会内生展开推理，Kojima 那句 "step by step" 与少样本 CoT 演示仍然是最划算的增益（本文实测用的就是这一档，所以对照里的差异主要落在成本上，而不是正确率上）。
2. **步骤本身就是业务要求**。审批报告必须含"风险点/依据/结论"三段、代码评审必须先列变更面再给建议——这是**输出契约**，不是推理教学。写法上把顺序放进输出格式小节，并给一个具体样例。
3. **需要人类可审计的中间产物**。让模型把检索到的证据、判定理由打印出来，是为了让你（和评测器）能定位错误来源，而不是为了帮它想清楚——这两者的措辞重点不同：前者约束"必须打印什么"，后者约束"必须怎么想"。
4. **多 Agent 或链式环节之间的交接**。每一环的输出格式必须写死，这属于《提示链与任务分解（Prompt Chaining）》的范围。

判断口径很简单：**这句"步骤"是在约束接口，还是在教模型思考？** 前者保留，后者删掉并用 `reasoning_effort` 或换档来解决。

## 常见坑

- **把 `verbosity` 当成 `reasoning_effort` 用**。"请简短回答"压的是答案长度，思考照样花钱；想省推理成本要降 effort 档或换非推理档。
- **在提示词里写"请先思考再回答"却把 `max_output_tokens` 卡死**。轻则超时贵，重则空回复。
- **把旧提示原样搬过来不做减法**。上一代留下的"你必须逐步分析""给出详细解释""分五步"这类句子，在新模型上多半只留下成本；官方口径是**先删重复与矛盾，再谈加指令**。
- **用同一套提示覆盖所有难度**。工程上更划算的做法是分层：简单意图走 minimal/low 档或直接用非推理模型，复杂多步才升到 high——这正是模型路由与成本控制的主线（见《成本与 Token 优化：Prompt Caching 与 Batch API》）。
- **以为"少写"就是"随便写"**。目标、口径、边界、输出契约这四件事一个字都不能少，能删的只有"教它怎么想"那部分。

## 小结

- 推理模型把 CoT 从提示技巧变成内建能力：提示词的重心从"过程"移到**问题定义 + 口径 + 输出契约**；
- 思考长度用参数（`reasoning_effort` / `thinking` / extended thinking）控制，答案长度用 `verbosity` 或明确的字数约束控制，两者不要混；
- 手写步骤咒语在推理模型上基本只剩副作用：输出被模板绑架、token 上涨、预算不足时正文为空；
- 值得写的三类内容：上下文收集口径、持久性提醒、可判定的输出格式。
