上下文是 AI Agent 的一种关键却**有限**的资源。在这篇文章里，我们探讨如何有效地策划与管理驱动 Agent 的上下文。

在应用 AI 领域被"提示工程"占据焦点数年之后，一个新术语开始崭露头角：**上下文工程**（context engineering）。用语言模型构建应用，正变得越来越不是"为提示词找到合适的字句"，而是回答一个更宏观的问题：**"什么样的上下文配置最有可能让模型产生我们期望的行为？"**

**上下文**指的是从大语言模型（LLM）采样时纳入的那组 token。而这里的**工程**问题，就是在 LLM 的固有限制下优化这些 token 的效用，以持续达成期望的结果。有效地驾驭 LLM 往往需要"在上下文中思考"（thinking in context）——也就是随时审视 LLM 当下可用的整体状态，以及这一状态可能引发哪些行为。

本文将探索上下文工程这门新兴技艺，并为构建可引导、高效的 Agent 提供一个更精炼的心智模型。

## 上下文工程 vs 提示工程

在 Anthropic 看来，上下文工程是提示工程的自然演进。提示工程指的是为获得最佳效果而编写与组织 LLM 指令的方法（概述与实用的提示工程策略见[我们的文档](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)）。**上下文工程**则指在 LLM 推理过程中策划并维护最优 token（信息）集合的一整套策略——包括提示词之外、可能落入上下文的其他所有信息。

在 LLM 工程的早期，提示编写是 AI 工程工作的最大组成部分，因为日常聊天交互之外的大多数用例，都需要为一次性分类或文本生成任务优化提示。顾名思义，提示工程的核心关注点是**如何写好提示**，尤其是系统提示词。但随着我们转向工程化更强的 Agent——它们在多轮推理、更长的时间跨度上运行——我们就需要管理**整个上下文状态**的策略（系统指令、工具、[模型上下文协议](https://modelcontextprotocol.io/docs/getting-started/intro)（MCP）、外部数据、消息历史等）。

一个在循环中运行的 Agent 会不断产生"可能与下一轮推理相关"的数据，这些信息必须被循环地精炼。上下文工程，就是从这片持续演化的可能信息宇宙中，挑选出什么将进入有限上下文窗口的[艺术与科学](https://x.com/karpathy/status/1937902205765607626?lang=en)。

![提示工程 vs 上下文工程](https://www-cdn.anthropic.com/images/4zrzovbb/website/faa261102e46c7f090a2402a49000ffae18c5dd6-2292x1290.png)

*与"写一条提示"这种离散任务不同，上下文工程是迭代的——每当我们决定向模型传入什么时，都会经历一轮策划。*

## 为什么构建强大的 Agent 离不开上下文工程

尽管 LLM 速度快、能处理越来越大的数据量，我们观察到：和人类一样，LLM 到了某个程度也会失焦或混乱。"大海捞针"（needle-in-a-haystack）类基准的研究揭示了一个概念——[上下文腐烂](https://research.trychroma.com/context-rot)（context rot）：随着上下文窗口中 token 数量的增加，模型从该上下文中准确召回信息的能力会下降。

虽然某些模型的退化比其他模型更平缓，但这一特征在**所有**模型上都会出现。因此，上下文必须被当作一种**边际收益递减的有限资源**。就像人类[工作记忆容量有限](https://journals.sagepub.com/doi/abs/10.1177/0963721409359277)一样，LLM 在解析大量上下文时也依赖一个"注意力预算"（attention budget）。每引入一个新 token 都会消耗这个预算，这使得精心策划 LLM 可用的 token 变得更加必要。

这种注意力稀缺源于 LLM 的架构约束。LLM 基于 [transformer 架构](https://arxiv.org/abs/1706.03762)，其中每个 token 都能[关注](https://huggingface.co/blog/Esmail-AGumaan/attention-is-all-you-need)（attend to）整个上下文中的所有其他 token——对 n 个 token 会产生 n² 个两两关系。

随着上下文长度增加，模型捕捉这些两两关系的能力被摊薄，上下文规模与注意力聚焦之间形成天然张力。此外，模型的注意力模式是从训练数据分布中学来的，而训练数据里短序列通常远多于长序列。这意味着模型对跨全上下文的依赖关系经验更少、专用参数也更少。

像[位置编码插值](https://arxiv.org/pdf/2306.15595)（position encoding interpolation）这类技术让模型能通过适配原本训练时较小的上下文来处理更长序列，但对 token 位置的理解会有所退化。这些因素共同造就的是一条**性能梯度**而非断崖：模型在长上下文下依然很强，但在信息召回与长程推理上的精度可能低于短上下文表现。

这些现实意味着：要构建强大的 Agent，深思熟虑的上下文工程不可或缺。

## 有效上下文的解剖

既然 LLM 受限于有限的注意力预算，*好的*上下文工程就意味着：找到**尽可能小的**高信号 token 集合，使期望结果出现的概率最大化。实践远比说来难，下面我们把这个指导原则落到上下文的各个组成部分上。

**系统提示词**应当极其清晰，用简单、直接的语言，在**合适的高度**（right altitude）上向 Agent 呈现思想。所谓合适的高度，是两种常见失败模式之间的"刚刚好"区间。一个极端是：工程师在提示词里硬编码复杂、脆弱的逻辑，以诱发精确的 Agent 行为——这会制造脆弱性，并随时间推高维护复杂度。另一个极端是：工程师给出含糊的高层指导，既没有给 LLM 提供期望输出的具体信号，又错误地假设了共享上下文。最优高度介于两者之间：**足够具体以有效引导行为，又足够灵活以给模型留下强启发式规则的空间**。

![在上下文工程中校准系统提示词](https://www-cdn.anthropic.com/images/4zrzovbb/website/0442fe138158e84ffce92bed1624dd09f37ac46f-2292x1288.png)

*光谱的一端是脆弱的 if-else 式硬编码提示；另一端是过度笼统、错误假设共享上下文的提示。*

我们建议把提示词组织成不同的小节（如 `<background_information>`、`<instructions>`、`## Tool guidance`、`## Output description` 等），并使用 XML 标签或 Markdown 标题来划分——尽管随着模型能力增强，提示词的具体格式正变得不那么重要。

无论你如何组织系统提示词，都应追求**能完整刻画期望行为的最小信息集合**。（注意"最小"不等于"短"；你仍需要在开始就给 Agent 足够的信息，确保它遵循期望的行为。）最佳实践是：先用能拿到的最强模型测试一个最小提示，看它在你的任务上表现如何，然后依据初始测试中发现的失败模式，增补清晰的指令与示例来改进。

**工具**让 Agent 能操作环境、并在工作时拉取新的附加上下文。工具定义了 Agent 与其信息/动作空间之间的契约，因此工具必须促进效率——既返回 token 高效的信息，也鼓励高效的 Agent 行为。

在《[为 AI Agent 编写工具——用 AI Agent 来写](https://www.anthropic.com/engineering/writing-tools-for-agents)》一文中，我们讨论过如何构建 LLM 易于理解、功能重叠最少的工具。与设计良好的代码库中的函数一样，工具应当自包含、对错误健壮、对其预期用途极其清晰。输入参数同样应当描述性强、无歧义，并顺应模型的固有优势。

我们最常见的失败模式之一是**臃肿的工具集**：覆盖过多功能，或在"该用哪个工具"上制造模糊的决策点。如果人类工程师都无法明确说出给定情境该用哪个工具，就不能指望 AI Agent 做得更好。后文还会讲到：为 Agent 策划一个"最小可行"工具集，也有助于在长交互中更可靠地维护与修剪上下文。

提供示例——即少样本提示（few-shot prompting）——是人尽皆知的最佳实践，我们仍然强烈建议使用。但团队常会把一长串边缘情况塞进提示词，试图穷尽 LLM 在某任务上应遵循的每一条规则。我们**不**建议这样做。更好的做法是：精心策划一组**多样、典范**的示例，有效呈现 Agent 的期望行为。对 LLM 来说，示例是胜过千言的"图画"。

我们对上下文各组成部分（系统提示词、工具、示例、消息历史等）的总体建议是：深思熟虑，让上下文**信息丰富而紧凑**。接下来让我们深入运行时的动态上下文检索。

## 上下文检索与 Agent 式搜索

在《[构建有效的 AI Agent](https://www.anthropic.com/research/building-effective-agents)》中，我们辨析了基于 LLM 的工作流与 Agent 的差异。自那篇文章之后，我们逐渐倾向一个[简单定义](https://simonwillison.net/2025/Sep/18/agents/)：**Agent 就是 LLM 在循环中自主使用工具**。

在与客户的合作中，我们看到整个领域正收敛到这个简单范式。随着底层模型能力增强，Agent 的自主性可以随之扩展：更聪明的模型让 Agent 能独立穿行于微妙的问题空间、并从错误中恢复。

工程师为 Agent 设计上下文的方式正在发生转变。今天，许多 AI 原生应用采用某种形式的**基于嵌入的推理前检索**（embedding-based pre-inference retrieval）来浮出供模型推理的重要上下文。随着领域转向更 Agent 化的方式，我们越来越多地看到团队在这些检索系统之上叠加"**即时**"（just in time）上下文策略。

采用"即时"方式的 Agent 不再预先处理所有相关数据，而是维护轻量的**标识符**（文件路径、存储的查询、网页链接等），并在运行时借助工具以这些引用为线索把数据动态加载进上下文。Anthropic 的 agentic 编码方案 [Claude Code](https://www.anthropic.com/claude-code) 就用这种方式对大型数据库执行复杂的数据分析：模型可以编写有针对性的查询、保存结果，并利用 `head`、`tail` 等 Bash 命令分析海量数据，而无须把完整数据对象载入上下文。这种做法映射了人类认知：我们通常不会背诵整个信息库，而是建立文件系统、收件箱、书签这类外部组织与索引系统，按需检索相关信息。

除了存储效率，这些引用的**元数据**还提供了一种高效精化行为的机制——无论是显式提供的还是直观可感的。对一个在文件系统中工作的 Agent 来说，`tests` 目录里出现一个名为 `test_utils.py` 的文件，与 `src/core_logic/` 下同名文件，暗示的用途截然不同。目录层级、命名规范、时间戳都在提供重要信号，帮助人类与 Agent 理解如何以及何时使用某条信息。

让 Agent 自主导航与检索数据还带来**渐进披露**（progressive disclosure）：Agent 可以通过探索增量地发现相关上下文。每次交互都产出指导下一步决策的上下文——文件大小暗示复杂度，命名规范暗示用途，时间戳可以是相关性的代理指标。Agent 逐层组装理解，只在工作记忆中保留必要之物，并借助笔记策略做额外持久化。这种自我管理的上下文窗口让 Agent 聚焦于相关子集，而不是淹没在穷尽却可能无关的信息里。

当然这里有权衡：运行时探索比取回预计算数据更慢。不仅如此，还需要有态度、有思考的工程，确保 LLM 拥有恰当的工具与启发式来有效导航它的信息版图——缺乏引导的 Agent 会滥用工具、钻牛角尖、或识别不出关键信息，从而浪费上下文。

在某些场景下，最有效的 Agent 会采用**混合策略**：预先检索一部分数据求快，再按需自主探索。自主程度的"正确"边界取决于任务。Claude Code 就是一个采用混合模型的 Agent：[CLAUDE.md](http://claude.md) 文件被直接预先放入上下文，而 glob、grep 等原语让它能导航环境、按需检索文件， effectively 绕开了索引过期与复杂语法树的问题。

混合策略或许更适合内容动态性较低的领域，如法律或金融工作。随着模型能力提升，Agent 设计将趋向"让聪明的模型自己聪明地行动"，人的策划成分逐步减少。鉴于这个领域的演进速度，"用能用的最简单方案"（do the simplest thing that works）很可能仍是我们给 Agent 构建者的最佳建议。

### 长时程任务的上下文工程

长时程任务要求 Agent 在动作序列中保持连贯性、上下文与目标导向的行为，而其 token 数量超出了 LLM 的上下文窗口。对于持续几十分钟到数小时的任务——大型代码库迁移、综合性研究项目——Agent 需要专门的技术来绕开上下文窗口大小的限制。

"等更大的上下文窗口"看似一条明显的策略。但很可能在可预见的未来，**所有**尺寸的上下文窗口都会受困于上下文污染与信息相关性问题——至少在你追求最强 Agent 表现的场景如此。为了让 Agent 在延长的时间跨度上高效工作，我们发展了几种直接应对上下文污染约束的技术：**压缩**（compaction）、**结构化笔记**（structured note-taking）与**多 Agent 架构**（sub-agent architectures）。

**压缩（Compaction）**

压缩是指：当对话接近上下文窗口上限时，把其内容摘要，再用该摘要重新启动一个新的上下文窗口。压缩通常是上下文工程中驱动更好长期连贯性的第一根杠杆。其核心是以高保真的方式蒸馏上下文窗口的内容，让 Agent 以最小的性能损失继续工作。

以 Claude Code 为例，我们的实现是把消息历史交给模型去总结并压缩最关键的细节：模型保留架构决策、未解决的 bug 与实现细节，丢弃冗余的工具输出或消息。之后 Agent 带着这份压缩上下文加上最近访问的五个文件继续工作。用户获得了连续性，而不必担心上下文窗口限制。

压缩的艺术在于**取舍**——过度激进的压缩会丢失那些微妙却关键的上下文，其重要性往往要到很久之后才显现。对实现压缩系统的工程师，我们建议在复杂的 Agent 轨迹上仔细调优你的压缩提示：先把召回（recall）最大化，确保压缩提示从轨迹中捕捉到每一条相关信息，再通过剔除多余内容迭代提升精确率（precision）。

一个"低垂的多余内容"是**清除工具调用与结果**——一个工具早已在消息历史深处被调用过，Agent 为什么还需要再看一遍原始结果？最安全、最轻量的压缩形式之一就是工具结果清除（tool result clearing），最近已作为[一项功能在 Claude 开发者平台上线](https://www.anthropic.com/news/context-management)。

**结构化笔记（Structured note-taking）**

结构化笔记，或称 **Agent 记忆**（agentic memory），是一种让 Agent 定期把笔记持久化到上下文窗口之外的记忆中、并在稍后把它们拉回上下文窗口的技术。

这一策略以极小的开销提供了持久记忆。像 Claude Code 创建待办清单，或你的自定义 Agent 维护一个 NOTES.md 文件，这个简单的模式让 Agent 能跨复杂任务追踪进度，保住那些否则会在几十次工具调用之间丢失的关键上下文与依赖关系。

[Claude 玩宝可梦](https://www.twitch.tv/claudeplayspokemon)展示了记忆如何在非编码领域改造 Agent 能力。该 Agent 在数千个游戏步骤间维护精确的计数——追踪诸如"过去 1234 步我都在 1 号道路训练我的宝可梦，皮卡丘已朝着 10 级的目标升了 8 级"这样的目标。没有任何关于记忆结构的提示，它自己发展出已探索区域的地图、记住自己解锁了哪些关键成就、并维护战斗策略的战略笔记，帮助它学会对不同的对手哪些招式最有效。

在上下文重置之后，Agent 读取自己的笔记，继续多小时的训练序列或地牢探索。这种跨摘要步骤的连贯性，使长时程策略成为可能——只靠 LLM 上下文窗口本身是做不到的。

作为 [Sonnet 4.5 发布](https://www.anthropic.com/effective-context-engineering-for-ai-agents)的一部分，我们在 Claude 开发者平台公开测试版中发布了[记忆工具](http://anthropic.com/news/context-management)，通过基于文件的系统更轻松地在上下文窗口之外存储与查阅信息。这让 Agent 能随时间积累知识库、跨会话维护项目状态、并引用此前的工作——而不必把一切都塞进上下文。

**子 Agent 架构（Sub-agent architectures）**

子 Agent 架构提供了绕开上下文限制的另一条路。与其让一个 Agent 试图在整个项目上维护状态，不如让专精的子 Agent 各自带着干净的上下文窗口处理聚焦的任务。主 Agent 以高层计划进行协调，子 Agent 执行深入的技术工作或使用工具寻找相关信息。每个子 Agent 可能大量探索、消耗数万甚至更多 token，但只返回一份浓缩的、蒸馏过的工作摘要（通常 1000–2000 token）。

这种方式实现了清晰的关注点分离——详细的搜索上下文被隔离在子 Agent 内部，主 Agent 专注于综合与分析结果。这一模式在《[我们如何构建多 Agent 研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)》中有过讨论，在复杂研究任务上相比单 Agent 系统有显著提升。

在上述方法之间如何选择，取决于任务特征。例如：

- **压缩**适合需要大量来回交互的任务，维持对话流；
- **笔记**适合有清晰里程碑的迭代式开发；
- **多 Agent 架构**适合并行探索能带来收益的复杂研究与分析。

即使模型持续进步，在延长交互中保持连贯性的挑战，仍将位居构建更有效 Agent 的核心。

## 结论

上下文工程代表了我们用 LLM 构建应用方式的一次根本转变。随着模型能力增强，挑战不再只是写出完美提示词，而是**深思熟虑地策划**在每一步进入模型有限注意力预算的信息。无论你是在为长时程任务实现压缩、设计 token 高效的工具，还是让 Agent 即时探索环境，指导原则始终如一：**找到那组最小的、高信号的 token，让期望结果出现的概率最大化。**

文中概述的技术会随模型进步继续演化。我们已经看到：更聪明的模型需要更少的规定性工程，Agent 得以更自主地运行。但即使能力不断扩展，把上下文当作珍贵而有限的资源来对待，仍将始终是构建可靠、有效 Agent 的核心。

欢迎今天就在 Claude 开发者平台开始实践上下文工程，并通过我们的[记忆与上下文管理](https://platform.claude.com/cookbook/tool-use-memory-cookbook) cookbook 获取实用技巧与最佳实践。
