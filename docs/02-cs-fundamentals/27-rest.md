REST 是 **RE**presentational **S**tate **T**ransfer（表述性状态转移）的缩写，是一种面向**分布式超媒体系统**的架构风格。Roy Fielding 于 2000 年在其著名的博士论文中首次提出。从那时起，它已成为构建 Web API（应用编程接口）最广泛使用的方式之一。

REST 不是协议也不是标准，而是**架构风格**。在开发阶段，API 开发者可以用多种方式实现 REST。

与其他架构风格一样，REST 也有其指导原则与约束。一个服务接口要被称为 **RESTful**，就必须满足这些原则。

> 符合 REST 架构风格的 Web API（或 Web 服务）称为 **REST API**（或 RESTful API）。

## 1. REST 的六条指导原则

REST 建立在一组促进**简单性、可扩展性与无状态性**的约束与原则之上。RESTful 架构的六条指导原则（约束）如下：

### 1.1 统一接口（Uniform Interface）

把**通用性原则**应用到组件接口上，可以简化整体系统架构、提升交互的可见性。多条架构约束共同促成统一接口、引导组件行为。以下四条约束能实现统一的 REST 接口：

- **资源的标识**（Identification of resources）——接口必须唯一标识客户端与服务器交互中涉及的每个资源。
- **通过表述操作资源**（Manipulation of resources through representations）——资源在服务器响应中应有统一的表述（representation）；API 消费者应使用这些表述来修改服务器上资源的状态。
- **自描述的消息**（Self-descriptive messages）——每个资源表述应携带足够的信息，说明如何处理该消息；还应提供客户端可对该资源执行的附加操作的信息。
- **超媒体作为应用状态的引擎**（HATEOAS，Hypermedia as the engine of application state）——客户端只需持有应用的初始 URI；客户端应用应借助超链接动态驱动其余的资源与交互。

简单地说，REST 为客户端与服务器的交互定义了一致而统一的接口。例如，基于 HTTP 的 REST API 使用标准 HTTP 方法（GET、POST、PUT、DELETE 等）与 URI（统一资源标识符）来标识资源。

### 1.2 客户端-服务器（Client-Server）

客户端-服务器设计模式强制**关注点分离**，让客户端与服务器组件独立演化。

把用户界面 concerns（客户端）与数据存储 concerns（服务器）分开，可以提升用户界面在多个平台上的可移植性，并通过简化服务器组件提升可扩展性。

客户端与服务器各自演化的同时，必须确保两者之间的**接口/契约**不被破坏。

### 1.3 无状态（Stateless）

无状态性要求：客户端发给服务器的**每个请求**，都必须包含理解并完成该请求所需的**全部**信息。

服务器不得利用任何先前存储在服务器上的上下文信息。

因此，客户端应用必须完整地保存会话状态。

### 1.4 可缓存（Cacheable）

可缓存约束要求：响应应隐式或显式地把自身标记为可缓存或不可缓存。

若响应可缓存，客户端应用就获得了在指定时段内、把该响应数据复用于等价请求的权利。

### 1.5 分层系统（Layered System）

分层系统风格通过约束组件行为，让架构由层级构成。在分层系统中，每个组件**看不到**它与之交互的直接层之外的任何东西。

分层系统的一个通俗例子是 **MVC 模式**——清晰的关注点分离让应用更易开发、维护与扩展。

### 1.6 按需代码（Code on Demand，可选）

REST 还允许通过下载并执行小程序（applet）或脚本的形式扩展客户端功能。

下载的代码简化了客户端——减少了必须预先实现的功能数量。服务器可以把交付给客户端的部分功能以代码形式提供，客户端只需执行代码。

## 2. 什么是资源？

REST 中关键的**信息抽象**是**资源**（resource）。任何可以命名的东西都可以是资源。例如，REST 资源可以是一份文档或图片、一个临时服务、一组其他资源的集合，或一个非虚拟对象（如一个人）。

资源在任一特定时刻的状态称为**资源表述**（resource representation）。资源表述由三部分组成：

- **数据**（data）
- 描述数据的**元数据**（metadata）
- 帮助客户端过渡到下一目标状态的**超媒体链接**（hypermedia links）

> REST API 由相互链接的资源组装而成。这组资源称为 REST API 的**资源模型**（resource model）。

### 2.1 资源标识符

REST 使用资源标识符标识客户端与服务器组件交互中涉及的每个资源。

### 2.2 超媒体

表述的数据格式称为**媒体类型**（media type）。媒体类型标识了一份规范，定义表述应如何被处理。

**RESTful API 看起来像超文本（hypertext）。**每个可寻址的信息单元都携带地址——或显式（如 link 与 id 属性），或隐式（如从媒体类型定义与表述结构推导）。

> **超文本**（或超媒体）意味着**信息与控制的同时呈现**，使信息成为一种 affordance——用户（或自动机）借以获得选项、选择行动的东西。
>
> 记住：超文本不必是浏览器上的 HTML（或 XML、JSON）。当机器理解数据格式与关系类型时，它们也能跟随链接。
>
> —— Roy Fielding

### 2.3 自描述

此外，**资源表述应是自描述的**：客户端不需要知道一个资源是员工还是设备；它应根据与资源关联的媒体类型行事。

实践中我们会创建大量**自定义媒体类型**——通常一种媒体类型对应一类资源。

每种媒体类型定义一个默认的处理模型。例如，HTML 定义了超文本的渲染过程与每个元素对应的浏览器行为。

> 媒体类型与资源方法 GET/PUT/POST/DELETE……没有关系——除了某些媒体类型元素会定义这样的处理模型："带 `href` 属性的锚元素创建一条超文本链接，被选中时对 `href` 属性（CDATA 编码）对应的 URI 发起检索请求（GET）。"

## 3. 资源方法

与 REST 相关的另一件要事是**资源方法**（resource methods）：用于在资源的两个状态之间执行期望的转移。

大量人错误地把资源方法等同于 HTTP 方法（GET/PUT/POST/DELETE）。Roy Fielding 从未提过"什么条件下该用哪个方法"的建议；他强调的只是：它应当是一个**统一接口**。

例如，如果我们决定应用的 API 用 HTTP POST 更新资源——而不是更常见的 HTTP PUT——完全没问题；应用接口依然可以是 RESTful 的。

理想情况下，转移资源状态所需的一切都应是资源表述的一部分——包括所有被支持的方法、以及它们会以何种形式离开该表述。

> 我们进入一个 REST API 时，除了初始 URI（一个书签）与一组适合目标受众的标准化媒体类型（即任何可能使用该 API 的客户端都被期望能理解的媒体类型），不应携带任何先验知识。
>
> 从那一刻起，所有应用状态转移都必须由客户端对"接收到的表述中服务器提供的选择"的挑选来驱动，或由用户操作这些表述所隐含的方式驱动。
>
> 转移可以由客户端对媒体类型与资源通信机制的知识决定（或受限）——这两者都可以即时改进（如按需代码）。[此处失败即意味着：是带外信息而非超文本在驱动交互。]

## 4. REST 与 HTTP 不是一回事

许多人喜欢把 HTTP 与 REST 相提并论。**REST 与 HTTP 不是一回事。**

> **REST != HTTP**

虽然 REST 也意在让 Web（互联网）更精简、更标准，Roy Fielding 主张更严格地遵循 REST 原则——人们正是从这里开始把 REST 与 Web 放在一起比较的。

Fielding 在其论文中没有给出任何实现上的指引——包括任何协议偏好，甚至没提 HTTP。只要我们尊重 REST 的六条指导原则，就可以把自己的接口称为 RESTful。

## 5. 小结

简单地说，在 REST 架构风格中：数据与功能被视为**资源**，通过**统一资源标识符**（URI）访问。

资源通过一组简单、定义良好的操作来施加行为。资源必须与其**表述**解耦，使客户端能以多种格式访问内容——HTML、XML、纯文本、PDF、JPEG、JSON 等。

客户端与服务器使用标准化接口与协议交换资源的**表述**。通常 HTTP 是最常用的协议，但 REST 并不强制它。

资源的元数据可用并用于控制缓存、检测传输错误、协商合适的表述格式、执行认证或访问控制。

最重要的是：与服务器的**每次交互都必须无状态**。

所有这些原则帮助 RESTful 应用做到简单、轻量、快速。
