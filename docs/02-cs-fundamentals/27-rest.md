本章介绍并详细阐述面向**分布式超媒体系统**（distributed hypermedia systems）的**表述性状态转移**（Representational State Transfer，REST）架构风格：描述指导 REST 的软件工程原则，以及为保留这些原则而选择的交互约束，并将它们与其他架构风格的约束相对比。REST 是一种**混合风格**（hybrid style），由若干基于网络的架构风格推导而来，再加上定义**统一连接器接口**（uniform connector interface）的额外约束组合而成。

> 译注：REST 这个词正是 Roy Fielding 在 2000 年的这篇博士论文第 5 章中定义的。今天我们说"RESTful API"，其全部评判标准都源自本章。本篇为该章的中文翻译，是 REST 名正言顺的一手来源。

## 5.1 REST 的推导

Web 架构背后的设计原理，可以用一种架构风格来描述——它由施加在架构内各元素上的一组**约束**（constraints）构成。通过考察每条约束在风格逐步演化过程中被加入时产生的影响，我们就能识别出 Web 的这些约束所诱发的性质。随后还可以施加额外的约束，形成一种更好地体现现代 Web 架构期望性质的新架构风格。本节通过完整走一遍"把 REST 作为架构风格推导出来"的过程，给出 REST 的总体概览；后续小节再更详细地描述构成 REST 风格的具体约束。

### 5.1.1 从"空风格"出发

关于架构设计的过程——无论是建筑设计还是软件设计——常见两种视角。第一种认为：设计者从一无所有出发（一块白板、一块画图板），用熟悉的组件搭建起架构，直到它满足目标系统的需要。第二种认为：设计者从系统整体的需要出发、起初不加任何约束，然后逐步识别约束并施加到系统元素上，以此划分设计空间，让影响系统行为的各种力量自然流动、与系统和谐共处。第一种强调创造力与无边的愿景，第二种强调克制与对系统语境的理解。REST 的提出采用的是后一种过程。

**空风格**（null style）就是一组空约束。从架构视角看，它描述的是一个组件之间没有任何显著边界的系统。它是我们描述 REST 的起点。

### 5.1.2 客户端-服务器

往混合风格里加入的第一条约束，来自客户端-服务器（client-server）架构风格。**关注点分离**（separation of concerns）是这条约束背后的原则：把用户界面方面的关注点与数据存储方面的关注点分开，我们就能提升用户界面跨多种平台的**可移植性**，并通过简化服务器组件来提升**可扩展性**。而对 Web 来说最重要的或许是：这种分离让各组件得以**独立演化**（evolve independently），从而支持"跨越多个组织边界"这一互联网规模的要求。

### 5.1.3 无状态

接下来我们给客户端-服务器交互再加一条约束：通信必须在本质上**无状态**（stateless），即客户端-无状态-服务器（client-stateless-server，CSS）风格。这样，客户端发给服务器的每个请求，都必须包含理解该请求所需的**全部**信息，不能利用服务器上存储的任何上下文。会话状态（session state）因此完全保存在客户端。

这条约束带来**可见性**（visibility）、**可靠性**（reliability）与**可扩展性**（scalability）三方面的性质。可见性得到提升，是因为监控系统只需查看单个请求的数据，就能完整判断这个请求的性质。可靠性得到提升，是因为它让从局部故障中恢复变得更容易。可扩展性得到提升，是因为服务器不必在请求之间保存状态，可以快速释放资源；同时服务器也无需跨请求管理资源的使用，实现因此更简单。

和大多数架构选择一样，无状态约束反映的是一种设计上的取舍。缺点是：一系列请求中重复发送的数据（每次交互的固定开销）可能变多——因为这些数据无法以共享上下文的形式留在服务器上——从而可能降低网络性能。此外，把应用状态放在客户端一侧，会削弱服务器对"应用行为一致性"的控制力，因为应用从此依赖于多个客户端版本各自对语义的正确实现。

### 5.1.4 缓存

为了提升网络效率，我们再加入**缓存**（cache）约束，构成客户端-缓存-无状态-服务器（client-cache-stateless-server）风格。缓存约束要求：响应中的数据必须被隐式或显式地标记为**可缓存**（cacheable）或**不可缓存**（non-cacheable）。若响应被标记为可缓存，客户端缓存就获得了把该响应数据复用于"此后等价请求"的权利。

加入缓存约束的好处是：它有可能部分或完全消除某些交互，通过降低一串交互的平均延迟，改善效率、可扩展性与用户感知性能。其代价则是：如果缓存中的过期数据与"请求直接发给服务器本可获得的数据"差异显著，缓存会降低可靠性。

早期 Web 架构就是由客户端-缓存-无状态服务器这组约束定义的。也就是说，1994 年之前 Web 架构的设计原理，聚焦在"通过无状态的客户端-服务器交互，在互联网上交换静态文档"。当时的交互协议对非共享缓存只有初步支持，并未把接口约束为"对所有资源一致的一组语义"；相反，早期 Web 依赖一个公共的客户端-服务器实现库（CERN libwww）来维持各 Web 应用之间的一致性。

Web 实现的开发者们早已超越了早期设计：除了静态文档，请求还能指向动态生成响应的服务，例如图像映射（image-map，Kevin Hughes 的工作）与服务器端脚本（Rob McCool 的工作）。中介组件的工作也已起步——以代理（proxy）与共享缓存的形式——但要让它们可靠地通信，还需要对协议进行扩展。下面几节描述的，正是为引导这些扩展、最终形成现代 Web 架构而加入 Web 架构风格的那些约束。

### 5.1.5 统一接口

把 REST 架构风格与其他基于网络的风格区分开来的核心特征，是它对组件之间**统一接口**（uniform interface）的强调。通过把软件工程的**通用性原则**（principle of generality）应用到组件接口上，整体系统架构得以简化，交互的可见性得到提升。实现与它们提供的服务解耦，这鼓励了独立的可演化性。其代价则是：统一接口会降低效率，因为信息以标准化的形式传输，而不是针对特定应用需求优化的形式。REST 接口的设计目标是让"大粒度超媒体数据传输"高效——为 Web 的常见情形做优化——但由此得到的接口对其他形式的架构交互并非最优。

要获得统一接口，需要多条架构约束共同引导组件的行为。REST 由四条接口约束定义：**资源的标识**（identification of resources）；**通过表述操作资源**（manipulation of resources through representations）；**自描述的消息**（self-descriptive messages）；以及**超媒体作为应用状态的引擎**（hypermedia as the engine of application state）。这些约束将在 5.2 节中详细讨论。

### 5.1.6 分层系统

为了进一步满足互联网规模的要求，我们再加入**分层系统**（layered system）约束。分层系统风格通过约束组件行为，让架构得以由层级构成：每个组件都"看不到"与之交互的直接层之外的任何东西。把对系统的了解限制在单一层内，我们为整体系统复杂度设定了边界，并促进了对底层基础设施的独立性。分层可以用来封装遗留服务、保护新服务不受遗留客户端的侵扰，并把不常用的功能移到共享的中介组件上，从而简化各组件。中介还可以实现跨多个网络与处理器的服务负载均衡，提升系统可扩展性。

分层系统的主要缺点是：它给数据处理增加了开销与延迟，降低用户感知性能。对于支持缓存约束的基于网络的系统，这一缺点可以被"在中介处共享缓存"的好处抵消。把共享缓存部署在组织域的边界上，可以带来显著的性能收益；这类层次还可以对跨越组织边界的数据强制执行安全策略——防火墙正是这么做的。

分层系统与统一接口两条约束的组合，会诱发与统一"管道-过滤器"风格类似的架构性质。REST 交互虽然是双向的，但超媒体交互的大粒度数据流可以各自像数据流网络那样被处理：过滤组件有选择地施加在数据流上，在数据经过时对其进行变换。在 REST 中，中介组件可以主动变换消息的内容——因为消息是自描述的，其语义对中介是可见的。

### 5.1.7 按需代码

REST 约束集合的最后一条补充来自**按需代码**（code-on-demand）风格：REST 允许通过下载并执行小程序（applet）或脚本的形式来扩展客户端功能。这简化了客户端——减少了必须预先实现的功能数量；允许功能在部署之后再下载，也改善了系统的**可扩展性**（extensibility）。但代价是它降低了可见性，因此在 REST 中它只是一条**可选**约束。

"可选约束"这个说法听起来自相矛盾，但它在跨越多个组织边界的系统架构设计中确实有用：只有当可选项已知在系统某个范围内生效时，架构才获得（或承受）这条约束带来的好处与坏处。例如，若已知某组织内部的所有客户端软件都支持 Java 小程序，那么该组织内部的服务就可以借"下载 Java 类获得增强功能"的方式构建；但与此同时，该组织的防火墙可能阻止来自外部的 Java 小程序传输，于是在 Web 的其余部分看来，这些客户端就像不支持按需代码一样。可选约束让我们可以设计"在一般情形下支持期望行为"的架构，同时明白它在某些语境下可能被关闭。

### 5.1.8 风格推导小结

REST 由一组架构约束构成，选择它们的原因是它们能给候选架构带来理想的性质。虽然每条约束都可以孤立地看待，但把它们描述为"从常见架构风格逐步推导而来"，更容易理解其选择背后的原理。

## 5.2 REST 的架构元素

表述性状态转移风格是对分布式超媒体系统中架构元素的一种抽象。REST 忽略组件实现与协议语法的细节，聚焦于：组件扮演的角色、组件之间交互所受的约束、以及对关键数据元素的解读。它包含了对组件（components）、连接器（connectors）与数据（data）的基本约束——正是它们定义了 Web 架构的基础，也定义了 Web 作为一种基于网络的应用的本质行为。

### 5.2.1 数据元素

与分布式对象风格不同（后者把所有数据封装并隐藏在处理组件之内），架构的数据元素的性质与状态是 REST 的关键面向。这一设计原理可以从分布式超媒体的本质中看出：当一个链接被选中时，信息需要从"存储它的位置"移动到"使用它的位置"——大多数情况下，使用者是一个人类读者。这与许多其他分布式处理范式不同：在那些范式里，把"处理代理"（如移动代码、存储过程、检索表达式等）移动到数据所在处，往往比把数据搬到处理器那里更可行、也更高效。

分布式超媒体架构师只有三种根本选项：1）在数据所在地完成渲染，把固定格式的图像发给接收方；2）把数据与渲染引擎封装在一起，二者一起发给接收方；3）把原始数据连同描述其数据类型的元数据一起发给接收方，由接收方自选渲染引擎。

三种选项各有优劣。选项 1（传统客户端-服务器风格）允许关于数据真实形态的全部信息都留在发送方内部，避免对数据结构做任何假设，客户端实现也更容易；但它严重限制了接收方的功能，并把大部分处理负载压在发送方身上，带来可扩展性问题。选项 2（移动对象风格）在提供信息隐藏的同时，借由数据专属的渲染引擎实现对数据的专门处理，但把接收方的功能限制在该引擎预先设想的范围内，还可能大幅增加传输的数据量。选项 3 让发送方保持简单、可扩展，并使传输字节数最小化，但失去了信息隐藏的优势，并要求收发双方理解相同的数据类型。

REST 提供了三种选项的混合：聚焦于"以元数据对数据类型建立共享理解"，但把所揭示的范围限定在一个标准化接口之内。REST 组件通过"转移资源的一个表述（representation）"来通信，表述的格式取自一个不断演化的标准数据类型集合，并依据接收方的能力或意愿以及资源本身的性质动态选择。表述是与原始来源同格式、还是从来源派生而来，这一细节同样被隐藏在接口之后。移动对象风格的好处被近似地保留下来——通过发送"由标准数据格式的指令构成、内嵌渲染引擎"的表述（如 Java）实现。REST 由此获得了客户端-服务器风格的关注点分离、又没有服务器的可扩展性问题；经由通用接口实现信息隐藏，使服务得以封装与演化；并通过可下载的"功能引擎"提供了多样的功能。

#### 5.2.1.1 资源与资源标识符

REST 中关键的信息抽象是**资源**（resource）。任何可以被命名的东西都可以是资源：一份文档或图像、一个临时服务（例如"洛杉矶今天的天气"）、其他资源的集合、一个非虚拟的对象（例如一个人），等等。换句话说，任何可能成为作者超文本引用目标的概念，都必须能装进资源的定义里。**资源是对一组实体的概念映射（conceptual mapping），而不是某一时刻与该映射对应的那个实体本身。**

更精确地说，一个资源 R 是一个随时间变化的成员函数 M_R(t)，对时间 t 给出一组等价的实体或值的集合。集合中的值可以是**资源表述**和/或**资源标识符**。资源可以映射到空集——这使得"某概念尚无任何实现时就能引用它"成为可能；在 Web 之前，这一观念对大多数超文本系统而言是陌生的。有些资源是静态的：在创建之后的任何时刻考察，它总是对应同一组值。另一些资源的值随时间变化剧烈。对资源而言，唯一必须保持静态的是**映射的语义**——正是语义把一个资源与另一个资源区分开来。

例如，一篇学术论文的"作者首选版本"是一个值随时间变化的映射；而"发表在会议 X 论文集中的那篇论文"是静态的映射。这是两个不同的资源，即便它们在某些时刻映射到同一个值。这个区分是必要的：如此二者才能被独立地标识与引用。软件工程中也有类似例子：受版本控制的源码文件，"最新修订版"、"1.2.7 号修订版"与"随 Orange 版本发布的那一修订版"是三个被分开标识的引用。

资源的这种抽象定义让 Web 架构的几个关键特性成为可能。第一，它提供了**通用性**：把众多信息来源纳入其中，而无须按类型或实现人为区分它们。第二，它允许**引用与表述之间的晚绑定**（late binding），使内容协商可以依据请求的特征进行。第三，它允许作者引用**概念本身**而不是概念的某个单一表述——于是当表述发生变化时，无须改动所有既有链接（前提是作者用对了标识符）。

REST 用**资源标识符**（resource identifier）来标识组件交互中涉及的特定资源。REST 连接器为"访问与操作资源的值集合"提供通用接口，无论成员函数如何定义、也无论处理请求的是哪类软件。指派资源标识符、从而使资源可被引用的**命名权威**（naming authority），负责长期维护该映射语义的有效性（即确保成员函数不变）。

传统超文本系统通常运行在封闭或本地环境中，使用"信息一变就跟着变"的唯一节点或文档标识符，依靠链接服务器把引用与内容分开维护。集中式链接服务器与 Web 的巨大规模、多组织域的要求水火不容，因此 REST 改为依赖**作者选择最契合被标识概念本质的资源标识符**。当然，标识符的质量通常与"为维持其有效性所花的钱"成正比——于是随着朝生暮死（或缺乏维护）的信息迁移或消失，链接就断了。

#### 5.2.1.2 表述

REST 组件对资源执行动作的方式是：用一个**表述**（representation）捕获资源的当前或期望状态，并在组件之间转移该表述。表述是一个字节序列，加上描述这些字节的**表述元数据**。表述的其他常见但欠精确的名字包括：文档（document）、文件（file）、HTTP 消息实体（message entity）、实例（instance）、变体（variant）。

一个表述由**数据**、描述数据的**元数据**、以及偶尔存在的"描述元数据的元数据"（通常用于验证消息完整性）构成。元数据以"名字-值"对的形式出现，名字对应着一个定义了该值结构与语义的标准。响应消息可以同时包含表述元数据与资源元数据：后者是关于资源本身（而非本次所给表述）的信息。

**控制数据**（control data）定义消息在组件之间的目的，例如请求的动作是什么、或响应的含义是什么。它也用于参数化请求、覆盖某些连接元素的默认行为。例如，缓存行为可以被请求或响应消息中携带的控制数据修改。

依据消息控制数据的不同，同一个表述可以表示：被请求资源的**当前状态**、被请求资源的**期望状态**、或某个其他资源的值——例如客户端查询表单中的输入数据的表述、或响应中某种错误状态的表述。例如，对资源进行远程创作（remote authoring）时，作者要把一个表述发给服务器，从而为该资源建立一个可被后续请求检索的值。如果资源在给定时刻的值集合包含多个表述，可以用**内容协商**（content negotiation）为某条消息挑选最合适的表述。

表述的数据格式称为**媒体类型**（media type）。一个表述可以包含在消息中，由接收方依据消息的控制数据与媒体类型的性质进行处理。有些媒体类型面向自动化处理，有些面向渲染给用户观看，少数两者兼顾。**复合媒体类型**（composite media types）可以把多个表述封装进单条消息。

媒体类型的设计会直接影响分布式超媒体系统的用户感知性能。接收方在开始渲染之前必须先收到的任何数据，都会增加交互的延迟。一种数据格式若把最重要的渲染信息放在前面，使初始信息可以增量渲染、其余信息边接收边继续，其用户感知性能就远好于"必须全部收完才能开始渲染"的格式。例如，一个能在接收过程中增量渲染大型 HTML 文档的浏览器，其用户感知性能就显著好于"等整个文档完全收完再渲染"的浏览器——即便网络性能完全相同。值得注意的是，表述的渲染能力还受内容选择的影响：如果动态尺寸的表格与内嵌对象必须先确定尺寸才能渲染，它们出现在页面可视区域内就会增加延迟。

### 5.2.2 连接器

REST 使用多种**连接器**（connector）类型来封装"访问资源"与"转移资源表述"的活动。连接器为组件通信提供抽象接口：以干净的关注点分离提升简单性，并隐藏资源与通信机制的底层实现。接口的通用性还带来了**可替换性**（substitutability）：只要用户对系统的唯一访问途径是抽象接口，实现就可以被替换而不影响用户。由于连接器为组件管理网络通信，信息可以在多次交互之间共享，以改善效率与响应性。

**表 5-2：REST 连接器**

| 连接器 | 现代 Web 示例 |
|---|---|
| 客户端（client） | libwww、libwww-perl |
| 服务器（server） | libwww、Apache API、NSAPI |
| 缓存（cache） | 浏览器缓存、Akamai 缓存网络 |
| 解析器（resolver） | bind（DNS 查询库） |
| 隧道（tunnel） | SOCKS、HTTP CONNECT 之后的 SSL |

所有 REST 交互都是**无状态**的。也就是说，每个请求都包含连接器理解该请求所需的全部信息，独立于之前可能发生过的任何请求。这一限制达成四项功能：1）连接器无须在请求之间保留应用状态，减少了物理资源的消耗并改善可扩展性；2）交互可以被并行处理，而处理机制无须理解交互语义；3）中介可以孤立地查看并理解一个请求——当服务被动态重排时这可能很必要；4）所有可能影响"缓存响应可复用性"的信息都被迫出现在每个请求里。

连接器接口类似于过程调用（procedural invocation），但参数与结果的传递方式有重要差别：入参由请求控制数据、一个指明请求目标的资源标识符、以及一个可选表述组成；出参由响应控制数据、可选的资源元数据、以及一个可选表述组成。从抽象视角看，调用是同步的，但入参与出参都可以作为数据流传递。换言之，处理可以在参数值尚未完全已知时就被启动，从而避免"批处理大数据传输"的延迟。

主要连接器类型是**客户端**与**服务器**。二者的本质差别在于：客户端通过发起请求来启动通信，而服务器监听连接、响应请求，以便提供对其服务的访问。一个组件可以同时包含客户端与服务器两种连接器。

第三种连接器类型是**缓存**（cache），可以位于客户端或服务器连接器的接口上，把当前交互中可缓存的响应保存下来，供之后被请求的交互复用。客户端可用缓存来避免重复的网络通信；服务器可用缓存来避免重复生成响应的过程——两种情形都降低交互延迟。缓存通常实现在使用它的连接器的地址空间之内。

有些缓存连接器是**共享的**（shared）：其缓存的响应可以被用来回答"并非最初获取该响应的那个客户端"的请求。共享缓存能有效降低"突发人群"（flash crowds）对热门服务器负载的冲击，尤其是把缓存按层级组织、覆盖大群用户时——例如公司内网内的用户、某 ISP 的客户、或共享全国骨干网的大学。不过，如果缓存的响应与"发起新请求本可获得的响应"不符，共享缓存也会导致错误。REST 试图在"缓存行为的透明性"与"对网络的高效利用"之间求得平衡，而不是假定任何情况下都必须绝对透明。

缓存之所以能判定一个响应的可缓存性，是因为接口是通用的、并非对每种资源各有一套。默认情况下，检索（retrieval）请求的响应是可缓存的，其他请求的响应不可缓存。若请求中带有某种用户认证，或响应声明自己不应被共享，则该响应只可被非共享缓存保存。组件可以通过携带控制数据来覆盖这些默认值：把交互标记为可缓存、不可缓存、或仅在有限时间内可缓存。

**解析器**（resolver）把部分或完整的资源标识符翻译成"建立组件间连接所需的网络地址信息"。例如，大多数 URI 都包含一个 DNS 主机名，作为标识资源命名权威的机制。要发起请求，Web 浏览器会从 URI 中取出主机名，用 DNS 解析器获得该权威的 IP 地址。另一个例子是某些标识方案（如 URN）需要中介把永久标识符翻译成较易变化的地址才能访问被标识的资源。使用一层或多层中间解析器可以借由间接改善资源引用的寿命，但也会增加请求延迟。

最后一种连接器类型是**隧道**（tunnel）：它只是在连接边界（如防火墙或更低层的网络网关）两侧中继通信。之所以把它建模为 REST 的一部分、而不是抽象掉归入网络基础设施，是因为有些 REST 组件可能动态地从"主动组件行为"切换为"隧道行为"。最主要的例子是 HTTP 代理：收到 CONNECT 方法请求时切换为隧道，让它的客户端可以用另一种不允许代理的协议（如 TLS）与远程服务器直接通信。当两端都终止通信时，隧道随之消失。

### 5.2.3 组件

REST **组件**（component）按其在整体应用动作中扮演的角色分类。

**表 5-3：REST 组件**

| 组件 | 现代 Web 示例 |
|---|---|
| 源服务器（origin server） | Apache httpd、Microsoft IIS |
| 网关（gateway） | Squid、CGI、反向代理 |
| 代理（proxy） | CERN Proxy、Netscape Proxy、Gauntlet |
| 用户代理（user agent） | Netscape Navigator、Lynx、MOMspider |

**用户代理**使用客户端连接器发起请求，并成为响应的最终接收者。最常见的例子是 Web 浏览器：它访问信息服务，并按应用需要渲染服务的响应。

**源服务器**使用服务器连接器治理被请求资源的命名空间。它是其资源表述的权威来源，并且必须是任何"试图修改其资源值的请求"的最终接收者。每个源服务器以资源层级（resource hierarchy）的形式提供其服务的通用接口；资源实现的细节隐藏在接口之后。

**中介组件**同时扮演客户端与服务器，以便（可能带翻译地）转发请求与响应。**代理**（proxy）是由客户端选定的中介，用于对其他服务做接口封装、数据翻译、性能增强或安全防护。**网关**（gateway，又称反向代理）是由网络或源服务器施加的中介，同样用于接口封装、数据翻译、性能增强或安全强制执行。注意代理与网关的差别：**由客户端决定何时使用代理**。

## 5.3 REST 架构视图

理解了 REST 架构元素各自的含义之后，我们可以用架构视图来描述这些元素如何协作构成架构。三类视图——过程视图、连接器视图与数据视图——对阐明 REST 的设计原则特别有用。

### 5.3.1 过程视图

架构的过程视图主要通过揭示数据的流动路径，来呈现组件之间的交互关系。真实系统的交互通常涉及大量组件，总体视图往往被细节淹没。从基于 REST 的架构的过程视图可以看到：REST 的客户端-服务器关注点分离简化了组件实现、降低了连接器语义的复杂度、改善了性能调优的效果、并提升了纯服务器组件的可扩展性。分层系统约束允许中介——代理、网关与防火墙——在通信路径的各处引入，而不改变组件之间的接口，从而让它们协助完成通信翻译，或经由大规模共享缓存改善性能。REST 通过"把消息约束为自描述的"来支持中间处理：请求之间交互无状态、用标准方法与媒体类型指示语义并交换信息、响应显式标明可缓存性。

由于组件是动态连接的，它们在特定应用动作中的排布与功能带有"管道-过滤器"风格的相似特征。REST 组件虽经由双向流通信，但每个方向的处理相互独立，因此可以被流变换器（过滤器）加工；通用连接器接口允许组件依据每个请求或响应的性质被安插到流上。

服务可以由复杂的中介层级与多个分布式源服务器共同实现。REST 的无状态本质让每个交互都独立于其他交互：组件无须感知整体组件拓扑——对互联网规模的架构而言那是无法完成的任务——并允许组件依据每个请求的目标动态充当目的地或中介。连接器只需在通信范围之内知晓彼此的存在；出于性能考虑，它们也可以缓存其他组件的存在与能力。

### 5.3.2 连接器视图

架构的连接器视图聚焦于组件间通信的机制。对基于 REST 的架构，我们尤其关心定义"通用资源接口"的那些约束。

客户端连接器检查资源标识符，为每个请求选择合适的通信机制。例如，当标识符表明这是本地资源时，客户端可以被配置为连接某个特定的代理组件（比如充当批注过滤器的一个代理）；客户端同样可以被配置为拒绝某些标识符子集的请求。

REST 不把通信限定在某个特定协议上，但它确实约束了组件之间的接口——从而约束了交互的范围以及组件之间可能预设的实现假定。例如，Web 的主要传输协议是 HTTP，但该架构也包括对源自既有网络服务器的资源的无缝访问，如 FTP、Gopher 与 WAIS。与这些服务的交互被限定在 REST 连接器的语义之内。这一约束牺牲了其他架构的部分优势（例如 WAIS 那类带状态的相关性反馈交互），以换取"连接器语义的单一通用接口"的好处。作为回报，通用接口使"经由单个代理访问众多服务"成为可能。如果应用需要另一种架构的额外能力，它可以把这些能力实现为一个并行运行的独立系统并加以调用——就像 Web 架构与 "telnet"、"mailto" 资源的对接方式一样。

### 5.3.3 数据视图

架构的数据视图揭示应用状态如何随信息流经组件而变化。REST 明确面向分布式信息系统，它把一个应用看作信息与控制选项的内聚结构，用户借其完成期望的任务。例如，在在线词典里查一个词是一个应用，逛虚拟博物馆是，复习一组课堂笔记备考也是。每个应用都为底层系统定义了目标，系统的性能可以对照这些目标来度量。

组件交互以动态大小的消息的形式发生。小粒度与中粒度消息用于控制语义，而应用工作的主体经由包含完整资源表述的大粒度消息完成。最常见的请求语义是"检索资源的一个表述"（例如 HTTP 中的 GET 方法），这类请求通常可以被缓存复用。

REST 把全部控制状态都集中在"交互响应中收到的表述"里。其目标是消除服务器在当前请求之外感知客户端状态的必要，从而改善服务器的可扩展性。因此，应用的状态由以下内容定义：待处理的请求、已连接组件的拓扑（其中一些可能在过滤被缓冲的数据）、这些连接器上的活动请求、响应这些请求的表述数据流、以及用户代理收到这些表述后对它们的处理。

当一个应用没有未决的请求时，它就达到了一个**稳态**（steady-state）：即没有待处理的请求，且对当前这组请求的所有响应都已被完整接收、或已接收至可作为表述数据流处理的地步。对浏览器应用而言，这个状态对应一个"网页"——包括主表述与辅助表述（内联图片、内嵌小程序、样式表等）。应用稳态的意义体现在它对用户感知性能与网络请求流量突发性的双重影响上。

浏览器应用的用户感知性能由**稳态之间的延迟**决定：从一个网页上选中某个超媒体链接，到下一个网页可用信息被渲染出来的那段时间。浏览器性能的优化因此围绕降低这一通信延迟展开。由于基于 REST 的架构主要通过转移资源表述来通信，延迟同时受通信协议的设计与表述数据格式的设计影响。能否在接收响应数据的同时增量渲染，取决于媒体类型的设计以及每个表述中布局信息（内联对象的视觉尺寸）的可用性。

一个有趣的观察是：最高效的网络请求是压根不走网络的那一个。换言之，复用缓存响应的能力能带来应用性能的显著提升。虽然使用缓存给每个单独请求增加了查找开销，但只要较小比例的请求命中可用缓存，平均请求延迟就会大幅下降。

应用的下一个控制状态就在第一个被请求资源的表述里，因此获取第一个表述是头等大事。所以，"先响应、后思考"的协议能改善 REST 交互：一个协议若要求每个用户动作都先经历多轮交互（例如在发送内容响应之前协商功能能力），其感知速度就会慢于"先把最可能合适的东西发出去、再附一列备选项让客户端在第一响应不理想时取回"的协议。

应用状态由用户代理控制与保存，可以由来自多个服务器的表述组合而成。除了把服务器从"保存状态"的可扩展性难题中解放出来，这还让用户可以直接操纵状态（例如浏览器的历史记录）、预判状态的变化（例如链接地图与表述预取）、并在应用之间跳转（例如书签与 URI 输入框）。

因此，模型化的应用就是一台引擎：它检查当前一组表述中给出的备选状态转移、并从中选择，从而从一个状态移动到下一个状态。毫不意外，这恰好与超媒体浏览器的用户界面完全吻合。不过，这种风格并不假定所有应用都是浏览器。事实上，应用的细节被通用连接器接口对服务器隐藏了——用户代理同样可以是为索引服务执行信息检索的自动化机器人、寻找符合特定条件数据的个人代理、或是巡检失效链接与内容变更的维护蜘蛛。

## 5.4 相关工作

（本节为精简译出。）Bass 等人对 WWW 架构的描述只涵盖了 CERN/W3C 的 libwww（客户端与服务器库）及 Jigsaw 软件内部的实现架构；这些实现确实反映了 REST 的许多设计约束（毕竟其作者熟悉 Web 的架构设计原理），但真实的 WWW 架构独立于任何单一实现——现代 Web 由其标准接口与协议定义，而非某个软件中的实现方式。REST 的组件交互呈分层客户端-服务器结构，通用资源接口带来的额外约束创造了可替换性、以及中介检视交互的机会；请求与响应看似远程调用风格，但 REST 消息面向的是概念资源而非实现标识符。有人尝试把 Web 架构建模为分布式文件系统（如 WebNFS）或分布式对象系统，但它们把各种 Web 资源类型与实现策略当作"无趣的"排除在外，而这些恰恰推翻了此类模型的底层假定——REST 之所以运转良好，正因为它不把资源的实现限制在任何预定义模型上，允许每个应用选择最贴合自身需要的实现，并让实现可在不影响用户的前提下被替换。REST"向消费组件发送资源表述"的交互方式与基于事件的集成（EBI）风格有相似之处，关键差别在于 EBI 是推送式的——状态持有者在状态变化时发出事件，无论是否有组件感兴趣；而 REST 的消费组件通常拉取表述，单个客户端监控单个资源时效率略低，但 Web 的规模使不受管的推送模型不可行。REST 与 C2 架构风格也关系密切：C2 通过结构化地使用连接器支持分布式动态应用，依赖状态变化的异步通知；但 C2 缺少 REST 那些对中介友好的约束——通用资源接口、有保证的无状态交互、以及对缓存的内在支持。

## 5.5 小结

本章介绍了面向分布式超媒体系统的表述性状态转移（REST）架构风格。REST 提供了一组架构约束——当它们被作为整体应用时——强调：组件交互的可扩展性、接口的通用性、组件的独立部署，以及用中介组件来降低交互延迟、强制安全、封装遗留系统。本章描述了指导 REST 的软件工程原理、以及为保留这些原理而选择的交互约束，并将它们与其他架构风格的约束做了对比。

下一章将通过把 REST 应用于现代 Web 架构的设计、规范制定与部署所获得的经验与教训，对 REST 架构做出评价。这项工作包括撰写超文本传输协议（HTTP/1.1）与统一资源标识符（URI）的现行互联网标准族规范，并通过 libwww-perl 客户端协议库与 Apache HTTP 服务器实现该架构。

> 译注：读完本章再回看本模块，一条完整的线索就接上了——一次 REST API 调用，沿 DNS（解析器连接器把标识符翻译成地址）→ TCP（可靠传输）→ TLS（加密）→ HTTP（统一接口的具体协议化）层层落地；Fielding 的约束（无状态、缓存、统一接口、自描述消息）正是 HTTP 缓存头、状态码与媒体类型协商的设计源头。另外两条常被误解的点，本章原文说得很清楚：其一，REST 是架构风格而非协议，REST 与 HTTP 不是一回事，Fielding 从未规定"什么资源该用哪个 HTTP 方法"；其二，资源是"对一组实体的概念映射"而非实体本身——理解了这一点，"同一 URI 为何能随时间返回不同内容"与"内容协商为何可能"就都顺理成章。
