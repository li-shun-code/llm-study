本章讨论 OS 提供给用户的最基本抽象之一：**进程**（process）。进程的非正式定义非常简单：**运行中的程序**。程序本身是死物——它只是躺在磁盘上的一堆指令（也许还有些静态数据），等待登场。是操作系统把这些字节变成运行的东西，把程序转化为有用的东西。

人们常常想同时运行多个程序：浏览器、邮件、游戏、音乐播放器……一个典型系统表面上可能同时运行着几十甚至上百个进程。这让系统易于使用——你从不需要操心 CPU 是否空闲，只管运行程序。于是有了挑战：

> **问题的核心：如何提供"有许多 CPU"的幻觉？**
> 物理只有寥寥几个 CPU，OS 如何提供"几乎无限个 CPU"的幻觉？

OS 通过**虚拟化 CPU** 制造这个幻觉：运行一个进程、停下它、再运行另一个……如此往复，让"存在许多虚拟 CPU"的假象成立，而物理上只有一个（或几个）CPU。这一基本技术称为 CPU 的**时分共享**（time sharing），它允许用户想跑多少并发进程就跑多少；潜在代价是性能——CPU 被分享后，每个进程都跑得慢一些。

> **技巧：时分共享（与空分共享）**
> 时分共享是 OS 共享资源的基本技术：让资源先被一个实体用一小会儿，再给另一个用一小会儿……这样资源（如 CPU、网络链路）就能被许多实体共享。与之相对的是**空分共享**（space sharing）：把资源在空间上划分给使用者。比如磁盘空间天然是空分共享的——一个块分配给某文件后，在用户删除该文件前一般不会再分配给别人。

要实现（并且实现好）CPU 虚拟化，OS 既需要低层机械装置，也需要高层智慧。低层机械装置称为**机制**（mechanism）：实现所需功能点的低层方法或协议。例如**上下文切换**（context switch）——让 OS 有能力停止运行一个程序、在给定 CPU 上开始运行另一个程序；所有现代 OS 都采用这一时分共享机制。机制之上是 OS 的"智慧"，即**策略**（policy）：在 OS 内做某种决策的算法。比如 CPU 上有一堆候选程序，该运行哪个？**调度策略**（scheduling policy）会综合历史信息（哪个程序最近跑得多？）、工作负载知识（在跑什么类型的程序）与性能指标（优化交互性能还是吞吐量？）来做决策。

> **技巧：策略与机制分离**
> 许多操作系统的通用设计范式：把高层策略与低层机制分开。机制回答"**怎么做**"（how）——比如 OS 如何执行上下文切换；策略回答"**做哪个**"（which）——比如 OS 现在应该调度哪个进程。二者分离可以独立更换策略而不必重想机制，是模块化这一软件设计通用原则的体现。

## 进程抽象

OS 对"运行中程序"的抽象就叫进程。进程就是运行中的程序；任一时刻，我们都可以盘点"程序执行过程中访问或影响的系统各部分"来概括一个进程。

理解进程的构成，就是理解它的**机器状态**（machine state）：程序运行时能读或能更新什么。任一时刻，机器中哪些部分对这个程序的执行是重要的？

- **内存**：指令躺在内存里，程序读写的数据也在内存里。进程可寻址的内存（称为其**地址空间**，address space）是进程的一部分。
- **寄存器**：许多指令显式读写寄存器，显然对进程执行至关重要。其中有一些格外特殊的寄存器：**程序计数器**（PC，Program Counter，有时称指令指针 IP）告诉我们程序将执行哪条指令；**栈指针**（stack pointer）及关联的帧指针用于管理函数参数、局部变量与返回地址所用的栈。
- **I/O 信息**：程序还常访问持久存储设备，这类状态可能包括进程当前打开的文件列表。

## 进程 API

所有现代操作系统都以某种形式提供这些 API：

- **创建**（Create）：OS 必须有创建新进程的方法。你在 Shell 里敲命令、双击应用图标时，OS 就被调用来创建新进程运行你指定的程序。
- **销毁**（Destroy）：有创建就该有强拆。许多进程跑完自己退出；但它们不退出时，你可能想杀掉它——终止失控进程的接口相当有用。
- **等待**（Wait）：有时等一个进程停止运行很有用，因此常提供某种等待接口。
- **杂项控制**（Miscellaneous Control）：除了杀掉与等待，还有其他控制：比如多数 OS 提供暂停进程（停一会儿）再恢复（继续运行）的方法。
- **状态**（Status）：查询进程状态的接口，比如它跑了多久、处于什么状态。

## 进程创建的更多细节

程序如何变成进程？OS 如何把程序跑起来？

运行程序的第一步，是把它的代码和静态数据（如初始化过的变量）**加载**（load）进内存、装进进程的地址空间。程序最初以某种可执行格式躺在磁盘（或闪存 SSD）上，OS 要把这些字节从磁盘读出、放到内存某处。早期（或简单）的 OS 采用**急切加载**——运行前一次性全部装入；现代 OS 则是**懒惰加载**（lazily）——只在程序执行需要时才载入相应的代码或数据（要真正理解惰性加载，需要后面讲分页与交换的知识）。

代码与静态数据装入内存后，OS 还要：

1. 为程序的**运行时栈**（run-time stack）分配内存。C 程序用栈存放局部变量、函数参数与返回地址；OS 还会用参数初始化栈——填好 `main()` 的 `argc` 与 `argv`。
2. 为程序的**堆**（heap）分配内存。C 程序中堆用于显式请求的动态分配数据：`malloc()` 申请、`free()` 释放；链表、哈希表、树等数据结构都靠它。堆初始很小，随着程序运行通过 `malloc()` 请求更多内存，OS 会介入分配。
3. 其他初始化任务，尤其与输入/输出（I/O）相关的。比如 UNIX 系统中每个进程默认打开三个**文件描述符**（file descriptor）——标准输入、输出与错误，让程序能方便地从终端读输入、往屏幕打印输出。

万事俱备后是最后一项任务：从入口点 `main()` 开始运行程序。通过专门的机制跳到 `main()`，OS 把 CPU 控制权交给新创建的进程，程序开始执行。

## 进程状态

简化的视角下，进程在任一时刻可处于三种状态之一：

- **运行**（Running）：进程正在处理器上运行——正在执行指令。
- **就绪**（Ready）：进程万事俱备，但 OS 因某种原因选择此刻不运行它。
- **阻塞**（Blocked）：进程执行了某种操作，使其在其他事件发生前无法运行。典型例子：进程向磁盘发起 I/O 请求后进入阻塞，处理器可以让给其他进程。

```
          被调度              发起 I/O
  就绪 ─────────→ 运行 ─────────→ 阻塞
    ↑ ←─────────      ←─────────
    │    被去调度        I/O 完成
    └────────────────────────────┘
```

就绪 ↔ 运行之间的转换由 OS 决定：就绪→运行称为进程被**调度**（scheduled）；运行→就绪称为被**去调度**（descheduled）。进程一旦阻塞（如发起 I/O），OS 会让它保持阻塞直到事件发生（如 I/O 完成）；随后进程回到就绪态（若 OS 愿意，可能立即再次运行）。

两个进程的状态转换示例。第一个例子：两个进程只用 CPU、不做 I/O：

| 时刻 | 进程 0 | 进程 1 | 备注 |
|---|---|---|---|
| 1 | 运行 | 就绪 | |
| 2 | 运行 | 就绪 | |
| 3 | 运行 | 就绪 | |
| 4 | 运行 | 就绪 | 进程 0 结束 |
| 5 | – | 运行 | |
| 6 | – | 运行 | |
| 7 | – | 运行 | |
| 8 | – | 运行 | 进程 1 结束 |

第二个例子：进程 0 运行一段时间后发起 I/O。发起 I/O 后进程 0 阻塞，进程 1 得到运行机会；进程 1 运行期间 I/O 完成，进程 0 回到就绪；最后进程 1 结束，进程 0 运行至结束：

| 时刻 | 进程 0 | 进程 1 | 备注 |
|---|---|---|---|
| 1 | 运行 | 就绪 | |
| 2 | 运行 | 就绪 | |
| 3 | 运行 | 就绪 | 进程 0 发起 I/O |
| 4 | 阻塞 | 运行 | 进程 0 阻塞，进程 1 得以运行 |
| 5 | 阻塞 | 运行 | |
| 6 | 阻塞 | 运行 | |
| 7 | 就绪 | 运行 | I/O 完成 |
| 8 | 就绪 | 运行 | 进程 1 结束 |
| 9 | 运行 | – | |
| 10 | 运行 | – | 进程 0 结束 |

即便在这个简单例子里，OS 也要做不少决策：第一，进程 0 发起 I/O 时系统决定运行进程 1——保持 CPU 忙碌，提升资源利用率；第二，进程 0 的 I/O 完成时系统**没有**立刻切回进程 0——这是好是坏并不显然，你怎么看？这类决策由 **OS 调度器**（scheduler）做出（后续文章详谈）。

## 数据结构

OS 也是程序，同样有跟踪各类信息的关键数据结构。为跟踪每个进程的状态，OS 会为所有就绪进程维护某种**进程列表**（process list，也称任务列表 task list），并额外记录当前正在运行的进程；还要以某种方式跟踪阻塞进程——I/O 完成时，OS 得确保唤醒正确的进程并让它重新就绪。

存储单个进程信息的结构，常被称为**进程控制块**（PCB，Process Control Block，有时也叫进程描述符 process descriptor）——说白了就是一个包含进程信息的 C 结构体。下面是教学内核 xv6 的 `proc` 结构，Linux、macOS、Windows 中的对应结构要复杂得多：

```c
// xv6 为停止并随后重启进程而保存/恢复的寄存器
struct context {
    int eip;   // 指令指针
    int esp;   // 栈指针
    int ebx;
    int ecx;
    int edx;
    int esi;
    int edi;
    int ebp;
};

// 进程可能处于的状态
enum proc_state { UNUSED, EMBRYO, SLEEPING,
                  RUNNABLE, RUNNING, ZOMBIE };

// xv6 跟踪的每个进程的信息（含寄存器上下文与状态）
struct proc {
    char *mem;                // 进程内存起始地址
    uint sz;                  // 进程内存大小
    char *kstack;             // 该进程内核栈的栈底
    enum proc_state state;    // 进程状态
    int pid;                  // 进程 ID
    struct proc *parent;      // 父进程
    void *chan;               // 非 0 时表示在 chan 上睡眠
    int killed;               // 非 0 时表示已被杀死
    struct file *ofile[NOFILE]; // 打开的文件
    struct inode *cwd;        // 当前目录
    struct context context;   // 切换到该进程运行时要恢复的上下文
    struct trapframe *tf;     // 当前中断的陷阱帧
};
```

两点值得注意：

- **寄存器上下文**（register context）为被停止的进程保存寄存器内容。进程停止时寄存器值保存到这里；把这些值恢复到实际物理寄存器，OS 就能继续运行该进程——这项技术就是**上下文切换**。
- 除了运行/就绪/阻塞，还有别的状态：进程创建时的**初始态**（xv6 中是 EMBRYO），以及已退出但尚未清理的**最终态**——UNIX 系里叫 **zombie（僵尸）状态**。最终态很有用：它允许其他进程（通常是创建它的父进程）查看其返回码，判断它是否成功完成（UNIX 中成功通常返回 0，否则非 0）。父进程最后调用一次 `wait()` 等待子进程完成，同时告知 OS 可以清理与这个已消亡进程相关的数据结构。

> 译注： UNIX 里僵尸进程就是"已退出但父进程还没 wait() 收尸"的进程；相对好杀，只是通常不推荐用粗暴手段。至于真实系统里的状态机，比上面三态模型丰富得多（如 Linux 的 TASK_RUNNING/TASK_INTERRUPTIBLE/TASK_STOPPED 等）。

## 小结

- **进程**是 OS 对运行中程序的主要抽象。任一时刻，进程可由其**状态**描述：地址空间中内存的内容、CPU 寄存器的内容（含程序计数器与栈指针等），以及 I/O 信息（如打开的文件）。
- **进程 API** 包括创建、销毁、等待、杂项控制与状态查询等调用。
- 进程存在于多种**状态**之一：运行、就绪、阻塞等；调度、去调度、等待 I/O 完成等事件让进程在这些状态间转换。
- **进程列表**记录系统中所有进程；每个条目存放在**进程控制块**（PCB）中——就是一个包含特定进程信息的结构体。

有了进程这个概念视图，接下来是该抠细节了：实现进程所需的低层机制，以及智能调度进程所需的高层策略。把机制与策略结合起来，就能理解操作系统如何虚拟化 CPU——这正是后面"CPU 调度"一篇的主题。
