程序运行时到底发生了什么？

其实非常简单：运行中的程序就是在**执行指令**。处理器每秒取指令、解码（搞清楚这是条什么指令）、执行（做它该做的事，比如两数相加、访问内存、检查条件、跳转到函数……）数百万乃至数十亿次。一条指令做完，处理器接着处理下一条，如此往复，直到程序完成。这就是冯·诺依曼（Von Neumann）计算模型的基本图景。听起来简单，对吧？但就在程序运行的同时，还有大量"狂野"的事情在发生，它们的首要目标是**让系统易于使用**。

确实有这样一群软件，负责让运行程序变得容易（甚至看起来能同时运行很多程序）、让程序共享内存、让程序与设备交互等等。这群软件就叫**操作系统**（Operating System，OS），它负责确保系统以易用的方式正确、高效地运转。

> **问题的核心：如何虚拟化资源**
> 本书要回答的一个核心问题非常简单：操作系统是如何**虚拟化**（virtualize）资源的？为什么要这么做答案显而易见——让系统更好用；所以重点是"如何"：OS 实现了哪些机制（mechanism）与策略（policy）来达成虚拟化？如何高效地做到？需要什么硬件支持？

OS 实现这一切的基本手段是我们称为**虚拟化**（virtualization）的通用技术：OS 把物理资源（处理器、内存、磁盘）转换为更通用、更强大、更易用的虚拟形态。因此有时 OS 也被称为**虚拟机**（virtual machine）。

当然，为了让你能告诉 OS 做什么（运行程序、分配内存、访问文件），OS 还提供了一些可调用的接口（API）。一个典型的 OS 会向外导出几百个**系统调用**（system call）。因为 OS 提供这些调用来运行程序、访问内存与设备，我们有时也说 OS 为应用程序提供了**标准库**。

最后，虚拟化让多个程序共享 CPU、并发访问各自的指令与数据（共享内存）、访问设备（共享磁盘等），所以 OS 又被称为**资源管理器**（resource manager）。CPU、内存、磁盘都是系统资源；高效地、公平地（或按其他目标）管理它们正是 OS 的职责。

## 虚拟化 CPU

看第一个程序（`cpu.c`）：它调用 `Spin()`（反复检查时间、满一秒即返回），然后打印用户传入的字符串，无限循环。

```c
#include <stdio.h>
#include <stdlib.h>
#include <sys/time.h>
#include <assert.h>
#include "common.h"

int
main(int argc, char *argv[])
{
    if (argc != 2) {
        fprintf(stderr, "usage: cpu <string>\n");
        exit(1);
    }
    char *str = argv[1];
    while (1) {
        Spin(1);
        printf("%s\n", str);
    }
    return 0;
}
```

在只有一个处理器的机器上编译运行：

```
prompt> gcc -o cpu cpu.c -Wall
prompt> ./cpu "A"
A
A
A
（按 Control-c 终止）
```

平淡无奇。但如果我们同时运行这个程序的四个实例呢？

```
prompt> ./cpu A & ./cpu B & ./cpu C & ./cpu D &
[1] 7353
[2] 7354
[3] 7355
[4] 7356
A
B
D
C
A
B
D
C
...
```

有趣了：明明只有一个处理器，四个程序却好像**同时**在运行！这个魔法是操作系统（借助一点硬件帮助）制造的**幻觉**：把单个 CPU（或少量 CPU）变成看似无限多的虚拟 CPU，让许多程序看起来同时运行——这就是**虚拟化 CPU**。

当然，运行、停止程序、告诉 OS 该运行什么，需要一些接口（API），这是用户与 OS 交互的主要方式。你还会注意到"同时运行多个程序"带来一堆新问题：比如两个程序都想在某一时刻运行，该运行谁？这类问题由 OS 的**策略**（policy）回答。策略与机制配合，正是 OS 作为资源管理器的体现。

## 虚拟化内存

现代机器呈现的物理内存模型非常简单：内存就是**字节数组**。读内存要给地址，写内存还要给数据。程序运行时无时无刻不在访问内存：所有数据结构都在内存里；别忘了程序每条指令本身也在内存里，因此**取指令**也是内存访问。

看一个调用 `malloc()` 分配内存的程序（`mem.c`）：

```c
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>
#include "common.h"

int
main(int argc, char *argv[])
{
    int *p = malloc(sizeof(int)); // a1：分配内存
    assert(p != NULL);
    printf("(%d) address pointed to by p: %p\n",
           getpid(), p);          // a2：打印地址
    *p = 0;                       // a3：写入 0
    while (1) {
        Spin(1);
        *p = *p + 1;
        printf("(%d) p: %d\n", getpid(), *p); // a4：递增并打印
    }
    return 0;
}
```

程序每次打印还会输出**进程标识符**（PID），每个运行中的进程唯一。单个实例运行时，分配的内存位于地址 `0x200000`，程序慢慢递增并打印。

现在同时运行两个实例：

```
prompt> ./mem & ./mem &
[1] 24113
[2] 24114
(24113) address pointed to by p: 0x200000
(24114) address pointed to by p: 0x200000
(24113) p: 1
(24114) p: 1
(24114) p: 2
(24113) p: 2
...
```

每个程序分配到的内存都在 `0x200000`，却各自独立地更新这个地址上的值！仿佛每个程序拥有**私有内存**，而不是与其他程序共享同一物理内存。

事实正是如此——OS 在**虚拟化内存**。每个进程访问的是自己的私有**虚拟地址空间**（virtual address space，也称地址空间），由 OS 映射到机器的物理内存上。一个程序中的内存引用不会影响其他进程的地址空间（也不影响 OS 本身）；对运行中的程序来说，它独占全部物理内存。现实则是：物理内存是共享资源，由操作系统管理。

## 并发

本书（也是计算机系统）的另一大主题是**并发**（concurrency）——指同一程序中同时做多件事（并发地）时涌现、且必须解决的一整类问题。并发问题最早就出现在操作系统内部：上面的例子已经看到，OS 一直在"同时玩转"许多事，先运行一个进程再运行另一个。现代多线程程序同样会遇到这些问题。看一个多线程程序（`threads.c`）：

```c
#include <stdio.h>
#include <stdlib.h>
#include "common.h"
#include "common_threads.h"

volatile int counter = 0;
int loops;

void *worker(void *arg) {
    int i;
    for (i = 0; i < loops; i++) {
        counter++;
    }
    return NULL;
}

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "usage: threads <value>\n");
        exit(1);
    }
    loops = atoi(argv[1]);
    pthread_t p1, p2;
    printf("Initial value : %d\n", counter);

    Pthread_create(&p1, NULL, worker, NULL);
    Pthread_create(&p2, NULL, worker, NULL);
    Pthread_join(p1, NULL);
    Pthread_join(p2, NULL);
    printf("Final value : %d\n", counter);
    return 0;
}
```

基本思想：主程序用 `Pthread_create()` 创建两个线程。可以把线程理解为"在与其它函数相同的内存空间中运行的函数，且多个同时活跃"。每个线程都在 `worker()` 里把共享计数器递增 `loops` 次。`loops` 为 1000 时：

```
prompt> gcc -o threads threads.c -Wall -pthread
prompt> ./threads 1000
Initial value : 0
Final value : 2000
```

如你所料，两个线程各递增 1000 次，最终 2000。`loops` 为 N 时结果应为 2N。但生活没那么简单：

```
prompt> ./threads 100000
Initial value : 0
Final value : 143012   // 咦？？
prompt> ./threads 100000
Initial value : 0
Final value : 137298   // 什么鬼？？
```

输入 10 万，结果不是 20 万；再跑一次不但错还错得不一样；多跑几次你甚至可能碰对一次！原因在于指令是**一条一条**执行的：递增共享计数器这一关键操作其实是三条指令——从内存把计数器值加载（load）进寄存器、递增（increment）、存回（store）内存。这三条指令不是**原子**（atomic，一气呵成）执行的，怪事就可能发生。

> **问题的核心：如何构建正确的并发程序**
> 同一内存空间中有许多并发执行的线程时，如何构建正确工作的程序？需要 OS 提供什么原语？硬件应提供什么机制？如何用它们解决并发问题？

## 持久化

第三大主题是**持久化**（persistence）。系统内存（如 DRAM）以易失（volatile）方式存储数据——断电或系统崩溃，内存中的数据就没了。因此需要软硬件来持久地保存数据；用户非常在意自己的数据，这样的存储对任何系统都至关重要。

硬件形态是某种输入/输出（I/O）设备：现代系统中硬盘（HDD）是长期信息的常用仓库，固态硬盘（SSD）也在此领域攻城略地。OS 中管理磁盘的软件通常叫**文件系统**（file system），负责把用户创建的文件可靠、高效地存放在系统磁盘上。

与 CPU 和内存的抽象不同，OS **不会**为每个应用创建私有的虚拟磁盘——因为用户经常需要共享文件中的信息。写 C 程序的例子：先用编辑器创建/编辑源文件，再用编译器把源码变成可执行文件，最后运行它——同一个文件在不同进程之间流转。

看一段做 I/O 的代码（`io.c`）：创建包含 "hello world" 的文件 `/tmp/file`：

```c
#include <stdio.h>
#include <unistd.h>
#include <assert.h>
#include <fcntl.h>
#include <sys/types.h>

int main(int argc, char *argv[]) {
    int fd = open("/tmp/file",
                  O_WRONLY|O_CREAT|O_TRUNC,
                  S_IRWXU);
    assert(fd > -1);
    int rc = write(fd, "hello world\n", 12);
    assert(rc == 12);
    close(fd);
    return 0;
}
```

程序对 OS 做了三次调用：`open()` 打开并创建文件、`write()` 写数据、`close()` 关闭文件。这些系统调用被路由到 OS 中称为**文件系统**的部分，由它处理请求并返回错误码。

OS 实际怎么写到磁盘？文件系统要做不少事：先确定新数据放在磁盘哪个位置，再在它维护的各种结构中跟踪这些信息；这需要向底层存储设备发出 I/O 请求去读取或更新结构。写过设备驱动的人都知道，让设备替你办事是个精细活，需要深入理解低层设备接口及其确切语义。幸好 OS 通过系统调用提供了访问设备的标准而简单的方式。

出于性能考虑，多数文件系统会先延迟写入一段时间，攒成大批再写；为应对写入过程中崩溃的问题，多数文件系统引入了精巧的写协议（如日志 journaling 或写时复制 copy-on-write），小心安排写盘顺序，确保写序列中途失败后系统仍能恢复到合理状态。为了让常见操作高效，文件系统使用从简单链表到复杂 B 树等多种数据结构与访问方法。

> **问题的核心：如何持久地存储数据**
> 文件系统是 OS 中负责管理持久数据的部分。怎样做才算正确？需要什么机制与策略才能高性能？面对软硬件故障，如何保证可靠性？

## 设计目标

至此你知道了 OS 做什么：虚拟化物理资源（CPU、内存、磁盘），处理并发相关的棘手问题，持久地存储文件。要构建这样的系统，得有设计目标来聚焦实现、做出取舍——找到正确的取舍正是构建系统的关键。

- **抽象**：最基本的目标是建立抽象，让系统便利易用。抽象是计算机科学一切活动的根基：把大程序拆成小而可理解的模块、用高级语言写程序而不用考虑汇编、用汇编而不用想逻辑门、用逻辑门搭处理器而不用细想晶体管——全是抽象的功劳。
- **高性能**：另一个目标是提供高性能，即最小化 OS 的开销（overhead）。虚拟化与易用性值得追求，但不能不计代价；开销表现为额外的时间（更多指令）与额外的空间（内存或磁盘）。完美并不总能达到，要学会识别并（在合适时）容忍。
- **保护与隔离**：在应用之间、以及应用与 OS 之间提供保护。既然允许多个程序同时运行，就要确保一个程序的恶意或意外劣行不会伤害他人；更不能让应用伤害 OS 本身。保护是**隔离**（isolation）原则的核心：进程间相互隔离是保护的关键，也是 OS 大量工作的基础。
- **可靠性**：OS 必须不间断运行；它一挂，系统上的所有应用都挂。因此 OS 追求高度可靠性——随着 OS 日趋复杂（动辄数百万行代码），构建可靠的 OS 相当有挑战性。
- 其他目标同样合理：能源效率、（保护之延伸的）安全、移动性等。按使用方式不同，OS 的目标与实现会有差异，但构建 OS 的许多原理在各设备上是通用的。

## 一点历史

**早期操作系统：只是函数库。** 最初的 OS 没做什么大事，基本就是一组常用函数库：比如代劳低层 I/O 处理代码，让开发者轻松一点。那时一台大型机一次只跑一个程序，由人工操作员控制；许多你认为"OS 该干的活"（比如决定作业运行顺序）都是操作员干的。聪明的开发者会对操作员客气点，好让自己的作业排到队列前面。这种模式叫**批处理**（batch processing）：一批作业由操作员成批运行。计算机不用于交互——太贵了：让人坐在计算机前使用，机器大部分时间闲置，每小时的成本高达数十万美元。

**超越函数库：保护。** OS 开始承担管理机器的更核心角色后，一个重要认识是：**代表 OS 运行的代码是特殊的**——它控制着设备，理应区别于普通应用代码。想象一下允许任何应用读磁盘任意位置会怎样：隐私荡然无存。于是**系统调用**的思想被发明（由 Atlas 系统开创）。与"把 OS 例程当库函数调用"不同，系统调用增加了特殊的硬件指令对与硬件状态，让进入 OS 成为受控的正式过程。系统调用与过程调用的关键区别：系统调用在把控制（跳转）交给 OS 的同时**提升硬件特权级**。用户应用运行在**用户模式**（user mode），硬件限制其能力——比如不能发起磁盘 I/O、不能访问任意物理内存页、不能发网络包。发起系统调用（通常通过称为 trap 的特殊硬件指令）时，硬件把控制交给预先设定的**陷阱处理程序**（trap handler），特权级同时升至**内核模式**（kernel mode）；在内核模式下 OS 拥有对硬件的完全访问权。OS 服务完毕后通过 return-from-trap 指令返回用户模式，把控制交回应用离开之处。

**多道程序设计时代。** 超越大型机的时代由小型机（minicomputer）开启。DEC 的 PDP 系列等经典机器让计算机便宜了一大截，组织内的一小群人也能拥有自己的计算机。成本下降带来开发者活动的激增。为了更好地利用机器资源，**多道程序设计**（multiprogramming）蔚然成风：OS 一次加载多个作业进内存，在它们之间快速切换以提升 CPU 利用率——I/O 设备很慢，让程序在等待 I/O 时占着 CPU 是浪费，不如切去跑别的作业。支持多道程序设计与 I/O/中断重叠的需求，推动了 OS 概念的多方向创新：内存保护变得重要（不能让一个程序访问另一个程序的内存）；处理中断引入的并发问题也至关重要。这一时期最重大的实践成果是 **UNIX** 的诞生——主要归功于贝尔实验室的 Ken Thompson（与 Dennis Ritchie）。UNIX 从多个系统（尤其是 Multics）汲取优秀思想，却做得更简单易用，很快风靡。

**现代时代。** 小型机之后是更便宜、更快、面向大众的**个人计算机**（PC）。早期的 PC 操作系统却是一次大倒退：DOS 不做内存保护，恶意（或单纯写得很烂）的应用可以把内存涂得一塌糊涂；初代 Mac OS 采用协作式调度，一个意外陷入死循环的线程就能霸占整个系统、逼人重启。所幸几年苦难之后，小型机时代锤炼出的特性陆续回归桌面：Mac OS X/macOS 以 UNIX 为核心；Windows 自 NT 起也采纳了计算史上诸多伟大思想；如今的手机运行的操作系统（如 Linux）更接近 1970 年代小型机运行的系统，而非 1980 年代 PC 的系统。而且这些思想仍在演进。

> **附：UNIX 的重要性 / 然后有了 Linux**
> UNIX 在操作系统史上的地位怎么强调都不为过。其统一原则是构建"小型而强大、可彼此连接形成更大工作流"的程序——Shell 提供管道等原语支持这种元级编程（`grep foo file.txt | wc -l`）。UNIX 对程序员友好、附带 C 编译器、作者免费分发副本（早期开源形态），加上内核小巧优美、可读性强，引来无数人把玩和添砖加瓦——伯克利的 Bill Joy 团队做出了带先进虚拟内存、文件系统与网络子系统的 BSD 发行版。后来商业公司纷纷争夺所有权（SunOS、AIX、HPUX、IRIX 等），法律纠葛给 UNIX 蒙上阴影。
> 所幸，年轻的芬兰黑客 Linus Torvalds 决定自己写一个借鉴 UNIX 原则与思想、但不基于其代码的版本，避免了法律问题；他借助已存在的成熟 GNU 工具，联合世界各地的帮手，Linux 诞生（现代开源运动也随之而起）。互联网时代，Google、Amazon、Facebook 等公司选择免费且可自由定制的 Linux；智能手机时代 Linux 又借 Android 占领移动端；乔布斯把基于 UNIX 的 NeXTStep 带回 Apple，让 UNIX 在桌面流行。UNIX 活到了今天，且比以往任何时候都更重要。

## 小结

今天的操作系统让计算机系统相当易用，你用过的几乎所有操作系统都深受上述发展的影响。OS 的核心内容——CPU 与内存的虚拟化基础、并发、经由设备与文件系统的持久化——也是本模块后续文章的主线：进程、线程、调度、内存管理、虚拟内存、文件系统与锁。路很长，但大部分内容相当酷；走完这条路，你会对计算机系统如何真正运转有全新的认识。
