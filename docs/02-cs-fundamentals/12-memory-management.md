早年间，构建计算机系统很容易。为什么？因为用户期望不高。正是那些对"易用性""高性能""可靠性"抱有期待的可恶用户，带来了这一切头疼的问题。下次遇到计算机用户，请感谢他们制造的所有麻烦。

## 早期系统

从内存的角度看，早期机器几乎不向用户提供什么抽象。物理内存大致是：

```
0KB  ┌────────────────────────┐
     │ 操作系统（代码、数据等）  │
64KB ├────────────────────────┤
     │ 当前程序（代码、数据等）  │
     │  ……                    │
max  └────────────────────────┘
```

OS 是驻留在内存中的一组例程（其实就是一个库），同时只有一个运行中的程序（进程）占用物理内存的其余部分。这里没什么幻觉可言，用户对 OS 也没太多指望。那个年代 OS 开发者的日子真是轻松啊。

## 多道程序设计与分时

不久之后，由于机器昂贵，人们开始更高效地**共享**机器，于是**多道程序设计**时代诞生：给定时刻有多个进程就绪待运行，OS 在它们之间切换（比如某个进程决定做 I/O 时），从而提高 CPU 的有效利用率。在每台机器动辄数十万美元（甚至上百万）的年代，这种效率提升尤其重要。

很快，人们开始向机器索取更多，**分时**（time sharing）时代到来了。具体说，许多人认识到了批处理计算的局限——尤其是对程序员本身：漫长（因而低效）的"改程序—调试"循环让人厌倦。**交互性**（interactivity）变得重要：多个用户可能同时使用一台机器，每个人都在等待（或盼着）自己当前任务的及时响应。

实现分时的一种方式：让一个进程运行一小会儿、独占全部内存，然后停下它、把它的全部状态（包括整个物理内存）存到磁盘，再载入另一个进程的状态运行一会儿……如此粗糙地共享机器。不幸的是，这种方式有个大问题：**太慢**，内存越大越慢。保存/恢复寄存器级状态（PC、通用寄存器等）相对很快，但把整块内存内容写盘是惨绝人寰的低性能。我们更愿意在切换时**让进程留在内存里**，让 OS 高效地实现分时：

```
0KB   ┌────────────────────────┐
      │ 操作系统（代码、数据等）  │
64KB  ├────────────────────────┤
      │ 进程 A（代码、数据等）    │
128KB ├────────────────────────┤
      │ 进程 B（代码、数据等）    │
192KB ├────────────────────────┤
      │ 进程 C（代码、数据等）    │
320KB ├────────────────────────┤
      │ （空闲）……              │
512KB └────────────────────────┘
```

三个进程 A、B、C 各分得 512KB 物理内存的一小块。假设单 CPU，OS 选择运行其中一个（如 A），其余（B、C）在就绪队列等待。

随着分时普及，你能猜到 OS 面临了新需求：让多个程序**同时驻留内存**，使**保护**成为关键问题——你不会希望一个进程能读、更糟的是**写**另一个进程的内存。

## 地址空间

不过还得惦记那些讨厌的用户——这要求 OS 为物理内存创建一个易用的抽象。我们把这个抽象称为**地址空间**（address space）：它是运行中的程序对系统内存的**视图**（view）。理解这一 OS 内存基础抽象，是理解内存如何被虚拟化的关键。

进程的地址空间包含运行程序的**全部内存状态**：

- **程序代码**（指令）必须存放在内存某处，因此在地址空间中；
- 程序运行时用**栈**（stack）记录函数调用链的位置、分配局部变量、传递参数与返回值；
- **堆**（heap）用于动态分配、由用户管理的内存——比如 C 里 `malloc()` 返回的、或 C++/Java 等面向对象语言里 `new` 得到的。

当然地址空间里还有别的东西（如静态初始化的变量），但暂且只看三件套：**代码、栈、堆**。看一个 16KB 的小地址空间：

```
16KB ┌──────────────────┐
     │ 栈 ↓              │  栈段：局部变量、例程参数、
15KB │  （空闲）          │        返回值等（向下增长）
2KB  ├──────────────────┤
     │ 堆 ↑              │  堆段：malloc 的数据、动态数据结构
1KB  ├──────────────────┤              （向上增长）
     │ 程序代码          │  代码段：指令所在地
0KB  └──────────────────┘
```

程序代码位于地址空间顶部（本例从 0 开始、打包在前 1K 中）。代码是静态的（因此容易安置），可以放在开头并确定它在程序运行中不需要更多空间。

接下来是两个可能随程序运行而增长（或收缩）的区域：堆（上）与栈（下）。这样安排是因为两者都想增长；把它们放在地址空间的两端，就可以各自生长——只要方向相反。堆从代码之后（1KB 处）开始向下增长（比如用户通过 `malloc()` 请求更多内存时）；栈从 16KB 处开始向上增长（比如发生函数调用时）。不过这种摆法只是**约定**；你完全可以另行安排（后面会看到，当多个线程共存于一个地址空间时，这种漂亮的划分方式就不复存在了）。

关键在于：当我们描述地址空间时，描述的是 **OS 提供给运行程序的抽象**。程序其实并不在物理地址 0 到 16KB——它被加载在某个任意物理地址（见图中 A、B、C 各自加载在不同地址）。于是问题来了：

> **问题的核心：如何虚拟化内存？**
> OS 如何在单一的物理内存之上，为多个并发运行（共享内存）的进程构建"私有的、可能很大的地址空间"这一抽象？

OS 做到这一点时，我们就说 OS 在**虚拟化内存**（virtualizing memory），因为运行中的程序以为它被加载在特定地址（比如 0），并且拥有可能很大的地址空间（比如 32 位或 64 位）——现实完全不同。比如图中进程 A 尝试在地址 0 执行加载（我们称之为**虚拟地址**，virtual address）时，OS 必须协同某种硬件支持，确保这个加载不会真的去物理地址 0，而是去物理地址 320KB（A 被加载之处）。这就是**内存虚拟化**的关键，它支撑着当今世界上每一个现代计算机系统。

## 目标

于是我们明确了 OS 的任务：**虚拟化内存**。而且要有风格地虚拟化。为此需要目标来指引（这些目标在导论篇见过，值得重复）：

1. **透明**（transparency）：OS 实现虚拟内存的方式应当对运行程序**不可见**。程序不该察觉内存被虚拟化了，而应表现得如同拥有自己的私有物理内存；幕后 OS（和硬件）包办在多个作业间复用内存的全部工作，维持这个幻觉。（注意这里 transparency 的用法：不是"公开透明"，而是"难以察觉"。）
2. **效率**（efficiency）：OS 应追求虚拟化尽可能高效——时间上（不让程序明显变慢）与空间上（不为支持虚拟化的结构占用过多内存）。要实现时间高效的虚拟化，OS 必须依赖硬件支持，包括 TLB 这类硬件特性（后面详谈）。
3. **保护**（protection）：OS 必须保护进程彼此不伤害、并保护 OS 本身不受进程伤害。进程执行加载、存储或取指时，不应能以任何方式访问或影响任何其他进程（或 OS 自身）的内存内容——即地址空间之外的任何东西。保护使进程间的**隔离**（isolation）得以实现：每个进程都应运行在自己的隔离茧中，免受其他故障甚至恶意进程的荼毒。

> **技巧：隔离原则**
> 隔离是构建可靠系统的关键原则：若两个实体被恰当隔离，则一个失败不会影响另一个。操作系统力求隔离进程防止互相伤害；内存隔离进一步保证运行中的程序无法影响底层 OS 的运转。一些现代 OS 把隔离做得更绝——把 OS 的一部分与另一部分隔开，这类**微内核**（microkernel）设计可能比典型的单体内核（monolithic kernel）更可靠。

后续的探索将聚焦虚拟化内存所需的基本机制（硬件与操作系统的支持），以及 OS 中会遇到的若干重要策略——如何管理空闲空间、内存吃紧时把哪些页踢出内存。由此你将建立对现代虚拟内存系统真实运作方式的理解。

## 小结

我们引入了一个重要 OS 子系统：**虚拟内存**（VM）。VM 系统负责向每个运行程序提供"庞大、稀疏、私有"地址空间的幻觉；每个虚拟地址空间包含程序全部指令与数据，程序通过**虚拟地址**引用它们。OS 借助硬件的大力协助，把每个虚拟内存引用转换成**物理地址**，再送往物理内存去取数或更新。OS 同时为许多进程提供这一服务，并确保程序互不干扰、OS 受到保护。整套方法需要大量**机制**（low-level machinery）与一些关键**策略**；我们自底向上，先讲关键机制——下一篇虚拟内存（TLB 与空闲空间管理）正是其中核心。

## 附：你看到的所有地址都是虚拟的

写 C 程序时打印过指针吗？你看到的值（某个大数，常以十六进制输出）就是**虚拟地址**。想知道程序代码在哪？也可以打印出来——能打印出来的，同样是虚拟地址。事实上，作为用户级程序员，你能看到的**任何地址**都是虚拟地址。只有 OS 通过其巧妙的内存虚拟化技术，才知道这些指令与数据真正躺在机器物理内存的哪个角落。所以永远记住：程序里打印出的地址是虚拟的，是内存布局的幻象；只有 OS（和硬件）知道真相。

一个小程序（`va.c`），打印 `main()` 例程（代码）的位置、`malloc()` 返回的堆分配值的位置、以及栈上整数的位置：

```c
#include <stdio.h>
#include <stdlib.h>
int main(int argc, char *argv[]) {
    printf("location of code : %p\n", main);
    printf("location of heap : %p\n", malloc(100e6));
    int x = 3;
    printf("location of stack: %p\n", &x);
    return x;
}
```

在 64 位 Mac 上运行输出如下：

```
location of code : 0x1095afe50
location of heap : 0x1096008c0
location of stack: 0x7fff691aea64
```

可以看到：代码在地址空间最前，然后是堆，栈则远在巨大虚拟空间的另一端。这些地址都是虚拟的，将由 OS 与硬件翻译，去真正的物理位置取值。
