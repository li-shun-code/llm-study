我们已经知道 IP 负责在互联网上路由流量，也知道它用 **IP 地址**干活——IPv4 常以点分数字格式示人，如 `10.1.2.3`。

但作为人类，我们极少用 IP 地址。用浏览器时，你一般不会在地址栏里敲 IP。

甚至在我们的项目里，我们也习惯敲 `localhost` 而不是 `127.0.0.1`。

把人类使用的名字（如 `www.example.com`）转换为计算机使用的 IP 地址的通用过程，称为**域名解析**（domain name resolution）；它由一群分布式服务器提供，合称**域名系统**（Domain Name System，DNS）。

## 31.1 典型用法

从用户视角：我们把自己的设备配置成"有一个**名字服务器**（name server）可以联系、用于把名字转换成 IP 地址"。（多半由 DHCP 配置，后文再提。）

当你尝试连接 `example.com` 时，你的计算机联系那个名字服务器索取 IP 地址。

如果该名字服务器知道答案，它就直接提供；不知道的话，一整台"机器"就运转起来了。

我们深入这个过程看看。

## 31.2 域名与 IP 地址

如果你从没注册过域名（比如 `example.com`、`oregonstate.edu`、`google.com`、`army.mil`），流程大致是：

1. 联系一家**域名注册商**（有权出售域名的公司）；
2. 挑一个没人注册过的域名；
3. 每年付点钱使用它；
4. ……
5. 赚钱！

但这件事与 IP 地址的概念**完全无关**。确实，域名可以没有 IP 地址而存在——只是没法被使用而已。

有了域名后，你可以联系托管公司，由它给你提供某台服务器上的一个 IP 地址。

现在你有了两块拼图：域名和 IP 地址。

但你还得把它们**连起来**，让别人拿到你的域名就能查到你的 IP。

为此，你向 DNS 版图中的某台服务器——一台**域名服务器**——添加一条含相关信息的数据库记录。

## 31.3 （域名）名字服务器

通常简称**名字服务器**。这些服务器保存着它们具有**权威**（authority）的域名的 IP 记录。也就是说，一台名字服务器并没有全世界的记录，只有特定域名或子域名的记录。

> **子域名**（subdomain）是由域名所有者管理的域。比如 `example.com` 的所有者可以造出子域名 `sub1.example.com` 与 `sub2.example.com`。它们本身不是主机——但可以有各自的主机，如 `host1.sub1.example.com`、`host2.sub1.example.com`、`somecompy.sub2.example.com`。域名所有者想要多少个子域名都行，只要配好处理它们的名字服务器。

对特定域名具有权威的名字服务器，可以被问及该域名上的任何主机。主机常是域名的第一个"词"，但未必——比如 `www.example.com`，主机是 `example.com` 域上名为 `www` 的那台计算机。

一台名字服务器可以对多个域名具有权威。

而且，即便名字服务器不知道被问域名的 IP，它也可以联系其他名字服务器把答案查出来。从用户视角，这一切是透明的。

所以，很简单喽？我不知道某个域名，就去联系该域名的名字服务器拿答案，对吧？

## 31.4 根名字服务器

但有个问题：如果我不知道某域名的名字服务器是谁，我怎么连上那台名字服务器？

为解决它，我们有若干**根名字服务器**（root name servers）帮忙引路。当我们不知道某个 IP 时，可以从根服务器开始，请它告诉我们 IP——或告诉我们该去问哪台服务器（稍后详述这个过程）。

计算机出厂预配置了 **13 台根名字服务器**的 IP 地址。这些 IP 极少变化，而且只需其中一台可用即可。频繁执行 DNS 的计算机会定期取回列表以保持最新。

根名字服务器从 `a` 到 `m` 命名：

```
a.root-servers.net
b.root-servers.net
c.root-servers.net
...
k.root-servers.net
l.root-servers.net
m.root-servers.net
```

## 31.5 一次查询实例

以查询名为 `www.example.com` 的计算机为例。我们需要它的 IP 地址；不知道负责 `example.com` 域的名字服务器是谁，只知道根名字服务器列表。

1. 随便挑一台根服务器，比如 `c.root-servers.net`。联系它："你好，我们在找 `www.example.com`，能帮忙吗？"
   根名字服务器不知道这个。它说："这个我不知道，但你要找任何 `.com` 域名的话，可以联系这些名字服务器中的任何一台。"它附上一份知道 `.com` 域的名字服务器列表：

   ```
   a.gtld-servers.net
   b.gtld-servers.net
   c.gtld-servers.net
   ...
   m.gtld-servers.net
   ```

2. 于是我们挑一台 `.com` 名字服务器。
   "你好 `h.gtld-servers.net`，我们在找 `www.example.com`，能帮忙吗？"
   它答："这个名字我不知道，但我知道 `example.com` 的名字服务器。你可以去找它们。"它附上知道 `example.com` 域的名字服务器列表：

   ```
   a.iana-servers.net
   b.iana-servers.net
   ```

3. 于是我们挑其中一台。
   "你好 `a.iana-servers.net`，我们在找 `www.example.com`，能帮忙吗？"
   那台名字服务器答："能！我知道这个名字！它的 IP 地址是 `93.184.216.34`！"

所以任何一次查询，都从根名字服务器出发，由它指引我们去哪找更多信息（除非信息已在某处被缓存——见下）。

## 31.6 区域（Zones）

域名系统被划分为逻辑上的管理**区域**（zone）。粗略地说，区域是某台特定名字服务器权威之下的域名集合。

但这么说有点过度简化：同一个区域里可以有一个或多个域名；同一个区域里也可以有多台名字服务器协同工作。把区域想成"某个管理机构负责的所有域名与子域名"即可。例如根区域有多台名字服务器负责查询；`.com` 区域同样有多台具有权威的名字服务器。

## 31.7 解析器库

当你编写使用域名的软件时，是调用一个**库**来完成 DNS 查询的。你可能注意到，在 Python 里调用：

```python
s.connect(("example.com", 80))
```

根本不用操心 DNS——幕后，Python 把在 DNS 中查找该域名的活儿全干了。C 语言里干同样事情的是 `getaddrinfo()` 函数。

简言之：有现成的库可用，我们不必自己写这些代码。

OS 还保存着一条记录：默认用于查询的名字服务器。（有时手工配置，但更常通过 [DHCP](https://en.wikipedia.org/wiki/Dynamic_Host_Configuration_Protocol) 配置。）你发起查询时，计算机先去找这台服务器。

且慢——这和前面那套根服务器层级怎么扯上关系？

答案：**缓存**！

## 31.8 缓存服务器

想象全球正在发生的所有 DNS 查询。如果**每一次**请求都要跑去根服务器，不但重复请求耗时长，根服务器也会被锤爆。

为避免这一点，所有 DNS 解析器库与 DNS 服务器都会**缓存**（cache）结果。

> 事实上，即便有缓存，根服务器每天也要处理数以万亿计的请求。

这样就能避免重复请求压垮根服务器。于是前面的流程要修订一下：

1. 问我们的解析器库要 IP。它缓存里有，直接返回。
2. 没有，问我们的本地名字服务器。它缓存里有，直接返回。
3. 没有缓存，**且**这台名字服务器还有上游名字服务器（即它可以去求答案的另一台名字服务器），就问上游。
4. 没有缓存，**且**没有上游名字服务器，就去根服务器，流程照旧开始。

有这么多拿到缓存结果的机会，根名字服务器的压力就大大缓解了。

你买的很多 WiFi 路由器自己也跑着缓存名字服务器：DHCP 配置你的计算机时，你的计算机会把这台路由器当作 LAN 上各设备的 DNS 服务器——到路由器的 ping 时间极短，DNS 查询自然飞快。

### 31.8.1 生存时间（TTL）

由于域名或主机的 IP 可能变化，缓存条目必须有过期机制。

这由 DNS 记录中的一个字段实现：**生存时间**（time to live，TTL）——服务器应缓存结果多少秒。常设为 86400 秒（1 天）；按区域管理员对"这个 IP 多久变一次"的预估，也可以更多或更少。

缓存条目过期后，若有人再请求，名字服务器就得重新向上游或根服务器要数据。

## 31.9 记录类型

到目前为止，我们谈的是用 DNS 把主机或域名映射到 IP 地址——这只是 DNS 服务器为一个域名存储的记录类型之一。

常见记录类型有：

- **`A`**：IPv4 地址记录——就是我们一直在说的这种。回答"这台主机/域名的 IPv4 地址是什么？"
- **`AAAA`**：IPv6 地址记录。回答"这台主机/域名的 IPv6 地址是什么？"
- **`NS`**：某域名的名字服务器记录。回答"哪些名字服务器为这台主机/域名应答？"
- **`MX`**：邮件交换记录。回答"哪些计算机负责处理这个域名的邮件？"
- **`TXT`**：文本记录。存放自由格式的文本信息；有时用于反垃圾邮件与证明域名所有权。
- **`CNAME`**：规范名记录，可视为别名。表达"域名 xyz.example.com 是 abc.example.com 的别名"。
- **`SOA`**：权威起始记录。包含一个域名的信息，包括其主名字服务器与联系信息。

DNS 记录类型还有[很多](https://en.wikipedia.org/wiki/List_of_DNS_record_types)。

## 31.10 动态 DNS

典型的互联网用户在家里并没有**静态 IP 地址**（专用且不变）。重启一下调制解调器，ISP 可能就发给你一个不同的 IP。

这会给 DNS 惹麻烦：所有指向其公网 IP 的 DNS 记录都过时了。

**动态 DNS**（Dynamic DNS，DDNS）旨在解决这个问题。简言之，有两个机制在起作用：

1. 一种让客户端告诉 DDNS 服务器"我的 IP 是什么"的方式；
2. DDNS 服务器上该记录设一个**非常短的 TTL**。

虽然 DNS 定义了发送更新记录的方式，一种常见的替代做法是：LAN 上的一台计算机定期（如每 10 分钟）以经过认证的 HTTP 请求联系 DDNS 服务商；DDNS 服务器看到请求来源的 IP，用它更新记录。

## 31.11 反向 DNS

如果你手里是点分数字的 IP 地址，想要该 IP 对应的主机名呢？可以做**反向 DNS**（reverse DNS）查询。

注意：并非所有 IP 都有这类记录，反向 DNS 查询经常一无所获。

- 根名字服务器知道世界上每一个 IP 地址吗？
- 人们为什么会用动态 DNS？
- TTL 是干什么用的？

> 译注：回到本模块的视角——你在代码里写 `api.openai.com`，`getaddrinfo()` 先问本地缓存、再问递归解析器、最后沿"根 → .com → 权威服务器"逐级问路拿到 IP，然后才轮到 TCP 三次握手、TLS 握手与 HTTP 请求。DNS 是每一次 API 调用静默的第一步；理解它，也就理解了为什么"解析慢/缓存失效"会让你的服务莫名变慢。
