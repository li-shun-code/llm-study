至此我们见证了两个关键 OS 抽象的形成：**进程**（CPU 的虚拟化）与**地址空间**（内存的虚拟化）。二者合力，让程序仿佛运行在自己私有的隔离世界里：好像独占处理器、独占内存。这个幻觉让系统编程容易得多，如今不仅盛行于桌面与服务器，也日益普及到手机等一切可编程平台。

本篇往虚拟化拼图里再添一块关键拼图：**持久存储**。持久存储设备（如经典硬盘或更现代的固态存储设备）永久地（至少长期）保存信息。与断电即失的内存不同，持久存储设备会让数据完好无损。因此 OS 必须对这类设备格外上心：**用户真正在乎的数据都放在这里**。

## 文件与目录

存储虚拟化在历史中形成了两个关键抽象。

第一个是**文件**（file）。文件就是一个**字节的线性数组**，每个字节你都可以读或写；每个文件有某种低层名字——通常是某种数字，用户往往并不知晓（后面会看到）。出于历史原因，文件的低层名字常被称为 **inode 号**（i-number）。在多数系统中，OS 并不深究文件的**结构**（它是图片、文本还是 C 代码？）；文件系统的职责只是把数据持久地存到磁盘上，并确保你再次请求时拿回当初放进去的东西。做起来可不像听起来那么简单！

第二个抽象是**目录**（directory）。目录与文件一样也有低层名字（inode 号），但它的内容非常特定：一组**（用户可读名，低层名）对**的列表。比如某文件低层名为 "10"、用户可读名为 "foo"，那么 "foo" 所在目录里就有一条 ("foo", "10") 条目，把用户可读名映射到低层名。目录中的每条条目既可指向文件、也可指向其他目录。目录套目录，用户就能构建任意的**目录树**（目录层次），所有文件与目录都挂在树下。目录层次从**根目录**开始（UNIX 系统中根目录就记作 `/`），用某种分隔符逐级命名子目录，直到点出想要的文件或目录。比如在根目录下创建目录 `foo`、再在 `foo` 里创建文件 `bar.txt`，那么该文件的**绝对路径名**就是 `/foo/bar.txt`。文件与目录只要在文件系统树的不同位置就可以同名（如 `/foo/bar.txt` 与 `/bar/foo/bar.txt`）。

示例中的文件名常有形如 `bar.txt` 的两段式结构：句点前是任意取名，后缀习惯上指示文件类型（`.c` 是 C 代码、`.jpg` 是图片、`.mp3` 是音乐）。但这通常只是**约定**——并没有强制保证名为 `main.c` 的文件里装的真是 C 源码。

文件系统由此提供了一个伟大的东西：**为我们关心的所有文件提供一种便利的命名方式**。名字在系统中至关重要，因为访问任何资源的第一步都是能叫出它。UNIX 系统中，文件系统提供了访问磁盘、U 盘、CD-ROM 等许多设备乃至更多东西的**统一**方式——它们全都位于这棵单一的目录树下。

> **技巧：仔细考虑命名**
> 命名是计算机系统的重要方面。UNIX 系统里，你能想到的几乎一切都通过文件系统命名：除了文件，设备、管道、甚至进程（`/proc`）都能在看似普通的文件系统里找到。命名的统一性简化了你的系统概念模型，让系统更简单、更模块化。因此，创建系统或接口时，请仔细考虑你使用的名字。

## 创建文件

最基本的操作是创建文件，用 `open` 系统调用并传入 `O_CREAT` 标志即可：

```c
int fd = open("foo", O_CREAT|O_WRONLY|O_TRUNC,
              S_IRUSR|S_IWUSR);
```

第二个参数：文件不存在则创建（`O_CREAT`）、只能写入（`O_WRONLY`）、已存在则截断为零字节清空原内容（`O_TRUNC`）；第三个参数指定权限（本例所有者可读写）。

`open()` 一个重要方面是它的返回值：**文件描述符**（file descriptor）。文件描述符只是一个整数，**每个进程私有**，UNIX 系统用它访问文件；文件打开后，你就用描述符来读写它（前提是有权限）。从这个角度看，文件描述符是一种**能力**（capability）——一个不透明（opaque）的句柄，赋予你执行特定操作的权力。另一种理解：文件描述符是指向 file 类型对象的指针；拿到对象后，就能调用其他"方法"访问文件，如 `read()` 和 `write()`。

文件描述符由 OS 按**每进程**管理：UNIX 系统在 proc 结构里维护一个简单数组（如 xv6 的 `struct file *ofile[NOFILE]`），以描述符为下标，跟踪该进程打开了哪些文件。

> **技巧：使用 strace（及类似工具）**
> `strace` 提供了观察程序行为的绝佳途径：跟踪程序发出的每个系统调用、查看参数与返回码，从而对程序的所作所为获得极清晰的认识。常用参数：`-f` 跟随 fork 出的子进程；`-t` 显示每次调用的时刻；`-e trace=open,close,read,write` 只跟踪指定调用。Linux 上是 strace，Mac 上有 dtruss，老式 UNIX 变体上是 truss。

## 读写文件

有了文件自然要读写。命令行里，`echo hello > foo` 把 "hello" 写进文件 foo，然后 `cat foo` 把内容倒到屏幕上。但 `cat` 是怎么访问 `foo` 的？用 `strace cat foo` 看看（为可读性略去若干调用）：

```
prompt> strace cat foo
...
open("foo", O_RDONLY|O_LARGEFILE)   = 3
read(3, "hello\n", 4096)            = 6
write(1, "hello\n", 6)              = 6
hello
read(3, "", 4096)                   = 0
close(3)                            = 0
...
```

`cat` 首先打开文件（只读 `O_RDONLY`），调用成功并返回文件描述符 **3**。为什么是 3 而不是 0 或 1？因为每个运行中的进程已经默认打开了三个文件：**标准输入**（读入数据）、**标准输出**（写出信息到屏幕）、**标准错误**（写出错误信息），分别由描述符 0、1、2 代表。所以你第一次打开别的文件，几乎必然拿到描述符 3。

打开成功后，`cat` 用 `read()` 反复读入若干字节。`read()` 第一个参数是文件描述符（进程可能同时打开多个文件，描述符让 OS 知道这次读的是哪个文件）；第二个参数指向放置读出结果的缓冲区（strace 在该处显示了结果 "hello"）；第三个参数是缓冲区大小（本例 4KB）。`read()` 成功返回读到的字节数（6 = "hello" 5 个字母 + 1 个行尾符）。

接着你看到另一个有趣的结果：一次 `write()` 调用、写到描述符 **1**——标准输出，把 "hello" 打到屏幕上（`cat` 的本职）。它直接调用 write 吗？也许（如果高度优化）；也可能调用库函数 `printf()`，由 printf 内部处理格式化、最终写往标准输出。

然后 `cat` 尝试继续读，但文件已无字节可读，`read()` 返回 0——程序由此知道已读完整个文件，于是调用 `close()` 表明用完了 "foo"，传入相应描述符。文件关闭，读取完成。写文件与之类似：先以写方式打开，再 `write()`（大文件可能反复调用），最后 `close()`。

> **附：数据结构——打开文件表**
> 每个进程维护一个文件描述符数组，每个描述符指向**系统级打开文件表**（open file table）中的一个条目。表中条目跟踪描述符所指的底层文件、当前偏移量，以及其他相关信息（文件可读还是可写等）。

## 非顺序读写：lseek

到目前为止，所有访问都是**顺序**的——从头读到尾或从头写到尾。有时你需要在文件的**特定偏移**处读写：比如为文本文档建了索引、要按索引查词，就可能从文档中的随机偏移读取。这用 `lseek()` 系统调用：

```c
off_t lseek(int fildes, off_t offset, int whence);
```

第一个参数是熟悉的文件描述符；第二个是偏移量；第三个参数 `whence`（出于历史原因这么叫）决定寻址方式——按手册页：

- `SEEK_SET`：偏移量设为 offset 字节；
- `SEEK_CUR`：偏移量设为当前位置加 offset 字节；
- `SEEK_END`：偏移量设为文件大小加 offset 字节。

可见：对进程打开的每个文件，OS 都跟踪一个"当前"偏移，决定下一次读/写在文件中的起点。这个偏移的更新有两种方式：读/写 N 字节时自动加 N（每次读写隐式更新偏移）；或显式调用 `lseek` 修改。偏移量就保存在前面看到的 `struct file` 里：

```c
struct file {
    int ref;
    char readable;
    char writable;
    struct inode *ip;
    uint off;
};
```

OS 由此得知打开的文件可读/可写、指向哪个底层文件（inode 指针 ip）、当前偏移（off），还有一个**引用计数**（ref，后面讲）。这些结构代表系统中所有当前打开的文件，合称**打开文件表**。xv6 内核就用一个数组加一把自旋锁来实现。

几个例子帮助理解。**例一**：进程打开 300 字节的文件、每次 read 100 字节：

| 系统调用 | 返回码 | 当前偏移 |
|---|---|---|
| fd = open("file", O_RDONLY) | 3 | 0 |
| read(fd, buffer, 100) | 100 | 100 |
| read(fd, buffer, 100) | 100 | 200 |
| read(fd, buffer, 100) | 100 | 300 |
| read(fd, buffer, 100) | 0 | 300 |
| close(fd) | 0 | – |

注意：打开时偏移初始化为 0；每次 read 后偏移递增（进程只需不断 read 就能拿到文件的下一块）；越过文件末尾的 read 返回 0，表示读完了。**例二**：进程打开同一文件两次、各读一次——分配了两个描述符（3、4），各自指向打开文件表中**不同**的条目（如条目 10、11），两个当前偏移各自独立更新。**例三**：进程先 `lseek(fd, 200, SEEK_SET)` 把偏移定位到 200，再 read 50 字节——只需一个打开文件表条目，read 后偏移变为 250。

> **附：调用 lseek() 并不会执行磁盘寻道**
> 名字起得很糟的 `lseek()` 困惑过无数想理解磁盘与文件系统的同学。别把两者混淆！`lseek()` 只是修改 OS 内存中一个变量——某进程下一次读写将从哪个偏移开始。**磁盘寻道**（disk seek）发生于发给磁盘的读/写不在上一条读/写所在磁道上、因而需要移动磁头时。更让人混淆的是：调用 lseek 去随机位置读写，**随后**的读写确实会造成更多磁盘寻道。因此调用 lseek 可能"导致"之后的读或写发生寻道，但它本身绝不引发任何磁盘 I/O。

## 共享的文件表条目：fork() 与 dup()

许多情形下（如上面的例子），描述符到打开文件表条目是一对一映射：每个逻辑上的读或写相互独立、各有自己的当前偏移。但也有少数有趣情形下条目会被**共享**。

其一：父进程用 `fork()` 创建子进程时。看这段代码（fork-seek.c）：父进程创建子进程并等待；子进程用 lseek 调整当前偏移后退出；父进程随后检查当前偏移并打印：

```c
int main(int argc, char *argv[]) {
    int fd = open("file.txt", O_RDONLY);
    assert(fd >= 0);
    int rc = fork();
    if (rc == 0) {
        rc = lseek(fd, 10, SEEK_SET);
        printf("child: offset %d\n", rc);
    } else if (rc > 0) {
        (void) wait(NULL);
        printf("parent: offset %d\n",
               (int) lseek(fd, 0, SEEK_CUR));
    }
    return 0;
}
```

运行输出：

```
prompt> ./fork-seek
child: offset 10
parent: offset 10
```

子进程 lseek 改的偏移，父进程也"看到"了！其结构是：父与子各自的私有描述符数组，指向**同一个**打开文件表条目（引用计数为 2、偏移 10），该条目再指向底层文件系统的 inode。此处终于用上了**引用计数**：文件表条目被共享时引用计数递增；只有两个进程都关闭（或退出）该文件，条目才会移除。父子共享打开文件表条目偶尔很有用：比如多个进程协作完成一项任务时，它们可以无需任何额外协调就写同一个输出文件。

另一种共享发生在 `dup()` 系统调用（及其表亲 dup2、dup3）：它让进程创建一个新文件描述符，指向**与现有描述符相同的底层打开文件**：

```c
int fd = open("README", O_RDONLY);
assert(fd >= 0);
int fd2 = dup(fd);
// 现在 fd 与 fd2 可以互换使用
```

`dup()`（尤其 `dup2()`）在编写 UNIX Shell、实现输出重定向之类的操作时非常有用——花点时间想想为什么！

## 立即写盘：fsync()

多数时候，程序调用 `write()` 只是在告诉文件系统："请**在未来某个时刻**把这些数据写入持久存储。"出于性能考虑，文件系统会把这类写**缓冲**在内存里一段时间（比如 5 秒或 30 秒），届时才真正发往存储设备。从调用应用的角度看，写似乎很快完成；只有极少数情况（write 之后、真正写盘之前机器崩溃）数据才会丢失。

但有些应用需要比"最终保证"更强的东西：比如数据库管理系统（DBMS）要实现正确的恢复协议，就必须能不时**强制写盘**。为此多数文件系统提供额外控制 API。UNIX 世界里，这就是 `fsync(int fd)`：进程对某文件描述符调用 `fsync()` 时，文件系统强制把该文件所有**脏**（尚未写入）数据写到磁盘；fsync 在所有写入完成后才返回。

```c
int fd = open("foo", O_CREAT|O_WRONLY|O_TRUNC,
              S_IRUSR|S_IWUSR);
assert(fd > -1);
int rc = write(fd, buffer, size);
assert(rc == size);
rc = fsync(fd);
assert(rc == 0);
```

有趣的是，这个序列并不能保证你以为的一切：某些情况下，你还需要对**包含 foo 的目录**调用 fsync——这一步不仅确保文件本身在磁盘上，还确保新创建的文件持久地成为目录的一部分。不出所料，这种细节常被忽视，造成大量应用级 bug。

## 重命名文件

有时需要给文件改名。命令行里用 `mv foo bar`。用 strace 看，`mv` 使用的是 `rename(char *old, char *new)` 系统调用，恰好两个参数：原名与新名。

`rename()` 提供了一个有趣的保证：它（通常）实现为对系统崩溃**原子**的操作——若系统在改名过程中崩溃，文件要么叫旧名、要么叫新名，不会出现奇怪的中间态。因此 `rename()` 对需要原子更新文件状态的某些应用至关重要。具体一点：假设你在用编辑器往 foo.txt 中间插入一行。编辑器保证"新文件 = 原内容 + 插入行"的写法如下（略去错误检查）：

```c
int fd = open("foo.txt.tmp", O_WRONLY|O_CREAT|O_TRUNC,
              S_IRUSR|S_IWUSR);
write(fd, buffer, size);   // 写出新版文件
fsync(fd);
close(fd);
rename("foo.txt.tmp", "foo.txt");
```

做法简单：先用临时名写出文件新版本、fsync 强制落盘，确认新文件的元数据与内容都已在磁盘上后，把临时文件 rename 成原名。最后一步原子地"换入"新文件、同时删除旧版本——一次原子文件更新达成。

## 获取文件信息：stat()

除访问文件外，我们期望文件系统为每个文件保存相当多信息——通常称为**元数据**（metadata）。用 `stat()` 或 `fstat()` 系统调用查看：给定路径名（或描述符），填充一个 stat 结构：

```c
struct stat {
    dev_t st_dev;     // 包含文件的设备 ID
    ino_t st_ino;     // inode 号
    mode_t st_mode;   // 保护（权限）
    nlink_t st_nlink; // 硬链接数
    uid_t st_uid;     // 所有者用户 ID
    gid_t st_gid;     // 所有者组 ID
    dev_t st_rdev;    // 设备 ID（特殊文件）
    off_t st_size;    // 总大小（字节）
    blksize_t st_blksize; // 文件系统 I/O 块大小
    blkcnt_t st_blocks;   // 分配的块数
    time_t st_atime;  // 最后访问时间
    time_t st_mtime;  // 最后修改时间
    time_t st_ctime;  // 最后状态变更时间
};
```

每个文件保存的信息相当多：大小（字节）、低层名（inode 号）、所有权信息、访问/修改时间等。命令行工具 `stat` 可以直接看：

```
prompt> echo hello > file
prompt> stat file
  File: `file'
  Size: 6          Blocks: 8          IO Block: 4096  regular file
Device: 811h/2065d Inode: 67158084     Links: 1
Access: (0640/-rw-r-----) Uid: (30686/remzi)  Gid: (30686/remzi)
Access: 2011-05-03 15:50:20.157594748 -0500
Modify: 2011-05-03 15:50:20.157594748 -0500
Change: 2011-05-03 15:50:20.157594748 -0500
```

每个文件系统通常把这类信息保存在一个叫 **inode** 的结构中——把它想成文件系统维护的持久数据结构、包含上述信息即可；所有 inode 都在磁盘上，活跃 inode 的副本通常缓存在内存加速访问。

## 删除文件：unlink 之谜

会建会读了，怎么删？你可能觉得知道：跑 `rm`。但 `rm` 用的系统调用是什么？strace 一下：

```
prompt> strace rm foo
...
unlink("foo") = 0
...
```

只有一个调用了神秘系统调用 **unlink()** 的痕迹：它只接受要移除的文件名，成功返回 0。大谜题来了：为什么叫 unlink？为什么不叫 remove 或 delete？

要解开谜题，得先理解文件之外的东西——**目录**。

## 创建、读取与删除目录

除文件外，还有一组目录相关的系统调用用于创建、读取、删除目录。注意：你**永远不能直接写目录**——目录格式被视为文件系统元数据，文件系统认为自己对目录数据的完整性负责；你只能**间接**更新目录，比如在其中创建文件、目录或其他对象。这样文件系统才能确保目录内容符合预期。

创建目录用 `mkdir()` 系统调用（同名程序 `mkdir foo`）。新目录被视为"空"，但至少有两条内容：一条指向**自己**，一条指向**父目录**——前者叫 "."（点）目录，后者叫 ".."（点点）。给 `ls` 加 `-a` 就能看到它们。

读目录就是 `ls` 干的事。自己写一个类似 ls 的小工具？不是把目录当文件打开，而是用一组新调用——`opendir()`、`readdir()`、`closedir()`：

```c
int main(int argc, char *argv[]) {
    DIR *dp = opendir(".");
    assert(dp != NULL);
    struct dirent *d;
    while ((d = readdir(dp)) != NULL) {
        printf("%lu %s\n", (unsigned long) d->d_ino,
               d->d_name);
    }
    closedir(dp);
    return 0;
}
```

接口非常简单：一个循环逐条读目录项，打印每个文件的名字与 inode 号。目录项结构 `struct dirent` 包含文件名、inode 号等信息。由于目录里的信息很轻量（基本就是名字到 inode 号的映射），程序往往还要对每个文件调用 `stat()` 获取更多信息——这正是 `ls -l` 的做法（对带与不带 `-l` 的 ls 分别跑 strace 亲自验证吧）。

删除目录用 `rmdir()`（同名程序）。与删除文件不同，删目录更危险——一条命令可能删掉大量数据——因此 `rmdir()` 要求目录必须**为空**（只含 "." 与 ".."）才能删；试图删非空目录会直接失败。

> **技巧：当心强大的命令**
> `rm` 是"强大命令"的绝佳示例——力量太大有时是坏事。`rm *` 匹配当前目录所有文件；`rm -rf *` 更是递归删除目录及其全部内容。当你**不小心**在文件系统的根目录敲下这串字符时，灾难发生了：每个文件每个目录都被移除。哎呀！记住这把双刃剑：强大的命令让你用少量按键做大量工作，也同样能迅速造成巨大伤害。

## 硬链接

现在回到 unlink 之谜。理解它需要先认识一种在文件系统树中创建条目的新方式——`link()` 系统调用。`link()` 接受旧路径名与新路径名两个参数；把新文件名"链接"到旧名上，实际上是**创建了引用同一个文件的另一种方式**。命令行程序 `ln` 用于此：

```
prompt> echo hello > file
prompt> cat file
hello
prompt> ln file file2
prompt> cat file2
hello
```

`link()` 的工作方式：在目标目录中创建另一个名字，让它指向**原文件的同一个 inode 号**（低层名）。文件没有被复制——你只是有了两个都指向同一文件的人类可读名字（file 与 file2）。给 `ls` 加 `-i` 打印 inode 号便可验证：

```
prompt> ls -i file file2
67158084 file
67158084 file2
```

link 真正做的，只是对同一个 inode 号（本例 67158084）建立了一条新引用。

到这里你大概开始明白为什么删除文件叫 unlink 了。创建文件时你其实做了两件事：第一，创建一个结构（**inode**）跟踪文件的几乎所有相关信息——大小、块在磁盘的位置等等；第二，把一个人类可读名**链接**到该文件、放进某个目录。创建硬链接后，文件系统对原名与新名一视同仁——它们都只是指向 inode 67158084 中文件元数据的链接。

因此，从文件系统移除文件就是调用 `unlink()`：删除人类可读名（被删的文件）与给定 inode 号之间的"链接"，并把 inode 中的**引用计数**（reference count，有时称 link count，链接计数）减一；**只有引用计数归零时**，文件系统才释放 inode 及相关数据块、真正"删除"文件。上面的例子中删除 file 后，file2 依然完好：

```
prompt> rm file
removed `file'
prompt> cat file2
hello
```

用 stat 观察链接计数随创建/删除硬链接的变化：

```
prompt> echo hello > file
prompt> stat file
... Inode: 67158084 Links: 1 ...
prompt> ln file file2
prompt> stat file
... Inode: 67158084 Links: 2 ...
prompt> ln file2 file3
prompt> stat file
... Inode: 67158084 Links: 3 ...
prompt> rm file
prompt> stat file2
... Inode: 67158084 Links: 2 ...
prompt> rm file2
prompt> stat file3
... Inode: 67158084 Links: 1 ...
prompt> rm file3     # 计数归零，文件真正被删除
```

## 符号链接

还有一类非常有用的链接：**符号链接**（symbolic link），有时称**软链接**（soft link）。硬链接有些局限：不能对目录创建硬链接（怕在目录树中制造循环）；不能跨磁盘分区硬链接（inode 号只在特定文件系统内唯一）；等等。于是出现了符号链接。

创建符号链接仍用 `ln`，加 `-s` 标志：

```
prompt> echo hello > file
prompt> ln -s file file2
prompt> cat file2
hello
```

表面上看与硬链接差不多：原名与符号链接名都能访问原文件。但深入看，符号链接与硬链接**相当不同**。第一个区别：符号链接**本身就是一个文件**，只是类型不同——文件系统知道三种类型：普通文件、目录、符号链接。对它 stat 一看便知：

```
prompt> stat file
... regular file ...
prompt> stat file2
... symbolic link ...
prompt> ls -al
drwxr-x--- 2 remzi remzi 29 May 3 19:10 ./
drwxr-x--- 27 remzi remzi 4096 May 3 15:14 ../
-rw-r----- 1 remzi remzi 6  May 3 19:10 file
lrwxrwxrwx 1 remzi remzi 4  May 3 19:10 file2 -> file
```

ls 长格式的首字符：`-` 普通文件、`d` 目录、`l` 软链接。file2 为什么是 **4 字节**？因为符号链接的形成方式是：**把被链接文件的路径名作为链接文件的数据**。链接到名为 file 的文件，链接文件就只有 4 字节；链接到更长的路径名，链接文件就更大（如 15 字节的 alongerfilename）。

最后，由于符号链接的创建方式，可能出现所谓**悬空引用**（dangling reference）：

```
prompt> echo hello > file
prompt> ln -s file file2
prompt> cat file2
hello
prompt> rm file
prompt> cat file2
cat: file2: No such file or directory
```

与硬链接截然不同：删除原文件后，符号链接指向的路径名不复存在。

## 权限位与访问控制列表

进程抽象带来了两大虚拟化：CPU 与内存，都让进程产生"私有 CPU/私有内存"的幻觉，实际上 OS 在底下以各种技术在竞争实体间安全地共享有限物理资源。文件系统同样呈现磁盘的虚拟视图——把一堆原始块变成更友好的文件与目录。但这一抽象有个显著不同：文件**通常在不同用户与进程间共享**，并非（总是）私有。因此文件系统通常配备一套更全面的机制来支持不同程度的共享。

第一类机制是经典的 **UNIX 权限位**。看文件 foo.txt 的权限：

```
prompt> ls -l foo.txt
-rw-r--r-- 1 remzi wheel 0 Aug 24 16:29 foo.txt
```

关注开头的 `-rw-r--r--`。首字符表示文件类型（`-` 普通文件、`d` 目录、`l` 符号链接等），与权限无关。真正的**权限位**是随后的九个字符（rw-r--r--），它们决定谁、以何种方式访问每个文件/目录。权限分三组：**所有者**能做什么、**组**成员能做什么、**任何人**（other）能做什么；每组的能力包括读、写、执行。上例中：所有者可读写（rw-），wheel 组成员与其他任何人只读（r-- 与 r--）。

所有者可以用 `chmod`（change file mode）命令轻松更改权限。比如去掉所有者以外任何人的访问能力：

```
prompt> chmod 600 foo.txt
```

这条命令给所有者开读位（4）与写位（2）（按位或得 6），组与其他位置 0——权限变为 rw-------。

**执行位**尤其有趣。对普通文件，它决定程序能否运行：一个 shell 脚本若没有正确设置执行位，运行会得到 "Permission denied."。对**目录**，执行位含义稍有不同：它允许用户（或组、或所有人）`cd` 进入该目录；再配合写位，才能在其中创建文件。最好的学习方式是自己动手玩玩！

权限位之外，一些文件系统（如分布式文件系统 AFS）提供更精细的控制——以**访问控制列表**（ACL，access control list）的形式，通常是每个目录一个 ACL。ACL 是更通用、更强大的"谁能访问哪个资源"表示法：它让用户可以非常精确地指定谁能/不能读一组文件，突破了权限位相对有限的"所有者/组/所有人"模型。例如 AFS 中 `fs listacl private` 显示 system:administrators 与 remzi 都可以对该目录 lookup、insert、delete、administer、read、write、lock；`fs setacl private/ andrea rl` 则可授权他人。

## 制作与挂载文件系统

最后一个话题：如何把**多个底层文件系统**组装成一棵完整目录树？分两步：先**制作**文件系统，再**挂载**使其可访问。

制作文件系统：多数文件系统提供通常称为 `mkfs`（读作 "make fs"）的工具——输入一个设备（如磁盘分区 /dev/sda1）与一个文件系统类型（如 ext3），它就在该分区上写入一个**空文件系统**（从根目录开始）。mkfs 一声令下，文件系统就有了！

但文件系统创建后还需接入统一的文件系统树才能访问。这靠 `mount` 程序（底层调 `mount()` 系统调用）完成：取一个已有目录作为**挂载点**（mount point），把新文件系统"粘贴"到目录树的该位置。比如把存于 /dev/sda1 的 ext3 文件系统（含根目录及子目录 a、b，各有文件 foo）挂到 /home/users：

```
prompt> mount -t ext3 /dev/sda1 /home/users
```

挂载成功后，`ls /home/users/` 列出 `a b`——路径名 /home/users/ 现在指向新挂载文件系统的**根**；a、b 可经 /home/users/a、/home/users/b 访问，foo 则是 /home/users/a/foo 等。**mount 之美**：不再是若干分离的文件系统，mount 把所有文件系统统一为一棵树，使命名统一而便利。运行 `mount` 可查看系统当前挂载了什么、挂在哪：

```
/dev/sda1 on / type ext3 (rw)
proc on /proc type proc (rw)
sysfs on /sys type sysfs (rw)
/dev/sda5 on /tmp type ext3 (rw)
/dev/sda7 on /var/vice/cache type ext3 (rw)
tmpfs on /dev/shm type tmpfs (rw)
AFS on /afs type afs (rw)
```

这一大杂烩表明：ext3（标准磁盘文件系统）、proc（访问进程信息的文件系统）、tmpfs（临时文件专用）、AFS（分布式文件系统）等形形色色的文件系统，都被"胶水"粘到了同一台机器的文件系统树上。

> **技巧：当心 TOCTTOU**
> 1974 年 McPhee 就注意到：若"有效性检查"与"依赖该检查的操作"之间存在时间间隔，多任务环境下检查所依据的变量可能在此间隔内被故意改变，导致控制程序执行无效操作。今天我们称之为 **TOCTTOU**（Time Of Check To Time Of Use，检查时到使用时）问题——它至今仍可能发生。经典示例：以 root 运行的邮件服务把来信追加到用户收件箱前，先 `lstat()` 确认目标确实是该用户的普通文件、而不是不该更新的链接；检查通过后再更新。但检查与更新之间的空隙给了攻击者机会：在恰好的时机把收件箱 rename 成指向 /etc/passwd 之类的敏感文件——服务器就会欢快地把邮件内容写进敏感文件；攻击者由此获得向敏感文件写入的能力（提权！），甚至添加一个 root 权限账号、接管系统。TOCTTOU 没有简单完美的解法：减少需要 root 特权的服务有帮助；`O_NOFOLLOW` 标志让 open() 在目标为符号链接时失败，可避开依赖链接的攻击；更激进的事务性文件系统能根治，但部署不广。所以老生常谈（但正确）的建议是：编写高特权代码时务必小心！

## 小结：关键文件系统术语

- **文件**是可创建、读取、写入、删除的字节数组；有唯一指代它的低层名（数字），常称 **i-number**。
- **目录**是元组的集合，每个元组含人类可读名及其映射到的低层名；条目指向目录或文件；目录自身也有低层名。目录总有两个特殊条目：指向自己的 "." 与指向父目录的 ".."。
- **目录树/层次**把所有文件与目录组织成从根出发的一棵大树。
- 访问文件需先经**系统调用**（通常是 `open()`）向 OS 请求许可；获准后 OS 返回**文件描述符**，用于后续读写。
- 每个描述符是进程私有的实体，指向**打开文件表**的一个条目；条目记录该访问所指的文件、当前偏移（下次读写将访问文件哪个部分）等信息。
- `read()`/`write()` 自然地更新当前偏移；也可用 `lseek()` 显式修改，实现对文件各部分的**随机访问**。
- 要强制把更新写入持久介质，须用 `fsync()` 及相关调用；在保持高性能的同时正确地做到这点颇有挑战，动手前想清楚。
- 要让多个人类可读名指向同一底层文件，用**硬链接**或**符号链接**；各有适用场景，使用前权衡强弱。记住：删除文件只是把它从目录层次中做最后一次 `unlink()`。
- 多数文件系统都有启用/禁用共享的机制：基础形态由权限位提供；更精细的 ACL 允许精确指定谁能访问与操作信息。
