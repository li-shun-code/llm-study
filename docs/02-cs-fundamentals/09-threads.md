前面我们看到了 OS 的基本抽象如何形成：把单个物理 CPU 变成多个虚拟 CPU，制造多程序同时运行的幻觉；为每个进程制造庞大私有虚拟内存的幻觉——地址空间这一抽象让每个程序表现得像独占内存，而实际上 OS 正偷偷在物理内存（有时还有磁盘）上复用地址空间。

本章引入针对单个运行进程的新抽象：**线程**（thread）。经典视角下，程序只有一个执行点（即单个程序计数器 PC，指令从那里取来执行）；而多线程程序有**多个**执行点（多个 PC，各自取指执行）。另一种理解方式：每个线程都很像一个独立的进程，区别只有一点——**它们共享同一个地址空间，因此能访问相同的数据**。

## 线程的状态

单个线程的状态与进程非常相似。它有程序计数器（PC）跟踪取指位置；每个线程有自己私有的寄存器集合用于计算。因此，两个线程 T1、T2 在单个处理器上运行时，从运行 T1 切换到运行 T2 必然发生**上下文切换**：保存 T1 的寄存器状态、恢复 T2 的寄存器状态，然后才能运行 T2。进程之间切换时，状态保存到进程控制块（PCB）；线程之间切换则需要一个或多个**线程控制块**（TCB）来存储进程内每个线程的状态。与进程切换相比，线程上下文切换有一个主要区别：**地址空间保持不变**（不需要切换页表）。

线程与进程的另一个主要区别在于**栈**。经典进程（现在可称为单线程进程）的地址空间里只有一个栈，通常位于地址空间底部。而多线程进程中，每个线程独立运行、各自调用例程，所以**每个线程一个栈**。假如一个进程有两个线程，地址空间就变成两个栈散布其中——任何栈上分配的变量、参数、返回值都会放在所谓**线程本地存储**（thread-local storage）里，即对应线程的栈。

你可能注意到了：这毁掉了原本优美的地址空间布局——以前栈和堆可以各自增长，只有地址空间用尽时才会出问题；现在没这么美好了。幸好通常无妨，因为栈一般不需要很大（重度使用递归的程序除外）：

```
单线程地址空间                 多线程地址空间
┌──────────────┐              ┌──────────────┐
│ 栈            │              │ 栈 (1)        │
│   （空闲）     │              │ 栈 (2)        │
│ 堆            │              │  （空闲）      │
│ 程序代码       │              │  （空闲）      │
└──────────────┘              │ 堆            │
  代码段：指令                  │ 程序代码       │
  堆段：malloc 的动态数据        └──────────────┘
  栈段：局部变量、参数、返回值
```

## 为什么使用线程？

至少有两个主要原因。

**第一个原因很直接：并行**（parallelism）。想象你在写一个对超大数组做运算的程序，比如两个大数组相加、或把数组每个元素加某个值。单处理器上这任务很直白：一项项做完就是了。但如果运行在多处理器系统上，你可以让每个处理器承担一部分工作、显著加速。把标准的单线程程序改造成多 CPU 上并行工作的程序，叫**并行化**（parallelization）；每个 CPU 用一个线程来干活，是在现代硬件上让程序变快的自然而典型的做法。

**第二个原因更微妙：避免程序因慢 I/O 而停顿**。想象你写的程序要做各类 I/O：等待收发消息、等待显式的磁盘 I/O 完成，甚至（隐式地）等待缺页（page fault）处理完。程序与其干等，不如去做点别的——利用 CPU 做计算，甚至发出更多 I/O 请求。使用线程是避免"卡住"的自然方式：当程序中一个线程等待（被 I/O 阻塞）时，CPU 调度器可以切换到其他就绪线程做有用的事。线程让**单个程序内部**的 I/O 与其他活动重叠进行，正如多道程序设计在**多个程序之间**所做的那样；因此许多现代服务器应用（Web 服务器、数据库管理系统等）在实现上都使用线程。

当然，上述两种场景也可以用多个**进程**代替线程。但线程共享地址空间、共享数据轻而易举，是构建这类程序的自然选择；进程更适合逻辑上相互独立、几乎不需要共享内存数据结构的任务。

## 示例：线程创建

看创建两个线程、各打印 "A" 或 "B" 的程序（`t0.c`）：

```c
#include <stdio.h>
#include <assert.h>
#include <pthread.h>
#include "common.h"
#include "common_threads.h"

void *mythread(void *arg) {
    printf("%s\n", (char *) arg);
    return NULL;
}

int
main(int argc, char *argv[]) {
    pthread_t p1, p2;
    int rc;
    printf("main: begin\n");
    Pthread_create(&p1, NULL, mythread, "A");
    Pthread_create(&p2, NULL, mythread, "B");
    // join 等待线程结束
    Pthread_join(p1, NULL);
    Pthread_join(p2, NULL);
    printf("main: end\n");
    return 0;
}
```

主程序创建两个线程，各自运行 `mythread()`、参数不同（字符串 A 或 B）。线程创建后可能立即开始运行（视调度器心情而定），也可能先进入"就绪未运行"状态。多处理器上两个线程甚至真的可能同时运行——这一可能性暂且按下不表。创建完两个线程（记为 T1、T2）后，主线程调用 `pthread_join()` 等待特定线程完成；调用两次，确保 T1 与 T2 都运行并完成后，主线程才继续，打印 "main: end" 并退出。整个程序共有三个线程：主线程、T1、T2。

这个小程序的可能执行顺序不止一种。除了"T1 先跑完再 T2"的顺序，创建的线程也可能立即运行（甚至调度器可能先运行 T2——**没有理由假设先创建的线程先运行**）。把线程创建理解成一次函数调用有点像，但不一样：系统为被调用的例程创建一个**新的执行线程**，它与调用者独立运行——可能在 create 返回前就跑完，也可能很久之后才跑。接下来运行什么是 OS 调度器决定的；调度器虽大概率实现了某种合理的算法，但任何时刻谁在运行**很难预知**。正如你能从这个例子感受到的：线程让一切变复杂——没有并发，计算机已经够难懂了；有了并发，难懂只会更糟，糟得多。

## 更糟的事：共享数据

上面的例子展示了线程的创建与乱序运行，却没展示线程**访问共享数据**时如何相互作用。看两个线程更新一个全局共享变量的程序（`t1.c`）：

```c
#include <stdio.h>
#include <pthread.h>
#include "common.h"
#include "common_threads.h"

static volatile int counter = 0;

// mythread(): 在循环里反复给 counter 加 1
// （不，没人真的这么给计数器加一千万——但它很好地展示了问题）

void *mythread(void *arg) {
    printf("%s: begin\n", (char *) arg);
    int i;
    for (i = 0; i < 1e7; i++) {
        counter = counter + 1;
    }
    printf("%s: done\n", (char *) arg);
    return NULL;
}

// main(): 用 pthread_create 启动两个线程，pthread_join 等待它们

int main(int argc, char *argv[]) {
    pthread_t p1, p2;
    printf("main: begin (counter = %d)\n", counter);
    Pthread_create(&p1, NULL, mythread, "A");
    Pthread_create(&p2, NULL, mythread, "B");
    Pthread_join(p1, NULL);
    Pthread_join(p2, NULL);
    printf("main: done with both (counter = %d)\n",
           counter);
    return 0;
}
```

每个 worker 给共享变量 `counter` 加 1、循环一千万次（1e7），期望的最终结果是 20,000,000。编译运行，有时一切如预期（counter = 20000000）。但即使在单处理器上，也常常得不到期望结果：

```
prompt> ./main
main: begin (counter = 0)
A: begin
B: begin
A: done
B: done
main: done with both (counter = 19345221)
```

再跑一次验证自己没疯（计算机不是应该给出确定性结果吗？）：

```
prompt> ./main
main: done with both (counter = 19221041)
```

不但每次都错，而且**每次错得还不一样**！为什么会这样？

> **技巧：了解并使用你的工具**
> `objdump -d main`（Linux）之类的反汇编器能显示可执行程序由哪些汇编指令构成（配合 `-g` 编译还有符号信息）。除反汇编器外，调试器 gdb、内存分析器 valgrind/purify、编译器本身都值得花时间学习。工具用得越好，能构建的系统就越好。

## 问题的核心：不受控的调度

要理解为什么，必须看编译器为 `counter` 更新生成的指令序列（x86）：

```
mov 0x8049a1c, %eax
add $0x1, %eax
mov %eax, 0x8049a1c
```

假设 `counter` 位于地址 `0x8049a1c`。三条指令：x86 的 `mov` 先把该地址的内存值取到寄存器 `eax`；`add` 给 `eax` 加 1；最后 `mov` 把 `eax` 存回同一内存地址。

设想线程 1 进入这段代码准备递增 `counter`：它把 `counter` 的值（设初始为 50）载入 `eax`，即 `eax=50`；然后寄存器加一，`eax=51`。此时**不幸的事**发生了：时钟中断到来，OS 把当前线程状态（PC、包括 `eax` 在内的寄存器等）保存到 T1 的 TCB。更糟的是：线程 2 被选中运行，进入同一段代码，也执行第一条指令，把 `counter` 取进**自己的** `eax`（记住：每个线程运行时都有私有寄存器——寄存器由上下文切换代码保存与恢复，即被虚拟化）。`counter` 仍是 50，于是 T2 的 `eax=50`；接着 T2 执行后两条指令：`eax` 变 51、把 `eax` 存回 `counter`——全局变量 `counter` 现在是 51。最后又一次上下文切换，线程 1 恢复运行：它刚执行完前两条指令、正要执行最后一条 `mov`；它的 `eax=51`——最后一条指令执行，把 51 又存进内存。**递增代码运行了两次，counter 却只从 50 变成 51**；"正确"的版本本应是 52。

详细追踪一遍（假设代码加载在地址 100 处；x86 指令变长，`mov` 占 5 字节、`add` 占 3 字节）：

| 执行的指令（后） | PC | 线程1 eax | 线程2 eax | counter |
|---|---|---|---|---|
| 进入临界区前 | 100 | 0 | – | 50 |
| mov 8049a1c,%eax (T1) | 105 | 50 | – | 50 |
| add $0x1,%eax (T1) | 108 | 51 | – | 50 |
| ——中断：保存 T1，恢复 T2—— | 100 | 51 | 0 | 50 |
| mov 8049a1c,%eax (T2) | 105 | 51 | 50 | 50 |
| add $0x1,%eax (T2) | 108 | 51 | 51 | 50 |
| mov %eax,8049a1c (T2) | 113 | 51 | 51 | 51 |
| ——中断：保存 T2，恢复 T1—— | 108 | 51 | 51 | 51 |
| mov %eax,8049a1c (T1) | 113 | 51 | 51 | 51 |

我们所演示的称为**竞态条件**（race condition，更准确地说是**数据竞态** data race）：结果取决于代码执行的**时机**。运气不好（上下文切换恰好在尴尬的时点发生），就得到错误结果；而且每次可能不同——我们习惯于计算机给出漂亮的确定性计算，这种结果则称为**不确定**（indeterminate）：输出不可预知、很可能逐次不同。

因为多线程执行这段代码可能引发竞态条件，我们把这段代码称为**临界区**（critical section）：访问共享变量（或更一般地，共享资源）、并且**不得由多个线程同时执行**的代码段。

我们真正想要的性质叫**互斥**（mutual exclusion）：保证一个线程在临界区内执行时，其他线程都被挡在外面。

顺带一提，这些术语几乎都出自 Edsger Dijkstra 之手——这一领域的先驱，并因此项及其他工作获得图灵奖。他 1968 年的论文《Cooperating Sequential Processes》对该问题的阐述清晰得令人惊叹。

> **技巧：使用原子操作**
> 原子操作是构建计算机系统最强大的底层技术之一——从计算机体系结构、并发代码（我们正在学的）、文件系统、数据库管理系统，到分布式系统。把一系列动作做成原子的思想可以用"**要么全做，要么不做**"（all or nothing）概括：这些动作要么看起来全部发生、要么看起来一个都没发生，不存在可被观察到的中间状态。有时把多个动作打包成单个原子动作称为**事务**（transaction）——数据库与事务处理领域将这一思想发展得淋漓尽致。在并发主题中，我们将用**同步原语**把短指令序列变成原子的执行块；但原子性的含义远不止于此——比如文件系统用日志（journaling）或写时复制（copy-on-write）技术原子地迁移其磁盘状态，这是系统故障下正确运转的关键。

## 对原子性的渴望

解决这个问题的一条路是拥有更强大的指令：一步做完需要的一切，从根上排除不合时宜的中断。比如假设有这样一条超级指令：

```
memory-add 0x8049a1c, $0x1
```

它把一个值加到内存位置上，且硬件保证**原子**执行——不可能在指令中途被中断，因为硬件给的保证正是：中断发生时，这条指令要么完全没执行、要么已执行完毕，没有中间状态。硬件是不是很美好？

此处"原子"（atomic）意指"作为一个整体"，有时理解为"全有或全无"。我们真正想要的是**原子地**执行那条三指令序列。但一般情形下我们不会有这样的指令——想象你要构建并发 B 树并更新它：难道希望硬件提供"原子更新 B 树"指令吗？恐怕不希望，至少在理智的指令集里不会。

所以，正确做法是向硬件索要几条**有用的基础指令**，在它们之上构建一整套通用的**同步原语**（synchronization primitives）。借助这些硬件支持，加上操作系统的一些帮助，我们就能编写以同步、受控方式访问临界区的多线程代码，在并发执行如此艰难的条件下依然可靠地产生正确结果。相当酷，对吧？

## 再一个难题：等待彼此

本章把并发问题设定为线程之间唯一的交互是访问共享变量、需要为临界区提供原子性。但实际上还有另一类常见交互：**一个线程必须等待另一个线程完成某动作后才能继续**。比如进程执行磁盘 I/O 后被置为睡眠；I/O 完成时，进程需要被从睡梦中唤醒以继续。因此在后续学习中，我们不仅要研究支持原子性的同步原语，还要研究支持多线程程序中这种睡眠/唤醒交互的机制（提示：条件变量，condition variable）。

> **关键并发术语：临界区、竞态条件、不确定、互斥**
> - **临界区**：访问共享资源（通常是变量或数据结构）的一段代码。
> - **竞态条件**（或数据竞态）：多个执行线程大约同时进入临界区，都试图更新共享数据结构，导致令人意外（可能不合期望）的结果。
> - **不确定**：由一个或多个竞态条件构成的程序；其输出随运行而变，取决于哪个线程何时运行——非确定性，而我们通常期望计算机系统是确定的。
> - 为避免这些问题，线程应使用某种**互斥**原语；它保证任意时刻只有一个线程能进入临界区，从而避免竞态、产生确定的程序输出。

## 小结：为什么在操作系统课上讲这些？

一句话回答：**历史**。OS 是第一个并发程序，许多技术最初就是为 OS 内部创造的；后来随着多线程进程的出现，应用程序员也不得不面对同样的问题。比如两个进程都调用 `write()` 向同一文件追加数据：都要分配新块、在文件的 inode 中记录块位置、更改文件大小（等等）。因为中断随时可能发生，更新这些共享结构（分配位图、文件 inode 等）的代码都是临界区——自中断被引入之日起，OS 设计者就得操心 OS 内部结构的并发更新；不合时宜的中断会引发上述一切问题。毫不意外，页表、进程列表、文件系统结构乃至几乎每个内核数据结构，都必须以恰当的同步原语小心访问才能正确工作。你写的多线程应用同理——这也就是为什么每个后端工程师都需要懂并发。
