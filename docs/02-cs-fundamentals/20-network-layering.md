开始之前，先认识几个术语：

- **IP 地址（IP Address）**——历史上是 4 字节数字，唯一标识互联网上你的计算机。以"点分数字"记法书写，如 `198.51.100.99`。这是 IP 第 4 版（IPv4）地址；没有特别注明版本号时，通常默认指 v4。
- **端口（Port）**——程序通过端口通信，端口编号 0–65535，与 TCP 或 UDP 协议关联。同一个 IP 地址上可能同时运行多个程序，端口提供了在网络上唯一标识这些程序的方式。比如 Web 服务器监听 80 端口等待连接就非常常见。对服务器程序来说，公布端口号至关重要，因为客户端程序得知道往哪连；而客户端通常让 OS 随便挑一个未用端口——因为没人会主动来连客户端。URL 里端口号跟在冒号后面：`http://example.com:3490/foo.html` 表示连到 `example.com` 的 `3490` 端口。1024 以下的端口绑定需要 root/管理员权限（连接则不需要）。
- **TCP**——传输控制协议（Transmission Control Protocol），负责可靠的、按序的数据传输。往高处说，它让分组交换网络的感觉更接近电路交换网络。TCP 用端口号标识数据的发送者与接收者。这个协议发明于 1974 年，至今仍被海量使用。在套接字 API 中，TCP 套接字叫**流套接字**（stream sockets）。
- **UDP**——TCP 的兄弟，但更轻量。它不保证数据到达、不保证按序、也不保证不重复；如果数据到了，那它就是无差错的——但你能得到的也就这么多。套接字 API 里 UDP 套接字叫**数据报套接字**（datagram sockets）。
- **IPv6 地址**——4 字节不够给每台计算机发唯一地址了，于是 IP 第 6 版把地址大幅扩展到 16 字节。IPv6 地址长这样：`::1`、`2001:db8::8a2e:370:7334`，或者更长。
- **NAT**——网络地址转换（Network Address Translation）。一种让组织使用拥有非全局唯一地址的私有子网、而在数据经过路由器时翻译成全局唯一地址的机制。私有子网常以 `192.168.x.x` 或 `10.x.x.x` 开头。
- **路由器（Router）**——在分组交换网络中转发数据包的专用计算机。它检查目的 IP 地址，决定走哪条路由能让包更接近目标。
- **IP**——网际协议（Internet Protocol）。负责以 IP 地址标识计算机，并使用这些地址、经由一众路由器把数据路由给接收者。
- **LAN**——局域网（Local Area Network）。所有计算机实际上直接相连（不经路由器）的网络。
- **接口（Interface）**——计算机上的物理网络硬件。一台计算机可能有多个接口：你的电脑多半有两个——有线以太网接口与无线以太网接口。路由器可能有大量接口以便把包路由到大量目的地；你家的路由器大概只有两个接口：一个朝内对着你的 LAN，一个朝外对着整个互联网。每个接口通常有一个 IP 地址和一个 MAC 地址。接口的名字由 OS 起名，可能叫 `wlan0`、`eth2` 或别的什么——取决于硬件与 OS。
- **头部（Header）**——某个协议附加在其他数据前面的数据，包含适合该协议的信息。TCP 头部会带一些检错纠错信息和源/目的端口号；IP 头部带源/目的 IP 地址；以太网头部带源/目的 MAC 地址；HTTP 响应头部则会带数据长度、修改日期、请求是否成功之类。把头部加在数据前面，就好比把信装进信封（蜗牛邮递类比）；或者把信封再装进另一个信封。数据流经网络时，头部被不断添加和摘除。正常操作中通常只摘除/添加最顶上的头，像一个栈。（不过有些软硬件会往深处偷看。）
  - **网络适配器**（Network Adapter）——"网卡"的另一个名字，计算机上负责网络的硬件。
  - **MAC 地址**——以太网接口有 MAC 地址，形如 `aa:bb:cc:dd:ee:ff`，各字段是近似随机的单字节十六进制数。MAC 地址 6 字节长，必须在 LAN 内唯一。网卡出厂时会被赋予一个终身唯一的 MAC 地址。

## 4.1 分层网络模型

当你通过互联网发送数据时，数据被**封装**（encapsulate）进不同层次的协议中。概念化的分层网络模型中的各层，对应着各类协议；这些协议各司其职：描述数据、保证数据完整性、路由、本地投递等等。

这有点先有鸡还是先有蛋：不谈协议就说不清分层，不谈分层也说不清协议。最好的办法是直接潜下去，看看协议们如何把各自的头部叠在某些数据上。

## 4.2 实例：协议在数据上的分层

考虑一次 HTTP 请求发生了什么。

1. 浏览器构造出这样的 HTTP 请求：

   ```
   GET / HTTP/1.1
   Host: example.com
   Connection: close
   ```

   这就是浏览器关心的全部。它不关心 IP 路由、不关心 TCP 数据完整性、更不关心以太网。它只说："把这些数据发给那台计算机的 80 端口。"

2. OS 接手："好，你让我通过流式套接字发送，我将使用 TCP 协议，确保所有数据完好且按序到达。"于是 OS 把 HTTP 数据裹进一个**带端口号**的 TCP 头部。

3. OS 又说："你还要把它发给那台 IP 地址为 198.51.100.2 的远程计算机，所以用 IP 协议来办。"它把整个 TCP-HTTP 数据再裹进一个 IP 头部。现在数据长这样：**IP-TCP-HTTP**。

4. 然后 OS 查路由表决定下一步发到哪。可能 Web 服务器恰好就在 LAN 上；更可能在别处，那么数据将被发给家里的路由器、奔向更广阔的互联网。无论哪种，数据都要先发给 LAN 上的某台计算机（本地 Web 服务器，或出口路由器）。LAN 上的计算机有以太网地址（又称 **MAC 地址**——Media Access Control 的缩写），因此发送方 OS 查出下一个目的 IP 对应的 MAC 地址（通过所谓 **ARP 缓存** 的查找——这段故事改日再讲），并把整个 IP-TCP-HTTP 包裹进以太网头部，成为 **Ethernet-IP-TCP-HTTP**。Web 请求还在里面，只是被一层层协议埋在下面！

5. 最后，数据上线传输（哪怕是 WiFi，我们也说"上线"）。

目的 MAC 地址对应的那台计算机仔细监听着，看到线缆上的以太网包、把它读进来（以太网包称为**以太网帧**，Ethernet frame）。它剥掉以太网头部，露出下面的 IP 头部，看目的 IP 地址：

1. 如果检查者就是那台服务器、拥有这个 IP，其 OS 剥掉 IP 头部、继续深挖。（如果没有这个 IP，出问题了，丢包。）
2. 它看 TCP 头部，做所有 TCP 魔法以确保数据没坏；坏了就用 TCP 的魔法咒语回话："麻烦把那些数据再发一遍。"注意：Web 浏览器或服务器**完全不知道**这场 TCP 对话——都在幕后。在它们看来，数据就是完好、按序地"魔法般"抵达的。原因在于它们位于网络的更高层，不必操心路由或别的什么——低层包办了这一切。
3. TCP 一切正常，头部被剥掉，OS 手里剩下 HTTP 数据。它唤醒等待读取的进程（Web 服务器），把 HTTP 数据交给它。

但如果目的以太网地址是**中间路由器**呢？

1. 路由器照例剥掉以太网帧。
2. 路由器看目的 IP 地址，查路由表，决定从哪个接口转发该包。
3. 它把包从那个接口发出去——接口又把它裹进一个新的以太网帧、发给下一跳路由器。（也可能根本不是以太网！以太网只是一个协议，光纤等链路上还有别的低层协议。这正是分层抽象之美——你可以在传输中途切换协议，而上面的 HTTP 数据对发生的这一切浑然不觉。）

## 4.3 互联网分层模型

先看较简单的模型——自顶向下把传输过程拆成不同层次（协议清单远非穷尽）：

| 层 | 职责 | 示例协议 |
|---|---|---|
| 应用（Application） | 结构化的应用数据 | HTTP, FTP, TFTP, Telnet, SSH, SMTP, POP, IMAP |
| 传输（Transport） | 数据完整性、分包与重组 | TCP, UDP |
| 互联网（Internet） | 路由 | IP, IPv6, ICMP |
| 链路（Link） | 物理层、线缆上的信号 | Ethernet, PPP, token ring |

可以看到不同协议如何在模型中承担各层职责。另一种理解：所有实现 HTTP、FTP 或 SMTP 的程序都可以用 TCP 或 UDP 来传输数据（你写的所有套接字程序与实现任何协议的应用，通常都住在应用层）；所有经 TCP 或 UDP 传输的数据都可以用 IP 或 IPv6 做路由；所有用 IP/IPv6 路由的数据都可以用以太网或 PPP 等上线传输。

数据包在被发送上线之前**向下穿层**，每层的协议把各自的头部叠在目前为止的一切之上。这个模型对在互联网上干活来说足够复杂了——常言道：尽可能简单，但不能更简单。

不过宇宙中可能还有非互联网的网络，所以还有一个更通用的模型：OSI 模型。

## 4.4 ISO OSI 网络分层模型

如果你要考认证、或者要做的比普通程序员更深入（比如面网络岗），这个模型值得掌握。

互联网分层模型是这个更细致的模型——**ISO OSI 模型**（国际标准化组织开放系统互连模型；"ISO" 并非该组织英文名的直接缩写，但我没有足够的全球政治影响力去改变它）——的一个特例。

回到现实：OSI 模型就像互联网模型，只是更细粒度。互联网模型的单层映射到 OSI 模型的多层，对应如下：

| ISO OSI 层 | 互联网层 |
|---|---|
| 应用（Application） | 应用 |
| 表示（Presentation） | 应用 |
| 会话（Session） | 应用 |
| 传输（Transport） | 传输 |
| 网络（Network） | 互联网 |
| 数据链路（Data link） | 链路 |
| 物理（Physical） | 链路 |

看看 OSI 模型，同样能列出各层上存在的协议与职责，与我们看互联网模型时类似：

| ISO OSI 层 | 职责 | 示例协议 |
|---|---|---|
| 应用 | 结构化的应用数据 | HTTP, FTP, TFTP, Telnet, SMTP, POP, IMAP |
| 表示 | 编码转换、加密、压缩 | MIME, SSL/TLS, XDR |
| 会话 | 挂起、终止、重启计算机间的会话 | Sockets, TCP |
| 传输 | 数据完整性、分包与重组 | TCP, UDP |
| 网络 | 路由 | IP, IPv6, ICMP |
| 数据链路 | 封装成帧 | Ethernet, PPP, SLIP |
| 物理 | 物理层、线缆上的信号 | Ethernet 物理层, DSL, ISDN |

本课程（指南）将坚持使用互联网模型——对你可能做过的 99.9% 的网络编程工作而言它已经够用。但若你去面试网络方向的编程职位，请务必了解 OSI 模型。

## 4.5 思考题

- 路由器看到一个 IP 地址时，如何知道该把它转发到哪？
- 若 IPv4 地址是 4 字节，假设每台计算机地址唯一，总共大约能表示多少台计算机？
- 同样的问题，换成 16 字节地址的 IPv6 呢？
- 给统计迷的加分题：中超级乐透头奖的赔率约为 3 亿分之一；随机猜中我预设的 16 字节（128 位）数字的赔率是多少？
- 猜测一下：为什么在分层模型中是 IP 头部包住 TCP 头部，而不是反过来？
- 既然 UDP 不可靠而 TCP 可靠，猜测一下人们为什么有时还会用 UDP。

> 译注：后两个思考题分别对应本模块后续两篇《TCP》与《UDP》——"谁包住谁"体现的是依赖方向（传输层依赖网络层完成路由），而 UDP 的用武之地（低延迟、可容忍少量丢失的流媒体、DNS 查询等）也将在 UDP 篇中展开。
