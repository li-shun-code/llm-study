《Claude Skills：可复用技能包》讲的是机制——一个带 frontmatter 的 `SKILL.md` 怎么被自动加载。机制清楚之后，真正的问题是：**别人用这套机制造出了什么值得抄的东西？** 开源技能族很多，但绝大多数只是"提示词片段"；有一套例外，它把**整个软件开发流程**写成了技能：Jesse Vincent 的 **Superpowers**（obra/superpowers）。它不教 Claude 某项具体技术，而是强制规定智能体**该按什么顺序干活**——先头脑风暴拿批准、再写计划、每个任务派一个全新子智能体、红-绿 TDD、任务间评审、无证据不许宣布完成。

本系列按技能族拆成三篇，可以独立阅读：

- 本篇：**编码流程族**——Superpowers 的 14 个流程技能，回答"编码智能体该怎么干活"；
- 《开源编码 Skills（二）：技能写作与文档协作族》——**作者与文档族**，两门"写技能的技能"与长文档协作写法；
- 《开源编码 Skills（三）：工具集成族》——**工具集成族**，MCP 服务器构建、Web 应用测试、前端构建与 Claude API 开发。

> 时效注记：本节正文依据 2026-09-13 抓取的仓库 `README.md` 与 `skills/` 下各 `SKILL.md`（MIT 许可）。2026-09-19 复核仓库时 `skills/` 目录下已有 **15** 个技能：新增 `diagnosing-superpowers`（会话出问题时做取证的诊断技能，本篇最后一节补译），其余 14 个未变。Superpowers 的安装与触发方式随宿主演进很快，动手前请以官方仓库为准。

## 一、这套技能族是什么

*本节及下文各技能小节译自 [obra/superpowers](https://github.com/obra/superpowers) 仓库 README 与 `skills/` 目录下各技能的 `SKILL.md`（raw 抓取）。仓库许可：MIT。*

### 项目是什么

> **Superpowers** 是为你的编码智能体准备的**一套完整软件开发方法论**，构建在一组可组合的技能（skills）和一些初始指令之上——正是这些初始指令确保你的智能体真的会去使用这些技能。

**工作原理（How it works）**：

它从你启动编码智能体的那一刻就开始生效。一旦它发现你要构建点什么，它*并不*会一头扎进去写代码，而是先退后一步，问你真正想做的是什么。

等它从对话里一点点"磨"出一份规格说明（spec）之后，会把规格分成足够短的小块展示给你——短到你可以真的读完并消化。

在你签字确认设计之后，你的智能体会整理出一份实现计划，这份计划要清晰到足以让"一个热情高涨但品味堪忧、没有判断力、没有项目上下文、还讨厌写测试的初级工程师"照着执行。它强调真正的红/绿 TDD、YAGNI（You Aren't Gonna Need It，你不会需要它）与 DRY。

再往后，一旦你说"开始"，它就会启动*子智能体驱动开发*（subagent-driven-development）流程：让智能体逐个完成工程任务，检查并评审它们的产出，然后继续推进。你的智能体一次自主连续干上几个小时、却不偏离你们一起定的计划——这种情况并不罕见。

这套系统还有更多内容，但以上就是核心。而且由于技能是自动触发的，你不需要做任何特别的事。你的编码智能体就是"自带超能力"（has Superpowers）。

### 基本工作流（The Basic Workflow）

*译自 README 全节。这 7 步同时也是下面 14 个技能的"出场顺序"。*

1. **brainstorming**——在写代码之前激活。通过提问打磨粗略想法、探索备选方案、分节呈现设计以供确认，并保存设计文档。
2. **using-git-worktrees**——设计获批后激活。在新分支上创建隔离工作区，运行项目初始化，验证测试基线干净。
3. **writing-plans**——拿着获批的设计激活。把工作拆成一口大小的任务（每个 2-5 分钟）。每个任务都有精确的文件路径、完整的代码、验证步骤。
4. **subagent-driven-development** 或 **executing-plans**——拿着计划激活。前者为每个任务派出全新子智能体并做两段评审（先规格符合性、后代码质量）；后者分批执行、设人工检查点。
5. **test-driven-development**——实现过程中激活。强制红-绿-重构：写失败测试、亲眼看它失败、写最少代码让它通过、提交。先于测试写出的代码一律删除。
6. **requesting-code-review**——任务之间激活。对照计划评审，按严重程度上报问题。Critical 问题阻塞继续。
7. **finishing-a-development-branch**——任务全部完成时激活。验证测试，呈现选项（合并/PR/保留/丢弃），清理工作树。

**智能体在任何任务之前都会检查有无相关技能。这些是强制工作流，不是建议。**

**设计理念（Philosophy）**：

- **测试驱动开发**——永远先写测试
- **系统化优先于临时起意**——靠流程而不是靠猜
- **降低复杂度**——简洁是首要目标
- **证据优先于声称**——宣布成功之前先验证

## 二、十四个流程技能逐个详解

下面按"出场顺序"逐个给出每个技能的 `description`（决定它何时被自动加载）与核心流程。**这些是流程约束而非可选建议**——这也是这套技能族与散装的"提示词技巧"最本质的差别。

### using-superpowers——技能系统的"总开关"

> **description（全译）**：在开始任何对话时使用——确立如何查找和使用技能，要求在*任何*回应（包括澄清性提问）之前先调用技能。

*本技能正文较短，以下为全文翻译（省略平台参考文件清单两行）。*

开头的 `SUBAGENT-STOP` 块声明："如果你是作为子智能体被派来执行特定任务的，请忽略本技能。"

紧接着的 `EXTREMELY-IMPORTANT` 块是整个 Superpowers 的语气基线：

> 如果你认为哪怕有 1% 的可能性某个技能适用于你正在做的事，你就**绝对必须**调用该技能。如果技能适用于你的任务，你别无选择，必须使用它。这没有商量余地。你无法靠自我说服绕开这一点。

**规则**：**在任何回应或行动之前，先调用相关或被要求的技能**——包括澄清性提问、探索代码库、查看文件。如果事后发现它不适合当前情况，你可以不用它。**进入计划模式之前**：如果还没做过头脑风暴，先调用 brainstorming 技能。然后宣布"使用 [技能] 来 [目的]"，并严格遵循该技能；如果它有检查清单，就为每一项建一个 todo。

**技能优先级**：多个技能同时适用时，*流程技能*先行——它们设定方法，*实现技能*（如 frontend-design）随后执行。"我们来构建 X" → 先 superpowers:brainstorming，再实现技能；"修这个 bug" → 先 superpowers:systematic-debugging，再领域技能。

**红旗（Red Flags）表**——出现这些念头说明你在找借口，该停了：

| 念头 | 现实 |
|---------|---------|
| "这只是个简单问题" | 问题就是任务。检查技能。 |
| "我需要先了解更多上下文" | 技能检查在澄清提问*之前*。 |
| "让我先探索一下代码库" | 技能告诉你*怎么*探索。先查技能。 |
| "我先快速看下 git/文件" | 文件缺少对话上下文。先查技能。 |
| "我先收集些信息" | 技能告诉你*怎么*收集信息。 |
| "这不需要正式技能" | 有技能就用。 |
| "我记得这个技能" | 技能会演进。读当前版本。 |
| "这不算个任务" | 行动=任务。检查技能。 |
| "这个技能太小题大做" | 简单的事会变复杂。用它。 |
| "我先干这一件事" | 干任何事*之前*先查技能。 |
| "感觉挺有产出" | 无纪律的行动浪费时间。技能防的就是这个。 |
| "我知道那是什么意思" | 知道概念≠用技能。调用它。 |

**用户指令**：用户指令（CLAUDE.md、AGENTS.md、GEMINI.md 等及直接请求）优先于技能，技能又覆盖默认行为。只有人类伙伴明确让你跳过时，才可以跳过技能工作流或指令。

### brainstorming——把想法磨成设计

> **description（全译）**：任何创造性工作之前你**必须**使用本技能——创建功能、构建组件、添加能力或修改行为。在实现之前探索用户意图、需求与设计。

*正文较长（约 250 行，含 dot 流程图），以下译核心流程并注明节选；原文其余部分为示例与图示。*

**硬闸门（HARD-GATE）**：在你把意图告诉人类伙伴并获得批准之前，**不得**调用任何实现类技能、不得写任何代码、不得搭任何项目脚手架、不得采取任何实现动作。这对下面每条路径上的**每个**任务都成立——仪式感可以随任务缩放，批准闸门永远不能缩。

**三条路径**——在问第一个问题之前先给请求分类，并把分类*说出口*（"这个看起来是有界的，所以我在对话里给个简短设计就行，不用写规格"），让人类伙伴可以否决：

- **Spike（技术探针）**——可行性问题（"我们能不能……""有没有可能……""粗糙点没关系"），产出是一个答案，不是留下的代码。用 2-3 句话呈现问题与试探方案，得到点头后，以正确性允许的最廉价方式去探明。没有设计文档、没有 spec 文件；以建议形式报告发现，任何建出来的东西都标注为"一次性的"。
- **Bounded（有界）**——对仓库中已有代码的范围明确的改动：新开关、小端点、单文件修复。光了解这类应用不够——"有界"意味着你要改的流程*在这个仓库里已经有现成代码可读*。如果没有可改的既有流程，这个任务就不是有界的。问清关键问题，**在对话里**呈现一个简短设计（几句话到几小段），然后**停下**。只有人类伙伴对这个设计说"好"，实现才开始——有界任务的批准闸门和架构级一样硬。没有 spec 文件，没有实现计划文档。
- **Architectural（架构级）**——新项目、新子系统、会重构组件组合方式或改动他人依赖的接口的变更。走完整流程：提问、方案、分节设计、书面 spec，然后进入 writing-plans 技能。

两条路径之间拿不准时，选更重的那条。这个棘轮是单向的：任务中途发现的隐藏复杂度会*升级*路径——停下来说明情况，然后升级；任何路径都不会在任务中途降级。

**反模式："简单到不需要批准"**：每条路径都以人类伙伴批准你的意图、实现才开始告终。一个 todo 列表、一个单函数工具、一处配置改动——设计可以是对话里两句话，但你必须呈现并获得批准。"简单"任务恰恰是未经检验的假设造成最多返工的地方。随简单性缩放的是*产物*，永远不是批准。

**红旗表**（全译）：

| 念头 | 现实 |
|---------|---------|
| "这太简单了，不需要设计" | 简单意味着*短*设计，不是没设计。对话里两句话，然后求批准。 |
| "我就叫它有界，跳过 spec" | 试图靠标签跳过工作*本身就是*疑号——选更重的路径。 |
| "有界且设计显然——他们读的时候我就开工" | 闸门是批准，不是设计长度。呈现，然后停，直到听见"好"。 |
| "我懂这类应用，所以有界" | 有界衡量的是仓库，不是你的熟悉度。新项目没有既有流程——它是架构级。 |
| "探针能跑，所以代码留下" | 探针的产出是答案。留下代码是个新请求——重新分类。 |
| "它变大了，但我快做完了——不用重新分类" | 隐藏复杂度会在任务中途升级路径。停下来说明。 |
| "探针都批了，后续改动肯定也批了" | 每个任务都有自己的分类和自己的批准。 |

**检查清单**（全译）：先分类、宣布路径，然后为路径上的每一项建任务并按序完成。

- **Spike**：①探索项目上下文（足以框定探针即可）→ ②呈现问题+探针方案（2-3 句）→ ③获批准（点头即可）→ ④调查（以正确性允许的最廉价方式）→ ⑤报告发现（一条建议；建出的东西标注为一次性）。
- **Bounded**：①探索项目上下文（查文件、文档、近期提交）→ ②问澄清问题（一次一个，问要紧的）→ ③在对话里呈现简短设计（方法、涉及文件、测试）→ ④获批准（**停下**等明确的"好"；边呈现边开工就是跳闸）→ ⑤实现（按正常开发工作流，TDD 适用；不写计划文档）。
- **Architectural**：①探索项目上下文 → ②*适时*提供可视化伴侣（不要一上来就提；见下）→ ③问澄清问题（一次一个，弄清目的/约束/成功标准）→ ④提出 2-3 个方案（带权衡与你的推荐）→ ⑤分节呈现设计（每节篇幅与复杂度相称，每节后求确认）→ ⑥写设计文档，存到 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 并提交 → ⑦spec 自审（快速内联检查占位符、矛盾、歧义、范围）→ ⑧请用户评审书面 spec → ⑨转入实现（调用 writing-plans 技能）。

**过程要点**（各小节全译）：

- *理解想法*：先查看项目现状（文件、文档、近期提交）；在问细节问题之前先评估范围——如果请求描述了多个独立子系统（"做一个带聊天、文件存储、计费和分析的平台"），立刻指出，先分解再细化；项目大到单份 spec 装不下时，帮用户拆成子项目（哪些是独立件、如何关联、按什么顺序建），每个子项目走自己的 spec→计划→实现循环；规模合适的项目则一次只问一个问题来打磨想法，尽量用选择题，每条消息只问一个问题；聚焦理解目的、约束、成功标准。
- *探索方案*：提出 2-3 个带权衡的不同方案；以对话方式呈现选项、给出推荐与理由；把推荐方案放在最前并解释为什么；无情贯彻 YAGNI——从每个方案和设计中砍掉不必要的功能。
- *呈现设计*：确认理解后呈现设计；每节篇幅与复杂度相称（直白的几句话，繁复的最多 200-300 词）；每节之后问"到目前为止对吗"；覆盖架构、组件、数据流、错误处理、测试；随时准备回头澄清。
- *为隔离与清晰而设计*：把系统拆成更小的单元——每个单元目的单一、通过清晰定义的接口通信、可独立理解与测试；对每个单元要能回答：它做什么、怎么用、依赖什么；较小的、边界良好的单元也更好合作——一次能装进上下文的代码你推理得更好，文件聚焦时编辑更可靠；文件长得过大往往说明它干了太多事。
- *在既有代码库中工作*：先探索现状再提改动，遵循既有模式；既有代码里影响本工作的问题（文件过大、边界不清、职责纠缠）可以有针对性地纳入设计——好程序员都会顺手改进自己正在改的代码；但不要提无关重构，聚焦于服务当前目标。

**设计之后（architectural 路径）**：写 spec 并提交 git；spec 自审四项——占位符扫描（有无 TBD/TODO/含糊需求）、内部一致性（各节有无矛盾、架构与功能描述是否匹配）、范围检查（能否撑起单个实现计划）、歧义检查（有没有需求能被读出两种意思）；然后请用户评审书面 spec（原话："Spec 已写入并提交到 `<路径>`。请审阅，如果开始写实现计划前想改什么请告诉我"），等用户回复，要求改动就改完重跑自审，用户批准才继续；实现阶段**只**调用 writing-plans 技能，不调用其他任何技能。

**可视化伴侣（Visual Companion）**：一个浏览器伴侣，用于在头脑风暴中展示 mockup、图表与视觉选项。它是工具不是模式——**不要**一上来就提供；等某个问题"画出来比说出来真的更清楚"时再第一次提出（且必须单独成一条消息），用户接受才开服务器（`--open` 自动打开浏览器标签页），拒绝就全程纯文本且不再主动提。即便接受后，每个问题仍要单独判断用浏览器还是终端：视觉内容（mockup、线框、布局对比、架构图）用浏览器，文本内容（需求问题、概念选择、权衡清单、范围决策）用终端——"UI 话题的问题"不等于"视觉问题"。

### writing-plans——写给"零上下文工程师"的实现计划

> **description（全译）**：当你已有规格说明或需求、要开始多步骤任务、还没碰代码时使用。

*正文较长，以下译核心流程（原文的示例计划头与任务结构模板以代码块保留）。*

**概览（全译）**：编写全面的实现计划，*假设执行工程师对我们的代码库零上下文、品味存疑*。把他们需要知道的一切写成文档：每个任务动哪些文件、代码、测试、可能要查的文档、怎么测。把整个计划拆成一口大小的任务。DRY、YAGNI、TDD、频繁提交。假设他们是熟练开发者，但对我们的工具链和问题域几乎一无所知，也不太懂好的测试设计。

开场宣布："I'm using the writing-plans skill to create the implementation plan."（我正在使用 writing-plans 技能创建实现计划。）计划保存到 `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`（用户偏好可覆盖此默认位置）。

**范围检查**：如果 spec 覆盖多个独立子系统，建议拆成多份计划——每份计划都应能独立产出可运行、可测试的软件。

**文件结构**：定义任务之前，先画出要创建/修改哪些文件、各自负责什么——分解决策在这里锁定。设计边界清晰、接口定义良好的单元，每个文件一个清晰职责；一起变化的文件放在一起，按职责而不是技术分层拆分；在既有代码库中遵循既有模式——但如果你要改的文件已经臃肿，把拆分纳入计划是合理的。

**任务尺寸**：任务是"携带自己的测试循环、且值得一个全新评审者把关"的最小单元。画任务边界时：把准备、配置、脚手架、文档步骤折叠进需要它们的交付任务；只在"评审者可能拒掉这个任务却批准相邻任务"的地方才拆分。每个任务以可独立测试的交付物收尾。

**一口大小的粒度**——每步一个动作（2-5 分钟）："写失败测试"是一步；"运行确认它失败"是一步；"写最少量代码让测试通过"是一步；"运行测试确认通过"是一步；"提交"是一步。

**计划文档头**——每个计划必须以此开头：

```markdown
# [功能名] 实现计划

> **给智能体执行者**：必需子技能：使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 逐任务实现本计划。步骤使用复选框（`- [ ]`）语法跟踪。

**目标：** [一句话描述构建什么]

**架构：** [2-3 句方法]

**技术栈：** [关键技术/库]

**规格：** [本计划实现的 spec/设计文档路径——计划从 spec 出发论证，
spec 随计划一起走；执行者两份都读]

## 全局约束

[spec 中项目级的要求——版本下限、依赖限制、命名与文案规则、平台要求——
每行一条，精确值从 spec 原样复制。每个任务的要求隐式包含本节。]
```

**任务结构**（原文模板节选）：

````markdown
### 任务 N：[组件名]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 消费：[本任务用到的前序任务产物——精确签名]
- 产出：[后续任务依赖的东西——精确函数名、参数与返回类型。
  任务的实现者只看得到自己的任务；这个区块就是他们了解邻近任务
  名称与类型的途径。]

- [ ] **步骤 1：写失败测试**（附完整测试代码）
- [ ] **步骤 2：运行测试验证失败**（运行命令与预期失败信息）
- [ ] **步骤 3：写最小实现**（附完整实现代码）
- [ ] **步骤 4：运行测试验证通过**
- [ ] **步骤 5：提交**（附 git 命令）
````

**禁止占位符**——以下都是**计划缺陷**，永远不要写："TBD""TODO""以后实现""补充细节"；"加适当的错误处理/校验/边界情况处理"；"为上述内容写测试"（却不给测试代码）；"类似任务 N"（把代码重复写出来——执行者可能乱序阅读）；只说做什么不展示怎么做；引用任何任务中都未定义的类型/函数/方法。

**自审**：写完计划后以全新眼光对照 spec 检查——①spec 覆盖：逐节能否指到实现它的任务，列出缺口；②占位符扫描：搜上述红旗模式并修掉；③类型一致性：后段任务用到的类型/签名/属性名与前段定义的是否一致（任务 3 里叫 `clearLayers()`、任务 7 里变成 `clearFullLayers()` 就是 bug）。发现问题直接内联修掉即可。

**执行交接**：保存计划后提供两个执行选项——**1. 子智能体驱动（推荐）**：每个任务派全新子智能体、任务间评审、快速迭代（必需子技能 superpowers:subagent-driven-development）；**2. 内联执行**：用 executing-plans 在本会话分批执行、设检查点（必需子技能 superpowers:executing-plans）。问用户选哪种。

### executing-plans——独立会话分批执行（全文翻译）

> **description（全译）**：当你有一份书面实现计划、要在独立会话中带评审检查点地执行时使用。

**概览**：加载计划、批判性评审、执行全部任务、完成后报告。

开场宣布："I'm using the executing-plans skill to implement this plan."（我正在使用 executing-plans 技能实现这份计划。）

**注意**：告诉人类伙伴，Superpowers 在有子智能体的情况下效果好得多（Claude Code、Codex CLI、Codex App、Copilot CLI、Gemini CLI 都符合；各平台工具参考见 `../using-superpowers/references/`）。如果子智能体可用，请改用 superpowers:subagent-driven-development，不要用本技能。

**流程**：

*第一步：加载并评审计划*——①确保有隔离工作区：用 superpowers:using-git-worktrees 创建或验证现有的；②读计划文件；③批判性评审——找出对计划的疑问或担忧；④有担忧：开工前先向人类伙伴提出；⑤无担忧：为计划条目建 todo 并继续。

*第二步：执行任务*——对每个任务：标记 in_progress → 严格按每一步执行（计划是口大小的小步）→ 按规定运行验证 → 标记 completed。

*第三步：完成开发*——全部任务完成并验证后：宣布"我正在使用 finishing-a-development-branch 技能收尾这项工作"；**必需子技能**：使用 superpowers:finishing-a-development-branch——按该技能验证测试、呈现选项、执行选择。

**何时停下求助**——遇到以下情况**立即停止执行**：碰到阻塞（缺依赖、测试失败、指令不清）；计划有关键缺口无法开工；你不理解某条指令；验证反复失败。**宁可问清，不要猜。**

**何时回到早期步骤**——伙伴根据你的反馈更新了计划、或根本方法需要重新思考时，回到第一步的评审。**不要硬闯阻塞点**——停下来问。

**记住**：先批判性评审计划；严格按计划步骤执行；不跳过验证；计划让引用技能时就引用；被阻塞就停，不猜；未经用户明确同意绝不在 main/master 分支上直接开始实现。

### subagent-driven-development——子智能体驱动开发（本族最大的技能）

> **description（全译）**：在当前会话中执行包含独立任务的实现计划时使用。

*正文约 570 行（含大幅流程图与提示词模板引用），以下译核心流程并注明节选。*

一句话概括：**每个任务派一个全新的实现者子智能体，每个任务之后做一次任务评审（规格符合性+代码质量），最后做一次覆盖整个分支的大评审。**

**为什么用子智能体**：你把任务委托给拥有隔离上下文的专门智能体。通过精心构造它们的指令与上下文，确保它们保持专注、完成任务。它们*绝不应该*继承你会话的上下文或历史——你要精确构造它们需要的东西。这也为你自己的上下文留出协调工作的空间。

**核心原则**：每任务全新子智能体 + 任务评审（规格+质量）+ 最终大评审 = 高质量、快迭代。

**连续执行**：不要在任务之间停下来向人类伙伴签到。除了下面点名的四件事或全部任务完成，不要停。"要继续吗？"之类的提示和进度汇总浪费他们的时间——他们让你执行计划，你就执行。

**做裁决，不要停摆**：运转中的计划不等人类。冲突、歧义、计划缺陷、一个你本想请示才能突破的上限——*裁决*它们。spec 是约束性权威，计划是它的论证，两者都没回答的由你的判断定。把每个决定记进台账（ledger），格式为 `Ruling: <你决定了什么> — <为什么> — <错了代价是什么>`，然后继续。一个错误裁决的代价是伙伴看得见、能回退的返工；一个停在问题上的会话浪费他们一整天却一无所获。**只有四件事能让你停下**：不可逆或破坏性操作；安全敏感动作；规范要求先问的、本工作树之外的副作用（合并、推共享分支、发布）；以及烂到每条路都是猜的计划。除此之外，停下来问仅限这四类。

**何时使用**：有实现计划、任务大体独立、留在本会话 → 用本技能；任务紧耦合 → 先拆；要开并行会话 → 用 executing-plans。相对 executing-plans 的优势：同会话无切换成本、每任务新子智能体无上下文污染、每任务后评审、无任务间人工等待故迭代更快。

**准备（Setup）**：用 using-git-worktrees 确保隔离工作区；未经人类伙伴明确同意绝不在 main/master 分支上开始实现。对话记忆挺不过压缩——真实会话里，丢过位置的控制器把*整段已完成的任务序列重新派发了一遍*，这是迄今观察到的最昂贵的失败。所以进度要记在**台账文件**里而不只是 todo 里：每个计划拥有自己的工作区（`<repo-root>/.superpowers/sdd/<plan-basename>/`，git 忽略），台账、简报、报告、评审包都在里面；检查 `<workspace>/progress.md` 有无本计划的台账——首行写着本计划文件名、且带 `Task <N>: complete` 行的任务就是已完成，**不要重派**，从第一个没有完成行的任务续跑；创建台账时把身份写在首行：`# SDD ledger — plan: <计划文件路径>`。压缩之后，信台账和 `git log`，不要信你自己的回忆。通读计划一遍（如果它点名了 spec，spec 也读——spec 是计划据以论证的权威，计划内部的冲突以 spec 裁决），每任务建一个 todo。派任务 1 之前对计划做一次**预检扫描**并把你查过什么记录下来：互相矛盾或与全局约束矛盾的任务；计划明文强制、而评审规则视为缺陷的东西。扫描的产出是一张表而非一个结论——每个共享文件或接口的任务对一行、每个任务的自洽性一行；"扫过了"却没有这些行就不算扫过。把表写进台账，在开工前对每条发现按计划文本做出裁决并记录。

**模型选择**：每个角色用能胜任的最弱模型，省成本提速度。机械实现任务（孤立函数、清晰规格、1-2 个文件）用快而便宜的模型——计划写得好的话多数实现任务都是机械的；集成与判断任务（多文件协调、模式匹配、调试）用标准模型；架构与设计任务用最强模型——最终全分支评审就是这种，要派在最强模型上而不是会话默认模型上。评审任务按 diff 的规模/复杂度/风险定档；修复循环 4-5 轮的升级用比卡住的实现者高一档以上的模型。**派子智能体时永远显式指定模型**——省略会继承会话模型（往往最强也最贵），悄悄毁掉这一节。**轮次数压过 token 单价**：最便宜的模型在多步工作里常要多花 2-3 倍轮次，总价反而更高，所以评审者和照散文简报干活的实现者以中档为下限；只有当计划文本里已含完整代码（实现即转录+测试）或单文件机械修复时才用最便宜档。

**任务循环**：

1. **派实现者**。派发前记录 BASE（`git rev-parse HEAD`）。先用本技能的 `scripts/task-brief PLAN_FILE N` 把该任务的全文提取到一个唯一命名的文件；派发提示里简报是需求的唯一来源：(1) 一行说明本任务在项目中的位置；(2) 简报路径（"先读这个——它是你的需求，其中的精确值原样使用"）；(3) 简报无法预知的、来自早期任务的接口与决定；(4) 你对简报中歧义的裁决；(5) 报告文件路径与报告契约。精确值（数字、魔法字符串、签名、测试用例）只出现在简报里。**永远不要让子智能体读整份计划文件。** 报告文件按简报命名（`…/task-N-brief.md` → `…/task-N-report.md`）；实现者把完整报告写进文件，只返回状态、提交、一行测试摘要和担忧。派发提示描述的是*一个任务*，不是会话历史——真实会话里有派发提示达 4.2 万字符、其中 99% 是粘贴的历史。实现者**永不再派子智能体**（既无帮手、更无评审者）——评审由你来做；真实会话里工人自派的每个评审者都在重复控制器派的任务评审。绝不并行派多个实现子智能体（会冲突）。
2. **处理报告**。实现者报四种状态之一：**DONE**——生成评审包（`scripts/review-package PLAN_FILE BASE HEAD`；BASE 是你派发前记录的提交，*永远不要*用 `HEAD~1`，它会悄悄丢掉多提交任务里除最后一个外的全部提交），派任务评审者；**DONE_WITH_CONCERNS**——先读担忧：关于正确性或范围的先处理再评审；观察性的（"这文件变大了"）记下来照常评审；**NEEDS_CONTEXT**——补上下文重派；**BLOCKED**——评估阻塞：上下文问题就补上下文同模型重派；需要更多推理就换更强模型；任务太大就拆；计划本身错了就裁决、记台账、带着裁决重派。**绝不**无视升级、也绝不原样硬重试。
3. **评审任务**。每任务评审是任务级闸门；大评审只在最后的全分支评审发生一次。绝不跳过任务评审，也绝不接受缺任一结论（规格符合性*与*代码质量）的报告；实现者自评不能替代任务评审。把 diff 作为文件交给评审者（评审包文件），评审者拿三个路径——同一份简报、报告文件、评审包——外加约束本任务的全局约束。全局约束块是评审者的注意力透镜：从计划的全局约束节或 spec 逐字复制精确值、精确格式与组件间关系。不要加开放性指令（"检查所有用法""有用就跑跑竞态测试"）；不要让评审者重跑实现者已跑过的测试；**不要替评审者预判结论**——如果你想好某条发现会是误报，也让评审者提出来、在评审循环里裁决；你写的提示里若出现"不要标记""别把 X 当缺陷""至多 Minor""计划选了"——停，你在预判。评审者可能报"⚠️ 无法从 diff 验证"项（需求落在未改动的代码里或跨任务）——不阻塞评审其余部分，但**你**必须在标记任务完成前逐项解决：你手里有评审者没有的计划与跨任务上下文。
4. **修复循环**。评审报规格不通过、任何 Critical/Important 发现、或你确认属实的 ⚠️ 项时触发。Minor 发现随手记台账（`Task <N>: minor (deferred): <一句话>`），留给最终大评审分流；Minor 永不进循环。与计划文本冲突的发现由*你*裁决后行动并记台账。其余全进循环——一个修复轮 = 一次修复派发 + 一次范围化重评审，**每任务最多五轮**：第 1-3 轮恢复原实现者（把未决发现原样发给它；它上下文完好）；第 4-5 轮按模型选择派全新实现者、换更强模型，并交代"先前实现者已尝试 [N] 次，现在归你了，读报告文件看试过什么"——三轮恢复还收敛不了，通常说明实现者看不见自己的问题，换新眼睛加升能力一步到位。每轮：实现者修复、重跑覆盖被改代码的测试、把修复报告追加到同一报告文件；重派评审前确认修复报告含覆盖测试、运行命令与输出。重评审是**范围化的**：只对每条发现给 ADDRESSED/NOT ADDRESSED 结论、只标记修复 diff 里的新破坏；修复 diff 里新的 Critical/Important 加入未决清单；跑题观察记为缓期 Minor，永不延长循环。每轮后台账追加 `Task <N>: fix round <R>/5 (…)`。**绝不在控制器会话里亲手修**——你的上下文要为协调保持干净，且控制器修复绕过了评审。**熔断器**：第 5 轮重评审后仍有未决发现就停止派发，由你逐条裁决——评审者错了或可争辩 → 搁置并记裁决（`Task <N>: parked — <发现> — Ruling: <代码为何成立>`）；真问题但无下游依赖 → 同样搁置、注明属实但缓期；真问题且承重（后续任务建立在上面，或暴露计划缺陷）→ 裁决解锁依赖的最小改动、记台账、带进下一任务的派发。只有当缺陷让每条前路都是猜时才停。**只在熔断时裁决**——提前裁决是预判的另一个名字；每次裁决都是台账条目，静默丢弃被禁止。
5. **完成任务**。评审干净（或熔断后全部搁置有据）时，台账追加 `Task <N>: complete (commits <base7>..<head7>, review clean)`（熔断后为 `<K> parked`），标记 todo 完成，进入下一任务。评审还有既没修也没在熔断时搁置有据的 Critical/Important 时，绝不进入下一任务。

**最终评审**：全分支评审也有评审包（`MERGE_BASE` = 分支起点），派在最强模型上，用 requesting-code-review 的 code-reviewer 模板，并把台账里的缓期 Minor 与搁置行指给它以便分流。若有发现，派**一个**修复子智能体带完整清单——不要一条发现一个修者（真实会话里最终评审的修复波比所有任务加起来还贵）；然后对修复波做**恰好一次**范围化重评审；残余发现按熔断规则裁决。没有第二修复波——残余承重发现会在 finishing-a-development-branch 呈现选项时浮出给人类伙伴。

**收尾**：删任何东西之前，把台账里所有含 `Ruling:` 的行收集进最终消息的"我做的裁决"清单（按时间顺序，各附错了的代价）；清单必须穷尽——"死在工作区里的裁决就是瞒着人做的决定"。最终评审干净且修复合入后删除本计划的工作区（git 历史即记录）；兄弟目录属于其他计划，别动。然后使用 superpowers:finishing-a-development-branch。

**常见理性化（节选）**："规格符合性差不多就行"——评审者发现规格缺口=没完成，修或熔断裁决，二选一；"派发太麻烦，我自己修"——控制器修复污染上下文且绕过评审，恢复原实现者；"再来一轮就收敛了"——过熔断点后轮次不再收敛，失败是结构性的；"修复很小，免了重评审吧"——未经评审的修复正是回归上线的路径；"评审拖慢循环"——没有评审的循环只是未验证的原地打转；"记账是开销"——台账是压缩后唯一活下来的东西。

### dispatching-parallel-agents——并行派发子智能体

> **description（全译）**：当面临 2 个以上可独立进行、无共享状态、无顺序依赖的任务时使用。

**概览（全译）**：你把任务委托给拥有隔离上下文的专门智能体。通过精确构造它们的指令与上下文，确保它们保持专注并完成任务。它们绝不应继承你会话的上下文或历史——你要精确构造它们所需之物。这同时也为你自己的上下文保留了协调工作的空间。当你面对多个互不相关的失败（不同测试文件、不同子系统、不同 bug）时，逐个串行调查是浪费时间——每项调查都独立，可以并行。

**核心原则**：每个独立问题域派一个智能体，让它们并发工作。

**何时使用**：3 个以上测试文件因不同根因失败；多个子系统各自独立地坏了；每个问题不需要其他问题的上下文就能理解；各调查之间无共享状态。**不该用**：失败相关联（修一个可能连带修好其他）；需要理解全系统状态；智能体之间会互相干扰。

**模式四步**：①识别独立域——按坏了什么分组（文件 A 测工具审批流、文件 B 测批量完成行为、文件 C 测中止功能），各域独立；②创建聚焦的智能体任务——每个智能体拿到：具体范围（一个测试文件或子系统）、清晰目标（让这些测试通过）、约束（不许改其他代码）、期望输出（发现与修复摘要）；③并行派发——**在同一个回复里**发出全部三个子智能体派发，它们才会并行；一条回复一个派发=串行；④评审与集成——智能体返回后：读每份摘要、核实修复互不冲突、跑全量测试、集成所有改动。

**智能体提示词结构**——好的提示词：聚焦（一个清晰问题域）、自包含（理解问题所需的全部上下文）、对输出具体（智能体该返回什么）。原文给出示例模板（节选）：

```markdown
修复 src/agents/agent-tool-abort.test.ts 中 3 个失败测试：
1. "should abort tool with partial output capture" - 期望 message 里有 'interrupted at'
2. "should handle mixed completed and aborted tools" - 快工具被中止而非完成
3. "should properly track pendingToolCount" - 期望 3 个结果却得到 0

这些是时序/竞态问题。你的任务：
1. 读测试文件，理解每个测试验证什么
2. 找根因——时序问题还是真 bug？
3. 修复方式：
   - 用基于事件的等待替换随意设的超时
   - 若发现中止实现中的 bug 则修复
   - 若测试的是已变更行为则调整测试期望

不要只是加大超时——找出真问题。

返回：你发现了什么、修了什么的摘要。
```

**常见错误**：太宽泛（"把测试都修了"——智能体会迷路）vs 具体（"修 agent-tool-abort.test.ts"）；无上下文 vs 贴上错误信息与测试名；无约束（智能体可能把一切重构了）vs 明确"不得改生产代码/只修测试"；输出含糊 vs "返回根因与改动摘要"。

**验证**：智能体返回后——①逐份读摘要；②查冲突（是否改了同一处代码）；③跑全量测试套件；④抽查——智能体可能犯系统性错误。

### requesting-code-review——请求代码评审

> **description（全译）**：完成任务、实现重要功能之后，或合并之前使用——验证工作满足需求。

*本技能正文较短，以下为全文翻译（省略末尾模板文件链接两处）。*

派一个代码评审子智能体，在问题滚雪球之前抓住它们。评审者拿到的是精确构造的评审上下文——绝不是你的会话历史。

**核心原则：早评审，勤评审。**

**何时请求评审**——强制：子智能体驱动开发中每个任务之后；完成重要功能之后；合并进 main 之前。可选但有价值：卡住时（换双新眼睛）；重构之前（基线检查）；修完复杂 bug 之后。

**如何请求**——①取 git SHA：`BASE_SHA=$(git rev-parse HEAD~1)`（或 origin/main）、`HEAD_SHA=$(git rev-parse HEAD)`；②派 `general-purpose` 子智能体，填 code-reviewer 模板——占位符：`{DESCRIPTION}` 构建内容简述、`{PLAN_OR_REQUIREMENTS}` 应该做什么、`{BASE_SHA}` 起始提交、`{HEAD_SHA}` 结束提交；③按反馈行动：Critical 立即修；Important 继续之前修；Minor 记下以后处理；评审者错了就带着推理反驳。

原文示例（节译）：刚完成任务 2"添加验证函数"后，取 `BASE_SHA`/`HEAD_SHA`，派评审子智能体（描述：加了带 4 种问题类型的 verifyIndex() 与 repairIndex()；计划依据：部署计划的任务 2），子智能体返回"优点：架构干净、测试真实；问题：Important 缺进度指示、Minor 报告间隔魔法数 100；结论：可继续"——你修掉进度指示，继续任务 3。

**常见理性化（全译）**：

| 借口 | 现实 |
|--------|---------|
| "我自己看 diff 就行，不用派评审者" | 你是控制器——内联看 diff 烧掉的是你继续驱动工作所需的上下文窗口。派评审子智能体：diff 和评估留在它的上下文里，回到你这里的只有结论。 |
| "评审者需要我的全部会话历史才能理解改动" | 给它精确构造的上下文，绝不给会话历史。这让评审者盯着工作产出，而不是你的思考过程。 |

**红旗**——绝不：因为"很简单"跳过评审；无视 Critical 问题；带着没修的 Important 问题继续；和有效的技术反馈争论。评审者错了：用技术推理反驳；出示证明可行的代码/测试；请求澄清。

### receiving-code-review——接住代码评审

> **description（全译）**：收到代码评审反馈时、实现建议之前使用——尤其当反馈不清楚或技术上可疑时。要求技术上的严谨与验证，而不是表演性认同或盲目实现。

*正文较长，以下译核心内容（省略部分示例块）。*

**概览**：代码评审需要的是技术评估，不是情绪表演。**核心原则：先验证再实现。先问清再假设。技术正确性高于社交舒适。**

**响应模式**：

```text
收到代码评审反馈时：
1. READ：读完整个反馈，不反应
2. UNDERSTAND：用自己的话复述需求（或提问）
3. VERIFY：对照代码库现实核查
4. EVALUATE：对*这个*代码库在技术上是否成立？
5. RESPOND：技术性确认，或有理有据的反驳
6. IMPLEMENT：一次一项，逐项测试
```

**禁止的回应**——**绝不**说："You're absolutely right!"（"你说得太对了！"——这是对指令文件的公然违反）；"Great point!"/"Excellent feedback!"（表演性夸赞）；"我马上实现"（验证之前）。**取而代之**：复述技术需求；提澄清问题；错了就用技术理由反驳；或者直接开始干活（行动大于言辞）。

**反馈不清时**——任何一项不清楚就**停**：先别实现任何东西，就不清楚的项问清。原因：各项可能相关，一知半解=错误实现。原文示例：伙伴说"修 1-6"，你懂 1、2、3、6，不懂 4、5——错误做法是先修 1、2、3、6 回头再问；正确做法是"我理解 1、2、3、6。4 和 5 需要澄清后再动手"。

**按来源区别处理**——来自人类伙伴：可信，理解后实现；范围不清仍要问；不表演性认同；直接行动或技术确认。来自外部评审者：实现之前查五件事——对*这个*代码库技术是否正确？会不会破坏既有功能？当前实现是否有其原因？在所有平台/版本上都成立吗？评审者是否了解全部上下文？建议似乎错了就带技术理由反驳；无法轻易验证就直说："没有 [X] 我无法验证，要我 [调查/去问/继续] 吗？"；与人类伙伴此前决定冲突就先停下找伙伴讨论。

**对"专业功能"做 YAGNI 检查**——评审者建议"把它做正规"时：先 grep 代码库看有没有实际调用。没人用 → "这个端点没人调用，删掉它（YAGNI）？"有人用 → 那就做正规。伙伴的规矩原话："你和评审者都向我汇报。如果我们不需要这个功能，就别加。"

**实现顺序**——多项反馈：先澄清所有不清楚的；然后按此顺序实现：阻塞性问题（破坏、安全）→ 简单修复（错字、import）→ 复杂修复（重构、逻辑）；逐项单独测试；确认无回归。

**何时反驳**——建议破坏既有功能；评审者缺上下文；违反 YAGNI（没被使用的功能）；对该技术栈技术上不正确；存在兼容/历史原因；与伙伴的架构决定冲突。怎么反驳：用技术推理，不防御；问具体问题；引用能跑的测试/代码；涉及架构就拉伙伴进来。不方便公开反驳就点破这份张力，把你看到的问题告诉伙伴——他们会感谢你的诚实。

**承认正确的反馈**——反馈确实对时："修了。[改动简述]"；"好眼力——[具体问题]。已在 [位置] 修复"；或者直接修掉，让代码自己说话。**绝不**说"You're absolutely right!""Great point!""Thanks for catching that!"以及**任何**感谢表达。为什么不感谢：行动即证明，代码本身就说明你听进了反馈。发现自己在写"谢谢"就删掉，换成修复说明。

**优雅收回反驳**——反驳错了就承认："你是对的——我查了 [X]，它确实 [Y]。现在实现。"；"验证过了你对，我最初理解错了，因为 [原因]。在修。"绝不长篇道歉、绝不为反驳辩护、绝不过度解释。陈述事实，继续前进。

**常见错误表（全译）**：表演性认同 → 陈述需求或直接行动；盲目实现 → 先对照代码库验证；批量不测 → 一次一项逐项测；假设评审者对 → 查会不会弄坏东西；回避反驳 → 技术正确性>舒适；部分实现 → 先澄清全部条目；无法验证仍继续 → 说明限制、请求方向。

**GitHub 回帖**：在 GitHub 上回复行内评审评论时，回复在评论串里（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），不要发顶层 PR 评论。

### systematic-debugging——系统化调试

> **description（全译）**：遇到任何 bug、测试失败或意外行为时使用——在提出修复之前。

*正文较长，以下译核心流程（省略部分示例与图表）。*

**概览**：**核心原则：永远先找到根因，再谈修复。治标就是失败。** 违反流程的字面，就是违反调试的精神。

**铁律**：`没有根因调查，就没有修复`（NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST）。第一阶段没完成，就没有资格提出修复。

**何时使用**：任何技术问题——测试失败、生产 bug、意外行为、性能问题、构建失败、集成问题。**尤其**要用在：时间压力下（紧急让人想猜）；"就改一行"看起来显而易见时；已经试了多个修复时；上一个修复没用时；你还不太理解这个问题时。**不要因为**"问题看起来简单"（简单 bug 也有根因）、"你在赶时间"（赶路保证返工）、"经理现在就要"（系统化比瞎折腾更快）而跳过。

**四个阶段**——必须逐阶段完成才能进入下一阶段：

**阶段一：根因调查**（在做任何修复之前）：
1. **仔细读错误信息**——别跳过报错和警告，它们常常就写着答案；完整读堆栈；记下行号、文件路径、错误码。
2. **稳定复现**——能可靠触发吗？精确步骤是什么？每次都发生吗？不能复现 → 收集更多数据，别猜。
3. **检查近期变更**——什么改动可能引发？git diff、近期提交、新依赖、配置变更、环境差异。
4. **在多组件系统中收集证据**——系统有多个组件时（CI→构建→签名，API→服务→数据库），在提修复之前先加诊断插桩：在每个组件边界记录进出数据、验证环境/配置传播、检查每层状态；跑一遍拿到"哪里断"的证据，再分析定位失败组件，再深入那个组件。原文给出的多层示例（工作流层打印密钥是否在环境、构建脚本层打印环境变量、签名脚本层列出钥匙串、实际签名层开 verbose 跑 codesign）能直接揭示断在哪一层（密钥→工作流 ✓，工作流→构建 ✗）。
5. **追踪数据流**——错误深埋调用栈时，参见同目录 `root-cause-tracing.md` 的完整回溯技术。速记版：坏值从哪来？谁用坏值调了它？一直向上追到源头；在源头修，不在症状处修。

**阶段二：模式分析**——修复之前先找规律：①找同代码库里能正常工作的相似代码；②有参考实现就把参考实现**完整读一遍**——别浏览，逐行读，应用之前完全理解该模式；③列出工作版与坏版之间的每一个差异，无论多小，别假设"这不可能有影响"；④理解依赖——需要哪些其他组件、什么配置与环境、做了哪些假设。

**阶段三：假设与检验**——科学方法：①形成单一假设——清楚地说"我认为 X 是根因，因为 Y"，写下来，要具体；②最小检验——用**最小**的改动检验假设，一次一个变量，不要同时修多处；③继续之前先验证——成了进阶段四；没成就形成**新**假设，别在上面继续叠修复；④不知道就说"我不理解 X"，别装懂，求助或继续研究。

**阶段四：实现**——修根因，不修症状：①先建失败测试用例——最简可复现，能自动化就自动化，没有框架就写一次性脚本；修复之前必须有；用 superpowers:test-driven-development 技能写规范的失败测试。②实现单一修复——针对已定位的根因，一次一个改动，不顺手改进，不捆绑重构。③验证修复——测试过了吗？别的测试没坏吗？问题真解决了吗？宣布成功前用 superpowers:verification-before-completion 技能。④修复无效就**停**——数一数试了几个修复：少于 3 个 → 回到阶段一带新信息重新分析；达到 3 个 → 停下质疑架构，没有架构讨论不许试第 4 个。⑤**3 个以上修复失败：质疑架构**——指示性模式：每个修复都在不同位置揭示新的共享状态/耦合/问题；修复需要"大规模重构"才能实现；每个修复在别处制造新症状。停下来质疑根本：这个模式根本成立吗？我们是不是"纯粹靠惯性硬撑"？该重构架构还是继续修症状？尝试更多修复之前先和人类伙伴讨论。**这不是假设失败，这是架构错误。**

**红旗——停下，回到流程**：出现这些念头就回到阶段一："先随便修一下，回头再查""就改改 X 看看行不行""多改几处一起跑测试""跳过测试我手动验证""大概是 X，我修一下""没全搞懂但这也许行""模式说 X 但我换个用法""主要问题有这些"（没调查就列出修复清单）；追完数据流之前就提解决方案；**"再试一次修复"（已经试过 2 次以上）**；**每个修复都在新地方暴露新问题**。3 个以上修复失败：质疑架构。

**伙伴在提醒你做错了的信号**："不是已经发生了吗？"——你没验证就假设了；"它能给我们看到……吗？"——你本该先收集证据；"别猜了"——你在没理解的情况下提修复；"往死里想这个"——该质疑根本而不是症状；"我们卡住了？"（沮丧）——你的方法不奏效。看到这些：停下，回阶段一。

**常见理性化（全译）**：

| 借口 | 现实 |
|--------|---------|
| "问题简单，不用流程" | 简单问题也有根因。对简单 bug，流程反而快。 |
| "紧急，没时间走流程" | 系统化调试比猜-验-再猜的瞎折腾**更快**。 |
| "先试试这个再调查" | 第一个修复定基调。从一开始就做对。 |
| "确认修复有效后我再补测试" | 没测试的修复站不住。测试先行才能证明。 |
| "一次修多处省时间" | 没法隔离哪处起了作用，还会引入新 bug。 |
| "参考实现太长，我改造着用" | 一知半解保证出 bug。完整读。 |
| "我看见问题了，让我修" | 看见症状≠理解根因。 |
| "再试一次"（已失败 2 次以上） | 3 次以上失败=架构问题。质疑模式，别再修。 |

**速查表**：阶段一（根因）读报错/复现/查变更/收证据 → 搞清是什么与为什么；阶段二（模式）找正常样本/比对 → 找出差异；阶段三（假设）立论/最小检验 → 确认或换假设；阶段四（实现）建测试/修/验 → bug 解决、测试通过。

**当流程揭示"没有根因"**：如果系统化调查真的查明问题纯属环境、时序依赖或外部因素：你已完成流程——记录调查过程、实现恰当的处理（重试、超时、错误信息）、加监控/日志备查。**但：95% 的"没有根因"是调查不彻底。**

**支撑技术**（同目录文件）：`root-cause-tracing.md` 沿调用栈回溯 bug 找原始触发；`defense-in-depth.md` 找到根因后在多层加校验；`condition-based-waiting.md` 用条件轮询替换随意超时。

### test-driven-development——测试驱动开发

> **description（全译）**：实现任何功能或修复任何 bug 时使用——在写实现代码之前。

*正文较长（含大量代码示例），以下译核心规则与流程（代码示例节选）。*

**概览**：先写测试。亲眼看它失败。写最少的代码让它通过。**核心原则：没亲眼看到测试失败，你就不知道它测的是不是对的东西。** 违反规则的字面，就是违反规则的精神。

**铁律**：`没有先失败的测试，就没有生产代码`（NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST）。先写了代码再补测试？**删掉。重来。** 无例外：不留作"参考"、写测试时不"顺手改造"它、不看它。删就是删。从测试出发重新实现，就这样。

**何时使用**——永远要用：新功能、bug 修复、重构、行为变更。例外（须请示人类伙伴）：一次性原型、生成的代码、配置文件。冒出"就这次跳过 TDD"的念头？停。那是合理化。

**红-绿-重构循环**：

- **RED 写失败测试**：写一个最小测试，展示应有的行为。要求：一个行为；名字清晰；真实代码（除非不得已不用 mock）。原文 Good/Bad 对比——好测试名字具体（"失败操作重试 3 次"）、测真实行为、断言结果与尝试次数；坏测试名字含糊（"重试能用"）、测的是 mock 而不是代码。
- **验证 RED——亲眼看它失败**：**强制，绝不跳过。** 运行测试并确认：测试失败（而不是报错）；失败信息符合预期；失败原因是功能缺失（而不是错字）。测试直接通过了？你在测既有行为，改测试。测试报错了？先修错误，重跑到它"正确地失败"。
- **GREEN 最小代码**：写最简单的、能让测试通过的代码。原文 Good 示例就是一个三行 for 循环重试函数——刚好够通过；Bad 示例带 maxRetries/backoff/onRetry 一堆 options——过度设计（YAGNI）。不加功能、不重构别的代码、不做测试之外的"改进"。
- **验证 GREEN——亲眼看它通过**：**强制。** 确认测试通过、其他测试也通过、输出纯净（无错误无警告）。测试还失败？改代码，不是改测试。别的测试挂了？立刻修。
- **REFACTOR 清理**：绿了之后才允许：去重、改名字、提助手函数。保持全绿；不加行为。
- **重复**：为下一个功能写下一个失败测试。

**好测试**：最小（名字里有"和"就拆开）、清晰（名字描述行为）、表意（演示期望的 API）。写或改任何测试前，读同目录 `writing-good-tests.md` 的守则：写之前先说出"什么样的生产改动会让这个测试失败"；断言真实行为，绝不断言 mock 行为；测试专用代码放测试工具里，不进生产类；mock 依赖前先理解它的副作用。

**常见理性化（节选，原文 11 条全为反驳）**："太简单不用测"——简单代码也会坏，测试只要 30 秒；"回头再补测试"——后补的测试立即通过，而这什么都证明不了：它可能测错东西、测实现而非行为、漏掉你忘了的边界；没看过它失败，就永远没证明它能抓住 bug，测试先行就是强迫那次失败；"后写测试目的相同（要精神不要仪式）"——后写测试回答"它做了什么？"，先写测试回答"它该做什么？"；后写的测试被已写好的代码带偏，你验证的是记得住的用例；"已经手动测过了"——手动测试无记录、不可重放、压力下漏用例，"我试过没问题"≠全面；"删掉 X 小时的工作太浪费"——沉没成本谬误，真正的选择是用 TDD 重写（高置信）还是留着再钉测试（低置信、大概率有 bug），留着你信不过的代码才是浪费；"留作参考，测试先行写"——你会去改它，那就是后写测试，删就是删；"测试难写=设计不清"——听测试的，难测=难用；"TDD 拖慢我"——TDD 就是务实路线：提交前抓 bug、防回归、重构无惧，"务实"的捷径意味着在生产环境里调试，更慢；"现有代码没测试"——你在改进它，为既有代码补测试。

**红旗——停下重来**：先代码后测试；实现后才写测试；测试立即通过；说不清测试为什么失败；"以后再补"测试；合理化"就这一次"；"我已经手动测过了"；"后写测试目的相同"；"要精神不要仪式"；"留作参考"/"改造现有代码"；"已经花了 X 小时，删了可惜"；"TDD 太教条，我讲务实"；"这次不一样，因为……"。**以上任何一条都意味着：删代码，回到 TDD。**

**Bug 修复示例**（原文流程，代码节选）：bug 是"空邮箱被接受"。RED：写 `test('rejects empty email')` 断言返回错误信息"Email required"；验证 RED：`npm test` 输出 `FAIL: expected 'Email required', got undefined`；GREEN：在 `submitForm` 里加空值检查返回错误对象；验证 GREEN：`PASS`；REFACTOR：如需对多个字段校验则提取通用校验。

**验证清单**：标记完成前——每个新函数/方法都有测试；实现前亲眼看每个测试失败；每个测试都因预期原因失败（功能缺失，不是错字）；为每个测试写了最少实现；全部测试通过；输出纯净；测试用真实代码（mock 仅在不得已时）；覆盖边界与错误。有格子勾不上？你跳过了 TDD。重来。

**卡住了**：不会写测试 → 写你 wished-for 的 API，先写断言，问伙伴；测试太复杂 → 设计太复杂，简化接口；什么都得 mock → 代码太耦合，用依赖注入；测试准备太庞大 → 提取助手函数，仍复杂就简化设计。

**与调试的衔接**：发现 bug？写一个复现它的失败测试，走 TDD 循环。测试证明修复并防回归。**没有测试绝不修 bug。**

**最终规则**：`生产代码 → 存在先失败的测试；否则 → 不是 TDD`。未经人类伙伴许可，无例外。

### using-git-worktrees——用工作树隔离工作区

> **description（全译）**：开始需要与当前工作区隔离的功能开发时，或执行实现计划之前使用——通过平台原生工具或 git worktree 兜底，确保存在一个隔离工作区。

*正文较长，以下译核心流程。*

**概览**：确保工作发生在隔离工作区。优先用平台的*原生*工作树工具；只有在没有原生工具时才回退到手动 git worktrees。**核心原则：先检测既有隔离，再用原生工具，最后回退 git。永远不要和宿主对着干。** 开场宣布："I'm using the using-git-worktrees skill to set up an isolated workspace."

**Step 0：检测既有隔离**——创建任何东西之前，先检查是否已在隔离工作区：比较 `git rev-parse --git-dir` 与 `git rev-parse --git-common-dir`、看当前分支。**子模块防护**：`GIT_DIR != GIT_COMMON` 在 git 子模块里也为真——下结论"已在 worktree 里"之前，先用 `git rev-parse --show-superproject-working-tree` 确认不在子模块里（返回了路径就是子模块，按普通仓库处理）。若确已在链接工作树：直接跳 Step 2，**不要**再建一个；按分支状态报告（在分支上/分离 HEAD——分离 HEAD 外部托管，收尾时需要建分支）。若是普通检出：用户没有在指令里表明工作树偏好的话，先征求同意（"要我建一个隔离 worktree 吗？它能保护你当前分支不被改动"）；有既定偏好就不问照办；用户拒绝就原地工作、跳 Step 2。

**Step 1：创建隔离工作区**——两种机制按序尝试。**1a 原生工具（优先）**：有没有名字类似 `EnterWorktree`、`WorktreeCreate` 的工具、`/worktree` 命令或 `--worktree` 旗标？有就用它并跳 Step 2——原生工具自动处理目录位置、分支创建与清理；有原生工具却手动 `git worktree add` 会制造宿主看不见也管不了的"幻影状态"。**1b git worktree 兜底**（仅当 1a 不适用）：目录选择按优先级——指令里有声明偏好就用之；否则查项目内既有目录 `.worktrees`（首选，隐藏）或 `worktrees`，两者都在 `.worktrees` 胜出；全无指引就默认项目根的 `.worktrees/`。**安全验证（仅项目内目录）**：创建前**必须**验证目录已被 git 忽略（`git check-ignore`）；没忽略就先加进 .gitignore 并提交——否则会把整个工作树内容误提交进仓库。然后 `git worktree add "$path" -b "$BRANCH_NAME"` 并 cd 进去。**沙箱兜底**：`git worktree add` 因权限错误（沙箱拒绝）失败时，告知用户沙箱挡了创建、改为在当前目录工作，就地完成初始化与基线测试。

**Step 2：项目初始化**——自动检测并运行恰当的安装：有 `package.json` 就 `npm install`；`Cargo.toml` 就 `cargo build`；`requirements.txt` 就 `pip install -r`；`pyproject.toml` 就 `poetry install`；`go.mod` 就 `go mod download`。

**Step 3：验证干净基线**——跑项目测试（npm test / cargo test / pytest / go test ./...）。失败：报告失败并问是否继续或排查；通过：报告就绪（"Worktree ready at <完整路径>；测试通过（N 个测试，0 失败）；可以开始实现 <功能名>"）。

**快速参考（节译）**：已在链接工作树 → 跳过创建；在子模块 → 按普通仓库处理；有原生工具 → 用它；`.worktrees/` 与 `worktrees/` 都在 → 用 `.worktrees/`；目录未被忽略 → 加 .gitignore 并提交；创建遇权限错误 → 沙箱兜底就地工作；基线测试失败 → 报告并询问；无任何包清单 → 跳过依赖安装。

**常见理性化（全译）**："我显然不在 worktree 里，不用查"——跑 Step 0；宿主创建的隔离和子模块都能骗过肉眼，检测命令说了算。"`git worktree add` 比找原生工具快"——原生工具（如 `EnterWorktree`）管位置、分支与清理，绕开它是**第一大错误**，会造出宿主看不见的幻影状态。"worktree 目录肯定已被忽略"——跑 `git check-ignore`；未忽略的 worktree 目录会把整棵树提交进仓库。"目录叫什么都行"——显式指令>既有项目内目录>`.worktrees/` 默认。"工作区是新的，基线测试回头跑"——脏基线让之后每个失败都说不清；现在就跑；带失败继续是伙伴的决定。

### verification-before-completion——完成之前先验证

> **description（全译）**：即将声称工作已完成、已修复或通过时，在提交或创建 PR 之前使用——要求先运行验证命令并确认输出，再做任何成功声明；永远证据先于断言。

*本技能正文较短，以下为全文翻译（省略个别表行与重复示例）。*

**概览**：**核心原则：永远证据先于声称。** 违反本规则的字面，就是违反本规则的精神。

**铁律**：`没有新鲜的验证证据，就没有完成声明`（NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE）。这条消息里没运行过验证命令，就不能声称通过。

**闸门函数**：

```text
在声称任何状态或表达任何满意之前：
1. IDENTIFY：什么命令能证明这个声称？
2. RUN：完整运行该命令（新鲜的、完整的）
3. READ：读全部输出，查退出码，数失败数
4. VERIFY：输出是否证实声称？
   - 否：带证据陈述实际状态
   - 是：带证据陈述声称
5. 然后才可以：做出声称

跳过任何一步 = 在撒谎，不是在验证
```

**常见失败**：声称"测试通过"需要本次测试命令输出 0 失败——上一次的运行、"应该能过"都不算；"linter 干净"需要 linter 输出 0 错误——抽查和外推不算；"构建成功"需要构建命令退出码 0——linter 通过、日志好看都不算；"bug 修好"需要测原症状通过——代码改了、假定修了不算；"回归测试有效"需要红-绿循环验证过——测试只通过一次不算；"智能体完成了"需要 VCS diff 里有改动——智能体自报"成功"不算；"需求满足"需要逐条核对清单——测试通过不算。

**红旗——停下**：使用"应该""大概""看起来"；验证之前表达满意（"Great!""Perfect!""Done!"）；没验证就要 commit/push/PR；信智能体的成功报告；依赖部分验证；"就这一次"的念头；累了想收工；**任何没跑验证就暗示成功的措辞**。

**理性化预防（全译）**："应该行了吧" → 跑验证；"我有信心" → 信心≠证据；"就这一次" → 无例外；"linter 过了" → linter≠编译器；"智能体说成功了" → 独立验证；"我累了" → 疲惫≠借口；"部分检查够了" → 部分证明不了什么；"换个说法规则就管不着了" → 精神高于字面。

**关键模式**：测试——✅ 运行测试命令，看到 34/34 通过，才说"全部通过"；❌"现在应该能过了"/"看起来没问题"。回归测试（TDD 红绿）——✅ 写 → 跑（过）→ 撤销修复 → 跑（必须失败）→ 恢复 → 跑（过）；❌ 没做红绿验证就说"我写了回归测试"。构建——✅ 跑构建，看到退出码 0，才说"构建通过"；❌"linter 过了"（linter 不查编译）。需求——✅ 重读计划 → 建清单 → 逐条验证 → 报告缺口或完成；❌"测试都过了，阶段完成"。智能体委托——✅ 智能体报成功 → 查 VCS diff → 核实改动 → 报告实际状态；❌ 直接信智能体报告。

**何时应用**——**永远**要在以下之前：任何变体的成功/完成声明；任何满意表达；任何关于工作状态的正面陈述；提交、建 PR、标记任务完成；进入下一任务；委托智能体。规则适用于：精确措辞、转述与同义、成功暗示、任何暗示完成/正确的沟通。

### finishing-a-development-branch——开发分支的收尾

> **description（全译）**：实现完成、全部测试通过、需要决定如何集成这项工作时使用。

*正文较长（含各分支的 bash 细节），以下译核心流程。*

**核心原则**：验证测试 → 检测环境 → 呈现选项 → 执行选择 → 清理。开场宣布："I'm using the finishing-a-development-branch skill to complete this work."

**第一步：验证测试**——跑项目全量测试（`npm test` / `cargo test` / `pytest` / `go test ./...`）。失败：报告失败并停止——菜单要等全绿之后才来。通过：进第二步。

**第二步：检测环境**——记录 `GIT_DIR`（`git rev-parse --git-dir`）与 `GIT_COMMON`（`git rev-parse --git-common-dir`），并在仍在工作区里时先抓下 `WORKTREE_PATH`（`git rev-parse --show-toplevel`）——第五步会切目录，清理（第六步）要用这个值。这决定呈现哪个菜单、清理怎么做：普通仓库（两者相等）→ 标准 3 选项、无工作树要清理；命名分支的链接工作树 → 标准 3 选项、按"出处"清理（见第六步）；分离 HEAD → 缩减 2 选项（无合并）、外部托管——原地保留。

**第三步：确定基线分支**——基线分支是这项工作分叉出来的分支——通常写在计划、对话或分支的上游里。不知道就问："这个分支是从 <你的最佳猜测> 分出来的，对吗？"合并前必须确认——合错基线的撤销代价很高。

**第四步：呈现选项**——普通仓库与命名分支工作树：严格呈现这 3 项——①本地合并回 <基线分支>；②推送并创建 Pull Request；③分支原样保留（我稍后处理）。分离 HEAD：严格呈现这 2 项——①作为新分支推送并创建 PR；②原样保留。菜单照原文呈现，简洁、每一项都来自上面清单。**丢弃工作**只有在人类伙伴明确提出时才发生（见下）。等他们回答——集成决定是他们的。

**第五步：执行选择**——选项 1（本地合并）：切到主仓库根 → 先合并（checkout 基线、pull、merge 特性分支）→ 在合并结果上跑测试。合并结果测试失败：停下，工作树和分支原地保留、排查——还没推任何东西，合并是本地的、可恢复的。合并结果全绿：清理工作树（第六步），再删分支。选项 2（推送并建 PR）：`git push -u origin <feature-branch>`（分离 HEAD 用 `HEAD:refs/heads/<新分支>` 命名远端分支），然后用-forge 的工具（有 CLI 用 CLI，或用推送时打印的创建 URL）按仓库 PR 模板建 PR，把 URL 报给伙伴。**保留工作树**——伙伴要在里面迭代 PR 反馈。选项 3（原样保留）：报告"保留分支 <名>。工作树在 <路径> 原样保留。"。**伙伴明确要求丢弃时**：这是对"扔掉工作"的显式请求的唯一响应路径——先确认，列出将被永久删除的分支、全部提交、工作树路径，等对方**逐字**输入 `discard` 才动手，然后清理并强制删分支。

**第六步：清理工作区**——只在选项 1 和确认丢弃后运行；选项 2、3 永远保留工作树。`GIT_DIR == GIT_COMMON` → 普通仓库，无事可做。工作树在 `.worktrees/` 或 `worktrees/` 下 → 是 Superpowers 创建的，我们负责清理：`git worktree remove` + `git worktree prune`（自愈陈旧注册）。**移除被拒**（"包含修改过或未跟踪的文件"）：工作树里有别处不存在的文件——未提交的计划、笔记、草稿。**绝不自作主张 `--force`**：把 `git status --porcelain -uall` 的结果给伙伴看，三选一——提交到分支、挪回主仓库根、删除（不可恢复）；执行后再移除。其他情况 → 工作区归宿主环境管，原地保留；平台有工作区退出工具就用它。

**速查表**：合并 → 推送 → 保留工作树 → 清理分支：选项 1=是/否/否/是；选项 2=否/是/是/否；选项 3=否/否/是/否；丢弃（仅显式请求）=否/否/否/是（强制）。

**常见理性化（全译）**："测试这会儿之前过了"——对**即将集成**的这棵树跑；绿色只证明它跑在其上的那棵树。"他们显然想合并"——集成是伙伴的决定；呈现菜单并等待。"他们这功能好像完了，我主动提丢弃吧"——菜单就是全部；丢弃只在伙伴原话提出时发生。"'对，扔了吧'算确认吧"——只有键入的单词 `discard` 授权删除。"PR 都建了，工作树就是杂物了"——PR 反馈就在那个工作树里修；工作落地前它一直在。"那个别的 worktree 看着废弃了，顺手清了"——只清 `.worktrees/`/`worktrees/` 下的；其余归宿主。"移除被拒——`--force` 只是收尾而已"——拒绝意味着有文件只存在于该工作树，`--force` 永久销毁；给伙伴看并问。"合并结果失败大概是抖动"——合并结果失败就停一切；排查期间分支和工作树原地不动。"基线显然是 main"——确认分叉点或问；合错基线撤销代价很高。"推送被拒——强推解决"——被拒说明远端动了；先排查；强推只在伙伴明确要求时。

### diagnosing-superpowers——出问题时先取证，再诊断

> **description（全译）**：当一个 Superpowers 会话出了岔子、你的人类伙伴想知道为什么时使用——重复劳动、计划被忽略、中途绊倒、产出不行、某个技能没触发，以及"它怎么这么久""为什么这么贵""它到底在干什么"，或者要替 Superpowers 维护者写一份 bug 报告；针对当前会话或用 id/路径指定的历史会话，任何宿主都适用。

*本节译自 2026-09 新增的 `skills/diagnosing-superpowers/SKILL.md`。*

**概览**：和人类伙伴一起把"哪里不对"钉成一个可核对的陈述，读磁盘上的转录（transcript），然后**带着证据汇报发生了什么**。它明确划界：**你只汇报，不诊断 Superpowers 本身**——是否要改技能，由拿到取证包或 issue 的人决定。

**核心原则**：每一条发现都要引用 `path:line`；**没有引用就不算发现**。每一个数字都来自转录或你实际跑过的命令，**绝不凭记忆**。

**工作流**（每步建一个 todo；第 5-7 步只在各自条件成立时才跑）：

1. **问题受理**：一次只问一个问题，直到你能写出一句指名"哪个会话、哪个轮次区间、伙伴期待什么、实际发生了什么、盯的是哪个可观察量（墙钟时间、token、重复动作、某一个具体动作）"的话。"它花了太久"是抱怨，不是问题陈述。同时记下目标是不是要产出一份 Superpowers bug 报告。
2. **定位**：按 `references/session-discovery.md` 把每个会话解析成**已验证的绝对路径**；历史会话要用"引用它的首条提示与时间戳"来确认，并把**每一个被排除的候选连同排除理由**列出来（没有就写"无"）。枚举子智能体转录，在 `~/.superpowers/diagnosing-superpowers/<session-id>/` 建案例目录，告诉伙伴路径，再按其 `templates/case.md` 的溯源规则填写环境与技能观察。
3. **分流**：自己先读报错区域，然后**按维度并行派多个分析子智能体**，每个只领一个维度提示文件——`skill-timeline.md`（技能时间线）、`plan-adherence.md`（是否按计划走）、`repeated-work.md`（重复劳动）、`stumbles.md`（绊倒点）。

**为什么值得单独读**：这是全流程技能族里唯一面向"事后复盘"的一环。前面 13 个技能都在往前推工作，这一个负责**在你怀疑它没干活时，用转录和引用把怀疑变成事实**——也正是《AI 编码工具与模型评测基准：SWE-bench 与 Terminal-Bench》所说"证据先于声称"在自家会话上的应用。

## 三、把这套方法论接进自己的仓库（本站编者归纳）

*本节为编者基于上文译文的实践归纳，非原文翻译。*

**先想清楚要不要全装。** Superpowers 是**强制流程**：`using-superpowers` 要求"哪怕 1% 相关也必须调用技能"，`brainstorming` 带硬批准闸门，`test-driven-development` 的铁律是"没先失败的测试就没有生产代码，先写了代码就删掉重来"。装下去，你的会话会明显变"啰嗦"——它会先反问你、先写设计文档、先写失败测试。对个人脚本或一次性探索，这套仪式感常常过头；对要长期维护、多人协作、需要回归信心的代码，它省下的返工远大于开销。**判断依据就一条：这个仓库里出错的成本，是否大于走流程的成本。**

**分档落地**，不必一次全上：

| 档位 | 装什么 | 适合 |
| --- | --- | --- |
| 只装纪律 | `test-driven-development` + `verification-before-completion` + `systematic-debugging` | 你已经会自己拆任务，只缺"不许骗自己"的闸门 |
| 加上前置 | 再装 `brainstorming` + `writing-plans` | 需求经常被你自己改来改去的项目 |
| 全装 | 加上 worktrees、子智能体驱动、两段评审 | 长时自主任务、多任务并行、要交付给别人维护的代码 |

**三条最常见的失配**：

1. **宿主没有子智能体**。`executing-plans` 自己就写明"有子智能体的宿主效果好得多"，没子智能体时它退化成一份带检查点的清单——此时 `subagent-driven-development` 的收益直接归零。
2. **`docs/superpowers/` 目录进了你的仓库**。它会把设计文档、计划、台账写进 `docs/superpowers/specs/`、`docs/superpowers/plans/`、`<repo-root>/.superpowers/sdd/`。前者要提交（它们是团队可读的设计记录），后者是工作区、**必须 git 忽略**——SDD 一节里"压缩之后信台账和 `git log`，不要信你自己的回忆"整段机制都建立在这个目录上。
3. **遥测**。README 说明"可视化伴侣"功能默认会从 Prime Radiant 网站加载带版本号的标志图片；把 `SUPERPOWERS_DISABLE_TELEMETRY` 设为任意真值可关闭，它也遵循 Claude Code 的 `DISABLE_TELEMETRY` 与 `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`。企业内网建议先关掉再装。

**与站内其他文章的衔接**：这套流程的"计划→执行→评审→收尾"四拍，和《Claude Code 工作流与最佳实践》的"探索→计划→实现→提交"是同一件事的两种颗粒度；它的 worktree 一节对应《Git in AI 工作流：commit 即存档、worktree 隔离与审查流》；它的"把研究外包给子智能体"对应《Subagents 与并行会话：把探索外包出去》；它写技能的那部分（`writing-skills`）已单独收进《开源编码 Skills（二）：技能写作与文档协作族》。
