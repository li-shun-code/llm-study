在 500 行的新项目里用智能体是一回事，在一个二十年、两百万行、测试覆盖率 30% 的仓库里用它是另一回事。前两篇讲了工具怎么装（《环境搭建：Claude Code 与 Cursor 的安装与配置矩阵》）、扩展机制怎么配（《AGENTS.md 与 CLAUDE.md：给智能体的项目规范文件》《Claude Code Hooks：用确定性脚本守住智能体循环》），本篇回答落地时最贵的问题：**在大型与遗留代码库上，怎么让 AI 真的产出可信改动，而不是产出一堆看起来像代码的东西。**

素材来自两份一手资料：**Anthropic 官方的大型代码迁移方法论**（2026 年 7 月发布，来自 Bun 的百万行 Zig→Rust 移植与另一个 Python→TypeScript 165,000 行移植的实战复盘）与 **Claude Code 官方的 monorepo / 大型仓库配置指南**。

## 一、为什么这笔账现在才算得过来

*以下要点摘译自 [How Anthropic runs large-scale code migrations with Claude Code](https://claude.com/blog/ai-code-migration)。*

代码迁移过去是**多年期工程**。文章给出两个近期实例：**Bun 的 Zig→Rust**——100 万行代码在不到两周内产出，合并前 CI 上 100% 跑通 Bun 原有测试套件，合并后暴露 19 个回归且已全部修掉，Rust 版已在 6 月随 Claude Code 发布；另一个是 **Python→165,000 行 TypeScript**——一个周末完成，包含数百个智能体、8 道阶段闸门、3 轮对抗式评审，以及最后一次"每条命令的输出都与 Python 原件逐字节对拍"的平价校验。

**变化的不是"能翻译代码"，而是失败的代价**：过去你可能要维护两套代码库几个月甚至几年，最后只做到 90% 平价——那你得到的比开始时更糟。现在最坏情况是**把分支删掉重来**。

但**仍然需要成立的业务理由**，而且钱是真的：Bun 那次迁移消耗了 **59 亿未命中缓存的输入 token 与 6.9 亿输出 token，按 API 定价约 165,000 美元**；另一个移植的主体部分约 2,700 万 token。文章的原话很值得抄进立项材料——**迁移不再需要"生死攸关"才划算，"一年内存 bug 修补记录"或"一个长期瓶颈"就够**：那个 Python 项目每次发布要为每个平台跑约 8 分钟编译、整个构建矩阵等 30 分钟，移植后同样编译约 2 秒、二进制启动快 6 倍，还退役了一条独立发布流水线。

**为什么智能体特别擅长这类活**（原文列的五条，本质是"什么任务适合智能体"的通用判据）：

1. **工作可并行**——能拆成上千个独立单元（文件、crate），智能体之间不用互相等。
2. **上下文清晰且完备**——旧代码本身就是一份绝佳的 spec，还能反过来生成翻译指南。
3. **自带裁判**——大型代码库通常有测试套件。官方强调："验证客观时智能体表现最好，因为模型可以对着 ground truth 磨上好几天而不需要人来仲裁质量。"
4. **任务队列自己会长出来**——编译失败、测试失败，就是下一个待办。
5. **要求一致性与边界情况处理**——流程设计成"漂移无处藏身"：评审者每条发现都要引用规则出处，违规就变成队列项而不是悄悄分叉；智能体撞到边界情况，修完就成了一条所有后续智能体都要遵守的规则。

一句话总结整套方法论：**你修的不是代码，是产出代码的那个循环。**

## 二、前置条件：先有一个能判新旧两版的"裁判"

官方把这一步放在六步之前，并说明**没有它就没有退出条件、也没有成功度量**。

- **给现有测试分类**：让 Claude 判定哪些测试可以表达为"对外部接口的调用"，哪些依赖移植后根本不存在的内部函数。
- **为可移植性重写**：把面向外部的测试改成能同时跑在原实现与移植实现上的断言，并用**对抗式智能体**验证重写没有把断言弱化。
- **验证裁判本身**：先对原代码跑一遍确认通过，**再对故意破坏的代码跑一遍确认它会失败**——官方那句话应当贴在墙上："抓不住破坏的裁判不是裁判。"

那个 Python 移植的做法更接地气：建了一个覆盖 **7 个真实场景的平价 harness**，并**把任何行为差异都当成需要修的 bug**。

## 三、六步流程

### 步骤 1：写规则手册、依赖图与差距清单

**顺序很重要：规则手册必须先于差距清单**——"差距"的定义就是"规则手册默认覆盖不到的部分"，两者要在一次联合审计里一起验。

- **规则手册**取决于开局就得定的架构选择：新代码是**沿用原结构**（Bun 的选择，规则手册主体就是类型与惯用法的查表，难翻的部分指向差距清单），还是**彻底重设计**（另一个移植的选择，规则手册实际上是一份设计文档）。前者靠"和 Claude 聊出每个含糊之处的处理策略"，并派**八个子智能体各自盯一类常见失败模式**。
- **依赖图**决定并行批次：哪些文件先迁、哪些必须同批。有些语言/仓库有显式清单，但遗留代码库和 C/C++、Python 这类语言得**先发现再建图**——让 Claude Code 派智能体写一个**确定性脚本**去产出这张图，并用带"评审—修复"循环的工作流来保证脚本可信。
- **差距清单**装的是隐式知识：Zig→Rust 差的是手工内存管理（Zig 里调用方忘了 `defer allocator.free(buf)` **照样编译**，泄漏只在运行时暴露；Rust 的所有权与 drop 让"用了又释放""忘了释放"根本不编译）；Python→TypeScript 差的是契约（Python 里"任何有 `.setup()` 和 `.run()` 的对象都能传进来"，要想知道有哪些传进来得读遍全库，而 TypeScript 必须先把 interface 写出来才编译得过）。

Bun 是**提前**盘差距，另一个项目选择**先翻译、再事后审计补差距**——官方提醒：你可能两件都要做。

### 步骤 2：压力测试规则（试航）

拿几个文件做一次"迷你迁移"，给整套流程做震动试验。那次 Python 移植用三个智能体：**一个照规则手册翻 3 个文件；一个"像资深 Rust 工程师那样"翻 3 个文件；一个用两者的 diff 产出新的翻译规则**。就在这个阶段抓出了两个关键问题——它们如果扇出到全部 1,448 个文件，代价完全不同。

**注意适用边界**：这种试航**只对"保持结构"的迁移有效**。

### 步骤 3：全量翻译

从这里开始，后面反复用的都是同一套多智能体循环：**实现 → 评审 → 修复**。

- **模型分层**：实现可以交给小模型，评审要留大模型（那个项目扇出 12 个子智能体做主体迁移时用的是 Sonnet 档）。
- **工作队列必须是机械的、可续跑的**：一个批处理脚本靠"目标文件在磁盘上是否存在"判定完成，把待办文件切批派给实现智能体。队列每次都从磁盘重建，所以**迁移天然可续跑**。
- **翻译者不敢确信执行的东西一律打上 `// TODO(port): <原因>`**，留给第 4 步。官方描述从这儿之后的状态："编译器负责列举错误，冒烟测试负责找崩溃，测试套件负责报失败——待办清单自己会长出来。"
- **两个对抗式评审者用各自独立的上下文检查实现者的工作，评审者之间不同意就交给第三个智能体。**
- **同一个错误跨文件反复出现时，修法不是逐文件改**：往规则手册里加一句话，然后**重新生成受影响的批次**。规则手册一直长，代码从不手工对着它改。
- **一个值得注意的设计决定是编译器放在哪**：TypeScript 编译器秒级校验一个单元，所以放进每一轮循环；`cargo` 要几分钟，于是**整个从循环里禁掉**，推迟到下一步统一处理。
- 官方还观察到"这一步智能体会过度谨慎、做得太少"，解法是一句直白的提示词约束，并告诉它下一步编译器会抓到错误。**到这一步提示词会明显变短**——因为大部分知识已经沉进规则手册了。

### 步骤 4、5、6：编译、跑起来、行为对齐

这三步共享同一套循环，需要的人类判断逐步递减（第 4 步在某些语言里会直接并进第 3 步）。

- **第 4 步（编译）**：可以用一个编排脚本对整个 workspace 只跑一次编译器，把错误列表切成批次交给"修复智能体"并行处理并配对抗评审，然后重新构建、循环。**读错误列表能发现系统性问题**：Bun 在修掉 Zig 惰性编译所容忍的循环导入后，冒出成千上万个 Rust 模块错误——解法不是一个个修，而是写一段逻辑去分类"该删哪个依赖、该移哪个、该重构哪里的边界"。
- **第 5 步（冒烟测试）**：机械真源是**崩溃**。按根因把问题分类分组，交给对抗式子智能体评审。
- **第 6 步（行为对齐）**：分片跑测试套件（用第 0 步那个裁判），失败由"能同时看两套代码库"的修复智能体处理，修复再由对抗评审者检查。关键的工程细节是**构建守护进程（build daemon）**：它是**唯一被允许重建二进制的进程**——修复者只写补丁，daemon 批量收拢、**只重建一次**、只重跑受影响的测试再把结果喂回去。**把最昂贵的那个操作串行化，而不是让一堆智能体各自触发它。**
- 同一类失败在多个测试里重复出现时，**修法要上移一层**：改产出这个 bug 的那条规则，只重新生成该规则覆盖的文件。
- **没有测试套件不构成阻塞**：让 Claude 自己造一个。那个项目先跑 7 个真实场景对拍，每个失败场景各派一个修复智能体，循环到七个全过；然后**让 Claude 自己设计一套端到端测试、连续四个晚上自主跑、发现坏了就修再重跑**——它抓到了任何场景清单都预想不到的擦伤。**原始代码库无论如何都是 ground truth。**

## 四、官方总结的实践守则

*摘译自同文的 best practices 一节。*

- **别照这份指南照抄。** 每次迁移都不一样，把它当起点，**先和 Claude 一起规划你这次的具体迁移**。
- **别盯着单个失败。** 单个失败是循环的活，交给修复智能体烧掉；**你的注意力应该放在模式上**。
- **评审要对抗式，校验要机械式。** 对抗式评审让任务能跑得更久，通常值那些 token；让编译器、diff、测试套件这类脚本当裁判。
- **别什么都用最大的模型。** token 花在循环里，所以循环要刻意设计：小模型承担高吞吐的实现扇出，**把最大的模型留给评审者和任何"会写下别的智能体要遵守的规则"的环节**。
- **把人力前置。** 规则手册和压力测试最耗时，之后基本就是队列在烧。
- **工作队列要机械、可续跑。**"完成"的含义应当是"输出文件在磁盘上存在"。
- **评审循环的产出，而不是评审代码本身。**

成效也要照实说：Bun 的 Rust 代码里约 **4% 落在 `unsafe` 块**里（多是 C/C++ 边界上的单行指针操作）。但改善是可量的——团队工具能检出的内存泄漏全部修掉（一个 2,000 次重复构建的基准从 6,745 MB 降到 609 MB），Linux/Windows 上二进制小 19%，跨语言优化让 HTTP 服务与 `next build`、`tsc` 这类真实负载快 2–5%。

## 五、日常开发（而非迁移）的配置层

*本节译自 [Set up Claude Code in a monorepo or large codebase](https://code.claude.com/docs/en/large-codebases)。迁移是项目，日常开发是长期状态；后者的瓶颈不是"模型不够聪明"，而是**上下文与权限的范围控制**。*

官方先给了一张"我想干什么 → 用什么"的索引表，并强调**这些设置是叠加而非互相替换**：

| 诉求 | 手段 |
| --- | --- |
| 只加载你正在改的那部分约定，而不是一份覆盖所有子系统的根文件 | 按目录分层的 `CLAUDE.md` |
| 屏蔽你从不涉及的包的 `CLAUDE.md` | `claudeMdExcludes` |
| 拦住构建产物、生成代码、vendored 依赖的读取 | `permissions.deny` 里的 `Read(...)` 规则 |
| 用语言服务器跳定义/找引用，而不是扫文件 | 代码智能插件 |
| 建工作树时只检出这个任务需要的目录 | `worktree.sparsePaths` |
| 读改兄弟包或另一个仓库 | `--add-dir` 或 `additionalDirectories` |
| 某区域专属的操作步骤，且只在相关时加载 | 按目录的 skills |
| 用一套大家安装的约定替换许多按目录的 `CLAUDE.md` | 内部市场里的一个插件 |

**第一件事是决定从哪儿启动 `claude`**，因为它同时决定三件事：不用额外授权就能读写哪些文件、启动时哪些 `CLAUDE.md` 进上下文、以及哪份项目设置生效。从仓库根启动 = 所有文件 + 只加载根 `CLAUDE.md`（子目录的按需加载）；从子目录启动 = 只有那棵子树 + 该目录及其**所有祖先**的 `CLAUDE.md`。**注意 `.claude/settings.json` 不像 `CLAUDE.md` 那样向上继承**——每个子目录的设置文件必须自包含。

**分层 `CLAUDE.md` 的推荐切法**是两级：根文件写全局规则（"包脚本要在包目录里跑，不要在 monorepo 根""提交标题以包名开头，例如 `api: add rate limiting`""绝不改 `packages/*/generated/`，改跑 `npm run codegen`"），每个包一份写本包栈的约定（"跑任何东西之前先把 `.env.example` 复制成 `.env`，否则测试和 dev server 都会失败""数据库查询一律用 Knex 查询构造器，路由处理函数里不许出现裸 SQL 字符串""迁移合入后绝不修改，要改就加一条新迁移"）。用 `/context` 看 **Memory files** 一栏可以确认到底加载了哪些文件。

**保持这些文件不过期**的三条官方建议，比大多数团队自己的做法都实在：把 `CLAUDE.md` 的改动**当普通文档变更进 PR 评审**；**大模型版本更新后回来看一遍**——当年为绕开旧模型缺陷写的指令，新模型能自己搞定后就成了纯开销（例子：那条"重构必须限制在单文件内"的规则可以删了）；**加一个 `Stop` hook**，在 Claude 每次答完时拿到转录路径，让脚本复盘会话、趁着暴露出的缺口还新鲜时**提议更新 `CLAUDE.md`**（写法见《Claude Code Hooks：用确定性脚本守住智能体循环》）。

**减少"读了什么"**：Claude 的内容搜索默认尊重 `.gitignore`，所以 `node_modules/`、`dist/`、`build/` 天然不会进结果；对**已提交进仓库**的 vendored SDK 或生成的代码，加 `Read` deny 规则：

```json
{
  "permissions": {
    "deny": [
      "Read(./**/dist/**/*)",
      "Read(./**/build/**/*)",
      "Read(./**/*.generated.*)",
      "Read(./**/vendor/**/*)"
    ]
  }
}
```

三个必须知道的限制：**路径模式结尾写 `/**/*` 而不是 `/**`**，这样规则覆盖目录内容而不覆盖目录本身（Claude 还能 `ls dist`、`cd build`）；deny 规则覆盖内置文件工具、以及 Bash 里 `cat`/`head`/`grep`/`find` 这类**被识别的**文件命令，但**覆盖不了自己打开文件的子进程**（`grep -r` 扫一个含被拒文件的目录，结果里仍会出现它们）；放哪份文件决定覆盖谁——项目 `.claude/settings.json` 覆盖仓库内所有人，`.claude/settings.local.json` 只覆盖你（注意相对模式仍以会话当前目录为锚，从子目录启动时要写成 `//` 绝对路径），**托管设置才能覆盖所有会话且用户与项目设置无法压过它**。

再配**代码智能插件**：`/plugin install typescript-lsp@claude-plugins-official`，让 Claude 直接跳定义、找引用、看类型错误，而不是把剩下的东西翻一遍找定义。装不上就按报错区分：`Marketplace "claude-plugins-official" not found` 需要先 `/plugin marketplace add anthropics/claude-plugins-official`；插件本身找不到就核对名字。它要求各语言对应的 language server 二进制在每台开发机上存在，且从官方市场安装需要能访问 GitHub——受限内网要改成从内部 git 主机或本地路径添加市场。想让全仓库的人都启用，用项目的 `enabledPlugins` 设置而不是各自安装。

**工作树与跨包访问**：大仓库里 `--worktree` 默认检出整个仓库很慢，`worktree.sparsePaths` 用 git sparse-checkout 只写列出的目录加根级文件（提交的设置和个人的设置**会合并**，所以 local 文件只能加路径、不能删）。跨包任务（改一个共享类型及其所有调用点）需要授权兄弟目录：`permissions.additionalDirectories: ["../shared", "../web"]`，或启动时 `claude --add-dir ../shared`。**两者的加载语义不同**——`additionalDirectories` 设置**永远不**加载那个目录的 `CLAUDE.md`/rules/skills；`--add-dir`/`/add-dir` 会加载它的 skills，而 `CLAUDE.md` 与 rules 需要额外设 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`。

**分层到不再可扩展时就要集中**：按目录的 `CLAUDE.md` 会漂移、会过期、根文件没人认领，而这件事通常落在"维护仓库 Claude Code 配置的那个团队"身上而不是每个开发者。做法是把约定与参考内容移出常驻的 `CLAUDE.md`，放进**按需加载**的机制：skills（相关时才读）、plugins（版本化的技能+hook+命令集合，由平台团队集中维护）、MCP servers（组织里已有代码搜索或 RAG 索引的话，就把它作为工具暴露出去，让 Claude 去查而不是直接读文件）。

**跨包改动怎么给**：两条官方建议——**把整个改动放进同一个会话**（共享类型的修改和它的调用点一起给，各次编辑背后的决策才一致，而不是每个包重新推导一遍）；**先计划再编辑**（plan 模式里先探索、把计划写成文件；长会话中途会压缩上下文，而 **Claude Code 会在每次压缩后重新注入那个计划文件**，计划能活下来、对话历史未必）。

## 六、落地路线：给一个没人敢动的仓库（本站编者补充）

把上面两份材料压成一条可执行顺序：

1. **先建裁判，再谈智能体**。没有能客观判对错的测试/对拍脚本，前面所有机制都只是更快地生产未经检查的代码——这也是《第一次 AI 结对：从零做一个命令行小工具》里"用测试定义完成"在大仓库上的版本。裁判建不起来就先造（第 6 步的做法：让 Claude 自己设计端到端测试并自主夜跑）。
2. **从"只读"起步**：先让智能体回答"这段代码为什么这样写""谁调用了它"，配合代码智能插件把探索外包给子智能体（见《Subagents 与并行会话：把探索外包出去》）。这一步零风险，且能暴露规范文件缺什么。
3. **写两份规范而不是四十份**：根 `CLAUDE.md` 只放"处处适用的规则 + 明确禁止项"，每个子系统一份局部约定。**先少写**——规范文件每轮都收租。
4. **把不可逆动作变成 hook**：保护 `.env`、锁生成物、禁 `git push`、拦 `rm -rf`。用第五节那套 deny 规则 + `PreToolUse` 脚本，记住它们**在 `bypassPermissions` 下仍然生效**。
5. **挑一个"边界清楚、失败便宜"的切片**做第一次真改动：一个内部工具的重写、一处废弃 API 迁移、一批 lint 规则清零。用它把规则手册/评审/闸门跑通，再谈放大。
6. **放大时才引入并行与 worktree**：切片稳定后再按文件分区并行、稀疏检出、多个会话同时跑；同时把成本观测接上（见《成本管理：Token 消耗、订阅选择与用量优化》），因为**并行成倍放大 token 消耗**是官方明写的。
7. **迁移/改造类大工程照第二至四节做**：裁判 → 规则手册 → 试航 → 扇出 → 编译/冒烟/行为对齐，并且**每次跨文件重复出现的错误都回去改规则、重新生成批次**。
