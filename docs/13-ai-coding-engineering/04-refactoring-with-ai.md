## 一、主篇：Anthropic 的大规模代码迁移方法论（官方博客全文节译）

*以下译自 [How Anthropic runs large-scale code migrations with Claude Code](https://claude.com/blog/ai-code-migration)（2026-07-16）。*

代码迁移——把生产代码库移植到新语言——直到最近还是"以年为单位"的工程。而过去一个月里，Anthropic 的工程师用 Claude Fable 5、Claude Opus 4.8 与动态工作流（dynamic workflows）迁移了 10 个代码包，规模从数万到数十万行：

- **Bun 从 Zig 移植到 Rust**：Bun 联合创始人 Jarred Sumner（现 Anthropic 工程师）用 Claude Code 在不到两周产出一百万行 Rust，合并前 Bun 既有测试套件 100% 通过 CI；合并后出现 19 个回归、随后全部修复。Rust 版已随 2026 年 6 月的 Claude Code 发布。
- **Python 移植到 165,000 行 TypeScript**：Anthropic Labs 负责人 Mike Krieger 用一个周末完成，动用数百个智能体、八道阶段闸门、三轮对抗式评审，最后用"逐命令对比输出"的 parity 校验收尾。

这篇文章的核心洞察是一句话：**你不修代码，你修"产生代码的那个流程（循环）"**。

### 什么时候迁移、为什么 AI 改变了算术

迁移的动因是生态位移：某个当初的取舍变成了枷锁、更好的方案出现、或原生态在萎缩（Jarred 选 Zig 是因为它以极简提供 C 级性能，适合"LLM 出现之前独自一年写 Bun"）。而大型迁移是高级模型的绝佳用例，因为：

- **工作天然可并行**：数千个独立单元（文件、crate）可同时处理
- **上下文清晰而完备**：旧代码本身就是最好的规格说明，也是编写"翻译指南"的核心参照
- **自带裁判**：大型代码库通常有测试套件，验证是客观的——模型可以对着一个 ground truth 连续磨几天，不需要人仲裁质量
- **队列自己会生长**：编译器或测试一失败，失败清单就是下一个待办队列
- **一致性与边缘情况**：流程设计让漂移无处藏身——评审者引用规则条目报告问题，违规变成队列项而非悄悄的偏离；智能体撞上边缘情况，修复就变成所有后续智能体都要遵守的新规则

### 前置条件：先造一个"裁判"

迁移开始前必须有一个强力的裁判（judge），否则没有退出条件、没有成功度量。裁判必须能以同等标准评判旧代码与新代码——旧语言写的测试套件往往依赖目标代码里不存在的内部函数。造裁判三步：

1. **分类既有测试**：让 Claude 区分"可改写为外部调用"的测试与"依赖不可移植内部实现"的测试
2. **改写为可移植断言**：把外部可见的测试改写成能同时跑在旧实现与新实现上的断言，并让对抗式智能体验证改写没有弱化断言
3. **验证裁判**：先对旧代码跑，必须通过；再对故意弄坏的代码跑，必须失败——**抓不出破坏的裁判不是裁判**

Mike 没有（也不需要）移植测试套件：他为 Python→TypeScript 的移植造了 7 个真实场景的 parity harness，任何行为差异都算 Bug。

### 六步流程

**第 1 步——规则书、依赖图与差距清单。**迁移的地基：一份"哪些地方需要重构而非直译"的清单、一本"如何翻译代码"的规则书（rulebook）、一张排序并行工作流的依赖图。顺序重要：**规则书先于差距清单**——差距清单由"规则书默认值覆盖不了的"定义，两者还要做联合审计。规则书的形态取决于首要架构决策：新代码保持原结构（Jarred 的路线，规则书主要是类型与惯用法的对照表），还是彻底重设计（Mike 的路线，规则书即设计文档）。Jarred 通过与 Claude 对话为每类歧义制定策略，并用 8 个子智能体分别审查 8 类他自己直觉中的常见失败模式。依赖图则由智能体写一个确定性脚本生成（Zig→Rust 的差距是手动内存管理；Python→TypeScript 的差距是接口与契约）。

**第 2 步——压力测试规则。**一次"试航级"迷你迁移：Jarred 用三个智能体分别按规则书译 3 个文件、"像资深 Rust 工程师一样"译 3 个文件、以及对比两版 diff 产出新翻译规则。这一步抓出的两个关键问题，若直接扇出到全部 1,448 个文件将造成无数问题。**译出的文件全部扔掉——目标是打磨规则，不是攒进度**。此法只适用于结构保持型迁移（同文件可逐行对比）；重设计型迁移的等价动作是让对抗式评审直接攻击设计文档，再用一次性的端到端运行验证。

**第 3 步——全量翻译。**此后各步跑同一个多智能体循环架构：实现 → 评审 → 修复。实现者的活可以交给小模型（Mike 主迁移扇出 12 个 Sonnet 子智能体），评审留给大模型。工作队列必须机械化：批处理脚本以"译文文件是否已存在于磁盘"判定完成、把待办切片分批——因为每次都从磁盘重建队列，**迁移天然可断点续跑**。翻译器没有把握的地方统一打 `// TODO(port): <原因>` 标记，留给第 4 步——从此待办清单自己会写：编译器枚举错误、冒烟测试找出崩溃、测试套件报告失败。对抗式评审者用独立上下文评估实现，评审者意见不一致时交给第三个智能体仲裁。**当某个评审者反复抓到同一类错误，修法不在逐个文件——往规则书里加一句话，重新生成受影响的批次。规则书不断生长，代码从不针对规则手工打补丁。**另一个关键设计：编译器放在循环内还是循环外——Mike 让 TypeScript 编译器跑在每次循环里（秒级）；Jarred 完全禁止编译器进循环（cargo 要分钟级），推迟到下一步。

**第 4/5/6 步——编译、运行、行为对齐。**三步共享同一循环架构、所需人工判断递减。第 4 步：编排脚本对整个工作区跑一次编译器，"修复智能体"并行消化错误清单并带对抗评审，如此往复——审查错误清单要盯系统性问题（Jarred 曾因修复循环 import 后冒出数千个 Rust 模块错误，于是把"如何分类删除/移动/重构依赖边界"的逻辑编进循环）。第 5 步：冒烟测试的崩溃清单是新的机械事实来源，按根因分组交对抗式子智能体评审。第 6 步：分片、用前置阶段造好的裁判跑测试套件，失败交给"修复智能体"对照两个代码库修复。关键组件是**构建守护进程（build daemon）**：唯一被允许重新构建二进制的进程——修复者交补丁，守护进程攒批、重建一次、重跑受影响测试并回喂结果，把最昂贵的操作串行化。同一失败在多个测试反复出现时，修法上游化：改产生 Bug 的那条规则、只重新生成该规则触过的文件。没有测试套件也不构成阻塞——**继承不来裁判，就让 Claude 造一个**：旧代码库就是 ground truth（Mike 的 Claude 甚至自建端到端测试、连续四个通宵自治运行，抓到了任何场景清单都预测不到的"纸割伤"）。

### 六条最佳实践（同文）

- **别盲从本指南**：每次迁移都不同，动手前先和 Claude 为你的迁移做具体规划
- **别盯单个失败**：单个失败是循环的工作，修复智能体会烧掉它们；你的注意力属于"模式"
- **评审对抗化、验证机械化**：对抗式评审支撑更长时段的自治运行，token 花得值；让脚本——编译器、diff、测试套件——当裁判
- **别把最大模型用在所有事上**：token 花销集中在循环里。小模型干高扇出实现，最大的模型留给评审者与"写规则的人"
- **前置人力工时**：规则书与压力测试最耗时，之后基本是队列燃烧
- **队列机械化、可续跑**："完成"应当意味着"输出文件已存在于磁盘"

### 结果与迁移的代价

Jarred 的 Bun 迁移已上生产。代价也有：约 4% 的 Rust 代码在 unsafe 块里（多为 C/C++ 边界的单行指针操作）。但新代码库可度量地更好：工具能查到的每个内存泄漏都已修复（2,000 次重复构建的基准从 6,745 MB 内存降到 609 MB）、二进制小了 19%、跨语言优化让它快了 2-5%。官方附赠了一份[迁移启动套件](https://github.com/anthropics/code-migration-kit-with-claude-code)（该流程的通用模板）。

## 二、对照：日常尺度下 AI 重构的失败模式（Aman Agrawal 观察摘译）

*以下摘译自工程师 Aman Agrawal《[Some Observations on AI/Agentic Refactoring](https://amanagrawal.blog/2025/05/06/some-observations-on-ai-agentic-refactoring/)》（2025-05-06）——把镜头从百万行拉回到"一个用例的重构"，失败模式看得更清楚。*

**场景一：开放式一句"重构这段代码"**。在一个从旧架构向新架构迁移中的后端服务里（新旧代码并存、多处 `Obsolete` 标记），直接要求"Refactor this code! Ignore the obsolete warnings"——结果：把值对象类型猜成了 `Guid`、改了明确说了不许动的废弃代码、还自作主张新增了一批没必要的替换类型；要求撤销时空文件留了一仓库；甚至给异步方法加了本仓库并不采用的 `...Async` 命名后缀并波及多处。三十分钟后作者已完全搞不清代码处于什么状态，只能 `git reset --hard` 从头再来。他的点评：熟手尚且如此，新人用 AI 重构完全可能净生产力为负。

**场景二：同样的代码，先只要建议**。换一个问法——"给出重构建议、等我选择"——质量立刻不同。

**他沉淀的三条启发式（Emerging heuristics）**：

- **小而聚焦的任务远好于"这是个大代码库，重构它"**。判据：*如果我自己都难以在脑子里推演这个改动、难以把它讲清楚，AI 也会挣扎，而它挣扎时的默认行为是幻觉*——它替不了批判性思考，它只是在预测下一个 token
- **人必须掌握工作流**：每次智能体改动之后小步走"测试 + 提交或回滚"（即 Kent Beck 的 TCR：test-commit-revert）**不可协商**。一个可行姿势是先让 AI 给出全部重构建议、再由人凭借领域经验挑选"真正有设计价值"的那些精确实施。要顶住"更快产出更多代码"的诱惑——初级工程师尤其容易中招，资深工程师时间久了也会
- **琐碎重构别麻烦智能体**：有专用工具或足够机械的重构（如删未使用的命名空间），手动几秒钟的事，让 AI 做反而几分钟+一串误伤还没做完

> 译注：把 Aman 的三条与主篇的六步放在一起读，会看到同一条规律的两个尺度——**人负责规则与方向，机器负责扇出与队列**。《TDD with AI：Kent Beck 的增强编程实践》 Kent Beck 的 TDD/TCR 实践正是这条规律的另一处现身。

## 三、官方工作流与产业案例（收束）

**官方日常配方**（译自 [Common workflows](https://code.claude.com/docs/en/common-workflows) "Refactor code" 一节）：识别遗留代码（"find deprecated API usage in our codebase"）→ 要建议（"suggest how to refactor utils.js to use modern JavaScript features"）→ 安全应用（"refactor utils.js to use ES2024 features while maintaining the same behavior"）→ 验证（"run tests for the refactored code"）。官方提示：让 Claude 解释新式写法的好处；需要时保持向后兼容；**小步、可测试地增量重构**。

**产业规模佐证**（译自 Anthropic 客户案例 Rakuten）：乐天机器学习工程师 Kenta Naruse 让 Claude Code 在 vLLM（1,250 万行、多语言的开源大库）中实现一个指定的激活向量提取方法——**单次运行 7 小时自治完成，未写一行代码，只偶给指导**，数值精度 99.9%；团队平均新特性上市时间从 24 个工作日降至 5 天（-79%）。

## 四、可复制的重构提示词与验收清单（本站编者整理）

> 上面三个尺度（日常 / 大规模迁移 / 产业案例）共用同一套动作，差别只在扇出规模。以下模板覆盖前两个尺度。

**模板 A：先要建议，不动手**（对应 Aman 的"场景二"）

```text
目标：把 <模块/文件> 从 <旧写法> 迁到 <新写法>，行为保持不变。
约束：不得改变公共 API 与序列化格式；不得顺手升级依赖；不得改动 tests/。
请先只输出重构方案：
1) 按风险从低到高列出可独立提交的小步（每步 ≤400 行变更）；
2) 每步注明：影响文件、可能破坏的行为、用哪个测试/命令验证；
3) 标出你认为"不该重构"的部分和理由。
不要在这轮修改任何文件。
```

**模板 B：执行其中一步**

```text
执行方案第 <n> 步。要求：
- 只改这一步涉及的文件；diff 里不得出现无关格式化或重命名
- 开始前先运行 `<验证命令>` 记录基线；结束后再运行一次，并逐项对比输出
- 若基线本身是红的，先停下告诉我，不要试图"顺手修好"
- 结束时给出：改动摘要、行为不变的证据（两次命令输出）、回滚方式（git revert 单个提交）
```

**模板 C：大规模迁移的规则书与压力测试**（对应主篇第 1—2 步）

```text
我们要把 <N> 个文件从 <源语言/框架> 迁到 <目标>。这一轮不产出迁移结果，只打磨规则。
1) 读 <旧代码目录>，产出 rulebook.md：类型映射、惯用法对照、错误处理约定、禁止事项，
   每条规则给出一个"旧写法 → 新写法"的真实例子（引用文件:行号）。
2) 按 rulebook 各译 3 个代表性文件；再按"资深 <目标语言> 工程师"的直觉译同一批文件。
3) 对比两版 diff，列出规则没覆盖的歧义点，把它们写成新规则补进 rulebook.md。
4) 译出的文件全部丢弃；本轮交付物只有 rulebook.md 与差距清单。
```

**验收清单（重构合并前逐项打勾）**

- [ ] 行为不变的证据是**机械的**：同一组测试/命令在改动前后输出一致（或差异已被解释）。
- [ ] 每一步是**一个可独立回滚的提交**，不存在"要回滚就得全回滚"的大提交。
- [ ] diff 里没有未要求的改动：新依赖、命名风格漂移、无关格式化、被顺手删掉的注释。
- [ ] 公共 API、序列化格式、错误码、日志字段四类契约逐项确认过。
- [ ] 性能没有静默退化：关键路径至少有一次前后对比数字（哪怕是粗略基准）。
- [ ] 规范文件已同步：若这次重构改变了约定，`AGENTS.md`/`CLAUDE.md` 里的相关条目同时更新（写法见《AGENTS.md 与 CLAUDE.md：给智能体的项目规范文件》）。
- [ ] 若属于大规模迁移：新增的失败模式已**回写进规则书**，而不是只在当前文件里打补丁。
