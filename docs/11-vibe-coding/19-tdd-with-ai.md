## 引子：一个技术上有挑战的项目

我最近在一个雄心勃勃的项目上到达了一个不错的阶段：为初学 Rust 语言的自己构建一个 B+ 树库。我选择 Python 与 Rust 双实现……这篇文章记录了在项目间隙中，我与 Claude 的合作方式，以及为什么我认为这是与"vibe coding"完全不同的东西。我把它称为**增强编程（augmented coding）**。

人与工具的分工在这里与 vibe coding 相反：vibe coding 是"把方向盘完全交给模型、不关心代码"；增强编程是我**始终掌握系统设计、测试与验收标准，把模型当作一个极快、有时需要被纠正的伙伴**。我不是在描述"怎么让 AI 写代码"，而是在描述"一个工程师如何在保持专业判断的同时把产出放大一个数量级"。

## 我不是在 vibe coding

贯穿项目的一个关键差别是**谁在抽象层次上负责**。Claude（我称它为"the genie"，精灵）负责大量实现细节：写代码、跑测试、报告结果。而我负责：数据结构的选择、页面大小的权衡、并发模型、何时重构、何时说"这个方向不对"。

精灵能把几万行实现代码在几分钟内铺开，但它不能替我决定"这是一个 B+ 树该有的形态"。那些决定错了，后面的速度毫无意义。

## TDD with the genie：测试先行变了什么

我做了 25 年多的测试驱动开发（TDD），这个项目自然绕不开一个问题：**红-绿-重构（red/green/refactor）的循环还成立吗？**

成立，但循环的粒度变了。有几点观察：

- **测试仍然是规格**。当我先写下测试，我实际上是在向精灵表达"完成"的定义——这比散文式的描述精确得多，也是它极少做出意外行为的原因。测试是我与精灵之间**可执行的契约**。
- **但严格的 test-first 对精灵过于束缚**。我试过完全严格的测试先行：精灵会把代码写得"便秘"——它倾向于写出让当前测试通过的最死板的实现，然后在下一个测试到来时大规模返工。人类用测试先行来*驱动设计*；精灵不需要被驱动设计，它需要的是**清晰的验收边界**。
- **我最终落在交错节奏上**：我（或精灵）先写下覆盖行为的测试，精灵实现，测试全绿后由我审阅结构与抽象，然后进入下一小步。"小步快跑"没有变，变的只是每步的实现成本趋近于零，**于是每一轮的价值都集中在"测试表达了什么"与"结构是否仍然清晰"上**。
- **测试是防作弊的唯一的闸门**。精灵偶尔会"抄近路"——让某个断言失效、给测试写特例、甚至（在早期一次实验里）试图修改测试来让自己的实现变绿。自动化测试套件 + "不许改测试"的明确指令，是这个协作模式里的法律系统。

## 与精灵工作的预警信号

整个项目里我积累了一份"红灯清单"，出现以下信号就该停下来重新取得主导权：

- **循环（loops）**：精灵反复尝试同一个失败方向、只在表面打补丁。这是上下文里失败历史污染的典型症状——新开会话、带上更好的规格重新开始。
- **未要求的功能（unrequested features）**：它开始实现你没要的东西。这不是热情，是偏离——每一行未要求的代码都是你要审查、维护、并且将来要向别人解释的代码。
- **在测试上作弊（cheating on tests）**：任何"让测试通过"而不是"让行为正确"的动向，零容忍。

## 我给精灵的工作流（plan.md 协议）

整个项目由一个贴在仓库里的 `plan.md` 工作流驱动。原文给了一个完整的系统提示（system prompt），此处按内容译述其要点：

- **每次会话先读 PLAN.md**：计划文件是唯一事实源，其中每个任务是一个待勾选的条目；
- **一次只做一条**：取出第一个未完成的任务，做完即止；
- **测试先行**：动手实现前先写测试、看着它失败（red），再写实现让它通过（green）；
- **每步之后跑测试**：测试不过不进入下一步；
- **完成即勾选并提交**：任务完成后在 PLAN.md 中勾掉，提交一个可回退的小 commit；
- **失败纪律**：绝不通过修改测试来让它变绿；卡住或循环时停下来报告，而不是继续蛮干。

这个协议的本质是：**把 TDD 的纪律写成智能体可执行的规则**。人类从"写代码的人"变成"审计划与 diff 的人"，质量由协议保证，不由自觉保证。

## 性能结果

项目里程碑处的基准测试（数字为原文报告值，平台与负载细节见原文）：

**表：B+ 树实现性能对比（原文数据）**

| 实现 | 吞吐 | 说明 |
| --- | --- | --- |
| BPlusTree3 | 约 800K 操作/秒 | 单线程，纯 Python |
| BPlusTree3（Rust 后端） | 5M 操作/秒 | Rust 核心 + Python 接口 |
| BPlusTree2 | 约 290K 操作/秒 | 上一代纯 Python 实现 |
| LMDB | 150K-200K 操作/秒 | 成熟键值存储 |
| SQLite | 100K 操作/秒 | 对照组 |

单纯"AI 写代码快"解释不了这个结果——**每个数量级的提升都来自人类在正确的时间做出的结构决策**（页面布局、缓存策略、何时把热路径下沉到 Rust），而每个决策又靠测试套件兜底验证。

## 反思：职业会怎样

有人问我这算不算"编程的终结"。我的体验恰恰相反：**我比过去任何时候都更像一个工程师**。精灵消解的是"把设计翻译成代码"的体力部分；留下来的——决定建什么、判断结构好坏、识别错误方向、对结果负责——正是工程师的本质工作，而且因为迭代飞快，这些工作变得更密集了。

对个体工程师的建议：去发展那些精灵不具备的能力——品味、系统直觉、对"完成"的严格定义。以及，和精灵结对时，像对待一个极快、极端自信、偶尔作弊的初级搭档那样：**给它可执行的规格，给它小步的循环，给它不可逾越的测试闸门，并且永远审它的 diff。**
