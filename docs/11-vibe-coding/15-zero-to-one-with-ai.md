## 我把话放这儿

我说出来了：**到 2026 年底，大多数软件工程师还在手工雕琢每一个提交（artisanal hand-crafted commits）这件事，我看不出有任何路径能维持下去。**如果你是软件工程师，好奇我为什么这么想，我的置顶文章《adjusting to the future of software development》是个好的起点。你还应该看看"the hat tweak heard around the world"来理解我们此刻处在采纳曲线的什么位置。

巨大的变化正在到来，你需要的生存技能与把你带到今天这里的技能截然不同。昨天管用的明天不管用了——对在这个行业干了很多年的人来说，这很吓人。所以让我们聊聊未来，聊聊你需要什么技能才能成功。

我一直处在这场转变的前沿。我学到的是：软件开发的"怎么做（how）"已经根本改变了。"怎么做"曾经是手工雕琢的提交；"怎么做"如今越来越多地变成"**记录一切，写成规格（spec），让智能体去构建**"。能 thrive 的工程师，是那些能适应这种新工作方式的人。

## 案例：用智能体重建 Gumroad

Gumroad 创始人 Sahil Lavingia 做过一个著名的实验：用 AI 智能体重建自己的公司产品。他描述的流程是一个完整的"从 0 到产品"闭环：

1. **与智能体对话**：把需求、背景、约束全部聊出来；
2. **记录一切**：对话全程留痕；
3. **把记录变成规格**：把聊天记录整理成 spec 文档；
4. **清理规格**：人审规格、去掉噪声、补齐缺口；
5. **交给智能体编码**：Devin（或任意编码智能体）按规格实现；
6. **QA、合并、部署**：测试、走 PR、上线。

注意这个流程里人的位置：**人出现在"聊清楚需求"和"清理规格"两端，中间的实现交给循环**。这正是从 0 到 1 做产品的新形态——不是"人写代码变快了"，而是"把想法变成可运行产品的工作流被重组了"。

## 从想法到规格：计划就是图

Huntley 在文中强调的一个技巧：**用 Mermaid 图表达计划**。当你和智能体把想法聊清楚后，让它把计划画成 Mermaid 流程图/依赖图——图比散文更难产生歧义，还能直接被下一轮智能体读取执行。这个"计划即图、规格即交接物"的思路，在他的 Ralph 循环（本模块第 8 篇有引述）里被推到极致：spec.md 是给未来每一轮智能体的交接文档。

## 技术加固点：什么让智能体开发变得可靠

文中列出的三个"技术加固点（tech reinforcement points）"，是从 0 到 1 能交给智能体的前提条件：

- **类型系统（Type systems）**：静态类型是机器可校验的规格，让智能体的错误在编译期暴露，而不是在生产里；
- **测试**：失败的测试就是强化信号（reinforcement signal）——智能体靠它知道什么叫"做完"；没有测试的代码库，智能体只能靠"看起来能用"交差；
- **短周期（cycle times）**：快的反馈回路让智能体尽快闭合"改—测—改"循环。fail fast, recover quickly（快速失败，快速恢复）。

一句话：**工程纪律越好，智能体越强**。这与本模块第 1 篇 Simon Willison"LLM 奖励顶级工程实践"的观察完全互证。

## 采纳四阶段

文末把工程师对 AI 编码的采纳分为四个阶段：

1. **调整自己写码的方式**：用自动补全加速打字——工具还是工具；
2. **vibe code 低风险的个人工具**：周末项目、内部小工具，撒手让模型写；
3. **智能体工程（agentic engineering）**：把智能体编进工作流，审查它产出的一切，为结果负责；
4. **成为 builder（建造者）**：直接"just do things"——从想法到产品一条龙，不再把"写代码"当成瓶颈。

文章标题正是第四阶段的名字：**未来属于能把事情做出来的人**。

## 编者按：把这套流程落成你自己的 0→1 清单

> 本节为本站编者补充。综合 Huntley 的流程与第 3 篇 Claude Code 最佳实践（探索→计划→实现→提交）、第 8 篇 Spec Kit（constitution→specify→plan→tasks→implement→converge），一个可执行的从 0 到 1 清单：

**表：从 0 到 1 用 AI 做产品的实战清单**

| 阶段 | 动作 | 产出物 | 对应本模块篇章 |
| --- | --- | --- | --- |
| 1. 想法澄清 | 与智能体对话/让它采访你；全程留痕 | 对话记录、需求要点 | 03（让 Claude 采访你） |
| 2. 规格 | 把记录整理成 spec；只写"做什么、为什么" | spec.md / SPEC.md | 08（Spec Kit `/speckit.specify`） |
| 3. 计划 | 技术栈与架构决策；计划画成 Mermaid 图 | plan.md | 03（计划模式）、08（`/speckit.plan`） |
| 4. 脚手架 | 初始化项目：规范文件 + 测试框架 + CI | AGENTS.md、测试目录、流水线 | 05（AGENTS.md）、12（TDD） |
| 5. 迭代实现 | 任务拆解、逐个交给智能体；commit 即存档 | 小步提交序列 | 03、07（Git）、08（`/speckit.tasks`） |
| 6. 验证 | 全量测试 + 运行应用人工验收 + 截图比对 | 绿的测试套件、可运行产物 | 03（`/verify`）、12 |
| 7. 审查与上线 | 对抗式审查 diff → 合并 → 部署预览环境 | PR、预览链接 | 11（代码审查）、07 |
| 8. 加固 | 类型收紧、补测试、压缩周期，为下一轮循环提速 | 更强的基础设施 | 15 本篇"技术加固点" |

选型上的最低配置：任意一个第 2 篇对比过的智能体工具 + 一份 20 行的项目规范文件 + 一条"测试不过不合入"的规矩——就可以开始你的第一个从 0 到 1 了。
