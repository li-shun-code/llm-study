在应用 AI 领域被"提示工程（Prompt Engineering）"占据注意力数年之后，一个新术语崭露头角：**上下文工程（context engineering）**。用语言模型构建应用，越来越不是为提示词寻找恰如其分的措辞，而是回答一个更宏大的问题："什么样的上下文配置最有可能让模型产生我们想要的行为？"

**上下文**指从 LLM 采样时纳入的 token 集合；这里的**工程**问题，就是在 LLM 固有约束下优化这些 token 的效用，以稳定达成预期结果。驾驭 LLM 往往需要*在上下文中思考（thinking in context）*——通盘考虑 LLM 在任一时刻可用的整体状态，以及这种状态可能引发的行为。

## 上下文工程 vs 提示工程

Anthropic 把上下文工程视为提示工程的自然演进。提示工程指为获得最优结果而编写与组织 LLM 指令的方法；**上下文工程**则指在 LLM 推理期间策展并维护最优 token 集合（信息）的一系列策略——包括提示词之外可能落入上下文的所有其他信息。

在 LLM 工程的早期，提示是 AI 工程工作的最大组成部分，因为日常聊天之外的大多数用例都要求为一次性分类或文本生成任务优化提示。但随着我们转向在多轮推理、更长时距上运作的更强智能体，我们需要管理整个上下文状态的策略——系统指令、工具、模型上下文协议（MCP）、外部数据、消息历史等等。在循环中运行的智能体不断产生"可能相关"的数据，这些信息必须被循环精炼。上下文工程就是从不断演化的信息宇宙中，策展哪些内容进入有限上下文窗口的**艺术与科学**。

## 为什么上下文工程对构建强智能体如此重要

尽管速度飞快、数据吞吐越来越大，我们观察到 LLM 和人类一样，会在某个临界点失焦或混乱。"大海捞针"式基准研究揭示了**上下文腐坏（context rot）**现象：随着上下文窗口中 token 数量增加，模型从上下文中准确回忆信息的能力下降。

虽然不同模型的退化平缓程度不同，但这一特征横跨所有模型。因此，上下文必须被当作**边际收益递减的有限资源**。人类工作记忆容量有限，LLM 同样有一个在解析海量上下文时支取的"注意力预算"。每引入一个新 token 都会消耗一部分预算，这要求我们更谨慎地策展交给 LLM 的 token。

这种注意力稀缺源于架构约束。LLM 基于 Transformer 架构，让每个 token 可以关注上下文中的每个其他 token——n 个 token 产生 n² 个两两关系。随着上下文变长，模型捕捉这些两两关系的能力被摊薄，上下文规模与注意力聚焦之间存在天然张力。此外，模型的注意力模式来自训练数据分布，而短序列通常远多于长序列——模型对上下文级依赖经验更少、专用参数更少。位置编码插值等技术让模型能适配更长序列（对原始训练的较小上下文做调整），但 token 位置理解会有退化。这些因素造成的是性能梯度而非断崖：模型在长上下文下仍然强大，但信息检索与长程推理的精度可能不如短上下文。

这些现实意味着：深思熟虑的上下文工程，是构建强智能体的必备项。

## 有效上下文的解剖学

既然 LLM 受限于有限的注意力预算，*好的*上下文工程意味着：**找到能最大化预期结果可能性的、尽可能小的高信号 token 集合**。知易行难，下面按上下文的各个组件展开这一指导原则。

**系统提示词**应当极其清晰，用简单直接的语言、在*合适的高度（right altitude）*上呈现想法。合适的高度是两种常见失败模式之间的"刚刚好"区间：一端是把复杂脆弱的 if-else 逻辑硬编码进提示词去精确规定智能体行为——脆弱且维护成本随时间上升；另一端是给出模糊的高层指导，既没有给 LLM 具体的输出信号，又错误地假定了共享上下文。最优高度在两者间取得平衡：足够具体以有效引导行为，又足够灵活以给模型强启发式。我们建议把提示词组织成不同小节（如 `<background_information>`、`## Tool guidance`、`## Output description`），用 XML 标签或 Markdown 标题划分——不过随着模型变强，提示词的具体格式正变得不那么重要。无论怎么组织，都要追求"完整勾勒预期行为的最小信息集"（注意：最小不等于短；你仍需预先给足信息以确保模型遵循期望行为）。最佳路径是：先用最小提示词在最强模型上测试，再根据暴露的失败模式补充清晰指令与示例。

**工具**让智能体操作环境、在工作中拉入新的上下文。工具定义了智能体与信息/动作空间之间的契约，因此工具必须促进效率——既返回 token 高效的信息，也鼓励高效的行为。工具应当像设计良好的代码库中的函数：自包含、对错误健壮、用途极其明确；输入参数应描述性强、无歧义、顺应模型的天生强项。我们最常见的失败模式之一是臃肿的工具集——覆盖太多功能、或在"该用哪个工具"上制造模糊决策点。如果人类工程师都无法明确说出该用哪个工具，就不能指望 AI 智能体做得更好。为智能体策展一个最小可行工具集，还能让长交互中的上下文维护与剪枝更可靠。

**示例**（少样本提示）仍是强烈推荐的经典实践。但团队常把一长串边界情况塞进提示词，试图穷举 LLM 应遵循的每条规则——我们不建议这样做。更推荐策展一组多样的、典范性的示例，有效刻画智能体的期望行为。对 LLM 而言，示例是胜过千言的"图片"。

对上下文的各个组件（系统提示、工具、示例、消息历史等），总体指导是一致的：**让上下文信息丰富而紧凑**。

## 上下文检索与智能体搜索

在《Building effective agents》中我们区分了工作流与智能体。此后我们倾向一个简洁的定义：**智能体 = 在循环中自主使用工具的 LLM**。与客户合作中，我们看到整个领域正收敛到这个简单范式；随着底层模型变强，智能体的自治程度可以按需伸缩。

如今工程师对"为智能体设计上下文"的思考正在转变。今天许多 AI 原生应用采用某种基于嵌入的**推理前检索**，把重要上下文预先摆到智能体面前。而随着领域转向更智能体的方式，越来越多团队在检索系统之上叠加"**即时（just in time）**"上下文策略。

"即时"方式不是预先处理所有相关数据，而是让智能体维护轻量的标识符（文件路径、存储的查询、网页链接等），并在运行时用工具按需把数据加载进上下文。Anthropic 的智能体编码方案 Claude Code 就用这种方式对大型数据库做复杂数据分析：模型写出有针对性的查询、存储结果、并利用 `head`、`tail` 等 Bash 命令分析海量数据——从不把完整数据对象载入上下文。这种方式映射人类认知：我们通常不背下整个语料库，而是建立文件系统、收件箱、书签这样的外部组织与索引系统，按需取用。

引用的元数据还提供了高效精调行为的机制。对在文件系统中工作的智能体，`tests` 目录下的 `test_utils.py` 与 `src/core_logic/` 下的同名文件暗示不同用途；目录层级、命名约定、时间戳都在帮助人与智能体理解"何时、如何利用信息"。让智能体自主导航与检索还带来**渐进披露（progressive disclosure）**：智能体通过探索逐层发现相关上下文——文件大小暗示复杂度，命名暗示用途，时间戳可作相关性代理。智能体逐层组装理解，只在工作记忆中维持必要内容，并用笔记策略做额外持久化。

当然有代价：运行时探索比取回预计算数据慢；而且需要深思熟虑的工程来保证 LLM 有正确的工具与启发式去导航信息版图——缺乏引导的智能体会滥用工具、追死胡同、错过关键信息，白白浪费上下文。某些场景下最有效的智能体会采用**混合策略**：部分数据预先检索求快，其余按其裁量自主探索。Claude Code 就是混合模型：CLAUDE.md 文件朴素地预置进上下文，而 glob、grep 等原语让它即时导航环境取回文件，绕开了索引过期与复杂语法树的问题。内容动态性较低的场景（法律、金融）可能更适合预取。随着模型变强，智能体设计将趋向"让聪明的模型聪明地行动"，人工策展逐级减少。鉴于领域进展之快，"**做最简单的能用的东西**"仍是我们对团队的最佳建议。

## 长时程任务的上下文工程

长时程任务要求智能体在超过 LLM 上下文窗口的动作序列中保持连贯、上下文与目标导向——比如持续数十分钟到数小时的大型代码库迁移或综合研究项目。等更大的上下文窗口看似解药，但可以预见：**所有尺寸的上下文窗口都将受制于上下文污染与信息相关性问题**——至少在追求最强智能体表现时如此。为此我们发展了三种直面污染约束的技术：压缩、结构化笔记、子智能体架构。

**压缩（Compaction）**：把接近上下文窗口上限的对话摘要，用摘要重新初始化新窗口。这是上下文工程的第一杠杆。Claude Code 的实现是把消息历史交给模型总结压缩：保留架构决策、未解决的 bug、实现细节，丢弃冗余的工具输出或消息；随后智能体携带压缩后的上下文加上最近访问的五个文件继续。压缩的艺术在于取舍——过于激进会丢失那些"重要性事后才显现"的微妙关键上下文。调优建议：先在复杂智能体轨迹上最大化召回（确保摘要提示捕捉每条相关信息），再迭代提升精度。最容易摘的果实是**工具结果清理**——消息深处的工具调用结果，智能体何必再看原始值？这是最安全的轻触式压缩。

**结构化笔记（结构化记忆）**：智能体定期把笔记持久化到上下文窗口之外，之后再拉回上下文。这以极小开销提供持久记忆——像 Claude Code 创建待办清单，或你的自定义智能体维护 NOTES.md，让智能体跨复杂任务跟踪进度、保住那些会在几十次工具调用中丢失的关键上下文与依赖。Claude 打宝可梦演示了记忆如何变革非编码领域：跨数千游戏步数维持精确计数、绘制已探索区域地图、记住已解锁成就、维护对战策略笔记；上下文重置后读自己的笔记继续多小时的训练或地牢探索。Claude 开发者平台还发布了文件式记忆工具公测版，让智能体随时间积累知识库、跨会话维持项目状态。

**子智能体架构**：绕开上下文限制的另一条路。不是让一个智能体维护整个项目的状态，而是让专职子智能体带着干净上下文窗口处理聚焦任务；主智能体以高层计划协调，子智能体执行深钻的技术工作或检索。每个子智能体可能消耗数万 token 探索，但只返回浓缩的摘要（常为 1000-2000 token）。这实现了清晰的关注点分离——细节搜索上下文隔离在子智能体内，主智能体专注综合分析。该模式在《How we built our multi-agent research system》中有述，在复杂研究任务上显著优于单智能体。

**表：三种长时程技术的适用场景**

| 技术 | 适用场景 |
| --- | --- |
| 压缩 | 需要大量来回对话、保持会话流畅性的任务 |
| 结构化笔记 | 有清晰里程碑的迭代开发 |
| 子智能体架构 | 并行探索有回报的复杂研究与分析 |

即使模型持续进步，跨长交互维持连贯性的挑战仍将是构建更强智能体的核心。

## 结语

上下文工程代表我们用 LLM 构建应用方式的一次根本转变。模型越来越强，挑战不再是"打磨完美提示词"，而是**深思熟虑地策展每一步进入模型有限注意力预算的信息**。无论你在为长时程任务实现压缩、设计 token 高效的工具，还是让智能体即时探索环境，指导原则始终是：找到能最大化预期结果可能性的最小高信号 token 集合。

更聪明的模型需要更少的规约式工程，智能体将以更多自治运作。但即便能力扩张，把上下文当作珍贵而有限的资源，仍是构建可靠、有效智能体的核心。
